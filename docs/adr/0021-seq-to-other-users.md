# 0021. Обновления с seq другому пользователю: inbox-событие получателя

- Статус: accepted
- Дата: 2026-10-27
- Задача 010, этап 3. Дополняет ADR 0020 («Вне рамок»: обновления с `seq` другим пользователям) и ADR 0012 (п. 5: применение inbox-события ровно один раз). Не заменяет их.

## Контекст
- **ADR 0020 журналирует `seq` только для своего изменения.** `EmitSeqUpdate` пишет строку `user_seq_updates` и пуш в транзакции ящика владельца аккаунта. Но многие состояния аккаунта меняет другой пользователь:
  - участники базовой группы, её права, название и фото, заявки на вступление;
  - плашка чата с контактом после регистрации импортированного номера (ADR 0015);
  - имена и фото контактов.
  Сейчас это пуш с `seq = 0`. Офлайн-устройство его теряет, а `getDifference` ничего не находит.
- **Чужой ящик меняет только его собственная транзакция** (ADR 0011). Транзакция инициатора не может выдать `seq` получателю. Изменение переносит inbox-событие, которое применяет транзакция получателя (ADR 0012, п. 5).

## Решение
1. **Событие** `inbox.seqUpdatesToInbox user_id:long from_id:long updates:Vector<Update> = Void` (CRC `−61692106`), топик `Inbox-T`, ключ — `user_id`.
   - **Пользователей и чатов в событии нет.** Их строят при применении из текущих данных, такими, какими их видит получатель.
     - Инициатор видит тех же людей иначе: имена из своей телефонной книги, приватность номера. Посчитать вид для каждого получателя при записи — это N запросов в пути инициатора и N копий в событиях.
     - Событие может применяться позже записи (запаркованная полоса, повтор после dead). Данные на момент применения свежее.
     - Событие группы остаётся маленьким: без пользователей на каждого получателя.
   - **Цена.** Консьюмер `Inbox-T` спрашивает biz user и biz chat до транзакции получателя: внутри транзакции RPC запрещён (`tools/boxaudit`). Вид — снимок перед транзакцией: изменение между ними придёт своим обновлением. Устаревший кэш biz user (если удаление ключей после commit не удалось) даёт старый вид до истечения кэша, как при любом чтении.
2. **Запись** — `inbox.EmitSeqInbox(b, inboxTopic, to, updates...)` в транзакции ящика инициатора: строка `mq_outbox` коммитится вместе с изменением (`Box.Emit`). В biz user — `Dao.EmitSeqInbox`.
   - **Проверка при записи, а не при применении.** Отказ — `userbox.ErrInvalidEvent`, транзакция инициатора откатывается:
     - получатель `≤ 0` или сам инициатор (свой аккаунт — `EmitSeqUpdate`);
     - пустой список;
     - обновление не из `userbox.SeqUpdate`;
     - топик не класса inbox.
   - Почему так: плохое событие у получателя станет dead после трёх попыток и запаркует его полосу (ADR 0012, п. 5). Все его сообщения будут ждать повтора. Ошибка запроса инициатора видна сразу и ничего не задерживает.
   - Консьюмер проверяет тип ещё раз, для писателя в обход помощника: такое событие становится dead до запросов к biz.
3. **Применение** (`InboxSeqUpdatesToInbox` в msg).
   - **До транзакции:** `seqpeers.Pick` и `seqpeers.Resolve` (п. 7) запрашивают пользователей вместе с получателем и чаты.
     - Ошибка запроса — временная: повтор, партиция ждёт, через 2 мин алерт `DeliveryConsumerStuck`.
     - Получатель не найден — тоже временная ошибка: biz user отвечает на сбой пустым списком, а событие пишется только существующему пользователю.
   - **В транзакции получателя** (`apply`: `TakeEvent` … `FinishEvent`) каждое обновление уходит через `sync_client.EmitSeqUpdate`: свой `seq`, своя строка `user_seq_updates`, свой контейнер всем устройствам. В контейнере только пользователи и чаты этого обновления (`Peers.Of`).
4. **Порядок — порядок полосы получателя в `Inbox-T`** (ADR 0012, п. 5).
   - События одного инициатора идут в порядке его commit, между инициаторами — в причинном порядке.
   - `seq` получателя выдаётся в порядке его транзакций, вперемешку с его собственными изменениями.
   - Пример — регистрация: сначала сообщение (`pts`), потом плашка (`seq`). Клиент получает сообщение раньше, чем исчезает плашка.
5. **Ровно один раз.** Строку события удаляет та же транзакция, что пишет строки `seq` и пуши (`FinishEvent`: `DELETE`, `RowsAffected = 1`).
   - Повторная доставка не находит строки: `duplicate`, второго `seq` нет.
   - Сбой до commit не применяет ничего, событие придёт снова.
6. **Боты.** Событие боту завершается без журнала и пуша.
   - Боты не обслуживаются: `sync.pushBotUpdates` — заглушка enterprise, топик `BotSync` не настроен.
   - В Bot API этих обновлений нет: там свои (`my_chat_member` и другие), их строит шлюз ботов.
   - Если появятся боты по MTProto, решение пересматривается: журнал и для ботов, пуш через `BotSync`.
7. **Общий поиск peer** — пакет `app/service/biz/updates/seqpeers`, его используют `updates.getDifference` в bff и консьюмер msg.
   - API:
     - `Pick(h, selfId, updates...)` — id пользователей и чатов;
     - `Source` — интерфейс над `UserGetMutableUsers` и `ChatGetChatListByIdList`, которые уже встроены в Dao обеих сторон;
     - `Resolve(ctx, src, viewer, h)` — вид для `viewer`. Сбой одного запроса не отменяет другой: возвращается найденное и ошибки;
     - `Peers.Of(u)` — peer одного обновления.
   - Новые типы:
     - `updateChatParticipants` — чат, каждый участник и пригласивший, у `chatParticipantsForbidden` — свой участник;
     - `updateChat` — чат;
     - `updateChatDefaultBannedRights` — peer;
     - `updatePendingJoinRequests` — peer и `recent_requesters`;
     - `updateUserName`, `updateUser`, `updatePeerSettings` о другом пользователе — этот пользователь.
   - Каналы, как и раньше, не запрашиваются. Поведение `getDifference` для типов этапа 2 не меняется.
8. **Свёртка `getDifference`.** Остаётся последнее состояние на своём месте. Ключи у каждого типа свои:
   - `updateChatParticipants` и `updateChat` — по чату;
   - `updateChatDefaultBannedRights` и `updatePendingJoinRequests` — по peer.
   Имена и пользователи сворачиваются по id пользователя, как и раньше.
9. **Список типов с `seq`** — `userbox.SeqUpdate`, единственный источник. Добавлены `updateChatParticipants`, `updateChat`, `updateChatDefaultBannedRights`, `updatePendingJoinRequests`.
10. **Первый переведённый писатель** — доставка регистрации импортированного номера (`contact_signup.go`).
    - Было: `updatePeerSettings` импортёру пушем с `seq = 0`.
    - Стало: `EmitSeqInbox` в той же транзакции нового пользователя, после события сообщения.

## Последствия
- **Выкатка.** msg (консьюмер) выкатывается не позже писателей в biz.
  - Старый msg считает событие неизвестного метода неразбираемым: dead сразу, получатель запаркован. Автоповтор при получении лидерства новым msg вернёт полосу, но до этого сообщения получателя ждут.
  - Откат msg ниже этой версии — после отката писателей и когда в `mq_outbox` нет строк `inbox.TL_inbox_seqUpdatesToInbox` в pending и published.
  - Миграций нет: таблицы из ADR 0020.
- **Новая зависимость консьюмера.** Для этого события консьюмер `Inbox-T` спрашивает biz user и biz chat. Недоступный biz задерживает партицию (временная ошибка, алерт). Остальные события, как и раньше, обходятся без biz.
- **Объём веерной рассылки.**
  - Одно событие на получателя, одна транзакция получателя, один пуш на обновление.
  - Транзакция инициатора пишет N строк `mq_outbox` многострочными `INSERT` (до 500 строк и 4 МБ на запрос).
  - Пример — базовая группа на 200 участников, `updateChatParticipants` каждому. Это 200 событий по ~20 КБ (лимит события 4 МБ) и 200 запросов вида до 200 пользователей.
  - При 100 пользователях это миллисекунды. Если вырастет — кэшировать вид в пределах полосы или сжимать список.
- **Инициатор свои обновления получает сам.** Ответом RPC, своим `EmitSeqUpdate` или сообщением с `pts` — это решает писатель. Событие инициатору запрещено.
- **Что ещё переводит этап 3.** Каждый — отдельный срез по образцу регистрации:
  - участники базовых групп: создание, добавление, исключение, выход, админы (`updateChatParticipants`);
  - права по умолчанию (`updateChatDefaultBannedRights`);
  - заявки на вступление (`updatePendingJoinRequests`; `chatinvites`: вступление по ссылке, `hideChatJoinRequest`);
  - `updateChat`: название, фото, удаление группы;
  - имена и фото — тем, у кого пользователь в контактах (`updateUserName`/`updateUser`);
  - снятие закрепа при удалении диалога. Своё устройство — `EmitSeqUpdate` в транзакции удаления (msg `deleteHistory`, `dialog.deleteDialog`). У собеседника — в обработчике его inbox-события, который уже работает в ящике получателя.
- **biz chat пока без outbox.** Ему нужно:
  - `Topics` из конфигурации biz;
  - `outbox.Register`;
  - `userbox.Open` и `RunBox`;
  - изменение строк чата через `b.Tx()` в транзакции ящика инициатора вместе с `EmitSeqInbox` каждому участнику. Тогда изменение чата и события атомарны.
- **Признак пересмотра:**
  - эталон Telegram покажет, что эти типы идут без `seq` или с другим составом;
  - появятся боты по MTProto;
  - запросы вида станут заметной долей времени консьюмера.

## Рассмотренные альтернативы
- **Пользователи и чаты в событии (как `sendUserMessageToInboxV2`).** Отвергнуто:
  - вид пришлось бы строить для каждого получателя в пути инициатора;
  - событие группы росло бы как N²;
  - повтор после dead отдал бы устаревший вид.
- **Писать `seq` получателя в транзакции инициатора.** Нарушает ADR 0011: чужой ящик меняется только своей транзакцией, под блокировкой своего `user_state`.
- **Отдельный метод inbox на каждый тип обновления.** Пять одинаковых обработчиков и пять CRC без выигрыша: применение одно и то же — журнал и пуш каждого обновления.
- **Проверять обновления только при применении.** Ошибка писателя парковала бы полосу получателя вместо отказа запроса инициатора.
