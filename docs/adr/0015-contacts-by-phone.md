# 0015. Контакты по номеру: телефонная книга на сервере, лимит, уведомления о регистрации

- Статус: accepted
- Дата: 2026-10-24
- Задача 011. Опирается на ADR 0011 (транзакция ящика `pkg/userbox`) и ADR 0012 (события транзакции — строки `mq_outbox`, relay, применение у получателя ровно один раз).

## Контекст

Официальные клиенты синхронизируют адресную книгу через `contacts.importContacts`: Android (`ContactsController.performSyncPhoneBook`) и iOS (`ContactSyncManager.pushDeviceContactData`) шлют её порциями по 500, tdesktop — по одному номеру из окна «Добавить контакт» (`AddContactBox::save`). Номера приходят как в книге: Android — цифры с `+` (`PhoneFormat.stripExceptNumbers`), iOS — только цифры, tdesktop — с форматированием, в том числе национальные номера без кода страны. Ответ клиенты разбирают так: `imported{user_id, client_id}` и пользователь с `contact` в `users` — новый контакт (iOS берёт первого пользователя ответа за импортированный контакт), `popular_invites` — кого пригласить, `retry_contacts` — что прислать снова: Android через 5 минут, iOS через сутки.

Апстрим отвечал пустым ответом; `user.importContacts` писал незарегистрированные номера в фоновой горутине без ошибок, у таблицы `imported_contacts` уникальный ключ по одному `user_id`; уведомление о регистрации (`auth.signUp`) шло из горутины bff после ответа: падение bff теряло его, повтор дублировал.

Семантика Telegram, на которую опираемся:
- `inputPrivacyKeyAddedByPhone` — кто может найти пользователя по номеру (все или контакты); кого найти нельзя, тот для импортёра — номер без аккаунта.
- `contacts.resetSaved` «удаляет все контакты без связанного аккаунта Telegram» — номера книги; контакты остаются. Клиенты вызывают его при выключении синхронизации.
- `contacts.getSaved` — метод takeout API (`TAKEOUT_REQUIRED`, 403, вне `invokeWithTakeout`).
- `account.setContactSignUpNotification(silent)` выключает уведомления, но не сообщение: tdlib описывает опцию `disable_contact_registered_notifications` как «сообщение в личном чате всё равно придёт», Android не показывает уведомление для `messageActionContactSignUp` с флагом `silent` (`NotificationsController`). `account.getContactSignUpNotification` отвечает `silent` (Android: `enableJoined = response instanceof TL_boolFalse`).
- Изменения контактов другие устройства узнают из `updatePeerSettings` с пользователем и его флагом `contact` (Android `MessagesController.processUpdateArray` → `ContactsController.processContactsUpdates`); так отвечает и `contacts.addContact`.

## Решение

### Телефонная книга на сервере

- Номер нормализуется как при входе (`users.phone`: цифры E.164 без `+`), `pkg/phonenumber.NormalizeContact`. Номер без `+` сначала читается как национальный номер страны импортёра (`users.country_code`), иначе как международный — как его набрал бы телефон. Неразбираемые номера и собственный номер импортёра пропускаются без ответа.
- Номер аккаунта, который импортёр может найти (`addedByPhone`), становится строкой `user_contacts` с именем и номером из книги; любой другой номер — строкой `unregistered_contacts (phone, importer_user_id, имя)`. Это и есть книга на сервере: `contacts.getSaved` отдаёт контакты с номером и эти строки, `contacts.resetSaved` удаляет строки, `popular_invites.importers` — число строк номера.
- Импорт — одна транзакция ящика импортёра (`userbox.Run`): она сериализует импорты одного пользователя и повторяет 1213/1205. Внутри: окно лимита, известные номера, запись контактов, затем блокирующее чтение обратных строк для взаимности (`FOR UPDATE` после вставки своей строки: два встречных импорта ждут друг друга, InnoDB разрывает взаимоблокировку, повтор видит закоммиченную строку другого), запись книги, перепроверка регистрации номеров книги.
- Повторный импорт идемпотентен (уникальные ключи, upsert), меняет только имена. `update_id_list` — контакты, которые импорт добавил или изменил; bff шлёт другим устройствам импортёра `updatePeerSettings` с этими пользователями (`sync.updatesNotMe`, как `contacts.deleteContacts`).

### Лимиты

- Запрос: первые 500 контактов (порция Android и iOS), остальные — в `retry_contacts`.
- Новые номера (нет ни в книге, ни среди контактов): 2000 за окно 24 часа на пользователя (`contact_import_quota`: начало окна и счётчик). Повторная синхронизация той же книги лимит не тратит; сверх лимита номера уходят в `retry_contacts`, ничего о них не сообщая. После `resetSaved` номера снова считаются новыми.
- Обоснование: книга члена закрытой группы почти всегда меньше 2000 номеров, первая синхронизация укладывается в одни сутки; проверка списка чужих номеров ограничена 2000 в сутки на аккаунт, а регистрация только по allowlist.

### Уведомление о регистрации

- Аккаунт и строка `contact_signups (user_id, phone)` пишутся одной транзакцией (`CreateNewUserV2`). Регистрация не ждёт доставки.
- Доставка — одна транзакция ящика нового пользователя C: под его блокировкой она читает с `FOR UPDATE` строки книги с его номером, создаёт каждому импортёру контакт C с именем из книги (взаимный, если C уже добавил импортёра), удаляет строки книги и строку `contact_signups` и пишет события (`Box.Emit`): в ящик каждого импортёра — `inbox.sendUserMessageToInboxV2` со служебным `messageActionContactSignUp` от C (`silent`, если импортёр выключил уведомления), и push `updatePeerSettings` с C. Сообщение применяет консьюмер msg в транзакции ящика импортёра ровно один раз (ADR 0012), `dialog_message_id` — из idgen. Повтор доставки ничего не дублирует: строк уже нет.
- Гонка импорта и регистрации одного номера закрыта порядком: импорт пишет строку книги, затем перечитывает регистрацию номера; доставка ждёт незакоммиченную строку на блокирующем чтении. Либо доставка видит строку, либо импорт видит аккаунт (и тогда переплан: номер становится контактом без сообщения).
- Доставляет её `core.SignUpWorker` в процессе biz: сразу после создания аккаунта (`Notify`) и раз в 30 с для того, что оставили сбой или рестарт. Несколько экземпляров biz безопасны: блокировка ящика сериализует доставку, доставленной строки нет. Сбой — метрика `user_contact_signup_errors_total` и лог с `user_id`, без номера. biz регистрирует топики `Inbox-T` и `Sync-T` (секция `Topics`) и получает `IdgenClient`; строки забирает опросом relay msg (ADR 0012, п. 3).
- RPC `user.getImportersByPhone` и `user.deleteImportersByPhone` удалены: их работу делает доставка.

### Частые собеседники

- Рейтинг считается при запросе из исходящих сообщений пользователя (последние 10 000 строк его ящика `messages`): `Σ exp((t − now) / rating_e_decay)` по сообщениям после включения и после сброса пира в категории; `rating_e_decay` = 2 419 200 с, как в `help.getConfig`, — та же формула, по которой клиенты добавляют свои отправки к полученным рейтингам (Android `MediaDataController.increasePeerRaiting`, tdesktop `TopPeers`). Категории: `correspondents` (люди), `bots_pm`, `groups` (basic group, где пользователь ещё участник), `forward_users`, `forward_chats` (пересланные сообщения). Для inline-ботов, приложений ботов, звонков и каналов на сервере нет данных — категории приходят пустыми.
- Храним только состояние: `user_settings.topPeersSince` (нет — включено; `-1` — выключено; время — включено заново, считаются сообщения после него: выключение «удаляет данные», как предупреждают клиенты) и сбросы `user_top_peer_resets`. `contacts.getTopPeers` отдаёт `topPeersDisabled`, когда выключено, и `topPeersNotModified` при совпадении `hash` (алгоритм core.telegram.org/api/offsets, как tdesktop `TopPeers::countHash`); `users` идут в порядке рейтинга — iOS берёт этот порядок за ранжирование.

## Последствия

- Синхронизация книги официального клиента находит зарегистрированных, приватность `addedByPhone` соблюдается, книга на сервере обслуживает `getSaved`/`resetSaved`, лимит ограничивает перебор номеров.
- Уведомление о регистрации не теряется при падении процесса и не дублируется; при многих импортёрах регистрация не замедляется — доставка идёт после ответа, одной транзакцией.
- biz теперь пишет события (`mq_outbox`) и зависит от idgen; relay msg забирает эти строки опросом раз в 50 мс.
- Рейтинг частых собеседников читает чужую для сервиса пользователей таблицу `messages` (только чтение, ограниченное 10 000 строками на запрос).
- Пересмотреть: если пользователей станет больше нескольких сотен (лимит и окно — константы), если понадобится книга по устройствам (`phone_books` апстрима не используется) или рейтинг станет дорогим (тогда — счётчики в транзакции отправки).

## Рассмотренные альтернативы

- **Уведомления из bff после `auth.signUp`** (как в апстриме) — теряются при падении bff, повтор дублирует сообщение (новый `dialog_message_id`).
- **Доставка через `msg.pushUserMessage` по импортёру** — каждое сообщение надёжно, но вместе с созданием контактов не атомарно: сбой посередине даёт дубли или потери.
- **Фоновый обход «номера книги, ставшие аккаунтами»** без очереди — неотличимы номера, скрытые приватностью (их строки тоже лежат в книге): обход раскрыл бы скрытый аккаунт.
- **Лимит в Redis** — Redis по ADR 0005 только кэш; потеря сбрасывала бы лимит.
- **Не отправлять сообщение тем, кто выключил уведомления** (апстрим) — Telegram отправляет его с `silent`; клиенты рассчитывают на это.
- **`contacts.getSaved` без takeout** — расходится с Telegram; клиенты зовут его только в выгрузке данных (tdesktop export).
