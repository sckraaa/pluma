# 0019. Состав updates.getDifference и seq состояния

- Статус: accepted
- Дата: 2026-10-26
- Задача 010. Дополняет ADR 0011 (п. 7: журнал читается там же, где состояние; seq отложен до задачи 010).

## Контекст
- **Эталон Telegram.** Сценарий `saved_messages` (задача 007) записан с боевого Telegram 2026-10-26. Другой сеанс того же аккаунта запрашивает `updates.getDifference` от состояния до отправки сообщения в «Избранное».
  - После отправки и правки Telegram отдаёт:
    - в `new_messages` — сообщение в текущем виде, с правленым текстом и `edit_date`;
    - в `other_updates` — `updateMessageID` и `updateReadHistoryInbox`, без `updateEditMessage`.
  - После удаления: `new_messages` нет, в `other_updates` — `updateDeleteMessages`, затем `updateReadHistoryInbox`.
  - У обновлений в разнице `pts` равен итоговому, `pts_count` нет. `seq` состояния разницы равен `seq` из `updates.getState`.
- **Наш сервер до задачи 010.**
  - Сообщение отдавалось в виде на момент отправки, а правка — отдельным `updateEditMessage`.
  - Удалённое сообщение оставалось в `new_messages`, `updateMessageID` не было вовсе.
  - `seq` разницы был 0, а `getState` отдавал −1.
- **Журнал переписывать нельзя.** `user_pts_updates` хранит каждое обновление таким, каким оно было записано. На этом держатся проверка фиксации транзакции (сравнение байтов), ответ на повтор `random_id` и правило `tools/boxaudit` (ADR 0011). Правка записывает в журнал полное сообщение после правки, удаление мягкое.
- **Клиенты** (исходники tdesktop, TDLib, Telegram-Android, Telegram-iOS, октябрь 2026):
  - все четверо сначала вынимают из `other_updates` `updateMessageID`, затем добавляют `new_messages` как новые сообщения (уведомления, счётчики), затем применяют остальное по порядку без проверки `pts`;
  - без `updateMessageID` устройство-отправитель, потерявшее ответ на `sendMessage`, показывает дубль;
  - удалённое сообщение в `new_messages` даёт уведомление о нём, правка отдельным обновлением — уведомление со старым текстом;
  - TDLib, Android и iOS берут `seq` состояния разницы без условий.

## Решение
1. **Сворачивать журнал при чтении**, в `updates.getDifferenceV2` (`differenceBuilder`, `app/service/biz/updates`). Не по текущим строкам `messages`: свёртка описывает ровно диапазон `(pts, S.pts]` до отданного состояния и правильно режется на `differenceSlice`.
2. **`new_messages`** — сообщения, добавленные в диапазоне и не удалённые до его конца, в состоянии на его конец, по возрастанию id.
   - Правка такого сообщения заменяет его и отдельным обновлением не идёт.
   - Удаление убирает его из `new_messages`.
3. **`other_updates`**, по порядку:
   - сначала `updateMessageID` своих новых сообщений, по возрастанию id. `random_id` берётся из `messages.out_random_id` (есть только у копии отправителя), с мастера, как и журнал;
   - затем остальные обновления в порядке журнала:
     - правка старого сообщения — одна, в последнем виде, и ни одной, если его потом удалили;
     - удаления — одно обновление со всеми id, на месте последнего (id, которых клиент не видел, остаются: так у Telegram);
     - прочтение содержимого — так же;
     - закрепы, папки и прочее — каждое как пришло, без слияния: они могут быть про разные чаты;
   - последними — прочтение истории каждого чата, одно, с последним `max_id`: это состояние чата на конец диапазона.
     - Его `still_unread_count` тоже на конец диапазона: входящие неудалённые сообщения после `max_id`, добавленные до него (`messages.pts`). Клиенты берут это число как счётчик непрочитанных, iOS — как точное, раз `pts` итоговый. Число на момент прочтения было бы неверным, если после прочтения пришло сообщение или непрочитанное удалили.
   - У обновлений из журнала `pts` равен итоговому, `pts_count` нет.
4. **`seq`**:
   - одно значение для `updates.getState` и всех вариантов разницы (`state`, `intermediate_state`, `differenceEmpty`) — `user_state.seq`;
   - начальное значение — `userbox.BaseSeq = 1`, как `BasePts`, а не прежняя подмена 0 → −1. Первое обновление с `seq`, когда появится журнал `seq`, получит 2, и клиент с 1 применит его без дыры. С −1 все четыре клиента приняли бы его за дыру и лишний раз запросили бы разницу;
   - миграция `migrate-20261026-seq.sql`: `DEFAULT 1` и 0 → 1. Подменять 0 → 1 при чтении нельзя: будущий писатель начал бы с 1, равной уже выданной;
   - журнал `seq` по ключу (`auth_seq_updates`) никто не писал, его чтение убрано. Журнал `seq` будет по аккаунту, в транзакции ящика (ADR 0011, п. 13).

5. **Лимиты разницы** (этап 2 задачи 010):
   - **`pts_total_limit` — порог клиента**, как на странице метода: если `pts + pts_total_limit < pts` ящика, ответ — `differenceTooLong` с `pts` ящика. Его шлют Android (1000 или 5000 на первой разнице после запуска; на `differenceTooLong` он перечитывает диалоги) и Web K (1200, очищает состояние). Без этого поля `differenceTooLong` не отдаётся никогда: tdesktop его не поддерживает и перестаёт применять обновления, расширение уведомлений iOS на нём падает.
   - **Размер среза выбирает сервер:** 1000 строк журнала (`sliceRows`), в пределах рекомендованных Telegram 1000–10000. Длиннее — `differenceSlice`.
   - **Клиент впереди ящика** (например, после восстановления из бэкапа) получает `difference` без обновлений с состоянием ящика. Меньший `pts` из разницы принимают tdesktop, Android, iOS и Web K. При `differenceEmpty` клиент остался бы впереди и молча отбрасывал бы push с `pts`, который считает полученным. TDLib понижает `pts`, только если разница больше 1000009, ему не помогает ничего.
   - **`pts_limit` и `qts_limit` принимаются, но не исполняются.** `pts_limit` шлёт только TDLib (1 — для починки дыры в один `pts`); без него TDLib через 0,7 с делает полную разницу, то есть работает, только дороже. TDLib среди наших клиентов нет, поэтому поле во внутренний RPC не добавляется.

## Последствия
- Правка обязана записывать в журнал полное сообщение, иначе свёртка испортит `new_messages`. Сейчас пишет только `editRowWith`.
- На каждую разницу со своими новыми сообщениями — один запрос к `messages` по первичному ключу, на мастере. На каждый прочитанный чат в разнице — подсчёт непрочитанных по индексу диалога.
- В срезе (`differenceSlice`) сообщение, удалённое уже после конца среза, в счётчик не входит: в `messages` есть флаг удаления, но не его момент. Удаление приходит следующим срезом.
- Порядок `other_updates` выведен из двух ответов Telegram. Сценарий «устройство офлайн, события разных типов» (критерий задачи 010) должен подтвердить его или поправить.
- Не решено (задача 010 дальше):
  - журнал `seq` и обновления с `seq` — ADR 0020;
  - `pts_limit` (TDLib);
  - `unread_count` состояния всегда 0 — ни один клиент его не читает.
