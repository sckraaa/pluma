# 0071. HTTPS-CDN: Gcore тянет шифр из дома, ключи и хэши дома

- Статус: accepted (2026-11-16). Владелец выбрал Gcore (бесплатный 1 ТБ), аккаунт без карты, Россия — позже (шов оставлен). Реализовано задачей 107 в партии `batch/20261115`; проверки владельца 0–6 на живом аккаунте Gcore не проводились.
- Задача: 107 (`docs/tasks/107-https-cdn.md`). Обслуживаются `upload.getFile` с `cdn_supported` (ответ `upload.fileCdnRedirect` только патченным клиентам), `upload.getCdnFileHashes`, `upload.reuploadCdnFile`, `help.getCdnConfig` (пустой), `upload.getCdnFile` на DC 1 (`FILE_TOKEN_INVALID`).
- Связано: ADR 0057 (дом — ядро, VPS — труба для шифра; §3 «Файлы»), ADR 0061 (туннель; на VPS только DNAT портов ядра, TLS заканчивается дома в Caddy; исходящий трафик дома через VPS, §3), ADR 0065 (CDN-DC Pluma), ADR 0041 (всё открыто всем), ADR 0009 (правки proto).
- **Заменяет части ADR 0065:** §1 в части «VPS (узел `cdn`)», §4 (`request_token`, ожидание в `reuploadCdnFile`), §5 (узел `cdn` целиком), §6 в части таблицы `cdn_nodes`, заливки на узел, проверки узла и канала управления, §7 (`dc_options`), §8 (клиенты), «Последствия» в части сервера MTProto на VPS и `dc_options`, «Что не делается» в части Web K. Правило «редирект только на полную проверенную копию» заменяется на «редирект только на подготовленный файл» (§4 ниже). **Остаются в силе** из 0065: §2 (политика файлов, кроме секретных чатов — они исключены, §6), §3 (ключ, IV, AES-256-CTR, хэши 128 КБ открытого текста), §6 в части `cdn_files` и очереди с арендой.
- Отменяет правку ADR 0057 §2, которую вносил 0065: на VPS снова нет завершения MTProto ни в каком виде.

## Контекст

### Чего хочет владелец (2026-11-16)
- Вместо своего узла MTProto на VPS — CDN-провайдер со многими точками присутствия. Смысл 0065 сохраняется: у провайдера только шифр под неугадываемыми ссылками с ограниченным сроком; ключи и хэши клиент получает только по MTProto из дома, качает байты по HTTPS с `Range`, расшифровывает у себя, сверяет хэши и при любой ошибке докачивает из дома. CDN получает и веб-клиент.
- **Провайдер — Gcore** (бесплатный 1 ТБ в месяц). Сегодня весь исходящий трафик дома ≈ 50 ГБ/мес, из них через CDN пошло бы ≈ 30–45 ГБ; план — 100–300 ГБ/мес.
- **Россия — позже.** Пользователи в России сейчас ходят через VPN. Yandex и маршрут по стране из задачи убраны, но шов оставлен: интерфейс выдачи и правило маршрута, в котором сегодня одна запись (§1, §9).
- Приняты: файлы секретных чатов не идут через CDN; прокси — Desktop SOCKS5/HTTP через CDN, Android и iOS с любым прокси без CDN, MTProxy и WEB-прокси без CDN; постоянный `User-Agent: Pluma` в нативных клиентах; срок URL 6 ч, 404 — сразу домой, 10 минут без CDN после 3 отказов.

### Gcore (страницы прочитаны 2026-11-16)
- **Бесплатно:** 1 ТБ трафика и 1 млрд запросов в месяц, «No credit card needed»; сверх лимита — по тарифу, и страница советует «Add a payment method before you reach the limit to keep delivery running smoothly» (https://gcore.com/cdn/free-content-delivery-network). Сверх 1 ТБ — €0,01/ГБ и €0,75 за млн запросов (https://gcore.com/pricing/edge-network); страница бесплатного плана пишет 15 €/ТБ — расхождение, нас не касается, пока трафик в пределе.
- **В лимит входит и трафик «origin → CDN»,** и запросы CDN к источнику, не только отдача пользователям (https://docs.gcore.com/cdn/how-the-cdn-service-and-its-additional-options-are-billed.md). План один — PAYG с платой €0 (https://docs.gcore.com/cdn/cdn-packages).
- **Какие опции заперты на бесплатном/PAYG** — общей таблицы нет. Явно платные: Raw Logs (https://docs.gcore.com/cdn/logs/raw-logs-export-cdn-resource-logs-to-your-storage.md), видеоресурсы (overview ниже). Origin Shielding: «paid option» (https://docs.gcore.com/cdn/cdn-resource-options/general/enable-and-configure-origin-shielding.md), но PAYG — «Basic» (cdn-packages) и «includes … Origin Shielding» (https://docs.gcore.com/account-settings/billing/trial-conditions.md) — противоречие; дизайн на нём не держится. **Secure Token на бесплатном/PAYG — НЕ ПРОВЕРЕНО:** ни одна страница не ограничивает его планом (только привязка к подсети — Enterprise).
- **Ресурс:** до 30 ресурсов на аккаунт; домен ресурса может быть доменом Gcore — новый аккаунт получает суффикс `gcorecdn.com`, DNS не нужен; свой домен не меняется после создания. Новый ресурс по умолчанию включает Network Error Logging (заголовки `NEL`, `Report-To`) (https://docs.gcore.com/cdn/getting-started/create-a-cdn-resource/overview.md, https://docs.gcore.com/cdn/getting-started/create-a-cdn-resource/create-a-cdn-resource.md).
- **Secure Token:** `md5` = base64url(MD5(`{expires}{path} {key}`)) без `=`, параметры `?md5=…&expires=…`, ключ 6–32 символа в портале; CDN проверяет токен на краю, неверный, отсутствующий или истёкший — 403 (https://docs.gcore.com/cdn/cdn-resource-options/security/use-a-secure-token/configure-and-use-secure-token.md); страница «About» пишет 410 для верного, но истёкшего и 403 для неверного (https://docs.gcore.com/cdn/cdn-resource-options/security/use-a-secure-token/about-secure-token) — клиент обрабатывает оба одинаково. Gcore сам советует включить «Ignore query string», чтобы токен не делил кэш. Проверяется ли токен до поиска в кэше, ни одна из двух страниц прямо не говорит (первая — только «doesn't forward these requests to the origin») — проверка владельца 2.
- **Ключ кэша:** «Ignore query string → Ignore all» — объекты с разными параметрами кэшируются как один (https://docs.gcore.com/cdn/cdn-resource-options/cache/ignore-the-set-cookie-or-query-string-parameters-when-caching-content-on-cdn-servers.md). Передаются ли отброшенные параметры (`md5`, `expires`) источнику, страница не говорит — НЕ ПРОВЕРЕНО; источник поэтому обязан игнорировать строку запроса (§3).
- **Always online** (отдача устаревшего кэша) включается по условиям, среди которых `http_403`, `http_404`, `error`, `updating` (https://docs.gcore.com/cdn/cdn-resource-options/cache/always-online-provide-the-stale-cache-if-the-origin-is-unavailable.md). Включённая, она отдавала бы закэшированный шифр в ответ на 403/410 источника (режим `path-hmac`) и после удаления файла; значение по умолчанию страница не называет — владелец проверяет, что опция выключена.
- **Большие файлы (slice):** CDN тянет у источника куски по 10 МБ запросами `Range`, кэширует каждый отдельно и отдаёт клиенту запрошенный диапазон; источник обязан поддерживать `Range` и отдавать постоянные `Content-Length` и `ETag`; несовместимо с gzip, Brotli и Fetch Compressed; после включения — purge (https://docs.gcore.com/cdn/cdn-resource-options/optimize-large-file-delivery.md). **Код ответа клиенту (206) страница не называет — НЕ ПРОВЕРЕНО.**
- **Кэш:** в режиме «Origin controlled» сохраняются ответы 200, 201, 204, 206, 301, 302, 303, 307, 308, прочие (в т. ч. 404) — нет; файлы, которые не запрашивали 36 ч, удаляются из кэша независимо от настроек (https://docs.gcore.com/cdn/cdn-resource-options/cache/specify-cache-lifetime-on-a-cdn-resource-or-origin.md).
- **Источник:** URL/IP, S3 (Gcore, Amazon, другое), FastEdge (create-a-cdn-resource). Закрыть источник рекомендуется секретным заголовком (Gcore добавляет его к каждому запросу к источнику) при выборке по HTTPS с проверкой сертификата источника; списки адресов краёв меняются (https://docs.gcore.com/cdn/getting-started/configure-an-origin/add-cdn-servers-to-the-origin-acl-whitelist.md). Заголовок: до 50 на ресурс, значение в портале — буквы, цифры, `-_/:=.` и пробел (https://docs.gcore.com/cdn/cdn-resource-options/http-headers/specify-http-headers-that-cdn-adds-to-requests-to-the-origin.md).
- **Проверка сертификата источника — отдельная опция**, не флажок протокола: страница протокола тяги предлагает только HTTP / HTTPS / «HTTP and HTTPS» (`MATCH` в API) и о проверке сертификата молчит (https://docs.gcore.com/cdn/cdn-resource-options/general/specify-an-origin-and-the-origin-pull-protocol.md). Проверка — `proxy_ssl_enabled` с `proxy_ssl_ca` (загруженный в аккаунт сертификат CA, выпустившего сертификат источника) **и** обязательным `proxy_ssl_data` (клиентский сертификат и ключ; без него — «Can not enable proxy_ssl feature while both proxy CA certificate and proxy ssl data not specified»); описана только через API, SDK и Terraform, шагов в портале нет; включена ли она по умолчанию и принимает ли Gcore без неё любой сертификат источника — страница не говорит (https://docs.gcore.com/cdn/cdn-resource-options/general/enable-origin-ssl-validation.md). SNI к источнику по умолчанию берётся из Host header (https://docs.gcore.com/cdn/cdn-resource-options/security/set-the-hostname-passed-in-sni-requests-to-the-origin-server.md).
- **HTTPS на домене Gcore (`*.gcorecdn.com`)** — какой сертификат отдаёт общий домен, прочитанные страницы не говорят; бесплатный Let's Encrypt выпускается только для своего домена ресурса (https://docs.gcore.com/cdn/ssl-certificates/configure-a-lets-encrypt-certificate.md) — НЕ ПРОВЕРЕНО, проверка владельца 0.
- **Gcore Object Storage** (если бы источником был бакет): €0,04/ГиБ·мес, вход бесплатно, отдача в CDN бесплатно, запросы €0,03 за 10 тыс., пробного периода нет (https://docs.gcore.com/storage/how-storage-is-billed.md, trial-conditions); приватный бакет Gcore подключается к ресурсу без ключей (https://docs.gcore.com/cdn/cdn-resource-options/general/use-a-private-bucket-as-an-origin.md).
- **Purge:** по URL — 2 запроса в минуту на ресурс по 100 URL; по шаблону — 1 в минуту по 10 шаблонов (https://docs.gcore.com/cdn/clear-cdn-resource-cache-by-url-pattern-or-all.md). Нам не нужен (§5).
- **CORS и заголовки ответа:** опция `Access-Control-Allow-Origin` и «Response headers (add)» до 50 заголовков, флажок «Always add … regardless of response code» (https://docs.gcore.com/cdn/cdn-resource-options/http-headers/add-or-hide-response-headers.md, https://docs.gcore.com/cdn/cdn-resource-options/http-headers/add-the-access-control-allow-origin-header-to-the-browser-response.md).
- **Логи:** Log viewer показывает запросы за последние 3 дня — адрес клиента, время, метод, URL, код, размер, точка, `User-Agent`, статус кэша (https://docs.gcore.com/cdn/logs/log-viewer-view-and-download-cdn-resource-logs.md). ### Клиенты (`~/pluma-work/reference-src-new`: Android 13.2.1, iOS release-13.2, tdesktop 7.4.1, Web K)
- Ни один официальный клиент не умеет HTTPS-CDN: Android, tdesktop и iOS знают только MTProto-CDN (`upload.getCdnFile`), Web K — никакой CDN (`src/lib/appManagers/apiFileManager.ts:483-487`). Патч нужен во всех четырёх.

Непатченный Android на редирект с `dc_id`, которого нет в списке DC, ждёт этот DC бесконечно (`jni/tgnet/ConnectionsManager.cpp:2585-2590, :2849-2856, :3166-3168`).

## Решение

### 1. Провайдер и шов для следующих
- **Выдача 201 — Gcore CDN**, ресурс на домене Gcore (`<префикс>.gcorecdn.com`), источник — дом (§3). Если общий домен не отдаёт действительный для клиентов сертификат (проверка владельца 0, НЕ ПРОВЕРЕНО), ресурс создаётся на своём нейтральном домене (не `pluma.chat`) с бесплатным Let's Encrypt Gcore и CNAME; код не меняется — меняется `CDN_GCORE_BASE_URL`. Свой домен ресурса после создания не меняется (Контекст), поэтому выбор делается до создания.
- Термины кода: **выдача** (delivery) — способ подписать URL и номер `dc_id` в редиректе; **источник** (source) — откуда выдача берёт шифр: `home-origin` (CDN тянет из дома, сегодня) или в будущем `push-store` (дом заливает в бакет провайдера). Номера выдач < 1000, не 0, в `dc_options` их нет.
- **Маршрут** — упорядоченный список выдач; сегодня в нём одна запись `*:201`. Грамматика `CDN_ROUTES` та же, что понадобится для стран (`RU,BY:2xx;*:201`), но записи со странами при старте отклоняются, пока нет определения страны (`authsession.getIpCountry` — задача «Россия и СНГ», не эта). Добавление российского провайдера — новая выдача, при необходимости источник `push-store`, запись маршрута; клиенты не меняются: URL целиком приходит в `file_token`.

### 2. Как клиент узнаёт URL — без изменения TL
- Конструктор `upload.fileCdnRedirect{dc_id, file_token, encryption_key, encryption_iv, file_hashes}` прежний (слой 233).
- `file_token` = `"PLH1"` (4 байта ASCII) ‖ `id` (32 байта, `cdn_files.file_token`) ‖ `exp` (uint32 BE, unix-секунды) ‖ `url` (UTF-8 до конца, только `https://`).
- Клиент берёт `url` как есть; провайдера, хост и схему подписи можно менять без выпуска клиентов. `dc_id` — номер выдачи, клиент к нему не подключается.
- Ключ, IV и хэши — только в полях редиректа и в `upload.getCdnFileHashes` по MTProto из дома; `file_token` целиком уходит домой в `getCdnFileHashes`, дом находит файл по `id`. В URL ключа нет.
- URL: `https://<префикс>.gcorecdn.com/o/<hex(id)>?md5=<токен>&expires=<exp>` (Secure Token, §7).

### 3. Источник — дом, за VPS; шифрование на лету
**Выбрано (а): Gcore тянет шифр из дома.** Новая точка в bff (`pkg/cdn` origin), слушает только внутреннюю сеть Docker; домашний Caddy публикует её на отдельном имени (`PLUMA_CDN_ORIGIN_DOMAIN`, A-запись на адрес Pluma). VPS не меняется: 443 уже уходит домой DNAT (ADR 0061 §2), TLS заканчивается в Caddy.
- `GET`/`HEAD /o/<64 hex>` → файл по `id` из `cdn_files`, только если файл подготовлен (§4) и его вид разрешён политикой; иначе 404.
- **Шифр не хранится нигде.** AES-256-CTR позволяет зашифровать любой диапазон независимо: источник читает открытый текст нужного диапазона из того же источника байтов, что заливщик 102 (`app/bff/files/internal/svc/cdn_files.go`), и шифрует его ключом и IV файла по правилу 0065 §3 (смещение не обязано быть кратным 16: лишние байты потока ключей отбрасываются). Байты под именем неизменны: ключ и IV пишутся в `cdn_files` один раз.
- Ответы: `Range` (один диапазон) → 206 с `Content-Range`; без `Range` → 200; за концом → 416. `Content-Type: application/octet-stream`, `ETag: "<hex(id)>"`, `Last-Modified` = создание строки `cdn_files`, `Accept-Ranges: bytes`, `Cache-Control: public, max-age=2592000, immutable`. Постоянные `Content-Length` и `ETag` — требование slice.
- **Доступ только для Gcore:** заголовок `X-Pluma-Origin-Auth` с 256-битным значением (64 hex) Gcore добавляет к каждому запросу; источник сравнивает за постоянное время, без него — 403. Gcore тянет по HTTPS (Caddy, Let's Encrypt под CAA дома), так заголовок не идёт открытым текстом. Проверка сертификата источника у Gcore — отдельная опция только через API с загрузкой CA и обязательного клиентского сертификата (Контекст); она **не условие запуска**: заголовок защищает только от чужой нагрузки на канал дома, не тайну. Через источник уходит только шифр, а имя объекта — 256 бит; утёкший заголовок даёт тому, кто знает и его, и `id`, лишь тот же шифр, что и CDN. Подменённый посредником шифр ловят хэши клиента. Включить проверку (CA — корень цепочки сертификата источника, сегодня у Let's Encrypt это ISRG Root X1 или X2 — посмотреть на живом сертификате; клиентский сертификат — одноразовый самоподписанный, Caddy его не запрашивает) — шаг владельца «по желанию», когда он проверит это в API. Заголовок не попадает ни в клиент, ни в логи; смена — новое значение в портале и `.env`, затем деплой (минута 403 от источника — клиенты откатятся домой).
- Имя источника не секрет: оно попадает в журналы Certificate Transparency при выпуске сертификата. Поэтому источник не полагается на скрытость имени; без заголовка он не отличает существующий `id` от несуществующего (403 до разбора пути).
- **Строка запроса игнорируется:** путь сверяется по `URL.Path`; `?md5=…&expires=…`, которые Gcore может передать источнику (Контекст), на ответ не влияют. Условные запросы Gcore (`If-None-Match`, `If-Modified-Since`, `If-Range`) обрабатываются по RFC 9110 по постоянным `ETag`/`Last-Modified` (304 продлевает кэш, по странице кэша).
- Пределы источника: 16 одновременных запросов (сверх — 503, Gcore не кэширует 5xx, клиент откатится), таймаут записи 120 с, считает отданные байты (бюджет, §5).
- Канарейка `GET /c/v1`: 256 КБ детерминированных байт (SHA-256 счётчика от постоянной строки), тот же заголовок доступа.

**Почему не (б) Gcore Object Storage с заливкой по S3 API:**

| | (а) дом как источник (выбрано) | (б) бакет Gcore + заливка |
|---|---|---|
| Деньги | 0 (тяга источника входит в бесплатный 1 ТБ) | €0,04/ГиБ·мес + €0,03 за 10 тыс. запросов; нужна карта (у Object Storage нет пробного периода) |
| Что лежит у провайдера | шифр только в кэше точек, удаляется через ≤ 36 ч без запросов | полные копии в бакете до вытеснения домом |
| Трафик дома | каждый кусок 10 МБ — один раз на точку за 36 ч простоя | каждый файл — один раз |
| Сложность | точка источника + подготовка хэшей; нет ключей S3, вытеснения, сверки, жизненного цикла | заливщик, ключи S3 в `.env`, вытеснение, сверка, правило жизненного цикла |
| Отказы | дом лёг — CDN отдаёт только закэшированное; но и ключи с хэшами идут только из дома, так что без дома загрузка всё равно не начнётся | канал дома занят — новые файлы ждут заливки; бакет не зависит от дома |
| Первый зритель | тянет через Gcore со скоростью канала дома (как сегодня) | ждёт полной заливки, качает из дома (как сегодня) |

Канал дома остаётся узким местом для первого просмотра в обоих вариантах. При 30–300 ГБ/мес и нескольких точках в Европе повторная тяга (а) мала и укладывается в 1 ТБ вместе с отдачей. Шов `push-store` (§1) оставлен для провайдера без тяги из дома.

### 4. Подготовка файла и когда дом даёт редирект
- Редирект — только на **подготовленный** файл: строка `cdn_files` с ключом, IV и хэшами всех 128 КБ частей. Хэши требуют прочесть файл целиком; это делает заливщик 102, переделанный в **подготовщика**: та же очередь `cdn_replicas` с арендой, откаты, `short_read`, одна подготовка за раз, предел скорости чтения (`CDN_PREPARE_RATE_MBIT`, локальное чтение, по умолчанию 800). Цель очереди — `target_id` (1 = `home-origin`, файл только читается и хэшируется; ≥ 2 — будущие `push-store`, читается, шифруется и заливается).
- Первый `getFile` с `cdn_supported` по неподготовленному файлу — ответ из дома и постановка в очередь; следующие (обычно через секунды) — редирект.
- Редирект — только сессиям, в `initConnection.params` которых есть `pluma_cdn` (jsonNumber, версия схемы, сейчас 1), и только если в запросе стоит `cdn_supported` без `precise`. Признак читается из `params` ключа авторизации с LRU в bff (1 мин). Официальные клиенты его не шлют.
- **Сессия обязана сохранять смену признака.** Сегодня смена одних `params` в authsession не пишется (`clientNeedUpdate` закомментирован, `app/interface/session/internal/sess/main_auth_wrapper.go:472-475` в `batch/20261115`); Android шлёт `initConnection` только при смене версии (`lastInitVersion`, `jni/tgnet/Request.cpp:80-83`). Сессия пишет клиента в authsession, когда меняется разобранное значение `pluma_cdn` (не строка: `tz_offset` и `perf_cat` меняются сами). Остаточный риск: ручной откат на непатченную сборку с тем же ключом в течение TTL LRU — непатченный Android повиснет на одном файле до перезапуска.
- MTProto-редирект на CDN-DC (0065) больше не выдаётся никому.

### 5. Выбор выдачи, сигнал отката, здоровье, бюджет
- Выдача — первая в маршруте, которая здорова, в бюджете и не избегается этим ключом авторизации. Выбор держится на ключ 10 мин.
- **Сигнал отката.** Тот же ключ берёт тот же файл без `cdn_supported` в течение 5 мин после редиректа на выдачу P — это откат клиента: P избегается для ключа на 1 ч (с одной выдачей — этот ключ час качает из дома), растёт `pluma_cdn_fallback_total{dc}`. Правило «≥ 3 пользователя страны» из прежней редакции уходит вместе со странами. Ложные срабатывания (прокси включили сразу после редиректа, 404 по удалённому файлу) стоят одного часа без CDN одному ключу.
- **Здоровье** раз в минуту: подписанный `GET` канарейки через Gcore с `Range: bytes=131072-135167` → 206, длина, байты совпали — `healthy_until = now + 3 мин`. 4 КБ, а не 128 КБ: проба идёт в счёт лимита (128 КБ в минуту — ≈ 5,7 ГБ в месяц). Дом проверяет через VPS из Германии.
- **Бюджет** выдачи на месяц `CDN_GCORE_MONTHLY_GB` (по умолчанию 800 из 1 000): источник считает точно отданные Gcore байты; отдачу пользователям дом оценивает — размер файла на каждую пару «ключ, файл» в сутки. Сумма ≥ предела — выдача выводится из маршрута до конца месяца; 80 % — алерт. Что Gcore делает без карты сверх 1 ТБ, ни одна прочитанная страница не говорит (бесплатный план: сверх — «billed at the standard overage rate» и совет добавить способ оплаты; страница тарификации: у платных планов отдача останавливается при неуспешной оплате) — вывод «может остановить» НЕ ПРОВЕРЕН; предел дома срабатывает раньше.
- **Проба подписи:** в той же минуте второй запрос канарейки с испорченным `md5` (режим `gcore-md5`) или испорченной подписью в пути (`path-hmac`) обязан получить 403/410; 2xx — выдача нездорова с причиной `token_off` (кто-то выключил Secure Token в портале, и URL перестали истекать). Ответ без тела, в лимит почти не идёт.
- **Вытеснения и purge нет:** у провайдера нет наших копий, кроме кэша точек, который чистится сам (36 ч без запросов). Удалённый файл: дом перестаёт давать редиректы (проверки доступа), выданные URL живут ≤ 6 ч, источник отвечает 404, если байтов больше нет. Purge API (2 запроса в минуту) не используется, API-токен Gcore дому не нужен.

### 6. Политика файлов
- Через CDN — документы и размеры фото ≥ 1 МиБ (`CDN_KINDS=document,photo`, `CDN_MIN_FILE_SIZE`). **Файлы секретных чатов — нет** (принято владельцем): у такого файла один получатель, экономии нет, а провайдер увидел бы пару адресов собеседников. Источник отвечает 404 на вид вне политики, даже если `id` известен.

### 7. Подпись URL
- Интерфейс `Signer` в `pkg/cdn`: `SignURL(object string, exp time.Time) (string, error)`.
- **`gcore-md5` (основной):** `BaseURL + path + "?md5=" + base64url(MD5(exp + path + " " + key)) без "=" + "&expires=" + exp`, `path = "/o/<hex>"`, без привязки к IP (мобильные сети меняют адрес). Ключ 6–32 символа (портал). Эталон теста — вывод команды OpenSSL со страницы Gcore на значениях теста, записанный в `testdata`. Кэш не делится по токену: «Ignore query string → Ignore all».
- **`path-hmac` (запасной — если Secure Token на бесплатном плане недоступен):** `BaseURL + "/t/" + exp + "/" + base64url(HMAC-SHA256(key, exp|hex))[:22] + "/o/" + hex`. Проверяет источник; `exp` округляется вверх до границы `UrlTTL`, поэтому все клиенты в одном окне получают один и тот же URL и делят кэш точки; источник ставит `Cache-Control: public, max-age = exp − now`, и Gcore перестаёт отдавать закэшированный ответ одновременно с истечением URL. Цена: тяга из дома раз в окно на точку, срок URL от `UrlTTL` до 2·`UrlTTL`, истёкший URL получает 403/410 только от источника — поэтому в этом режиме обязательно выключенный Always online (иначе на 403 источника Gcore отдал бы устаревший кэш). Неугадываемость имени (256 бит) остаётся второй линией в обоих режимах.
- Срок URL — `CDN_URL_TTL`, 6 ч. На 403/410 патченный клиент повторяет `upload.getFile` с `cdn_supported` и получает свежий URL (до 3 раз на загрузку). Утёкший URL отдаёт только шифр.
- Отказ неверной или истёкшей подписи и для объекта, уже лежащего в кэше точки, — по странице «CDN validates the token at the edge before forwarding the request to the origin», но явно про кэш не сказано: проверка владельца.

### 8. Патченный клиент (одинаково на четырёх; без изменений по сравнению с прежней редакцией)
- Признак `pluma_cdn = 1` в `params`; `cdn_supported` — только если HTTPS-CDN разрешён сейчас (нет перерыва, прокси не запрещает, CDN для этого файла не выключен).
- Распознаёт `PLH1`; ошибка разбора или не-`https` URL — этот файл из дома без `cdn_supported`. К `dc_id` не подключается.
- `Range: bytes=a-b`; ответ — только 206 с `Content-Range` ровно `a-b/total` (короче — только на конце), `total` равен известному размеру, длина `b−a+1`. Таймауты: соединение 5 с, тишина чтения 10 с, весь запрос 30 с; один повтор через 300–800 мс при сетевой ошибке, таймауте, 5xx.
- Блоки 128 КБ, выровненные по 128 КБ; расшифровка по IV-правилу, SHA-256 каждого блока против хэша дома **до** того, как байты попадут в файл или плеер. Нет хэша — `upload.getCdnFileHashes` на DC 1.
- 403/410 — обновить URL, не больше 3 раз. **Любая другая ошибка, включая 404 и несовпадение хэша, — откат файла на дом до конца загрузки** (`getFile` без `cdn_supported`). `upload.reuploadCdnFile` не зовётся.
- 3 транспортных отказа подряд по разным файлам — 10 минут без `cdn_supported` во всём приложении.
- Прокси: MTProxy или WEB-прокси — HTTPS-CDN выключен. SOCKS5/HTTP: tdesktop — через тот же прокси (QNAM, application proxy, `core/sandbox.cpp:714-731`); Android и iOS — выключен. Веб — без ограничений.
- HTTP-кэш выключен; URL, ключ, IV — только в памяти загрузки; в логах — хост, статус, смещение. `User-Agent: Pluma` в нативных клиентах.

### 9. Сервер: что меняется в задаче 102

### 11. Что видит Gcore
- **Видит:** шифр AES-256-CTR в кэше точек под случайными 256-битными именами (≤ 36 ч после последнего запроса); размеры файлов (по ним можно угадать вид); адреса клиентов, время, диапазоны, `User-Agent: Pluma`; **какие адреса берут один и тот же объект** — кто смотрел один и тот же файл; имя источника (поддомен Pluma, и так публичное через Certificate Transparency) и адрес Pluma, то есть связь ресурса с Pluma. У веба — `Origin` веб-клиента. Логи запросов видны владельцу аккаунта 3 дня; что Gcore хранит дольше — НЕ ПРОВЕРЕНО. Gcore знает владельца аккаунта (KYC).
- **Не видит:** содержимое, ключи, IV, хэши открытого текста, имена и типы файлов, чаты, номера, id пользователей, сообщения.
- Подмену шифра ловят хэши. Network Error Logging на ресурсе выключается (иначе браузеры отправляли бы Gcore отчёты о сетевых ошибках веб-клиента).
- Юрисдикция — Люксембург (ЕС).

## Последствия
- Повторные просмотры больших файлов идут с точек Gcore, отдача дома на них падает до одной тяги куска на точку; первый просмотр — со скоростью канала дома, как сегодня.
- На VPS ничего нового; ADR 0057 §2 действует без исключений. Дом получает новый публичный путь — имя источника в Caddy, закрытое заголовком.
- Деньги: 0 при трафике до 1 ТБ в месяц (отдача + тяга + пробы); предел дома 800 ГБ.
- Патчи во всех четырёх клиентах (≈ 240–330 строк каждый). Старые сборки, официальные клиенты и сессии без признака качают из дома. Сервер можно выкатить раньше клиентов.
- Gcore закроет аккаунт или станет недоступен — редиректы прекращаются по здоровью или сигналу отката, всё качается из дома.
- **Если Gcore не выполнит жёсткое требование** — 206 с точным `Content-Range` на произвольный `Range` клиента (НЕ ПРОВЕРЕНО), либо KYC или AUP не пропустят аккаунт или такое содержимое, — запасной дизайн: **Cloudflare R2 + свой Worker** (Workers Paid $5/мес; Worker проверяет HMAC-подпись и отдаёт диапазон из R2 через `bucket.get(key, {range})`; кэш Cloudflare перед своим источником на бесплатном плане не годится по условиям для видео и больших файлов, https://www.cloudflare.com/service-specific-terms-application-services/; цены https://developers.cloudflare.com/r2/pricing/, https://developers.cloudflare.com/workers/platform/pricing/). Он ложится в тот же шов: источник `push-store` (заливка в R2) и подписчик `worker-hmac`; клиенты не меняются. Не-условия перехода (решаются внутри Gcore): нет Secure Token — `path-hmac`; нет сертификата на общем домене — свой нейтральный домен (§1); нет проверки сертификата источника — не требуется (§3).

- HTTPS-CDN через SOCKS5/HTTP-прокси на Android и iOS, через MTProxy — нигде.
- Предзагрузка файлов до первого запроса.

Справка из исследования 2026-11-16, сохранена для той задачи:

## Рассмотренные альтернативы
- **Узел MTProto на VPS (ADR 0065).** VPS на Hetzner из России закрыт (1/12), одна точка, сервер MTProto на VPS. Заменён.
- **Gcore Object Storage с заливкой** — §3, таблица.
- **Cloudflare R2 + Worker** — запасной дизайн (см. «Последствия»): $5/мес и заливка вместо бесплатной тяги.
- **Хранить шифр дома после первого редиректа** вместо шифрования на лету — лишнее место и сверка, а CTR и так даёт любой диапазон.
- **Новый конструктор TL для HTTPS-редиректа.** Правка схемы в четырёх клиентах без выигрыша.
- **Признак по `app_version`.** Свой формат у каждой платформы, хрупко.
