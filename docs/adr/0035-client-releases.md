# 0035. Выпуски клиентов: сервис `releases` на сайте, `help.getAppUpdate` по таблице, апдейтер Desktop со своим ключом

- Статус: accepted (2026-11-04; решения владельца — бриф 054, «Решения владельца»).
- Задача: 054. Исследование: `docs/tasks/054-research/clients.md` (Android `aac1efcb`, iOS `6ad963e5`, tdesktop `a1e89e1f`, со строками).
- Дополняет ADR 0010 (подписанные сборки не публикуются артефактами CI): после одобрения в `release` сборка уходит не в артефакт, а в сервис выпусков.

## Контекст
- Подписанные сборки Android и Desktop лежали в зашифрованных артефактах CI 30 дней; на сайте были заглушки ссылок. Ad hoc IPA уже уходил в `iosinstall` (задача 029).
- `help.getAppUpdate` был заглушкой upstream (`help.noAppUpdate`).
- Как клиенты обновляются (исследование, §1–3):
  - Android проверяет обновления только в standalone-сборке и получает APK документом в `help.appUpdate`, качает его по MTProto. Версии сравнивает сам: по частям через точку, только части, которые есть в обеих версиях (`SharedConfig.java:801`, `:811-824`); не число — `NumberFormatException`.
  - iOS сам версии не сравнивает: что ответил сервер, то и предлагает. Кнопка ведёт в App Store, без патча её не перенаправить.
  - tdesktop обновляется своим апдейтером: `<prefix>/current` и пакеты `t*upd<версия>`, подписанные RSA-1024 с SHA-1; префикс приходит в `help.getConfig` (`autoupdate_url_prefix`).

## Решение
1. **Сервис `releases`** — отдельный сервис на образе сервисов (`docker-compose.releases.yaml`), за Caddy на путях `/dl/*` доменов сайта. Отдельное имя `dl.pluma.chat` не заводим: те же сертификаты и тот же Caddy, без DNS-записи.
   - Приём от CI — `POST /dl/upload` с Bearer-токеном (сравнение за постоянное время), один токен на все клиентские репозитории, секрет `RELEASES_UPLOAD_TOKEN` окружения `release`.
   - Файлы неизменяемы: `files/<платформа>/<версия>`, повтор номера сборки или версии — `409`. Каталог переносится из рабочего одним `rename`, запись в таблицу — после; если запись не удалась, каталог удаляется.
   - Сайт читает `/dl/releases.json` и ставит кнопки на `/dl/<платформа>/latest` (302 без кэша): кнопки не меняются от выпуска к выпуску.
2. **Таблица `app_releases`** — одна строка на сборку, `UNIQUE (platform, build)`. Текущий выпуск — последняя по `build` строка с `withdrawn = 0`; откат — отзыв строки (`pluma-admin release withdraw`), без удаления файлов.
3. **APK — документ в DFS** (тем же путём, что каталог стикеров, `pkg/catalog/importer`). `help.appUpdate` несёт `document`, клиент качает его `upload.getFile`, как обычный файл.
4. **`help.getAppUpdate` решает сервер** по авторизации сессии: платформа — по `api_id` (10001 Android, 10002 iOS, 10003 Desktop, 10004 Web), установленная версия — по `app_version`.
   - Android: обновление, только если клиент по своему правилу сочтёт версию новее. Схема версий Pluma — `12.9.1.N`, 4 части; сборки со старой схемой `12.9.1` (3 части) обновления не увидят — правило клиента сравнивает лишь общие части. Их ставят заново с сайта один раз.
   - iOS: `app_version` собирает MtProtoKit — `"<версия> (<CFBundleVersion>) <суффикс>"`, суффикс на iOS пустой (`MTApiEnvironment.m:384-394` на `6ad963e5`; `AppDelegate.swift:528` — это другая строка, для списка изменений). Патч клиента ставит суффикс `adhoc`, если профиль сборки перечисляет устройства (`ProvisionedDevices` в `embedded.mobileprovision`: так у ad hoc и development, не у App Store). Сборки App Store и ad hoc — один скомпилированный код (`ci/build.sh` pluma-ios), поэтому признак определяется при запуске. Обновление со ссылкой `<сайт>/iphone/install` — только ad hoc-сборкам с меньшим номером; TestFlight-сборки обновляет TestFlight.
   - Desktop и Web — `help.noAppUpdate`.
   - Ошибка чтения таблицы или документа — `help.noAppUpdate` и строка в логе, не 500: проверка обновлений не должна ломать вход.
5. **Desktop** — апдейтер tdesktop включается в форке со своей парой RSA-1024 (формат tdesktop, решение владельца 4); `help.getConfig` даёт `autoupdate_url_prefix = <сайт>/dl/desktop`.
   - Апдейтер просит `<префикс>/current4`: суффикс — `AutoUpdateVersion()` из `lib_base` `82d182a2`, на всех системах, где Pluma запускается, это 4 (2 — только ниже macOS 10.13 или glibc 2.28; `base_info_mac.mm:210-215`, `base_info_linux.cpp:205-210`, `base_info_win.cpp:318-320`). Другой суффикс — другой апдейтер, ему 404.
   - Ответ — JSON tdesktop: ключ системы (`AutoUpdateKey()`: `mac`/`armac`, `win`/`win64`/`winarm`, `linux`) → `stable` → `released` (версия) и `link` (путь от префикса) (`update_checker.cpp:606-680`, `:804-850` на `a1e89e1f`). Ключ берётся из имени пакета Packer (`packer.cpp:498-502`); универсальный `tmacupd` служит и `mac`, и `armac`. Закрытый ключ создаётся сразу в `~/pluma-secrets/desktop` и секрете `release`, на экран не выводится.
6. **Windows** — пока без Authenticode (решение владельца 3).

## Последствия
- Один клик одобрения в `release` на платформу выкладывает сборку на сайт и предлагает её приложениям; ручных шагов нет.
- Каталог выпусков растёт на размер каждой сборки (APK ~80 МБ, Desktop ~3 × 100 МБ). Чистка старых каталогов — вручную по `docs/ops/releases.md`, пока их немного; автоматическая — при росте.
- Сервис держит токен загрузки и том с файлами; захват токена позволяет выложить сборку, но не подписать её: Android откажется ставить APK с чужой подписью поверх нашей, апдейтер Desktop проверяет подпись своим ключом. Риск для первой установки с сайта — тот же, что у любого сайта с загрузками.
- Подписи Android и ключ Desktop — навсегда: смена ключа означает переустановку у всех.

## Пересмотреть, если
- Пользователей станет больше и раздача файлов нагрузит сервер — вынести `/dl/` на CDN или объектное хранилище.
- Появится подпись Windows или выпуск в App Store — пересмотреть каналы iOS и Desktop.
