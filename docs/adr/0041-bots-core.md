# 0041. Боты на уровне MTProto: учётные записи, токены, путь управления

- Статус: proposed (2026-11-09).
- Задача: 070. Источники и подробности — бриф `docs/tasks/070-bots-core.md`.

## Контекст
Клиенты Telegram не создают ботов сами. Настоящий Telegram ведёт их через аккаунт `@BotFather` (core.telegram.org/api/bots/commands); логика управления целиком на стороне Telegram. Методы `bots.createBot` и `bots.exportBotToken` есть в схеме, но это другой путь: «управляемые боты», которых создаёт другой бот (`manager_id`; tdesktop `create_managed_bot_box.cpp`, Android `CreateBotAlert.java`).

Сервер обязан принимать `auth.importBotAuthorization` (core.telegram.org/method/auth.importBotAuthorization), отдавать `bot_*` флаги пользователей, `userFull.bot_info`, доставлять боту обновления. Upstream рассчитан на отдельный шлюз ботов: `sync.pushBotUpdates` — заглушка, тема `BotSync` не настроена, таблица `bots` не содержала колонок, которые читает сервис.

Проект закрытый, до 100 человек. Боты нужны нескольким людям, создающим их вручную.

## Решение
1. **Бот — обычный аккаунт MTProto.** Ключ привязывается `auth.importBotAuthorization`, новые сообщения идут в тот же журнал pts и пуши, что у пользователей (`EmitPushUpdates` без `BotSync`), `getDifference` отдаёт пропущенное. Отдельного шлюза нет; HTTP Bot API и мини-приложения — следующие задачи.
2. **Путь управления — `pluma-admin bot`, без BotFather-аккаунта.** `bot create <имя_bot> <название> [-owner <телефон>]`, `bot token`, `bot list`, `bot set`. Причина: разговорный BotFather — это отдельный продукт поверх ботов (сценарии диалога, локализация реплик), а для круга до 100 человек достаточно администратора. Владелец бота (`-owner`) видит `bot_can_edit` и может менять имя, описание через `bots.setBotInfo`, как у Telegram (core.telegram.org/method/bots.setBotInfo). `bots.createBot`, `bots.exportBotToken` остаются закрыты: управляемые боты — не этот сценарий.
3. **Токен `<id бота>:<секрет>`, в базе — только SHA-256 секрета** (`bots.token`). Секрет случаен, 208 бит, поэтому соль и медленный хэш не нужны. Токен печатается один раз; заменить — `bot token`: старый перестаёт работать сразу, уже вошедшие сессии бота завершаются (тот же `effects.Runner.Revoke`, что при бане), иначе утёкший токен оставался бы действующим входом.
4. **Запросы, которых ждёт пользователь (кнопка, инлайн), — ожидание в bff.** `messages.getBotCallbackAnswer` и `messages.getInlineBotResults` кладут запрос в журнал бота (seq, обновления без pts: `updateBotCallbackQuery`, `updateInlineBotCallbackQuery`, `updateBotInlineQuery`) и ждут ответ в Redis до 10 с, затем `BOT_RESPONSE_TIMEOUT`. В сессии такие запросы идут отдельной горутиной, чтобы не задерживать остальные запросы ключа. Отложенный ответ через `sync.pushRpcResult` не взят: пришлось бы отдельно доводить тайм-аут до клиента, ожидание проще при тех же последствиях потери.
5. **Конфиденциальность в группах — один предикат `pkg/botprivacy`**, в обоих местах доставки: при отправке в базовую группу (`msg`) и при пуше в супергруппу (`sync`).
6. **Списки команд — по области и языку (`bot_command_lists`), тексты на других языках — `bot_info_texts`, кнопка меню — `bot_menu_buttons`.** Порядок выбора списка — как в core.telegram.org/bots/api#determining-list-of-commands.

## Последствия
- Новые боты появляются только через администратора; разговорный BotFather можно добавить поверх, если круг вырастет.
- Запрос кнопки или инлайна занимает Redis и горутину на время ожидания ботом; при потере Redis пользователь получает `BOT_RESPONSE_TIMEOUT`.
- Секрет токена нельзя показать повторно.

## Что отвергнуто
- Разговорный BotFather сейчас: большой объём ради редкой операции.
- `bots.createBot` как путь создания: он о другом и требует управляющего бота.
- Отдельный шлюз ботов в духе upstream: лишний сервис для ≤100 пользователей.
