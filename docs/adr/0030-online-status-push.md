# 0030. Статус «в сети»: состояние каждой авторизации в Redis, рассылка updateUserStatus без seq

- Статус: proposed (2026-11-03).
- Задача: 032. Исследование: `docs/tasks/032-research/` (клиенты, сервер, сверка).

## Контекст
- `account.updateStatus` только записывал время и никому не слал `updateUserStatus`: рассылка апстрима закомментирована (`TODO: push`). Собеседник видел «в сети», только когда клиент сам перечитывал пользователя.
- Чтение статуса (`MakeUserStatus`) не учитывало сохранённый `expires`: «в сети» означало 60 с после последнего запроса. Поэтому после `offline=true` пользователь ещё минуту оставался «в сети». А Desktop, который шлёт запрос раз в 210 с (`online_update_period_ms` в `teamgramd/bin/config.json`), большую часть времени выглядел «был в сети».
- Клиенты повторяют `account.updateStatus(false)`: iOS раз в 30 с, Web K раз в 50 с, Android примерно раз в 55 с, tdesktop раз в 120 с по умолчанию и раз в 210 с с настройкой Pluma (`032-research/clients.md`, `check.md` п. 1, 5, 6).
- Клиенты сами переводят `userStatusOnline` в «был в сети», когда проходит его `expires` (Telegram-iOS `PeerPresenceStatusManager.swift`, tdesktop). Значит, важен `expires`, который сервер сообщил последним.
- core.telegram.org называет `updateUserStatus` «Contact status update». О других получателях документация молчит.

## Решение
1. **Состояние каждой авторизации — `pkg/presence`, Redis (`KV` bff).**
   - Хэш `presence_<user_id>`: у каждой постоянной авторизации свой момент «виден до». Это `now + 300` для `offline=false` и `now` для `offline=true`.
   - Пользователь «в сети», пока хоть одна авторизация в окне. Телефон, ушедший в фон, не уводит в офлайн работающий Desktop.
   - В том же хэше `told` — что получатели слышали последним: до какого момента пользователь «в сети», или 0 после офлайна.
   - Всё решает один Lua-скрипт, поэтому два устройства не разошлют одну смену дважды.
   - Ключ живёт 30 дней с последнего запроса.
2. **Когда рассылать.**
   - Пользователь пришёл в сеть, а получатели этого не знают (`told` в прошлом) → рассылка.
   - Пользователь «в сети», и от сообщённого окна осталось меньше половины (150 с) → рассылка с новым `expires`. Клиент с периодом больше 150 с (tdesktop) вызывает рассылку каждым запросом. Клиент с меньшим периодом успевает повторить запрос до конца окна.
   - Все авторизации вне сети, а получатели считают пользователя «в сети» → рассылка `userStatusOffline`.
   - Другие запросы ничего не рассылают. Частоту ограничивают сами смены состояния: не больше одной рассылки за 150 с на пользователя, пока он «в сети».
3. **Окно 300 с** — значение апстрима и `onlineCloudTimeout` tdesktop; оно больше самого длинного периода клиентов (210 с). Какое окно отдаёт сервер Telegram, не проверено.
4. **Хранение и чтение.**
   - `user_presences` хранит время запроса и окно: `last_seen_at = now`, `expires = «виден до» − now`, то есть 0 после офлайна. Запись идёт синхронно: сначала MySQL, потом кэш; ошибка возвращается.
   - `ImmutableUser.LastSeenAt` теперь значит «виден до» (`last_seen_at + expires`).
   - `MakeUserStatus` отвечает `userStatusOnline{expires}`, пока этот момент впереди, иначе `userStatusOffline{was_online}`. Правка в proto помечена `// pluma:` (ADR 0009); копия в `app/service/biz/user/user` правится так же.
   - Старые строки (окно 300 с) читаются по-новому без миграции.
5. **Получатели.**
   - Пользователи, у которых он в контактах (обратные контакты). Правило приватности `statusTimestamp` проверяется в обе стороны, как в `users.getUsers` (`ToUnsafeUser`).
   - Если хоть один из двоих заблокировал другого, получатель пропускается. Так задумано в закомментированном коде апстрима; правило Telegram для блокировок не проверено, выбран вариант, который сильнее защищает приватность.
   - Тем, кому видно только округлённое «недавно», не шлётся ничего: от прихода в сеть и ухода оно не меняется.
   - Другим авторизациям того же пользователя, кроме вызвавшей. iOS по своему «в сети» на другом устройстве откладывает уведомления (`AccountStateManagementUtils.swift`, `delayNotificatonsUntil`). tdesktop при своём «не в сети», пока окно активно, сразу снова сообщает «в сети» (`api_updates.cpp`).
   - Собеседники открытых личных чатов без контакта и участники общих групп **не** получают: документация говорит только о контактах. Это требует сверки с настоящим Telegram (ниже).
6. **Доставка** — `updateShort` без seq и pts через `sync.pushUpdates` / `sync.updatesNotMe` (ADR 0020 п. 2: статусы эфемерны). Без APNs/FCM. После рестарта ничего не повторяется: клиенты читают статус через `users.getUsers`, `contacts.getStatuses`, `getFullUser`.
7. **`contacts.getStatuses`** проходит ту же проверку приватности, что `users.getUsers`. Раньше он отдавал точное время всем контактам и терял ошибки.

## Последствия
- «В сети» доходит до контактов за время доставки sync (секунды), а «был в сети» — сразу после `offline=true` последнего устройства.
- Без `offline=true` (клиент убит, сеть пропала) получатели сами переводят статус в «был в сети», когда проходит сообщённое окно (до 300 с). Сервер в этом случае ничего не шлёт: сообщать ли офлайн по обрыву последней сессии, не проверено.
- Redis хранит небольшой хэш на каждого активного пользователя. Если Redis недоступен, `account.updateStatus` отвечает `INTERNAL_SERVER_ERROR` (клиенты повторят запрос).

## Открытые вопросы (сверка с Telegram, `reference-telegram-probe`)
- Получают ли статус собеседники без контакта и участники общих групп.
- Шлёт ли Telegram округлённый статус (`userStatusRecently` с `by_me`) и офлайн после обрыва.
- Правило блокировок и окно `expires` у Telegram.
- Ошибки вычисления приватности (`privacyIsAllow`: участники чатов, `DisallowContacts`) и `hide_read_marks` / `getOutboxReadDate` — отдельная задача: они затрагивают и фото, и телефон.
