# 0045. Сервер обслуживает несколько слоёв сразу

- Статус: accepted (2026-11-09).
- Заменяет: ADR 0008 («сервер и клиенты переходят на новый слой вместе»).
- Задача: 074. Источники — бриф `docs/tasks/074-client-update.md`, `docs/tasks/074-research/server.md`.

## Контекст
Клиенты 228 на устройствах обновляются постепенно, поэтому переход всех клиентов разом невозможен. Кодек upstream кончается слоем 231, генератор mtprotoc не опубликован. В кодеке union-сообщения хранят все поля всех слоёв, а `GetClazzID(predicate, layer)` выбирает конструктор при кодировании, но ошибки вложенных Encode проглатывались: при отсутствии конструктора в слое в сеть уходило усечённое тело.

## Решение
1. **Кодек.** `third_party/teamgram-proto` переведён на upstream v0.231.0 по ADR 0009; 232 и 233 добавляет генератор `tools/tllayergen` из tdesktop `api.tl` (`tools/tllayergen/schema/api_232.tl`, `api_233.tl`, копии из тегов v7.3.2 и v7.4.1): новые конструкторы и методы, новые id и `flags.N?true` у известных конструкторов, записи таблицы слоёв. Повторный запуск ничего не меняет. Модуль в `go.mod` называется `v0.233.0`.
2. **Одна сторона преобразования — сессия.** Объекты строятся без знания слоя и кодируются в `session` через `pkg/layercompat`. `EncodeFor(obj, layer)` возвращает полное тело или ошибку, никогда не часть. Преобразование идёт только на копии: пуши общие.
3. **Что делает `layercompat.For`:** конструктор, которого слой не имеет: `messageMediaUnsupported`, `messageActionEmpty`, `messageEntityUnknown` для соответствующих типов; элемент вектора выпадает; необязательное поле обнуляется, а если поле оказалось обязательным, объект считается непредставимым, и решение принимает родитель. `quote_rich` для слоёв до 232 дополняется плоским `quote_text`.
4. **Кодек возвращает ошибки вложенных Encode** (патч `third_party(proto)`). Ошибка у ответа — `INTERNAL_SERVER_ERROR` клиенту, у пуша — пропуск с логом.
5. **Клавиатуры хранятся и обрабатываются в форме 228** (`keyboardButton*`, `ReplyMarkup.rows`); на входе бота 229+ (`layercompat.Canonical`) приводится к ней, на выходе `layercompat.For` собирает `keyboardInlineButton`/`ButtonType` для сессий 229+. Поле `rows` оставлено под прежним именем патчем, иначе старые JSON-строки сообщений не читались бы.
6. **Новые методы:** пока не обслуживаются сервисом, отвечают 400 `ERR_ENTERPRISE_IS_BLOCKED` (нет маршрута в прокси `session`); перечислены в `RPCNotServed`, чтобы попасть в матрицу покрытия.

## Что с хранимым
- JSON в `message_data` и др. читается: у 7 переименованных полей 228→231 единственное хранимое — `ReplyMarkup.rows`, оно возвращено.
- Номера полей protobuf у 11 сообщений (`Update`, `ChatFull`, `MessageAction`, `KeyboardButton`, `ReplyMarkup`, `PageBlock`, `SendMessageAction`, `EphemeralMessage`, `InputInvoice`, `UrlAuthResult`, `Username`) возвращены к номерам 228: строки `mq_outbox` и бинарные ответы каталога остаются читаемыми. Поля, появившиеся между 228 и 231, получили свободные номера.
- Сервисы всё равно перезапускаются вместе: gRPC-контракт между ними сменился (`docs/ops/deployment.md`, раздел «Обновление»).
- Каталог собран на слое 228 и читается встроенной схемой 228 (`pkg/catalog/tl`), проверка слоя в импортёре относится к сбору, а не к серверу.

## Последствия
- Клиенты 228 продолжают работать; новые клиенты 233 подключаются.
- При переходе на новый upstream номера полей указанных сообщений сохранять тем же приёмом: сравнить с прежним `.proto`, вернуть номера.
- Update с `pts`, которого нет в старом слое, просто выпадает: разрыв `pts` у старого клиента. Сейчас такие update не создаются сервером; при появлении новой функции нужна своя конвертация для старых слоёв.
- Функции 229–233 подключаются отдельными задачами.

## Что отвергнуто
- Отдельная сборка сервера на слой: сломала бы смешанные чаты.
- Правка кодека руками для 232/233: 40+ конструкторов, 17 методов, ошибки вероятнее, для будущих слоёв всё заново.
- Хранить клавиатуры в новой форме: пришлось бы мигрировать все старые строки и переписать весь код, который читает разметку.
