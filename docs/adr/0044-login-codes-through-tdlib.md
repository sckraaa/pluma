# 0044. Коды входа пишет настоящий аккаунт Telegram: сервис на TDLib

- Статус: proposed (2026-11-09).
- Задача: 073. Источники — бриф `docs/tasks/073-login-codes.md`, эксплуатация — `docs/ops/login-codes.md`.

## Контекст
Чтобы регистрация могла быть открытой, код нужно доставлять без участия администратора. SMS дорогие, Telegram Gateway требует пополнения на 100 $. Владелец решил: коды пишет обычный аккаунт Telegram по `contacts.importContacts` (метод доступен только пользователям, core.telegram.org/method/contacts.importContacts), клиент — TDLib. Сессия хранится как секрет, сторонние клиенты могут завершать сессии без объяснений, поэтому запасной путь обязателен.

## Решение
1. **Отдельный сервис `app/ops/codes`, свой образ и compose-файл**, по умолчанию не запущен, память ограничена. Сессия TDLib — только в его томе, база зашифрована ключом из окружения. У него один узкий внутренний API: `POST /v1/send`, `GET /v1/state`, с токеном.
2. **TDLib официальная, по JSON-интерфейсу** через cgo: один файл привязки под тегом `tdlib`, поэтому остальной код сервиса собирается и тестируется без C++ библиотеки. Минимум методов: `importContacts`, `createPrivateChat`, `sendMessage`, `removeContacts`, вход по QR.
3. **Порядок доставки: приложение Pluma, затем аккаунт Telegram, затем администратор.** Код сохраняется (HMAC) только после того, как отправитель его принял, поэтому при отказе запрос остаётся как был: прежний код работает, администратор может выдать новый.
4. **Ответ клиенту при доставке через Telegram — `auth.sentCodeTypeApp`, `next_type` `auth.codeTypeSms`.** У этого типа во всех четырёх клиентах есть действие «код не пришёл»; его повторный запрос уводит к администратору. *Заменено задачей 076: доставка через Telegram отвечает `auth.sentCodeTypeFragmentSms`, App остаётся за кодом в другой сессии Pluma; переходы `auth.resendCode` — в разделе «Изменение 2026-11-11».*
5. **Сервис сам ограничивает аккаунт:** очередь с паузами, лимиты на номер и на весь аккаунт, ожидание по `FLOOD_WAIT` и охлаждение после `PEER_FLOOD`. Состояние лежит в файле тома и переживает перезапуск; номера в нём только как HMAC, коды — никогда на диске.
6. **bff ждёт результата до 6 секунд.** Обычно очередь пуста и клиент сразу узнаёт, ушёл ли код или нужен администратор. Сервис вернёт `queued`, если код ещё ждёт своей очереди: тогда он считается отправленным.

## Последствия
- Без `LOGIN_CODES_SENDER_URL` всё работает как раньше.
- Отзыв сессии виден по метрике, алерту и `/v1/state`, но вход снова делает оператор: повторить QR может только он.
- Если Telegram ограничит аккаунт, коды идут через администратора, пока ограничение не снимется; заменить аккаунт можно новым входом по QR.
- Импорт контакта раскрывает Telegram, какие номера входят на сервер.

## Что отвергнуто
- Самописный клиент на `pkg/mtclient`: отдельный протокол входа, MTProto Telegram меняется вместе с клиентами; TDLib — поддерживаемая Telegram библиотека.
- Бот и Telegram Gateway: бот не может написать по номеру, Gateway — условия владельца.
- Хранение очереди на диске: код в файле опаснее, чем код, потерянный при перезапуске; пользователь просто попросит новый.

## Изменение 2026-11-11: «Не пришёл код?» у кода в приложении и лимиты (задача 080)
**Инцидент.** Человек переустановил iOS-приложение (TestFlight → Ad-Hoc). Сессия старой установки осталась авторизованной, поэтому `auth.sendCode` ответил `auth.sentCodeTypeApp`: код ушёл в приложение, которого больше нет. «Не пришёл код?» перевёл его на экран «Код не дошёл до Telegram» без отправки, с отсчётом; код в Telegram ушёл только после «Отправить ещё раз». После неудачного входа (отдельная известная ошибка) он прошёл тот же путь, и второе «Отправить ещё раз» получило `FLOOD_WAIT_3313` (`send_code_phone_ip` 6/5): каждый `auth.resendCode` тратил все лимиты запросов кода, в том числе переходы между экранами, которые ничего не отправляют.

**Решение.**
1. `auth.resendCode` отправляет код способом `next_type` прошлого ответа: «Resend the login code via another medium», тип «determined by the return value of the previous auth.sendCode/auth.resendCode» (core.telegram.org/method/auth.resendCode; core.telegram.org/api/auth: «resend a code of type `next_type`»). Переходы:
   - App → сразу доставка через Telegram: успех — FragmentSms («Проверьте Telegram»), отказ — Sms (запасной экран с «Отправить ещё раз» через 30 с). Без отправителя — Sms без `next_type` (администратор), как раньше. Новый код в Telegram заменяет код приложения (тот же слот HMAC); экран говорит, где действующий код. Код администратора остаётся действительным.
   - FragmentSms → Sms без новой доставки, как раньше: код уже в Telegram.
   - Sms → новая попытка через Telegram, как раньше; не больше `maxTelegramAttempts` (4) доставок на запрос, включая первую.
2. `next_type` у ответа App остаётся `auth.codeTypeSms`, не `auth.codeTypeFragmentSms`. Пропатченные клиенты показывают «Не пришёл код?» именно для `next_type` SMS: Web K — `getPlumaResendLangKeys` в `ci/patch.py` pluma-web требует `auth.codeTypeSms`, иначе upstream-подписи; Android на экране App для `next_type` Fragment показывает upstream `DidNotGetTheCodeFragment` «Get a code via Fragment» (LoginActivity.java 4667-4679, strings.xml 54 у Telegram Android 13.2.1; патч pluma-android заменяет только ветку `DidNotGetTheCodeSms`). iOS (AuthorizationOptionText в патче pluma-ios) и Desktop (`codeResendable = next_type.has_value()` в патче pluma-desktop) вид `next_type` не различают.
3. **Лимиты запросов кода** (`send_code_ip`, `send_code_key`, `send_code_phone_ip`, `send_code_phone`) тратит только запрос, который отправляет код: `auth.sendCode` и `account.sendChangePhoneCode` всегда (`CheckSendCode`), `auth.resendCode` — только при доставке через Telegram (`ReserveSend`, перед доставкой; при `FLOOD_WAIT` уже сделанные списания возвращаются, запрос не меняется). Каждый `auth.resendCode` проходит allowlist, лимит проб номера с адреса и лимит проверок номера на auth key (`CheckPhone`). Защита от злоупотреблений прежняя: `TelegramCodePerIP`, 4 доставки на запрос, лимиты аккаунта рассылки на номер (3 в час, 8 в сутки).
4. **`send_code_phone_ip` — 8 в час вместо 5.** Путь из инцидента без платных переходов стоит 5 запросов (`sendCode`, доставка, «Отправить ещё раз»; затем `sendCode`, доставка) — ровно предел, без запаса на ещё одно «Отправить ещё раз». 8 вмещают два полных входа человека, которого Telegram сначала не нашёл (по `sendCode`, «Не пришёл код?» и два «Отправить ещё раз»). Цена: посторонний, знающий номер, исчерпывает общий лимит номера (20 в час) с 3 адресов вместо 4; `pluma-admin login-unblock` снимает его.

**Последствия.**
- Больше трёх принятых доставок в час на один номер не пропустит сам аккаунт рассылки (`PerRecipientHour`, app/ops/codes): тогда доставка отвечает запасным экраном, а не `FLOOD_WAIT`. Путь из инцидента (не нашёл, нашёл, затем ещё одна доставка) — ровно три попытки; отказ `no_telegram` аккаунт тоже считает (`Queue.reserve`, возврат только при `busy`). Поднимать лимит аккаунта — отдельное решение: он бережёт аккаунт от ограничений Telegram.
- Клиенты не меняются: переход App → FragmentSms после `auth.resendCode` все четыре показывают новым экраном (iOS — новый экран для нового типа, AuthorizationSequenceController 366-373 по патчу; Android — та же страница `VIEW_CODE_MESSAGE` с новыми параметрами, `setPage` → `setParams`; Desktop — `noTelegramCodeDone` → `fillSentCodeData` → `updateDescText`; Web K — `applyNewSentCode` на той же карточке).
