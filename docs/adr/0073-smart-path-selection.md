# 0073. Выбор пути к серверу по надёжной пробе: гонка по пропуску, память по сети, фоновый замер

- Статус: proposed (2026-11-18).
- Задача: 113 (`docs/tasks/113-smart-path-selection.md`).
- Связано: ADR 0072 (края WebSocket через CDN и узел amf, `pluma_edge`), ADR 0057 (внешние узлы — труба для шифра), ADR 0071 (Gcore, бюджет трафика).
- Дополняет ADR 0072 §2 и §4: для новых сборок правило «прямой путь первым, край после двух „замерзаний“, держаться края `sticky_s`» заменяется выбором по пробе. Края, контракт WebSocket, `pluma_edge` v1 и защита от «замерзания» в клиентах остаются.

## Контекст
- Из России путь к адресу Hetzner пропускает первые ~16 КБ соединения и замолкает без RST (бриф 092:21-22, внешние источники). Обмен ключами проходит (бриф 109:358).
- Все клиенты выбирают путь по пробе меньше порога, поэтому «замерзающий» путь выглядит быстрым и здоровым:
  - Desktop — поддельный `req_pq` тестового соединения, готово по `resPQ` (tdesktop v7.4.1, `mtproto/connection_tcp.cpp:413-421`, `:614-621`);
  - iOS — `req_pq_multi` ~40 байт, побеждает первый ответивший (MtProtoKit release-13.2, `MTDiscoverConnectionSignals.m:22-79`, `:335`);
  - Android — последовательный перебор без гонки и `TL_ping` (tgnet `7be672ea`, `Connection.cpp:276-357`, `ConnectionsManager.cpp:297-299`);
  - Web K — только открытие WebSocket за 2 с, и то выключено (`transports/controller.ts:38-82`, `authorizer.ts:609-618`).
- Правки задачи 109 ловят «замерзание» по таймаутам ответа, дважды: A-128, I-133, D-106 (`ci/patch.py` рабочих копий, ссылки — бриф 113, «Что есть сейчас»). Это ≈ 25–30 с, и у iOS и Desktop при каждом холодном запуске: выбор края живёт в памяти процесса. Web K не переключается вовсе.
- Переезд Россия → Германия: сервер по стране отдаёт другой `pluma_edge` (`appconfig/edge.go:107-212`), но клиент держится края `sticky_s` (30 мин) и перечитывает app config редко (iOS — раз в час, `ManagedAppConfigurationUpdates.swift:78-84`); пути никто не меряет.
- Владелец 2026-11-18: без ожидания пользователя; достоверная проба всех путей; задержка и скорость; лучший путь; память; перепроверка в фоне при каждом запуске.
- Механизмы, на которые можно опереться:
  - гонка тестовых соединений Desktop с приоритетами (`session_private.cpp:195-215`, `:2369-2438`);
  - параллельный поиск адреса iOS и сохранение выбранной схемы (`MTContext.m:901-929`);
  - мост A-128 и порядок адресов tgnet (patch.py:1093-1108, `:1213-1235`);
  - живая смена URL Web K (`tcpObfuscated.ts:238-245`, `apiManager.ts:124-141`).
- Шлюз до авторизации принимает только сообщения обмена ключами (`pkg/mtserver/handshake/handshake.go:235-292`). Все входы — TCP, WebSocket, `Edge` — идут через один разбор транспорта (`server_websocket.go:25-74`).

## Решение
1. **Проба в шлюзе, до авторизации, одна на всех входах.**
   - Незашифрованные `pluma.probe nonce down pad` и ответ `pluma.probeData nonce seq total server_ms pad` кусками по ≤ 16 КиБ.
   - Клиент меряет задержку до первого байта, скорость и остановку приёма. Проба идёт ровно по тому пути, по которому потом пойдёт MTProto.
   - Ключ, сессия и bff не нужны.
   - Пределы: 2 пробы на соединение, корзина на адрес, общий предел одновременных проб, зажимы размеров.
2. **Размер больше порога.**
   - Проба-пропуск — 64 КиБ вниз и 20 КиБ вверх: у Desktop на соединении, которое станет рабочим, у iOS, Android и Web K — на отдельном соединении того же пути (соединение поиска адреса iOS закрывается после ответа, `MTDiscoverConnectionSignals.m:147`).
   - Проба-замер — 192 КиБ, на отдельном соединении.
   - «Замёрз» — путь отдал хоть один байт, потом 1,5 с тишины (считая от последнего байта или от записи запроса плюс RTT), пришло не всё.
3. **Гонка по пропуску.** Путь становится рабочим, когда прошёл пробу-пропуск, а не по первому `resPQ`.
   - Пропуск нужен на первом подключении после запуска, после смены сети и после выбывания пути.
   - Есть свежая память — сначала лучший путь, остальные через 0,8 с. Нет памяти — сразу первая группа `pluma_edge.order` последней известной страны, остальные через 0,8 с (не «все сразу»: края видят только тех, кому они нужны).
   - Ничьи — по `pluma_edge.order` страны.
   - Выбор общий для процесса и всех аккаунтов; выбывание всех путей — это сеть, а не пути: повтор с отступом платформы, в память не пишется.
   - По клиентам:
     - Desktop — режим пробы тестовых соединений и приоритеты из памяти;
     - iOS — вторая фаза поиска адреса;
     - Android — гонка в Java рядом с мостом A-128: tgnet сразу подключается по порядку из памяти, проба меняет порядок и переподключает;
     - Web K — выбор URL в воркере и `changeUrl`.
4. **Оценка и гистерезис.**
   - Оценка: `score = rtt + 256 КиБ / скорость`. `frozen` исключает путь из гонки в этой сети на 24 ч (фоновый замер его не исключает), `failed` при живых других — на 5 минут.
   - Переключение по замеру: 0,7× два раза подряд (второй замер через 60 с после первого выигрыша) или 0,25× один раз; не чаще раза в 10 минут; не во время передачи файла.
   - Авария переключает сразу: не прошёл пропуск или сработала защита от «замерзания», которая остаётся страховкой.
   - `sticky_s` новые сборки не используют.
5. **Память по сети.**
   - Ключ: страна (от сервера, при запуске — последняя полученная) + хэш локального отпечатка сети платформы. Без SSID, геолокации и новых разрешений; у Web K — только страна.
   - Таблица одна на устройство, общая для аккаунтов; расширения iOS её только читают.
   - До 16 сетей, свежесть 7 дней.
   - Ошибка ключа безопасна: выбранный путь всё равно проходит пропуск.
6. **Фоновый замер.**
   - Когда: при запуске (не чаще раза в 30 минут на сеть), при смене сети, при подозрении на «замерзание» (4 с без байта на ожидающий запрос) и раз в 6 ч.
   - Прямой и текущий путь пробуются всегда. Прочие края — только если страна ставит края первыми или прямой путь плох.
   - Без периодических замеров в режимах экономии; без фоновых замеров в расширениях iOS и в запусках Android ради push.
   - При смене сети клиент перечитывает app config.
7. **Параметры с сервера** — новый ключ `pluma_probe` (`v`, `country`, размеры, пороги, интервалы). `pluma_edge` v1 не меняется. Метрики шлюза `gnetway_probe_total`, `gnetway_probe_bytes_total` без адресов.
8. **Прокси пользователя отключает пробы**, как он уже отключает края.

## Альтернативы
- **HTTP-эхо `/apiws-probe` на краях** (бриф 109:272). Не меряет прямой путь (obfuscated TCP на адрес Hetzner), который и «замерзает», — ранжировать нечем.
- **Метод bff (`help.*`) как проба.** Нужны ключ и сессия: не работает при первом запуске. Плодит сессии. Нет детерминированного ответа нужного размера.
- **Скачивать большой ответ существующим методом** (`langpack.*`, `help.getConfig`). Размер непостоянен, нужна авторизация, нагрузка на bff.
- **Всегда через край в России, всегда прямой вне неё** (только `EDGE_ROUTES` по стране). Не ловит переезд до перечитывания app config и `sticky_s`. Не выбирает между `ru` и Gcore по качеству. Не помогает, где прямой путь плох вне России.
- **Пробовать все пути у всех.** Точнее, но Gcore и amf видели бы адреса всех пользователей, а не только тех, кому край нужен (ADR 0072 §5).
- **Гонка в tgnet на C++ через проверку прокси** (`ConnectionsManager::checkProxyInternal`, `ConnectionsManager.cpp:3964-4004`). Требует ключа авторизации (`Datacenter.cpp:1312-1316`) и подставляет прокси, а не цель (`ConnectionSocket.cpp:81-110`). Java-проба рядом с мостом проще и не трогает перебор tgnet.
- **SSID в ключе сети.** Нужны разрешения геолокации. Страна и отпечаток дают то же для задачи, а ошибку ключа страхует пропуск.

## Последствия
- **Сервер:** два сообщения в `pkg/mtserver/handshake`, пределы и метрики шлюза, ключ `pluma_probe` в bff, проба и «замерзатель» в `pkg/mtclient` и `tools/freezeproxy` для e2e и ручных проверок.
- **Клиенты:** A-129, I-134, D-107, W-087 (размеры — бриф 113). Защита от «замерзания» задачи 109 остаётся страховкой. `sticky_s` остаётся только для выпущенных сборок.
- **Время до рабочего соединения в России** — RTT плюс 64 КиБ на скорости пути (доли секунды – 1–2 с) вместо 25–30 с. Переезд в другую страну — переход на лучший путь в течение одной-двух минут после смены сети.
- **Трафик:** пропуск ≈ 84 КиБ на запуск, замер ≈ 0,4–0,65 МБ. Оценка на всех ≈ 9 ГБ/мес, в бюджете Gcore 1 ТБ (ADR 0071). Не замер.
- **Приватность** не хуже ADR 0072 §5: края видят только тех, кому они нужны. Ключ сети — хэш на устройстве. Сервер знает только счётчики.
- **Отказы:**
  - старый шлюз без пробы закрывает соединение на `pluma.probe` сразу после верного `resPQ` — клиент считает пробы неподдерживаемыми (не `failed` путей), ничего не пишет в память и откатывается к правилам задачи 109 до следующего app config;
  - неверный ключ сети стоит одной неудачной пробы-пропуска.
- **Край Gcore** становится равноправным путём, выбор между `ru` и Gcore — по замеру. Включение — шаги владельца брифа 113, раздел 9.
- **Не проверено** (бриф 113): порог ~16 КБ (внешние источники), достаточность 64 КиБ, `stall_ms` на мобильных сетях, API сети платформ, Gcore WebSocket на плане.

## Что не делается
- Звонки: пути UDP выбирает ICE.
- Телеметрия проб с клиентов на сервер.
- Переключатель пути в интерфейсе: путь выбирается сам (`clients/patches/README.md`, «Правила»).
- Переезд страницы Web K на другой хост: вход и хранилище привязаны к хосту, меняется только путь WebSocket.
