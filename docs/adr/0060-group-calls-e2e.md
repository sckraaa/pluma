- Статус: proposed (2026-11-12).
- Дата: 2026-11-12.
- Задача: 094 (`docs/tasks/094-group-calls-e2e.md`).
- Связано:

## Контекст

### Решения владельца 2026-11-12
1. **Каждый групповой звонок сквозной**: звонки групп, каналов и конференции. Ради этого правятся все четыре клиента: конфиденциальность важнее объёма правок.
2. Защита — **от сервера**. Слушатели, вошедшие в звонок, получают ключ.
3. **Никакой обработки звука на сервере** — ни сейчас, ни потом: ни сведения, ни перекодирования, ни шумоподавления, ни записи, ни распознавания.
4. **RTMP-трансляции убираются из клиентов** и сервером не обслуживаются никогда.
5. **Рассинхрон ключей должен диагностироваться**, при этом сервер не видит ни ключей, ни медиа: несекретные отчёты об эпохах и отпечатках, счётчики ошибок расшифровки, видимое серверу состояние цепочки, самовосстановление.

### Как устроено сквозное шифрование групповых звонков в Telegram

**Объекты** (`e2e_api.tl:67-84`).
- Главная подцепочка 0 — блоки `e2e.chain.block#639a3db6`: подпись Ed25519, `prev_block_hash`, `changes`, `height`, `state_proof`, `signature_public_key`.
- Изменения: `changeNoop`, `changeSetValue`, `changeSetGroupState` (участники `{user_id, public_key, flags, version}` и `external_permissions`), `changeSetSharedKey` (`ek`, зашифрованный общий ключ, по заголовку на каждого участника).
- Подцепочка 1 — сверка эмодзи: `groupBroadcastNonceCommit#d1512ae7` и `groupBroadcastNonceReveal#83f4f9d8`, у обоих в открытом TL `user_id`, `chain_height`, `chain_hash`.

**Форма на проводе: сервер прибавляет 1 к первому int32 (магии) каждого блока, который отдаёт.**
- Клиент отправляет блок с обычной магией, а принимает только с магией +1. Иначе ошибка «Trying to apply local block, not from server» (`TDE Blockchain.cpp:742-760`, вызовы — `Call.cpp:597, 618, 670`).
- Эталонный сервер в тестах делает то же самое (`TDE TestBlockchain.cpp:204, 210`). Это подтверждает и `GC`.

**Методы** (все уже есть в `third_party/teamgram-proto` версии v0.233.0; `api.tl:466, 3151-3158`):
- Подцепочка 0 пишется только через `phone.createConferenceCall(public_key, block)`, `phone.joinGroupCall(public_key:flags.3?int256, block:flags.3?bytes)` и `phone.deleteConferenceCallParticipants(only_left|kick, ids, block)`.
- Подцепочка 1 пишется только через `phone.sendConferenceCallBroadcast(call, block)`.
- Читаются обе через `phone.getGroupCallChainBlocks(call, sub_chain_id, offset, limit)`, ответ — `Updates` с `updateGroupCallChainBlocks{call, sub_chain_id, blocks, next_offset}`.
- Каждая успешная запись возвращает это обновление, и сервер рассылает его всем участникам.
- tdesktop применяет блоки из ответа на вход («Accept initial join blocks», `TD/calls/group/calls_group_call.cpp:1797-1806`). Объект звонка клиент создаёт из последнего полученного блока (`TD/tde2e/tde2e_api.cpp:406-418`).
- Метод `phone.getGroupCallChainBlocks` маршрутизируется в `RPCConferenceCalls` (`third_party/teamgram-proto/mtproto/rpc_client_registers.go:244`).

**`offset` и `next_offset`.**
- В подцепочке 0 это высота: `next_offset` = высота последнего блока + 1.
- В подцепочке 1 это сквозной номер рассылки за всю жизнь звонка. Эталонный сервер держит один вектор и не сбрасывает его (`TDE TestBlockchain.cpp:221-225`).
- Клиент считает индекс первого блока как `next_offset − len(blocks)` (`TD/tde2e/tde2e_api.cpp:452-517`).
- `offset=-1, limit=1` — последний блок. tdesktop так спрашивает перед входом (`calls_group_call.cpp:1696-1726`).
- По `GC`, не участник получает только последний блок, что бы он ни спросил.

**Опрос.**
- tdesktop: каждые 5 с по 50 блоков на подцепочку, даже без событий (`TD/tde2e/tde2e_api.cpp:31-32, 562`; `calls_group_call.cpp:62, 1889-1915`).
- Android: раз в 1 с до готовности эмодзи, потом раз в 5 с (`AND/.../ConferenceCall.java:546-551`).
- iOS: `limit: 10`, таймер 1 с (`IOS/TelegramCore/Sources/State/ConferenceCallE2EContext.swift:234, 266-279`).
- При 100 участниках это порядка 40–200 запросов в секунду на звонок. Оценка по интервалам, не замер.

**Ошибки, которые клиенты разбирают.**
- `CONF_WRITE_CHAIN_INVALID*` (сравнение по префиксу) — цепочка ушла вперёд. tdesktop перечитывает последний блок и входит заново (`calls_group_call.cpp:1865`). Web K повторяет (`TWEB/lib/calls/groupCallInstance.ts:1036, 1082`).
- `BLOCK_INVALID` — блок испорчен.
- `GROUPCALL_FORBIDDEN` — пользователь не участник или уже нет. Все клиенты входят заново.
- Android на ошибку записи в цепочку вызывает `stopSelf()` (`AND/messenger/voip/VoIPService.java:2711`).

**Пустая цепочка.** Если последнего блока нет и `groupCall.version < 2`, tdesktop шлёт нулевой блок (высота 0, в составе только он сам): `TD/data/data_group_call.cpp:154`, `calls_group_call.cpp:1633-1650`, `TD/tde2e/tde2e_api.cpp:268-277`.

**Ключи.**
- Каждый принятый блок подцепочки 0 — новая эпоха с идентификатором `(height, hash блока)`. Предыдущая эпоха забывается через 10 с, активных не больше 15 (`TDE Call.h:98-99`, `Call.cpp:713-737`).
- Новый случайный 32-байтный ключ при входе и удалении создаёт клиент, который пишет блок. Ключ шифруется для каждого участника через ECDH с эфемерным `ek` (`TDE Call.cpp:635-659`). **Сервер ключа не видит и сам блок с ключом написать не может, не узнав ключа.**
- Ключ участника временный, свой на каждый вход. Повторный ключ `Call::create` отвергает (`TDE Call.cpp:611-617`).
- Любая ошибка применения блока, расшифровки заголовка или проверки «залипает» в `Call::status_`: дальше не работают ни шифрование, ни расшифровка (`TDE Call.cpp:668-678`).
- По `GC`, участник, который не смог расшифровать ключ, обязан выйти из звонка.

**Права в цепочке.**
- Клиенты всегда создают `external_permissions = AddUsers|RemoveUsers` и дают каждому участнику флаги 3 (`TDE e2e_api.cpp:429-461`).
- Значит, цепочка не мешает никому, ни серверу, ни постороннему, добавить себя или удалить другого. Кто входит, решает только политика сервера, а подмену ловит сверка эмодзи.

**Шифрование кадров** (`TGC GroupInstanceCustomImpl.cpp:1393-1525`; `TDE Call.cpp:344-437`).
- Кадр шифруется в трансформере WebRTC после кодера и до упаковки в RTP.
- Формат: `prefix ‖ header_a (int32: число эпох; затем по 32-байтному хэшу каждой эпохи) ‖ header_b (32 байта на эпоху) ‖ AES-CBC (канал, seqno, данные) ‖ подпись Ed25519 64 байта ‖ uint32 длина prefix`.
- Окно повторов — 1024 seqno (`TDE Call.cpp:470-494`).
- **SFU видит в открытом виде:**
  - заголовки RTP и расширения (SRTP снимает SFU);
  - RTCP и канал данных;
  - у VP8 — дескриптор упаковщика и первый байт кадра, а у ключевых кадров 10 байт (`TGC …:1254-1280`);
  - у H.264 — заголовки NAL (`:1110-1250`).
- **Зашифровано:**
  - весь кадр Opus, включая байт TOC;
  - настоящий уровень звука и признак речи — 2 байта в конце шифра (`:1466-1481, 1498-1520`).
- **Уровень в расширении 1.** Получатели в сквозном режиме его не используют (`:2184, 2219-2229`). Отправитель огрубляет его до 0/106/127 (`GroupNetworkManager.cpp:60-87`). Но байт переписывается, только если признак речи отличается, поэтому точный уровень может утекать. Это прочтение кода, не проверено.
- **Видео в конференции идёт одним слоем:** `numVideoSimulcastLayers = 1` при `isConference` (`TGC …:3708-3710`).

### Стоковые клиенты шифруют только конференции
Ни один клиент не выбирает режим по `groupCall.conference` с сервера: режим задаёт путь входа.
- **tdesktop.** `GroupCall::conference()` = `_sharedCall->origin()==Conference || _startConferenceInfo` (`TD/calls/group/calls_group_call.cpp:1236-1243`). Звонок чата создаётся с `GroupCallOrigin::Group` (`TD/data/data_channel.cpp:1170-1176`, `TD/data/data_chat.cpp:242`). `public_key`/`block` уходят, только если есть `_e2e` (`calls_group_call.cpp:695-697, 1650-1667`).
- **iOS.** Шифрование включает `keyPair`. Звонки чатов создаются с `keyPair: nil, isConference: false` (`IOS/TelegramCallsUI/Sources/PresentationCallManager.swift:917-919, 1101-1103`), конференции — с `generateKeyPair()` (`:1124-1145`).
- **Android.** `isConference()` = `joinConference != null || conference != null` (`AND/messenger/voip/VoIPService.java:308-309`). `public_key`/`block` уходят только при `conference != null` (`:2421-2425`). Шифрование в нативе — последний аргумент `makeGroup(..., conference != null)` (`:3029, 3165`; `jni/voip/org_telegram_messenger_voip_Instance.cpp:500-525, 579-580`).
- **Web K.** Звонки чатов идут через `joinGroupCall`, конференции — через `joinConferenceCommon` → `instance.attachE2e` (`TWEB/lib/calls/groupCallsController.ts:289, 803-1057`). `pFlags.conference` читается только чтобы пропустить звонок (`TWEB/lib/appManagers/appGroupCallsManager.ts:260`). В Web K есть свой TS-порт tde2e (`TWEB/lib/calls/e2e/*`). Его побайтная совместимость с tdlib заявлена, но независимо не проверена.

Поэтому флагом с сервера сквозной режим не включить. Пометить звонок чата как `conference` значит сломать в tdesktop и Web K обработку обычного звонка (join_muted, сообщения), а шифрование так и не включится.

## Решение

### 1. Каждый групповой звонок сквозной; путь — криптография конференций под интерфейсом звонка чата
- Звонок группы или канала **сохраняет весь интерфейс и права звонка чата** из ADR 0059: администраторы чата, `manage_call`, `join_muted`, ссылки слушателя и выступающего, «завершить для всех», запланированные звонки.
- Его криптография идёт **путём конференции**:
  - вход с `public_key` и `block`;
  - подцепочки 0 и 1;
  - `updateGroupCallChainBlocks` и опрос;
  - удаление ушедших через `deleteConferenceCallParticipants(only_left)`;
  - сверка эмодзи;
  - шифрование кадров в tgcalls или в Web K.
- **Новых конструкторов TL нет.** Сервер обслуживает методы `RPCConferenceCalls` для любого звонка, у которого есть цепочка, — то есть для каждого.
- **Сервер не обслуживает несквозной звонок вообще.**
  - `joinGroupCall` без `public_key` и `block` отклоняется.
  - Комната SFU всегда создаётся сквозной.
  - Деление узлов на `plaintext: true/false` из ADR 0059 §3 снимается: открытых комнат больше нет.
- **Слушатели канала — участники цепочки** и получают ключ: так решил владелец. Каждый вход и выход пишет блок размером O(N) и меняет ключ, поэтому суммарная работа растёт как O(N²). При ≤100 это приемлемо, для больших каналов нет. Предел числа участников цепочки — `conference_call_size_limit` = 100 (ADR 0059 §9).
- **«Войти от имени канала» в сквозном звонке запрещено.**
  - tdesktop передаёт в tgcalls `userId = peerToUser(peer)`, а у канала это 0, и расшифровка невозможна (`TD/calls/group/calls_group_call.cpp:3310, 3435`).
  - iOS строит блок от `joinAsPeerId`, а контекст — от `account.peerId` (`IOS/TelegramCallsUI/Sources/PresentationGroupCall.swift:2054, 927`).
  - Сервер отклоняет `join_as` ≠ сам пользователь, а `getGroupCallJoinAs` возвращает только самого пользователя. Клиенты прячут выбор (патчи).
  - Это снимает пункт «войти от имени» этапа 1 (бриф 093) и требует подтверждения владельца.
- **Конференции** (`createConferenceCall`, ссылки `inputGroupCallSlug`, приглашения, перевод звонка один на один) используют тот же серверный код цепочки. Их собственный интерфейс и методы остаются этапом «конференции» ADR 0059 и в задачу 094 не входят.
- **Сообщения в звонке** могут быть только зашифрованными (`phone.sendGroupCallEncryptedMessage`, `api.tl:3158`). Открытый `sendGroupCallMessage` не обслуживается никогда. Сами сообщения — отдельный этап, после чтения клиентов.

### 2. Сервер: цепочка блоков
**Проверка блоков — свой порт tde2e на Go, пакет `pkg/tde2e`.** Это закрывает вопрос «порт или cgo» из ADR 0059 §7.
- Эталон — `ServerBlockchain`: `validate_signature=true`, `validate_state_hash=true`, все права (`TDE TestBlockchain.cpp:161-189`). Порт переносит из `Blockchain.cpp`, `Trie.cpp`, `BitString.cpp` только то, что нужно для проверки: разбор TL, хэш блока, подпись, применение состояния, trie для `kv_hash`.
- Тот же пакет даёт тестовому клиенту эмодзи и шифрование кадров (`Call.cpp`, `MessageEncryption.cpp`, `Keys.cpp`), см. §6. Серверный бинарь использует только проверку.
- **Почему не cgo.** cgo потянул бы в серверный образ tdutils, OpenSSL и генератор TL. Образы служб собираются с `CGO_ENABLED=0` (например, `teamgramd/deploy/sfu/Dockerfile:10`). Исключение одно — `codes` с tdlib (`teamgramd/deploy/codes/Dockerfile:24`, тег `tdlib`). Его способ сборки годится для утилиты дифференциального теста, но не для bff.
- **Как проверяется порт.** Векторы из `tde2e/test/EncryptionTestVectors.h` и `encryption_test.py`. Плюс дифференциальный тест против настоящего tde2e, собранного на CachyOS: отдельная утилита с cgo под build-тегом, не в сервере и не в CI.

**Проверки блока подцепочки 0** — точные правила tde2e:
- `height == last+1`, `prev_block_hash == SHA256(boxed последнего блока)`; у высоты −1 хэш нулевой (`TDE Blockchain.cpp:178-186, 671-693`).
- Подпись Ed25519 ключом `signature_public_key` (клиенты ставят его всегда; без него — ключ первого участника, `:540-556, 665`).
- Права: флаги подписавшего, если он участник, иначе `external_permissions`. Внешние права не растут; дать флаги, которых нет у себя, нельзя; `user_id` и `public_key` уникальны (`:368-433`).
- В блоке есть `SetGroupState` или `SetValue` (`:452-490`). Смена состава сбрасывает общий ключ; за ней обязан идти `SetSharedKey` ровно с одним заголовком на участника (`:401-450`).
- `state_proof` не содержит состава и ключа, если они изменились в этом блоке, и содержит, если не изменились. `kv_hash` равен хэшу trie: в звонках значения не пишутся, поэтому это хэш пустого trie (`TWEB/lib/calls/e2e/blockchain.ts:66-75`).

**Политика сервера поверх цепочки.** У tde2e её нет. `GC` говорит только «убедиться, что он добавляет лишь входящего»; код сервера Telegram закрыт, поэтому правила ниже — наш вывод:
- **Блок входа** (`joinGroupCall` и `createConferenceCall` с `join`). Новый состав = прежний минус старая запись того же `user_id` плюс `{user_id = вызывающий, public_key = аргумент}` (`TDE Call.cpp:600-608`). Подпись — этим ключом.
  - **Повторное использование ключа.** Ключ в звонке привязан к первому `user_id`, с которым он попал в цепочку.
    - Тот же пользователь с **тем же** ключом входит снова — это замена, блок принимается. Так iOS восстанавливает транспорт: `rejoinNeeded` tgcalls вызывает `requestCall` (`IOS PresentationGroupCall.swift:1909-1916`), блок входа строится из того же `self.keyPair` (`:2050-2077`), и так же входит `reconnect(with:)` по ссылке выступающего (`:3020-3023`). Своя старая запись уходит из состава по `TDE Call.cpp:600-602`, поэтому уникальность ключа в новом составе не нарушается (`TDE Blockchain.cpp:339-351`). То же верно, если пользователя уже удалили по `only_left`.
    - Ключ, который в этом звонке был у **другого** `user_id`, не принимается: `BLOCK_INVALID`.
    - Новый ключ после сбоя tde2e — не требование сервера, а клиента: tde2e не создаёт второй `Call` с тем же ключом (`TDE Call.cpp:608-617`, `CallKeyAlreadyUsed`).
  - Право входа — как в этапе 1: членство в чате, право канала или `invite_hash`. Нет права — `GROUPCALL_FORBIDDEN` (см. «Ошибки» ниже: что клиенты с ним делают).
  - На пустой цепочке принимается нулевой блок (высота 0, в составе только вызывающий).
  - **Ответ на вход** — `Updates`, в котором:
    - `updateGroupCall`, `updateGroupCallConnection` и `updateGroupCallParticipants` со своим участником (ADR 0059);
    - `updateGroupCallChainBlocks{sub_chain_id = 0, blocks = [блок этого входа], next_offset = высота блока входа + 1}`. Список кончается блоком входа; более ранних блоков в нём нет: клиент уже построил состояние из последнего блока до входа (tdesktop `refreshLastBlockAndJoin`, `TD/calls/group/calls_group_call.cpp:1632-1636`; Android `ConferenceCall.requestLastBlock`, `AND/messenger/voip/ConferenceCall.java:303-316`), а между ними чужого блока быть не может — высота проверена под блокировкой;
    - `updateGroupCallChainBlocks{sub_chain_id = 1, blocks = [], next_offset = broadcast_count}`: на новой высоте рассылок ещё нет, старые клиенты пропускают.
    - Обе подцепочки обязательны: iOS без любой из них считает вход неудачным (`IOS TelegramCore/Sources/TelegramEngine/Calls/GroupCalls.swift:922-944`). tdesktop применяет их как первые блоки (`calls_group_call.cpp:1806-1816`), Android берёт первый индекс как `next_offset − len(blocks)` (`ConferenceCall.java:449-453`).
    - Тот же блок рассылается остальным: `updateGroupCallChainBlocks` подцепочки 0 получают все участники прежнего и нового состава.
- **Блок удаления** (`deleteConferenceCallParticipants`) — прежний состав минус ровно `ids`.
  - `only_left`: все `ids` уже ушли из медиа, то есть строка участника в `pkg/groupcalls` — `left`, или участник не в звонке.
  - `kick`: у вызывающего права администратора звонка (создатель, `manage_call`).
  - Каждый оставшийся участник пытается удалить ушедшего сам (`TD/data/data_group_call.cpp:73-96, 233-255`; `calls_group_call.cpp:822-860`). Принимается первый блок, остальные получают `CONF_WRITE_CHAIN_INVALID`.
- **Удалённый.** Блок удаления рассылается и ему: он был в прежнем составе. Дальше:
  - запись (`sendConferenceCallBroadcast`, `deleteConferenceCallParticipants`) — `GROUPCALL_FORBIDDEN`;
  - чтение `getGroupCallChainBlocks` — по `GC`, только последний блок подцепочки 0, без ошибки, что бы он ни спросил.
  - **Ошибку опроса клиенты в основном не видят.** Android отбрасывает `err` ответа на опрос (`AND/messenger/voip/ConferenceCall.java:578-590`, `processUpdates` `:318-331` читает только `res`), iOS тоже (`GroupCalls.swift:3418-3422`, `catch` → `nil`). На `GROUPCALL_FORBIDDEN` при чтении входит заново только tdesktop (`calls_group_call.cpp:1909-1917`), при записи — tdesktop (`:848-853, 1930-1934`) и Web K (`TWEB/lib/calls/groupCallInstance.ts:784-798`).
  - Поэтому удалённый узнаёт об удалении сам: применяет блок удаления → tde2e `InvalidCallGroupState_NotParticipant` (300, `TDE Call.cpp:717`) → залипшая ошибка → повторный вход по правилу §5. Если блок удаления до него не дошёл, срабатывает правило отставания §5.
- **Пределы:**
  - участников в составе — `conference_call_size_limit` (100);
  - размер блока — 256 КиБ (100 участников с заголовками ключа — порядка 15 КиБ; оценка по формату);
  - `ids` удаления — не больше 100 (больше в составе не бывает): длинный список отклоняется `BLOCK_INVALID` до блокировки строки звонка, а строки участников блокируются только после проверки блока цепочкой;
  - `limit` чтения — не больше 100;
  - на подцепочке 1 — один commit и один reveal от пользователя на высоту.
  - Частоту записи ограничивает общий ограничитель bff: `FLOOD_WAIT_X`, как в других модулях.
- **Подцепочка 1** (`TDE Call.cpp:96-245`):
  - `chain_height` и `chain_hash` равны текущим (более старая высота принимается — клиенты её пропускают);
  - `user_id` в текущем составе, подпись его ключом;
  - один commit на пользователя; reveal только после commit всех; `SHA256(nonce) == nonce_hash`.
- **Ошибки:** `CONF_WRITE_CHAIN_INVALID` — устаревшая высота или хэш; `BLOCK_INVALID` — разбор, подпись, состояние, политика (в том числе чужой ключ); `GROUPCALL_FORBIDDEN` — нет права войти, или запись не участником; `GROUPCALL_PARTICIPANTS_TOO_MUCH` — предел состава.
  - **Что клиенты показывают на запрещённый вход** (`GROUPCALL_FORBIDDEN` в ответ на `joinGroupCall`):
    - tdesktop — выходит и показывает `lng_confcall_not_accessible` (`calls_group_call.cpp:1863-1886`);
    - iOS — общая ошибка входа (`GroupCalls.swift:704-750`: особые ветки только у `GROUPCALL_ANONYMOUS_FORBIDDEN`, `GROUPCALL_PARTICIPANTS_TOO_MUCH`, `JOIN_AS_PEER_INVALID`, `GROUPCALL_INVALID`, `CONF_WRITE_CHAIN_INVALID`);
    - Android — путь звонка чата шлёт `needShowAlert(6, text)` и кладёт трубку (`AND/messenger/voip/VoIPService.java:2185-2190`); `GroupCallActivity` показывает «Error occurred» с кодом (`AND/ui/GroupCallActivity.java:1332-1352`; особый текст только у `GROUPCALL_PARTICIPANTS_TOO_MUCH` и анонимного входа);
    - Web K — своего текста в пути звонка чата нет (`TWEB/lib/appImManager.ts:2455-2508`).
    - Вывод: `GROUPCALL_FORBIDDEN` клиенты обрабатывают как отказ без повторов; другого кода с понятным текстом на всех четырёх нет. Остаётся `GROUPCALL_FORBIDDEN`.
  - `CONF_WRITE_CHAIN_INVALID` на вход клиенты повторяют с новым последним блоком (tdesktop `joinFail`, `calls_group_call.cpp:1863-1872`; iOS `.restart`, `GroupCalls.swift:746-747`; Android-патч). Upstream Android на нём завершает звонок (`VoIPService.java:2711-2712`), патч это меняет.

**Хранение и порядок.**
- Блоки хранятся байтами в локальной форме, как их прислал клиент. Магия +1 ставится при отдаче. Хэш блока сервер считает по тем же байтам: побайтное совпадение с пересериализацией tde2e проверяется тестовым вектором.
- Таблица `group_call_chain_blocks`: `(call_id, sub_chain, idx)` — первичный ключ, `block` (`MEDIUMBLOB`), `hash` (32 байта), `user_id`, `height` (для подцепочки 1 — `chain_height` рассылки), `date`.
- Состояние цепочки — в строке звонка `group_calls`: `chain_height`, `chain_hash`, `broadcast_count`. Миграция `teamgramd/deploy/sql/migrate-20261118-group-call-chain.sql`, повторяемая.
  - Уточнение при реализации (задача 094): отдельного `chain_state` нет. Состав и общий ключ для проверки следующего блока восстанавливаются из последнего блока подцепочки 0 (`tde2e.RestoreChain`): блок несёт их в изменениях или в `state_proof`, а его хэш сверяется с `chain_hash`. Вторая копия состава в строке звонка могла бы разойтись с блоком.
  - Чей ключ — таблица `group_call_chain_keys(call_id, public_key, user_id)`: первый `user_id`, с которым ключ попал в цепочку (правило повторного использования ключа выше).
  - Подробности диагностики по участнику (§5) — `group_call_e2e_diag(call_id, user_id, updated_at, diag)`, JSON без ключей и телефонов; удаляется вместе с блоками.
  - Рассылка прошлой высоты (клиенты её пропускают, `TDE Call.cpp:112-116`) отвечается успехом, но не хранится и не рассылается: эталонный сервер её держит, но иначе один пользователь мог бы писать их без предела.
- **Порядок записи:** одна транзакция с блокировкой строки звонка — та же, что меняет `version` участников (ADR 0059 §2).
  - Проверка по `chain_height`/`chain_hash`, вставка блока, обновление состояния цепочки и, для входа, вставка или обновление участника с версией +1.
  - Затем `Join` в SFU, затем рассылка `updateGroupCallChainBlocks` участникам и возврат его в ответе.
  - Сбой SFU после принятого блока не откатывает цепочку. Участник есть в составе, но не в медиа, и его удаляют `only_left` остальные клиенты, как при обычном уходе. Сбой рассылки клиенты закрывают опросом.
  - Уточнения при реализации (задача 094): идентификатор соединения на SFU (`endpoint` в Colibri и в `groupCallParticipantVideo`) выбирает bff до транзакции и передаёт SFU (`JoinRequest.endpoint`), чтобы строка участника была полной до подключения. Если SFU не подключил участника, его строка выходит из звонка с версией +1 (остальные видят уход и удаляют его `only_left`), блок остаётся. Событие SFU об оборванном соединении несёт его SSRC, и выход по нему условен на этот SSRC: вход заново, записанный до подключения к SFU, им не снимается.
  - **Порядок рассылки** (уточнение 2026-11-13, задача 094). Строки участников и блок уходят остальным отдельными пачками `Updates`: в одной пачке tdesktop применяет блок первым (`TD/api/api_updates.cpp:305-326`).
    - Вход: сначала строка вошедшего, потом его блок. tdesktop считает ушедшим каждого участника цепочки, которого нет среди известных ему участников звонка, как только блок меняет состав, и шлёт `only_left` (`TD/data/data_group_call.cpp:85-93, 233-255`); к этому моменту вошедший должен быть среди них, иначе на каждый вход каждый tdesktop пишет отвергаемое удаление. Другое устройство того же пользователя видит свою строку с чужим SSRC и кладёт трубку (tdesktop `calls_group_call.cpp:2627-2636`, Android `VoIPService.java:1687-1692`, iOS `PresentationGroupCall.swift:1118-1122`) раньше, чем блок с чужим ключом сломает его tde2e и он по §5 войдёт заново и вытеснит новое устройство.
    - Вход, который SFU не подключил: сначала его выход, потом блок — удаление остальных принимается.
    - `kick`: сначала блок, потом строка: к выходу из звонка исключённого уже нет в составе, и tdesktop его удалять не пытается (`TD/data/data_group_call.cpp:73-84`).
  - Для `deleteConferenceCallParticipants` сначала проверяется высота, потом `only_left`: из нескольких удалений одного ушедшего все, кроме первого, — `CONF_WRITE_CHAIN_INVALID`, даже если он успел войти заново.
- **Чтение** — диапазон по первичному ключу. Состояние для быстрых ответов «последний блок» берётся из строки звонка. При ~40–200 запросах в секунду этого достаточно; кэш добавляется только по замеру.
- **Срок жизни.** Блоки удаляются вместе со звонком: сборщик после `discardGroupCall` и срока хранения из конфигурации. Подцепочка 1 не сбрасывается в течение звонка (`TDE TestBlockchain.cpp:221-225`).
- **Сервер никогда не пишет блоки сам.** Блок с новым ключом может написать только тот, кто ключ знает.

### 3. SFU после этого ADR
- Все комнаты сквозные. Узел SFU может стоять где угодно, в том числе на VPS вне доверенной зоны (ADR 0057). Флаг узла `plaintext` удаляется из конфигурации и из выбора узла.
- **Что SFU видит:** IP-адреса, SSRC, заголовки RTP и расширения, размеры и время пакетов, состав комнаты, открытые префиксы кадров видео, огрублённый уровень звука (с оговоркой об утечке в §«Контекст»), хэши эпох в `header_a`.
  - Из этого строится диагностика (§5). Отчёты и эпохи узла bff принимает только о звонке, размещённом на этом узле, и об участнике, который в звонке, и заново проверяет пределы отчёта (уточнение 2026-11-13, задача 094): иначе узел вне доверенной зоны мог бы поднимать тревоги в чужих звонках и без предела растить состояние и метрики bff.
  - Медиа и ключей SFU не видит.
- **Обработки звука на сервере нет ни в каком виде.** SFU пересылает пакеты, не разбирая Opus.
  - Отбор последних говорящих работает по огрублённому уровню из расширения 1.
  - Серверное выключение микрофона — отказ пересылать SSRC.
  - Запись, сведение, перекодирование, шумоподавление и распознавание звонков не делаются и не планируются.
- **Видео.** SFU переключает слои simulcast по открытому дескриптору VP8, как в этапе 1. Звонки чатов после патча продолжают слать 3 слоя: признак конференции в tgcalls, который снижает simulcast до одного слоя, патчи не выставляют.
  - Работает ли шифрование с simulcast в tgcalls (трансформер на каждом слое), не проверено. Проверка — e2e-тест с `groupcallpeer` и живой звонок на CachyOS.
  - Если не работает, звонок идёт одним слоем, как конференция Telegram.
- **Накладные расходы.** Заголовки эпох и подпись — около 180 байт на кадр и эпоху, плюс 64 байта на каждую лишнюю эпоху во время смены ключа. При ptime 120 мс (ADR 0059 §8) это около 12 кбит/с на поток звука, при 20 мс (этап качества) — около 72 кбит/с. Оценка по формату, не замер.

### 4. RTMP убирается
- **Сервер:**
  - `createGroupCall` с `rtmp_stream` отклоняется;
  - `getGroupCallStreamRtmpUrl`, `getGroupCallStreamChannels` и части `inputGroupCallStream` отвечают `ErrEnterpriseIsBlocked` (так уже в этапе 1, `app/bff/groupcalls/internal/core/not_served.go`);
  - `rtmp_stream` и `stream_dc_id` не выставляются;
  - в JSON ответа на вход никогда нет `"stream":true`: по нему tdesktop переходит в режим трансляции, где части приходят с сервера без шифрования (`TD/calls/group/calls_group_call.cpp:103-121, 2402-2430`; iOS `PresentationGroupCall.swift:1120-1131, 2155-2163`).
  - Тест закрепляет, что такого ответа нет.
- **Клиенты** — входы в RTMP убираются патчами. Точный перечень мест — в брифе 094:
  - tdesktop — пункт «Stream with…», `calls_group_rtmp.cpp`, URL и ключ в настройках;
  - iOS — `CreateExternalMediaStreamScreen`, пункт в профиле канала, ключ внутри трансляции;
  - Android — «Stream with another app», `CreateRtmpStreamBottomSheet`;
  - Web K — меню «Rtmp.Topbar.StreamWith», `components/rtmp/*`, `rtmpCallsController.ts`.
- **Живые истории** (live stories: `VideoStream` в tdesktop, `LiveStreamSettingsScreen` в iOS, `StoryPrivacyBottomSheet` в Android) — тоже групповой звонок без шифрования, с выбором RTMP.
  - Сервер их не обслуживает.
  - Убирать ли их входы из клиентов, решает владелец. Предложение — убрать вместе с RTMP по тому же решению «RTMP никогда».
- **Запись звонка** сервером не обслуживается: `phone.toggleGroupCallRecord` отвечает `ErrEnterpriseIsBlocked` (`app/bff/groupcalls/internal/core/not_served.go:23-28`); при сквозном шифровании записать звонок на сервере нельзя. Пункт меню записи **скрыт во всех клиентах**, чтобы не вести к ошибке:
  - tdesktop — `addEditRecording` (`TD/calls/group/calls_group_menu.cpp:510-512`, пункт `:543-576`);
  - Android — `recordItem` в `GroupCallActivity` (`AND/ui/GroupCallActivity.java:1693-1710`; upstream уже прячет его у конференции, `:1706-1708`);
  - iOS — блок записи меню при `canManageCall && !isConference` (`IOS/TelegramCallsUI/Sources/VideoChatScreenMoreMenu.swift:379-470`);
  - Web K — запись есть только в просмотрщике RTMP (`TWEB/components/mediaViewer/rtmp.ts:159`, `TWEB/components/rtmp/recordPopup.tsx:32`), который уходит вместе с RTMP; в звонке чата пункта нет.
  - В последних коммитах веток клиентов этого нет — добавляется.

### 5. Диагностика рассинхрона ключей
Принцип: сервер видит высоты, хэши блоков, эпохи в заголовках и счётчики. Ключей, nonce до reveal, эмодзи и содержимого кадров он не видит.

**Без патчей — на сервере и в SFU:**
- **Отставание опроса.** Для каждой пары (участник, подцепочка): `chain_height − offset` последнего `getGroupCallChainBlocks` и время этого опроса. Клиенты опрашивают со своей следующей ожидаемой высоты (tdesktop `calls_group_call.cpp:1889-1898`; Android `ConferenceCall.java:546-551`; iOS `ConferenceCallE2EContext.swift:266-279`; правило — `GC`). Участник, который перестал опрашивать, завис или упал.
- **Ход сверки эмодзи.** Кто прислал commit и reveal на каждой высоте подцепочки 1. Участник, который застрял на commit высоты h, застрял в tde2e на h или раньше.
- **Эпоха отправителя.** SFU разбирает `header_a` в пакетах звука: prefix у звука нулевой, поэтому заголовок стоит в начале полезной нагрузки (`TGC GroupFrameTransformer.h:78-86` на `c1de0882`; `TDE Call.cpp:286-350, 363-399`). Так SFU знает, какими эпохами шифрует каждый отправитель. Хэши эпох сервер считает из своих блоков. Видео не разбирается: префикс кодека и упаковка мешают.
- **Счётчики ошибок bff:** `CONF_WRITE_CHAIN_INVALID`, `BLOCK_INVALID`, `GROUPCALL_FORBIDDEN` по звонкам; повторные входы по участнику.
- **Состав цепочки против участников медиа:** кто в составе, но не в звонке дольше 30 с — его не удалил ни один клиент.

**С патчем клиентов — отчёт о состоянии шифрования.**
- **Канал:** канал данных WebRTC к SFU, `colibriClass` `"PlumaE2EStatus"`. Сегодня клиент шлёт по нему только `ReceiverVideoConstraints` (`TGC GroupInstanceCustomImpl.cpp:2777, 2833`; `GroupNetworkManager.cpp:536-538`). SFU не терминирует ничего нового и передаёт отчёты в поток `Events` (ADR 0059 §3). Новых методов MTProto нет: `phone.saveCallDebug` принимает только `InputPhoneCall` (`api.tl:3127, 3150`).
- **Контракт `PlumaE2EStatus` v1** — один для четырёх клиентов и сервера. Ветки клиентов `task/094-group-calls-e2e` сделали отчёт по-разному: имена полей (`v`/`version`, `height`/`height0`, `lastBlock`/`blockHash`/`lastBlockHash`, `duplicate`/`replayed`/`alreadyProcessed`), счётчики как приращения (Android: `PlumaE2EStats::take` обнуляет их) или как итоги (tdesktop `EncryptDecrypt::takeFrames` обнуляет только эпохи; iOS `TdCall.plumaStatus` и Web K `e2eReport` — ничего), пределы списков 8, 32 или 128. Ниже — что обязательно для всех; ветки приводятся к нему.
  - **Пример** (порядок полей не важен):
    ```json
    {"colibriClass":"PlumaE2EStatus","v":1,"seq":12,
     "height":41,"lastBlock":"9f3c0a1b2c3d4e5f","offset0":42,"offset1":17,
     "error":0,
     "sendEpochs":["9f3c0a1b2c3d4e5f","77aa01b2c3d4e5f6"],
     "decryptEpochs":["9f3c0a1b2c3d4e5f"],
     "unknownEpochs":[],
     "encrypted":250,"encryptFailed":0,
     "senders":[{"user":1000002,"ok":248,"unknownEpoch":0,"tooOld":0,"duplicate":1,"failed":0,"lastOkMs":40}]}
    ```
  - **Поля верхнего уровня** (все обязательны, других нет):

    | поле | тип | смысл |
    |---|---|---|
    | `colibriClass` | строка | ровно `"PlumaE2EStatus"` |
    | `v` | целое | версия схемы, `1`; смысл поля меняется только с новой версией |
    | `seq` | целое ≥ 1 | номер отчёта с последнего входа (новый вход — снова с 1); по пропускам сервер видит потерянные отчёты |
    | `height` | целое ≥ −1 | высота подцепочки 0, применённая tde2e (`call_get_height`); −1 — состояния нет (до входа или после сбоя) |
    | `lastBlock` | строка: 16 hex или `""` | первые 8 байт SHA-256 блока на высоте `height` в той форме, в которой его хранит сервер (магия −1, `TDE Blockchain.cpp:742-760`); `""` — состояния нет |
    | `offset0` | целое ≥ −1 | `next_offset` подцепочки 0, с которого клиент опрашивает; −1 — ещё не знает |
    | `offset1` | целое ≥ −1 | то же для подцепочки 1: курсор рассылок, сквозной номер |
    | `error` | целое | код залипшей ошибки tde2e по `TDE e2e_errors.h:13-40`, `0` — работает; порт Web K отображает свои ошибки на те же коды |
    | `sendEpochs` | массив строк, ≤ 15 | префиксы хэшей эпох из заголовка последнего зашифрованного кадра: какими эпохами клиент шифрует сейчас |
    | `decryptEpochs` | массив строк, ≤ 15 | префиксы хэшей эпох, названных в заголовках кадров, расшифрованных с прошлого отчёта |
    | `unknownEpochs` | массив строк, ≤ 8 | префиксы эпох из кадров, отвергнутых с `Decrypt_UnknownEpoch` с прошлого отчёта, первые 8 различных |
    | `encrypted`, `encryptFailed` | целые ≥ 0 | кадры всех своих потоков (звук, камера, экран), зашифрованные и не зашифрованные с прошлого отчёта |
    | `senders` | массив объектов, ≤ 100 | по отправителю, от которого с прошлого отчёта пришёл хотя бы один кадр, по возрастанию `user`; предел — `conference_call_size_limit` |

  - **Поля отправителя:** `user` (целое, `user_id`); `ok`; `unknownEpoch` (`Decrypt_UnknownEpoch`, 400, `TDE Call.cpp:349`); `tooOld` («Message is too old», `:482`); `duplicate` («Message is already processed», `:485`); `failed` (любая другая ошибка) — целые ≥ 0; `lastOkMs` — целое, миллисекунды от последнего удачного кадра этого отправителя до отправки отчёта, −1 — удачных не было.
  - **Приращения и значения.** Все счётчики кадров (`encrypted`, `encryptFailed` и пять счётчиков отправителя) — **приращения с прошлого отчёта**: клиент обнуляет их, когда отчёт ушёл. Списки `decryptEpochs` и `unknownEpochs` — тоже за интервал. `height`, `lastBlock`, `offset0`, `offset1`, `error`, `sendEpochs`, `lastOkMs` — **текущие значения**. Приращения выбраны потому, что тревоги считаются по окнам 5–15 с, а потерянный отчёт выпадает одним интервалом, который виден по `seq`.
  - **Единицы:** время — целые миллисекунды; префикс хэша — 8 байт в hex нижнего регистра; `user` — число JSON (id Pluma меньше 2^53).
  - **Частота:** каждые 5 с по своему таймеру, первый — через 5 с после входа; только по основному соединению (не экранному); только при открытом канале данных. Неотправленный отчёт не копится: его приращения уходят в следующем.
  - **Размер:** не больше 16 КиБ сериализованного JSON (100 отправителей — около 11 КиБ). Если отчёт вышел больше, клиент отбрасывает из `senders` записи с самыми большими `lastOkMs`.
  - **Сервер** принимает отчёт, только если `v == 1`, все поля на месте, типы и пределы соблюдены. Лишнее поле, другой `v`, размер больше 16 КиБ — отчёт отбрасывается и считается в метрике отброшенных по причине. `tools/logaudit` запрещает писать отчёт в лог целиком.
- **Запрещено в отчёте:** ключи, nonce, эмодзи, байты кадров, полные хэши. Префиксы хэшей эпох и блоков сервер и так может посчитать: эпохи видны SFU в открытом заголовке кадра, блоки хранятся на сервере.
- **Где считать:** в общем колбэке `EncryptDecrypt` каждого клиента. tdesktop — `TD/tde2e/tde2e_api.cpp:78-106`; Android — `jni/voip/org_telegram_messenger_voip_Instance.cpp:504-519`; iOS — `ios/third-party/td/TdBinding/Sources/TdBinding.mm:337-348`; Web K — свой трансформер `TWEB/lib/calls/e2e/*`. Сегодня все они ошибку выбрасывают молча (`TGC GroupFrameTransformer.h:18-21`). Получатель, который не может расшифровать, показывает отправителя молчащим, а не сломанным (`GroupInstanceCustomImpl.cpp:1427`).

**Что видит оператор.**
- Метрики Prometheus на уровне звонка, без меток пользователя:
  - высоты;
  - отставших участников;
  - ошибки по кодам;
  - повторные входы;
  - «отправляет, но никто не расшифровывает».
- Подробности по участнику — в `pluma-admin calls show <call>`: id пользователя, его высоты, эпоха отправки, счётчики из отчёта, ход эмодзи. Номеров телефонов и ключей там нет.

**Правила тревог** (`teamgramd/deploy/prometheus/server/rules/`):
| Сигнал | Тревога |
|---|---|
| отставание опроса > 0 | 15 с, или нет опроса 15 с |
| эпоха отправителя старше текущей высоты | > 12 с (окно забывания 10 с плюс запас) |
| commit или reveal не пришёл на высоте h, хотя остальные уже на h+1 | 15 с |
| `UnknownEpoch` у получателя на отправителя X | 5 с подряд; эпоха X текущая — отстал получатель, старая — отправитель |
| залипшая ошибка tde2e в отчёте | сразу; тревога, если повторного входа нет 10 с |
| в составе цепочки, но не в звонке | 30 с, пока в звонке есть другой участник цепочки (без него удалить ушедшего некому, а сервер блоков не пишет) |
| повторные входы участника (входы того, кто уже в составе цепочки; первый вход не считается) | > 3 за 5 мин (петля самовосстановления) |
| пакеты X идут в SFU, но ни один получатель X не расшифровывает | 10 с |

**Самовосстановление — в клиентах**, по образцу tdesktop: любая ошибка tde2e → «TdE2E: Got failure, scheduling rejoin!» → `startRejoin()` (`TD/calls/group/calls_group_call.cpp:786-789`). Одно правило для четырёх клиентов:
- **Повторный вход с новым ключом**, когда выполнено любое из условий:
  1. **Залипшая ошибка tde2e** (`error` ≠ 0 в отчёте) — сразу. Сюда же `InvalidCallGroupState_NotParticipant` после блока удаления и состояние, которое не строится из последнего блока.
  2. **Отставание:** `next_offset` подцепочки 0 из последнего ответа на опрос или рассылки больше своей `height + 1`, и блоки не применяются, дольше **12 с** непрерывно (окно забывания эпохи 10 с плюс запас, `TDE Call.h:98-99`).
  3. **`GROUPCALL_FORBIDDEN`** на запись в цепочку — сразу (tdesktop `calls_group_call.cpp:848-853, 1930-1934`; Web K `groupCallInstance.ts:784-798`), и на чтение у тех, кто ошибку чтения видит (tdesktop `:1909-1917`).
  4. **Расшифровка:** от **каждого** отправителя, приславшего кадры за последние **15 с**, не расшифрован ни один (`ok` = 0, есть `unknownEpoch` или `failed`), а своя цепочка не отстаёт. Это значит, что не так что-то у самого получателя. Если не расшифровывается один отправитель из нескольких, получатель не входит заново: неисправен отправитель, и его ловят его же условия 1–2, а оператор видит это по тревоге «UnknownEpoch у получателя на отправителя X». 15 с — как сторож синхронизации Web K (`TWEB/lib/calls/groupCallInstance.ts:51, 1274-1280`).
- **Пределы и задержки.**
  - Не больше **3** повторных входов по этим условиям за скользящие **5 мин**. Четвёртый случай — выход из звонка с сообщением (ключ локализации на всех языках клиента: Android `PlumaCallEncryptionFailed`, iOS `Pluma.GroupCall.EncryptionFailed`, tdesktop `lng_pluma_group_call_e2e_failed`, Web K — свой ключ). Так уже сделано в трёх ветках: Android `PLUMA_E2E_REJOINS`/`PLUMA_E2E_REJOIN_WINDOW_MS`, iOS `plumaE2ERejoinTimestamps`, tdesktop `kE2ERejoinsLimit`/`kE2ERejoinsPeriod`.
  - Задержка перед 1-м входом в окне — 0 с, перед 2-м — 2 с, перед 3-м — 5 с, к каждой — случайная добавка 0–1000 мс: каждый повторный вход меняет ключ у всех, и одновременные входы нескольких участников сталкиваются в `CONF_WRITE_CHAIN_INVALID`.
  - Одна неудача — один повторный вход: пачка блоков даёт по ошибке на блок (tdesktop `TD/tde2e/tde2e_api.cpp:458-505`), они сливаются.
  - Во время повторного входа условия 1–4 не проверяются; счётчики отчёта и `seq` начинаются заново.
- **Не считаются в предел** и идут без нового ключа:
  - восстановление транспорта (`GROUPCALL_SSRC_DUPLICATE_MUCH`, потеря соединения, ссылка выступающего): клиент вправе войти с тем же ключом, сервер это принимает (§2, iOS `PresentationGroupCall.swift:1909-1916, 2050-2077, 3020-3023`);
  - `CONF_WRITE_CHAIN_INVALID` на вход — перечитать последний блок и повторить (tdesktop `joinFail`, `calls_group_call.cpp:1863-1872`; iOS `GroupCalls.swift:746-747`). Предел — **10 отказов подряд, после которых последний блок не изменился**: цепочка стоит, значит отказ не из гонки. Пока последний блок меняется, клиент повторяет, но не больше 100 попыток на один вход (`conference_call_size_limit`). Потом общая ошибка входа.
    - Почему не «10 раз подряд» без условия (уточнение 2026-11-13, задача 094). После перезапуска SFU или потери узла (§3, ADR 0059 §3) входят заново все участники разом, и каждый вход — блок на одной и той же высоте h+1. За раунд проходит один, остальные получают `CONF_WRITE_CHAIN_INVALID`; последний из N проигрывает до N−1 раз подряд. Жёсткий предел выбросил бы из звонка тех, кому не повезло, как только участников больше предела. Upstream tdesktop повторяет без предела (`joinFail`, `calls_group_call.cpp:1863-1872`), iOS тоже (`restartOrMapError`, `GroupCalls.swift:963-966`); у Web K — 5 попыток (`TWEB/lib/calls/groupCallConnectionInstance.ts:385, 408`). Сервер развести такие входы не может: блок входа строит клиент на последнем блоке, и сервер сам блок не пишет (§2). Интеграционный тест `TestChainJoinsHerd` (`pkg/groupcalls`): 30 входов разом, все проходят по этому правилу.
- **Что в ветках клиентов расходится с правилом и должно быть поправлено** (по последним коммитам веток `task/094-group-calls-e2e`):
  - условие 2 есть только у Android (`ConferenceCall.checkBehind`, `BEHIND_LIMIT_MS`); у iOS, tdesktop и Web K его нет (у Web K есть свой сторож 15 с, `groupCallInstance.ts:1274-1280`, он остаётся);
  - условие 4 нет ни у кого;
  - задержек нет ни у кого;
  - Web K на сбое tde2e, кроме `NOT_PARTICIPANT`, выходит из звонка (`TWEB/lib/calls/groupCallInstance.ts:446-468`), его ветка этого не меняет — должна входить заново;
  - iOS и Android не видят `GROUPCALL_FORBIDDEN` опроса (`GroupCalls.swift:3418-3422`; `ConferenceCall.java:578-590`); Android-ветка добавила его обработку, iOS полагается на условия 1–2 — этого достаточно.
- **Сервер сам не лечит.** Он не может написать блок и не может заставить клиента применить блок. Подтолкнуть к повторному входу через SFU (закрыть транспорт участника) — возможный приём. Как клиенты на это ответят, не проверено, поэтому в этот ADR он не входит.

### 6. Тестовый клиент
- `pkg/groupcallpeer` (этап 1) получает сквозной режим на `pkg/tde2e`:
  - пара Ed25519;
  - нулевой блок и блок входа;
  - применение блоков подцепочки 0 с расшифровкой общего ключа;
  - commit и reveal на подцепочке 1;
  - шифрование и расшифровка звука в формате tde2e: уровень добавляется в конец, prefix 0;
  - блок удаления ушедшего по `only_left`;
  - отчёт `PlumaE2EStatus`.
- В pion клиент сам ставит полезную нагрузку RTP, поэтому трансформер кадров не нужен.
- Режим «сломанный участник» для тестов диагностики: перестаёт применять блоки, шифрует старой эпохой, не шлёт commit.

## Последствия
- **Патчи всех четырёх клиентов** в звонках — самой сложной части клиента. Каждое обновление апстрима требует сверки этих мест, причём у Android около 45 проверок `conference != null` (`VoIPService.java`).
- **Несовместимость со стоковыми и старыми клиентами Pluma.** Клиент без патча войти в групповой звонок не может (отказ на вход без `public_key`).
  - Выход этапа 1 к пользователям без этапа 2 означал бы период открытых звонков. Поэтому этап 1 к пользователям отдельно не выпускается: групповые звонки выходят сразу сквозными, вместе с обновлёнными клиентами. Решение владельца.
- **Браузеры без `RTCRtpScriptTransform`** групповые звонки в Web K теряют совсем (`TWEB/environment/conferenceCallSupport.ts`). Какие версии браузеров это затрагивает, не проверено.
- **«Войти от имени канала» исчезает.**
- **Запись звонков на сервере невозможна** по построению.
- **Каждый вход и выход меняет ключ** у всех. При 100 участниках в канале это заметная нагрузка на клиенты: O(N) расшифровок заголовков на каждое событие.
- **SFU свободно переносится** на VPS: это снимает ограничение ADR 0057 для обычных звонков.
- **Пересмотреть решение**, если:
  - аудитория вырастет настолько, что O(N²) станет заметной;
  - Telegram сменит формат цепочки (новый tde2e у клиентов);
  - в клиентах появится сквозной режим для звонков чатов без патчей.

## Рассмотренные альтернативы
- **Отмечать каждый звонок `conference` с сервера.** Клиенты по флагу режим не выбирают (§«Контекст»), а tdesktop и Web K ломают обработку звонка. Отклонено.
- **Превратить звонки чатов в настоящие конференции** (`createConferenceCall` при начале звонка в чате, ссылка `inputGroupCallSlug`). Теряются права администраторов чата, `join_muted`, строка звонка в чате и запланированные звонки: интерфейс конференции другой. Патчей не меньше. Отклонено.
- **Свой протокол ключей** вместо tde2e. Пришлось бы писать криптографию заново на четырёх клиентах вместо включения готовой. Отклонено.
- **tde2e через cgo на сервере** — см. §2. Отклонено. cgo остаётся только в утилите дифференциального теста.
- **Отчёты о шифровании новым методом MTProto.** Нужен новый конструктор TL (ADR 0009) и правка сетевого слоя четырёх клиентов. Канал данных к SFU уже есть. Отклонено.
- **Лечение на сервере** (сервер пишет блок удаления). Сервер узнал бы общий ключ. Отклонено.

## Что не делается
- Конференции как продукт: `createConferenceCall`, ссылки, приглашения, перевод звонка один на один. Остаются этапом «конференции» ADR 0059 и используют код этого ADR.
- Сообщения в звонке, в том числе зашифрованные.
- Запись, RTMP, трансляции, живые истории, любая обработка звука на сервере.
- «Войти от имени канала» в групповых звонках.
- Подтолкнуть клиента к повторному входу с сервера.
- `version` участника ≥ 1 (ключ через HMAC с хэшем блока): клиенты на `e894536b` всегда ставят 0 (`TDE e2e_api.cpp:461`). Сервер принимает оба значения и проверяет только права и состав.

## Решения владельца (2026-11-12)
- Подтверждены пункты 2–5 ниже: «войти от имени канала» убирается; этап 1 к пользователям только вместе с этапом 2; живые истории убираются вместе с RTMP; Web K в браузерах без `RTCRtpScriptTransform` групповые звонки не открывает (с сообщением).
- Пункты 1, 6, 7, 8 — технические, решены здесь как записано.

## Решения, требующие подтверждения владельцем
1. Звонки групп и каналов идут криптографическим путём конференций, сохраняя интерфейс звонка чата; конференции как продукт — позже.
2. «Войти от имени канала» в групповых звонках убирается.
3. Этап 1 не выходит к пользователям без этапа 2: групповые звонки выходят сразу сквозными, вместе с обновлёнными клиентами.
4. Живые истории убираются из клиентов вместе с RTMP.
5. Web K в браузерах без `RTCRtpScriptTransform` не входит в групповые звонки (показывает сообщение).
6. Проверка блоков — свой порт на Go (`pkg/tde2e`), без cgo на сервере.
7. Отчёты о шифровании идут по каналу данных к SFU; подробности по участнику видны в `pluma-admin`, метрики — без меток пользователя.
8. Код ошибки для клиента без `public_key`/`block` — выбирается после чтения того, как клиенты показывают `GROUPCALL_INVALID` и `GROUPCALL_FORBIDDEN`. Если ни одна ошибка не показывается понятно, нужен новый текст «обновите приложение».

## Не проверено
- tde2e у Android и tdesktop против `e894536b`.
- tgcalls iOS `c1de0882` в местах шифрования; эталонный движок iOS (`useReferenceImpl`, `PresentationGroupCall.swift:1888-1890`) с трансформером.
- Побайтная совместимость порта Web K с tdlib.
- `td::Ed25519::compute_shared_secret` по исходнику (аналог в Go на `filippo.io/edwards25519` и `crypto/ecdh` совпадает с вектором `tde2e/test/e2e.cpp:119-133`, но вектор один).
- Совпадение пересериализованного блока с присланными байтами.
- Шифрование вместе с simulcast в tgcalls.
- Утечка точного уровня звука в расширении 1.
- Полный путь повторного входа Android и читатель `isFailed` на iOS.
- Поддержка `RTCRtpScriptTransform` по версиям браузеров.
- Как tdesktop показывает выбор «войти от имени», когда `getGroupCallJoinAs` возвращает только пользователя.
- Политика сервера Telegram для `only_left` и `kick` (код закрыт; правила §2 — наш вывод).
