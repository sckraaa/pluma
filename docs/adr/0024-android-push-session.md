# 0024. Пуш-сессия Android (token_type 7)

- Статус: accepted
- Дата: 2026-10-30
- Задача 020. Заменяет утверждение ADR 0017 (раздел «Контекст», «Что `sync` уже умеет»), что Android сам MTProto-сессию push не регистрирует.

## Контекст
- **Что делает Android** (DrKLO/Telegram aac1efcb, проверено по коду 2026-10-30).
  - Сетевой слой tgnet держит, кроме основного, отдельное пуш-соединение на том же ключе авторизации, со своей сессией `pushSessionId`. Включает его `setPushConnectionEnabled`, а наш `help.getAppConfig` отдаёт `background_connection` и `keep_alive_service`.
  - Эту сессию tgnet регистрирует так: `account.registerDevice(token_type = 7, token = pushSessionId)`, без `secret` (`TMessagesProj/jni/tgnet/ConnectionsManager.cpp:2398-2419`).
  - Токен — id сессии беззнаковым десятичным числом (`Defines.h:190-194`, `to_string_uint64`). Примерно у половины id старший бит установлен, и запись выходит за диапазон int64.
  - Регистрация считается сделанной только при успешном ответе. До успеха tgnet повторяет её при создании сессии сервером и на каждый `pong` пуш-соединения (`ConnectionsManager.cpp:1122-1123, 1167-1170`).
  - Пробуждение — `updatesTooLong` в пуш-соединении. Получив его, tgnet будит сеть, если она спит, и зовёт `onInternalPushReceived` (`ConnectionsManager.cpp:1742-1753`). Дальше клиент подключает основную сессию и забирает разницу.
  - «MTProto separate session» — тип 7 в списке core.telegram.org/api/push-updates; подробностей там нет.
- **Что было у Pluma.**
  - Слой сессий перехватывает `account.registerDevice` с типом 7, привязывает пуш-сессию (`onBindPushSessionId`, id хранится в authsession) и шлёт в неё `updatesTooLong` на каждое обновление с флагом уведомления от sync (`app/interface/session/internal/sess/session_invoke.go`, `session_sync.go`, `main_auth_wrapper.go`). Механизм пришёл из апстрима.
  - Но bff после перехвата отвечал на тип 7 `TOKEN_TYPE_INVALID` (задача 009). Клиент считал регистрацию неудачной и повторял её: в логах сервера 13 ошибок за 72 ч от одного пользователя.
  - Слой сессий разбирал токен через `strconv.ParseInt` и игнорировал ошибку. Id со старшим битом не разбирались, и к ключу привязывалась сессия 0, до которой пробуждение не доходит.
- **Что отвечает Telegram, не проверено.** Вывод из кода клиента: флаг регистрации tgnet хранит в конфиге, и с серверами Telegram повторы прекращаются. Значит, Telegram отвечает на эту регистрацию успехом.

## Решение
1. **bff принимает тип 7.** Токен — десятичный id сессии без знака, не 0; иначе `TOKEN_INVALID`, пустой — `TOKEN_EMPTY`. `secret` не нужен. Ответ `boolTrue`. В хранилище push-устройств ничего не пишется: сервис `push` с провайдерами этим устройством не занимается.
2. **Разбор токена общий:** `pushdevices.PushSessionId`, беззнаковый разбор с сохранением 64 бит. Им пользуются bff и слой сессий; сессия 0 не привязывается.
3. **Доставка без изменений:** слой сессий будит клиента `updatesTooLong` в привязанной пуш-сессии.

## Последствия
- **FCM при живой пуш-сессии.** Пока пуш-соединение живо, авторизация считается онлайн (`setOnline` при привязке). По ADR 0017, п. 4, push через FCM этой авторизации тогда не уходит: клиент разбудит пуш-сессия. Если пуш-соединение оборвётся, статус погаснет так же, как у основной сессии, и пойдёт FCM.
- **Без Firebase.** Телефон без Google-сервисов получает уведомления в фоне только через пуш-сессию. Насколько долго Android держит её в режиме Doze, не проверено.
- **Huawei (тип 13)** по-прежнему не принимается: провайдера HMS у сервера нет.

## Рассмотренные альтернативы
- **Хранить тип 7 в `push_devices` и будить из сервиса `push`.** Отвергнута. Привязка уже живёт в слое сессий рядом с соединением; сервису `push` пришлось бы ходить в слой сессий за тем, что тот знает сам.
- **Продолжать отказывать.** Отвергнута: клиент повторяет регистрацию бесконечно, а при неразобранном id пробуждение не доходит.
