## Контекст

Задача 002 сделала изменение ящика одной транзакцией MySQL (`pkg/userbox.Run`). Побочные эффекты транзакции — push устройствам пользователя и события в чужие ящики — собираются через `Box.Emit` и публикуются в Kafka сразу после commit (`app/messenger/msg/internal/dao/box.go`, `RunBox` → `Dao.Publish` → `userbox.Publish`). Требования из ADR 0011 и брифа:

- событие одного инициатора доходит до получателя в порядке commit транзакций инициатора (отправка, затем правка, затем удаление);
- событие применяется у получателя ровно один раз: повторная доставка не создаёт вторую копию сообщения и не выделяет новый `pts`;
- ни сбой процесса, ни рестарт Kafka, MySQL, `session` или `sync` не теряют сообщение: после восстановления оно есть в журнале получателя и приходит push-ем или через `updates.getDifference`.

Что есть сейчас (по коду):

- **Публикация после commit.** Между commit и ответом брокера событие живёт только в памяти `msg`. Ошибка или таймаут (`EventTimeout` 10 с) — лог и `msg_post_commit_errors_total{kind="publish"}`, событие потеряно. Продюсер sarama контекста не принимает (`publisher.go`): событие, засчитанное как неопубликованное, может дойти позже и не в порядке. Две транзакции одного пользователя, закоммиченные подряд, публикуются в порядке публикации, а не commit. `kill -9 msg` между commit и ответом брокера теряет рассылку.
- **Консьюмер** — marmota `pkg/mq/consumer_group.go`: обработчик ничего не возвращает (`MessageHandlerF`), `MarkMessage` вызывается всегда, `OffsetNewest` для новой группы, autocommit, `Stop()` пустой. Обработчик inbox (`app/messenger/msg/inbox/internal/server/mq/mq.go`) повторяет повторяемые ошибки до 30 с, затем подтверждает событие и пишет его в лог (№6). Дедупликации у получателя нет: повторная доставка создаёт вторую копию с новым `pts`. Поиск копии по `dialog_message_id` идёт без индекса. Консьюмеры msg и sync создаются `MustKafkaConsumer`: без брокера процесс падает при старте.
- **Ошибки MySQL.** `userbox.Retryable` признаёт временными только 1213, 1205, `ErrBudget`, неприменённый `COMMIT`, `driver.ErrBadConn` и `mysql.ErrInvalidConn`. При перезапуске MySQL приходят и другие: `*net.OpError` (connection refused), 1040, 1053, 1290, 1317, 1927, 2006, 2013.
- **Продюсеры вне msg.** bff создаёт 14 продюсеров marmota (`kafka.MustKafkaProducer` в `app/bff/*/internal/dao/dao.go`) и публикует в `Sync-T` синхронно, внутри RPC клиента, в 33 местах: `sendMessage`, `sendMedia`, `sendMultiMedia` (через `doClearDraft`), `setTyping`, `saveDraft`, `updateProfile` и другие. Таймауты sarama по умолчанию — 30 с на соединение и чтение, 3 повтора. Без брокера bff не стартует, при зависшем брокере запрос клиента висит минутами. sync держит необязательный `PushClient`: продюсер без потребителя в репозитории, в конфигурациях выключен.
- **Отправка.** Идемпотентность `sendMessage` по `random_id` — только окно Redis 90 с (`msg/internal/dao/idempotent.go`, №10). Повтор клиента из офлайн-очереди позже окна создаёт дубликат.
- **Kafka** — один узел `apache/kafka:3.9.0` (KRaft) в `docker-compose-env.yaml`. `KAFKA_CREATE_TOPICS` этот образ не поддерживает: топики создаются автоматически с `KAFKA_NUM_PARTITIONS: 3`. `restart:` нет, том есть. Продюсеры marmota: `acks=all`, хеш-партиционер sarama, не идемпотентные, `Net.MaxOpenRequests = 5` по умолчанию — повтор отправки может переставить сообщения в партиции. Топик `teamgram-log` пишет filebeat того же compose, читает go-stash.
- **sync → session** (`app/messenger/sync/internal/dao/session_client.go`): push раскладывается по 100 горутинам round-robin (`atomic.AddUint64 % RoutineSize`), поэтому пуши одного пользователя переставляются. При первой ошибке `Unavailable`/`DeadlineExceeded` ставится флаг `unavailable`, и все дальнейшие пуши на этот узел выбрасываются. Флаг не сбрасывается: если `session` перезапустился с тем же адресом в etcd, объект `Session` переиспользуется (`watch`). `watch` пропускает пустой список узлов. Отправка в полный канал блокирует консьюмер. Ошибки пушей игнорируются (`_ =` в `core.go`). gRPC переподключается с паузой до 120 с (умолчание grpc-go, go-zero его не меняет). Breaker go-zero считает отказами `Unavailable`, `DeadlineExceeded` и `ResourceExhausted` (`zrpc/internal/codes.Acceptable`). Альтернативный `StreamingSession` (флаг `UseStreamSession`, выключен) — fire-and-forget без подтверждений.
- **session** (`session.pushUpdatesData_handler.go`) отвечает `BoolTrue`, даже когда `SyncDataArrived` выбросил push из-за полного `sessionDataChan` (4096). `getOrFetchMainAuthWrapper` создаёт обёртку для любого ключа, ошибки authsession уходят с произвольными кодами. Очередь сессии ограничена (`maxQueueSize`, вытесняет старые).
- **Контейнер.** ENTRYPOINT в shell-форме, `runall-docker.sh` запускает 11 процессов в фоне и висит на `tail -f /dev/null`. SIGTERM до сервисов не доходит, через 10 с SIGKILL, `Destroy` не выполняется. Упавший процесс никто не перезапускает. `proc.SetTimeToForceQuit` go-zero по истечении предела шлёт процессу SIGTERM повторно, а `commands.Runner` marmota перехватывает его (`signal.Notify`) и продолжает ждать `Destroy`: принудительный выход не срабатывает.
- **Дедлайны RPC.** `Timeout: 0` у серверов msg, bff, media, dfs, у клиентов bff → msg/media/dfs, media → dfs и session → bff. Клиенты без поля получают значение go-zero по умолчанию — 2 с.
- **Клиенты и `RANDOM_ID_DUPLICATE`.** Ни tdlib (`MessagesManager::on_send_message_fail` → `fail_send_message`), ни tdesktop (`ApiWrap::sendMessageFail`), ни Android (`SendMessagesHelper`), ни iOS (`PendingMessageManager`) не обрабатывают эту ошибку особо: сообщение помечается неотправленным.

Чем клиент Telegram восстанавливает пропущенное: обновление с `local_pts + pts_count < pts` — дыра, через 0,5 с `updates.getDifference`. `updatesTooLong` — немедленный `getDifference`. `new_session_created` после потери сессии сервером — клиент перезапрашивает состояние. По ADR 0011 (И1–И3) каждый `pts`, который видел клиент, закоммичен вместе со строкой журнала, и `getDifference` отдаёт все строки до закоммиченного `state.pts`. Значит, push может теряться и переставляться, если событие **применено** в ящике получателя: устройство догонит. Терять нельзя применение.

## Решение

Источник истины для события до его применения — строка таблицы `mq_outbox` в MySQL, записанная в той же транзакции, что и изменение, которое событие описывает. Kafka — транспорт, буфер и порядок доставки; для inbox-события копия в Kafka — только сигнал «строка готова», тело применяется из строки. Relay публикует строки по порядку `id` и остаётся единственным продюсером Kafka в системе. Транзакция получателя, применяющая inbox-событие, удаляет его строку. Наличие строки — это и проверка «уже применено», и порядок, и очередь повторной доставки, и место «мёртвых» событий.

### 1. Таблица `mq_outbox`

```sql
CREATE TABLE IF NOT EXISTS `mq_outbox` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT,          -- id события, заголовок event-id; не переиспользуется
  `initiator_id` bigint(20) NOT NULL,               -- чья транзакция записала строку; 0 — запись вне транзакции ящика
  `topic` varchar(64) NOT NULL,
  `recipient_id` bigint(20) NOT NULL,               -- ключ Kafka (десятичная запись)
  `method` varchar(128) NOT NULL,                   -- имя proto-сообщения
  `payload` mediumblob NOT NULL,                    -- JSON запроса
  `trace` varchar(64) NOT NULL DEFAULT '',          -- traceparent запроса, для сквозной трассировки
  `state` tinyint(4) NOT NULL DEFAULT '0',          -- 0 pending, 1 published, 2 dead, 3 parked
  `revision` int(11) NOT NULL DEFAULT '0',          -- +1 при каждом изменении state
  `publish_count` int(11) NOT NULL DEFAULT '0',     -- публикаций всего, для диагностики
  `kafka_partition` int(11) NOT NULL DEFAULT '-1',  -- где лежит последняя опубликованная копия
  `kafka_offset` bigint(20) NOT NULL DEFAULT '-1',
  `redeliveries` int(11) NOT NULL DEFAULT '0',      -- перепубликации по таймеру (п. 3)
  `deferrals` int(11) NOT NULL DEFAULT '0',         -- откладывания консьюмером (п. 5)
  `attempts` int(11) NOT NULL DEFAULT '0',          -- неудачные применения с детерминированной ошибкой
  `replays` int(11) NOT NULL DEFAULT '0',           -- автоматические повторы после dead (п. 5)
  `due_at` bigint(20) NOT NULL DEFAULT '0',         -- мс: published — когда проверить копию; dead — когда автоповтор
  `error` varchar(512) NOT NULL DEFAULT '',         -- последняя ошибка: коды и id, без содержимого
  `created_at` bigint(20) NOT NULL,                 -- мс, время Emit; заголовок created-at и timestamp записи Kafka
  PRIMARY KEY (`id`),
  KEY `state` (`state`, `id`),
  KEY `recipient` (`topic`, `recipient_id`, `id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

Имя отличается от «outbox» ящика отправителя (`outbox.go`), как требовал ADR 0011, п. 13.

**Класс топика.** У каждого топика один класс, и это свойство топика в реестре `pkg/outbox` (из конфигурации сервиса), а не поле строки:
- **inbox** (`Inbox-T`): применение — транзакция MySQL у получателя, она и удаляет строку;
- **push** (`Sync-T`, `BotSync`): доставка не транзакционна, строку удаляет relay после ответа брокера; пропущенный push с `pts` восстанавливается через `getDifference`.

Вызывающий код класс не задаёт и поэтому не может превратить inbox-событие в push, строку которого relay удалит до применения.

| Состояние | Кто ставит | Что дальше |
|---|---|---|
| pending (0) | транзакция инициатора (`Emit`) или `outbox.Insert`; консьюмер, откладывая событие; relay при получении лидерства (из published); таймер повторной доставки; автоповтор и `pluma-admin outbox replay` (из dead и parked) | relay публикует по возрастанию `id` |
| published (1) | relay после ответа брокера, только inbox | строку удаляет транзакция получателя; копию, которую консьюмер пропустил или которой нет в логе, таймер вернёт в pending |
| (строки нет) | транзакция получателя (inbox); relay после ответа брокера или при постоянной ошибке брокера (push); `pluma-admin outbox discard` | событие применено, отправлено или сознательно отброшено |
| dead (2) | консьюмер: детерминированная ошибка применения или строка блокирует полосу получателя (п. 5); relay: постоянная ошибка брокера для inbox-строки (п. 3) | автоповтор по `due_at`, `outbox replay` или `discard`; получатель запаркован |
| parked (3) | консьюмер: более позднее событие запаркованного получателя | возвращается в pending вместе с dead-строкой получателя |

- **Очистки нет:** строки удаляются применением или подтверждением брокера. Остаются только dead и parked, их повторяет relay (п. 5) или разбирает оператор. Размер таблицы — это отставание доставки, на него есть метрика и алерт (п. 10).
- **`id` не переиспользуется.** `TRUNCATE`, пересоздание таблицы и восстановление резервной копии без подъёма AUTO_INCREMENT запрещены (процедура — п. 11, `docs/ops`). На этом держится окончательность «строки нет» у консьюмера (п. 5).
- **Писатели.** В `mq_outbox` пишут только `pkg/userbox` (строки в транзакции ящика: `Emit`, `TakeEvent`, `FinishEvent`, `KeepEvent`, `FailEvent`) и `pkg/outbox` (`outbox.Insert` вне транзакции ящика, relay, операции оператора для `pluma-admin`). `pkg/outbox` пользуется `userbox.Run`, обратной зависимости нет.

### 2. Запись: `Box.Emit` — строка outbox в транзакции

- `Emit(ev)` проверяет событие: топик есть в реестре, `Recipient > 0`, `len(Data) ≤ MaxEventBytes` (4 МиБ), у inbox-события получатель ≠ инициатор (сейчас проверяет `EmitInbox`). Ошибка запоминается в `Box`, и `Run` откатывает транзакцию: операция завершается ошибкой до commit, клиент получает ошибку, ничего не записано. Событие, которое нельзя опубликовать, не попадает в таблицу.
- `Run` пишет события попытки **последними операторами перед `COMMIT`**, после условного `UPDATE user_state`: многострочные `INSERT INTO mq_outbox (...) VALUES (...), (...)` в порядке `Emit`, не больше 4 МиБ полезной нагрузки на оператор (рассылка в basic group — до 199 строк). Так окно между выделением `id` и commit минимально (это уменьшает число откладываний, п. 5), а размер оператора ограничен. Строки неудачной попытки исчезают вместе с откатом, как журнал.
- `userbox.Check` дополнительно проверяет `max_allowed_packet ≥ 16 МиБ`; при меньшем значении сервис не запускается.
- `trace` берётся из `b.Context()`, `created_at` — время `Emit` в миллисекундах.
- **Порядок `id` = порядок commit по инициатору.** `id` выделяется при вставке, внутри транзакции, которая держит блокировку строки `user_state` инициатора. Следующая транзакция того же пользователя вставляет свои строки только после commit предыдущей, а счётчик AUTO_INCREMENT только растёт. Значит, у всех строк, записанных транзакциями одного пользователя, порядок `id` совпадает с порядком commit, а внутри транзакции — с порядком `Emit`. Порядок строк разных пользователей с порядком commit не совпадает (транзакция с меньшим `id` может закоммититься позже), это учитывают relay и консьюмер.
- **Видимость.** Если relay видит строку транзакции T2 пользователя U, он видит и все строки предыдущей транзакции T1 того же U: T1 закоммичена раньше, чем T2 вставила строки (ADR 0011, И3).
- **Вне транзакции ящика** — `outbox.Insert(ctx, db, ev)`, одна autocommit-вставка, `initiator_id = 0`. Так пишут `msg.pushUserMessage` (ящик отправителя не меняется; ошибка вставки — ошибка RPC) и push-клиенты bff (п. 4).
- **После commit** `RunBox` будит relay своего процесса (`outbox.Notify`) и сбрасывает кэш. Ответ RPC больше не ждёт Kafka.
- **Удаляется:** `userbox.Publish`, `Failure`, `ErrSkipped`, `ErrTopicTimedOut`, `ErrPublishTimeout`, `EventTimeout`, `PublishTimeout`, `Result.Events`, `kafkaPublisher`, `Dao.Publish`/`PublishEvent` и кэш продюсеров marmota (`kafka.GetCachedMQClient`) в msg, метка `kind="publish"` у `msg_post_commit_errors_total`. msg не публикует в Kafka сам.
- `msg.MaxBoxOpTime` = сброс кэша + `userbox.MaxRunTime` + сброс кэша = 5 + 16 + 5 = 26 с, как `dialog.MaxBoxOpTime`.

### 3. Relay

**Где.** Пакет `pkg/outbox`, тип `Relay`. Запускается в процессе msg: msg пишет почти все строки и сам применяет inbox-события, поэтому пробуждение внутри процесса даёт задержку без опроса. Строки других процессов (push-и bff, `pluma-admin`, в задаче 010 — biz) подхватываются опросом раз в 50 мс: это до 50 мс задержки для пушей bff и 20 индексных выборок в секунду в простое.

**Один активный relay.** `SELECT GET_LOCK(CONCAT('mq_outbox_relay.', DATABASE()), 0)` на выделенном `*sql.Conn`: имя включает базу, потому что блокировки `GET_LOCK` общие на весь сервер MySQL (стенд и прод или параллельные тесты на одном сервере не мешают друг другу). Перед каждым раундом relay на **том же** соединении проверяет `IS_USED_LOCK(...) = CONNECTION_ID()`; при обрыве соединения MySQL снимает блокировку сам, relay прекращает публикацию и пытается взять её снова. Резервный экземпляр пробует раз в 5 с. Несколько relay с `SELECT … FOR UPDATE SKIP LOCKED` не годятся: строки одного получателя публиковались бы параллельно и переставлялись. Корректность от единственности relay не зависит (п. 5), блокировка лишь не даёт двум экземплярам публиковать всё дважды.

**Получив лидерство**, relay (1) переводит все published-строки в pending: это покрывает падение хоста, потерю тома или offset-ов Kafka и восстановление MySQL из копии без ожидания таймера; копии уже применённых событий консьюмер отбросит предпроверкой (п. 5); (2) запускает автоповтор всех dead-полос (п. 5).

**Kafka не нужна для старта.** Admin-клиент и продюсер relay создаёт в своём цикле, лениво. Брокера нет — повтор подключения 1 с → 30 с, метрика `outbox_relay_connected 0`; msg при этом запущен и отвечает на RPC, строки копятся в таблице. При каждом подключении и раз в 30 с relay сверяет топики (`DescribeTopics`): каждый топик реестра существует, число партиций равно ожидаемому (16). Топик, который не прошёл сверку, «не готов»: его строки не выбираются и ждут в pending (`outbox_topic_ready{topic} 0`, алерт), остальные топики публикуются.

**Раунд.**
1. Пробуждение: `Notify` после commit в процессе msg (RPC и inbox-консьюмер, включая откладывание), иначе опрос раз в 50 мс; после полного раунда — сразу следующий.
2. `SELECT id, revision, topic, recipient_id, method, trace, created_at, LENGTH(payload) FROM mq_outbox WHERE state = 0 AND topic IN (:ready) ORDER BY id LIMIT 500`, без строк «в полёте» (ниже). Полезная нагрузка читается вторым запросом по первичному ключу только для push-строк, по возрастанию `id`, не больше 16 МиБ на раунд; не поместившиеся строки уходят в следующем раунде. Inbox-строки публикуются без тела.
3. Отправка через `AsyncProducer` в порядке `id`. Запись Kafka: ключ `recipient_id` (у `sync.broadcastUpdates` — id чата, как сейчас), значение — `payload` (push) или пусто (inbox), заголовки `method`, `event-id`, `initiator`, `created-at`, `traceparent`, `Timestamp = created_at`. Relay ждёт ответа по каждому сообщению не дольше `RoundTimeout` = 10 с.
4. Результаты получает **финишер** — отдельная горутина со своим соединением, — а relay сразу начинает следующий раунд, не дожидаясь commit в MySQL. Отправленные, но ещё не записанные финишером `id` relay держит в памяти («в полёте») и пропускает при выборке. Финишер в одной транзакции READ COMMITTED: подтверждённые inbox-строки — `UPDATE mq_outbox o JOIN (VALUES ROW(:id, :revision, :partition, :offset), …) v ON o.id = v.id AND o.revision = v.revision SET o.state = 1, o.revision = o.revision + 1, o.publish_count = o.publish_count + 1, o.kafka_partition = …, o.kafka_offset = …, o.due_at = :now + 2 мин × 2^redeliveries` (не больше 1 ч); подтверждённые push-строки — `DELETE o FROM mq_outbox o JOIN (VALUES …) v ON o.id = v.id AND o.revision = v.revision`. Условие на `revision` не даёт relay затереть то, что консьюмер успел сделать со строкой за время отправки (отложить, запарковать). После commit `id` выходят из «полёта».
5. Неподтверждённые строки остаются pending и уходят в следующем раунде, снова по возрастанию `id`.

**Ошибки брокера** relay разбирает по каждому сообщению (`ProducerError.Err`):

| Ошибка | Что значит | Действие |
|---|---|---|
| `ErrMessageSizeTooLarge`, `ErrInvalidMessage`, `ErrInvalidMessageSize`, `ErrInvalidRecord`, ошибка кодирования в клиенте | сообщение не будет принято никогда | inbox-строка → dead (`error` = код), получатель паркуется механизмом п. 5; push-строка удаляется, `outbox_dropped_total{topic,reason}`, лог (id, топик, получатель, код). Остальные строки раунда не затрагиваются |
| `ErrUnknownTopicOrPartition`, `ErrInvalidTopic`, `ErrTopicAuthorizationFailed` | проблема топика, а не строки | внеочередная сверка топиков; топик «не готов», его строки ждут, алерт |
| остальные (сеть, брокер недоступен, `ErrNotEnoughReplicas`, таймауты) | временная | строка остаётся pending |

Общая пауза relay (100 мс → 5 с с удвоением) — только когда клиент Kafka недоступен или в раунде не подтвердилось ни одно сообщение. Если истёк `RoundTimeout`, продюсер отбрасывается (`AsyncClose` без ожидания, его поздние ответы игнорируются) и создаётся заново: повторы sarama и смена epoch идемпотентного продюсера не держат relay дольше предела. Одна «ядовитая» строка не замедляет остальные: она уходит из pending за один раунд.

**Повторная доставка** (только inbox). Раз в 10 с relay выбирает published-строки с `due_at ≤ now` (первый раз — через 2 мин после публикации) и сверяет место копии (`kafka_partition`, `kafka_offset`) с брокером через admin-клиент:

| Состояние у брокера | Вывод | Действие |
|---|---|---|
| закоммиченный offset группы inbox по партиции > `kafka_offset` | консьюмер прошёл копию, не применив (ошибка в коде) | pending, `redeliveries + 1`, `outbox_redelivered_total{reason="skipped"}` |
| начало лога > `kafka_offset` или конец лога ≤ `kafka_offset` | копии в логе нет (потеря тома, пересоздание топика) | pending, `redeliveries + 1`, `reason="log_lost"` |
| иначе | консьюмер до копии ещё не дошёл | ничего; `due_at` + 1 мин. Застрявшую партицию показывают лаг и `DeliveryConsumerStuck` |

Таймер не перепубликует то, до чего консьюмер просто не дошёл: при долгой остановке партиции хвост не дублируется, а `DeliveryRedelivered` срабатывает только на настоящий пропуск или потерю. Следующая проверка после перепубликации — через 2 мин × 2^`redeliveries`, не больше 1 ч; откладывания и сброс при получении лидерства счётчик не увеличивают.

**Перестановки.** Идемпотентный продюсер сохраняет порядок успешно записанных сообщений в партиции. Если в раунде одно сообщение не подтвердилось, а следующее того же получателя записалось, первое уйдёт в следующем раунде, то есть позже. Для `Inbox-T` это исправляет консьюмер (п. 5), для push-ей это дыра у клиента и `getDifference`.

**Рестарты.** Всё состояние в таблице. Строка, по которой брокер ответил, но финишер не записал результат (падение relay), будет опубликована ещё раз; консьюмер применит её один раз. Смена лидера даёт такие же повторы.

**Изоляция и блокировки.** Все запросы `pkg/outbox` вне `Run` (выборка и финишер relay, таймер, сверка, `outbox list`) выполняются в READ COMMITTED (`BeginTx` с `sql.LevelReadCommitted`; на выделенном соединении relay — `SET SESSION transaction_isolation = 'READ-COMMITTED'`) и меняют строки только по первичному ключу: сначала неблокирующая выборка `id`, затем `UPDATE`/`DELETE` с `JOIN (VALUES ROW(…))` по `id` и `revision`. Диапазонных блокирующих запросов нет, поэтому вставки транзакций отправителей не ждут relay. 1213 и 1205 — повтор того же оператора до 5 раз, без повторной публикации; не прошло — строки остаются в прежнем состоянии, и pending опубликуется ещё раз. План (`EXPLAIN`: доступ по `PRIMARY`) проверяет интеграционный тест. Изменения строк получателя R, которые зависят от состояния его полосы (отложить, запарковать, dead, автоповтор, `replay`, `discard` inbox-строки), выполняются внутри `userbox.Run(R)` (п. 5).

**Остановка.** Relay не начинает новый раунд, ждёт текущий не дольше `StopRoundWait` = 2 с, отбрасывает продюсер (`AsyncClose`), отпускает блокировку. Неподтверждённые строки остаются pending.

- **16 партиций.** Порядок по получателю даёт ключ, а число партиций — параллельность консьюмера и изоляцию: долгий повтор одного события задерживает примерно 1/16 пользователей, а не всех. Для одного брокера 16 партиций ничего не стоят.

Page cache Kafka теряется только при падении хоста, а оно перезапускает и msg. Потерянный push восстанавливает `getDifference`.
- **Что значит один брокер с RF=1.** Высокой доступности нет: брокер недоступен — доставка стоит, но отправка работает (строки копятся в `mq_outbox`, алерты). Ни один сервис не зависит от Kafka при старте: relay и консьюмеры подключаются в фоне, bff и sync продюсеров Kafka не имеют. Потеря тома Kafka не теряет inbox-события. Потеря `__consumer_offsets` (RF=1) даёт чтение с начала хранения (`OffsetOldest`): копии применённых событий отбрасываются предпроверкой без транзакции, старые push-и — по возрасту (п. 7). Пересмотр — при появлении второго хоста.

**Push-и bff и sync** идут через outbox. Интерфейс `SyncClient` (`app/messenger/sync/client`) получает реализацию поверх `outbox.Insert` (топик `Sync-T`) вместо продюсера marmota; 33 места вызова в bff не меняются. Push — одна autocommit-вставка в пул MySQL bff, ограниченная контекстом запроса: Kafka уходит с пути RPC, bff стартует и отвечает без брокера, а push-и становятся долговечными и упорядочены по `id` вместе с push-ами msg. Цена — одна вставка (fsync redo) на такой push и до 50 мс опроса relay. Обновления без `pts` (имя, черновики, набор текста) по-прежнему не журналируются (задача 010), но больше не теряются при сбое Kafka или sync, кроме устаревших (п. 7). Необязательный `PushClient` sync удаляется: потребителя у него нет, уведомления на выключенные устройства — задача 009. После этого marmota `pkg/mq` в коде не используется.

### 5. Консьюмер `Inbox-T`: применение ровно один раз и по порядку

Свой консьюмер в `pkg/mqconsumer` поверх `sarama.ConsumerGroup`, не marmota: обработчик возвращает результат, offset отмечается только после завершения события. Его используют msg (`Inbox-T`) и sync (`Sync-T`, п. 7) с разными политиками.

**Настройки группы:** `Version` `V3_6_0_0`; `Consumer.Offsets.Initial = OffsetOldest` (сообщения до первого назначения партиций не теряются); autocommit с интервалом 1 с, но `MarkMessage` вызывается только для завершённого события, поэтому offset не уходит дальше незавершённого; **статическое членство** `Group.InstanceId` = имя сервиса и хоста (`msg-<hostname>`): перезапущенный экземпляр сразу получает свои партиции, не дожидаясь, пока координатор исключит прежнего; `Group.Session.Timeout` 10 с, `Heartbeat.Interval` 1 с, `Rebalance.Timeout` 30 с; `Return.Errors = true`. Статический участник не покидает группу при закрытии (KIP-345, так делает sarama): партиции остановленного экземпляра ждут его 10 с, при одном экземпляре это и нужно. Подключение — в цикле `Start`, повтор 1 с → 30 с, без паники; `mq_consumer_assigned_partitions{group}` показывает назначенные партиции. Партиция обрабатывается последовательно, следующее сообщение берётся только после завершения текущего.

**Предпроверка** до транзакции, через пул, без блокировок:

```sql
SELECT topic, recipient_id, created_at FROM mq_outbox WHERE id = :x;
```

- строки нет → `outcome="duplicate"`, окончательно: `id` не переиспользуется, строку с тем же `id` никто не создаёт снова. `MarkMessage` без `Run` и без сброса кэша. Так копии после потери offset-ов или повторов relay стоят одну точечную выборку;
- топик, получатель (ключ) или `created_at` (заголовок `created-at`) не совпадают со строкой → `outcome="mismatch"`: чужое событие с тем же `id` (нарушена процедура п. 11). Пропуск, алерт; своя копия строки придёт отдельно или её вернёт таймер;
- иначе → транзакция получателя `Run(R)`.

**Проверка внутри транзакции получателя.** Хелпер `apply` в `inbox/internal/core/core.go` вызывает `Run(R)`, и первым делом внутри — `b.TakeEvent(x)`:

```sql
-- под блокировкой user_state получателя R, через b.Tx()
SELECT state, method, payload, trace, deferrals FROM mq_outbox WHERE id = :x;
SELECT id, state FROM mq_outbox
  WHERE topic = :topic AND recipient_id = :r AND id < :x ORDER BY id LIMIT 1;
```

| Что нашлось | Исход |
|---|---|
| строки `x` нет (применена между предпроверкой и блокировкой) | `duplicate`, пустышка |
| строка `x` в dead или parked | пустышка: ждёт повтора полосы |
| есть более ранняя строка R в pending или published | **отложить** (в этой же транзакции) |
| есть более ранняя строка R в dead или parked | **запарковать** (в этой же транзакции) |
| иначе | **применить**: обработчик декодирует `payload` строки по её `method` (тело копии в Kafka пустое), затем тело обработчика; после успеха хелпер вызывает `b.FinishEvent()` — `DELETE FROM mq_outbox WHERE id = :x`, `RowsAffected = 1` — или `b.KeepEvent()` для непоследней порции |

Применение и удаление строки коммитятся атомарно, поэтому повторная доставка (redelivery после падения до `MarkMessage`, повтор relay, таймер, смена лидера, перебалансировка группы) ничего не меняет: строки нет. Две копии одного события в двух консьюмерах во время перебалансировки сериализуются блокировкой `user_state(R)`, вторая видит, что строки нет. Тело события берётся только из строки, поэтому устаревшая копия не может применить чужие данные.

**Инвариант примитива.** `Box` помнит взятое событие. Если `TakeEvent` вернул «применить», `fn` вернула `nil`, а ни `FinishEvent`, ни `KeepEvent` не вызваны, `Run` откатывает транзакцию с `userbox.ErrEventNotFinished` (детерминированная ошибка: событие станет dead, а не зациклится). Обработчики `FinishEvent` и `KeepEvent` не вызывают: хелпер `apply(event, peer, fn func(b *userbox.Box) (done bool, err error))` заменяет `run` и вызывает их по результату `fn`. Каждая ветка-пустышка обработчика (копии нет, уже прочитано, нечего удалять, пустой список обновлений) возвращает `done = true`, и строка удаляется. Порционные события (`deleteMessagesToInbox`, `deleteUserHistoryToInbox`, `deleteChatHistoryToInbox`, по `Run` на порцию) возвращают `done = false`, пока порции остаются; хелпер запускает следующую `Run`, и `TakeEvent` проверяет порядок заново. Повтор после падения посреди порций продолжает с оставшихся id: уже удалённые не выбираются и не журналируются второй раз.

**Порядок.** Событие R применяется, только если все более ранние видимые строки R применены. Это порядок commit по каждому инициатору (п. 2) и вдобавок причинный порядок между инициаторами: если транзакция Bob-а видела сообщение Alice (ответ на него), строка Alice закоммичена и видна раньше, чем появилась строка Bob-а, и у Carol будет применена первой. Строка с меньшим `id`, которая ещё не закоммичена, не видна и не ждётся: причинной связи с ней быть не может.

**Отложить** — в той же `Run(R)`: неблокирующая выборка `id` опубликованных более ранних строк R и самой `x`, затем `UPDATE mq_outbox SET state = 0, revision = revision + 1 WHERE id IN (…)` по первичному ключу, у `x` ещё `deferrals + 1`. Журнала нет, состояние ящика не меняется, меняется только `mq_outbox`; commit, `Notify`, `MarkMessage`. Неприменённые события R и само это событие снова pending (у `x` растёт `revision`, даже если relay ещё не записал подтверждение, — иначе он перевёл бы `x` в published), и relay опубликует их по возрастанию `id`: «полоса» R перезапускается с самого раннего неприменённого события.

- **Почему это сходится.** Гонка (ранняя строка закоммичена позже, чем консьюмер получил позднюю) разрешается за один круг: после перепубликации ранняя строка идёт в партиции раньше поздней. Повторное откладывание `x` из-за той же строки означает ошибку, а не гонку.
- **Предел.** Если у `x` уже 10 откладываний, вместо очередного самая ранняя неприменённая строка R становится dead (`error = "lane_blocked"`), а `x` — parked. Получатель запаркован, срабатывает `DeliveryDeadEvents`, автоповтор (ниже) вернёт полосу. Горячего цикла relay ↔ консьюмер нет.
- **Как часто.** В обычной переписке откладываний почти нет. Когда несколько отправителей одновременно пишут одному получателю, окно гонки — от вставки строк до конца `COMMIT` отправителя (вставки стоят последними, п. 2), и доля откладываний может доходить до десятков процентов. Цена одного откладывания — перепубликация строк полосы и ещё один проход консьюмера, порядка одного раунда relay (миллисекунды, Kafka без fsync). Долю измеряют e2e «5 × 200» и `TestSendLatency` (п. 12), число записывается в бриф; критерий приёмки — задержка доставки, а не доля.

**Запарковать** — в той же `Run(R)`: `x` → parked (`state = 3`, `revision + 1`), commit, `MarkMessage`. Решение принимается и записывается под одной блокировкой `user_state(R)`, поэтому `replay` оператора или автоповтор, выполняемые тоже через `Run(R)`, не могут вклиниться между проверкой и записью.

**Классы ошибок и действия.** Детерминированные ошибки — закрытый список (`userbox.Deterministic`); всё, чего в нём нет, считается временным. `userbox.Retryable` (повторы внутри `Run`) не меняется.

| Класс | Что входит | Действие |
|---|---|---|
| неразбираемое | нет заголовка `event-id`, ключ не число, неизвестный `method` строки, ошибка JSON `payload`, получатель ≤ 0 или равен `from_id` | сразу dead (строка известна) или пропуск с метрикой (неизвестна) |
| детерминированное | бизнес-ошибка обработчика (`*mtproto.TLRpcError`); ошибки данных MySQL 1048, 1062, 1264, 1366, 1406, 3140; `errStateChanged`; ошибки использования `Box` (`ErrEventNotFinished`, вложенный `Run`, проверка `Emit`); паника обработчика | 3 попытки с паузами 100 и 200 мс, затем dead: `Run(R)` с `b.FailEvent(err)` ставит `state = 2`, `attempts`, `error`, `due_at = now + 15 мин` |
| временное — всё остальное | 1213, 1205, `ErrCommitUnknown` (повтор безопасен: если применилось, строки нет), `ErrBudget`, сетевые ошибки (`net.Error`, `io.EOF`, `driver.ErrBadConn`, `mysql.ErrInvalidConn`), 1040, 1053, 1290, 1317, 1927, 2006, 2013, ожидание соединения пула, дедлайн, любая неизвестная ошибка | повтор без ограничения числа, пауза 100 мс → 30 с с удвоением и разбросом; партиция ждёт; через 2 мин — алерт `DeliveryConsumerStuck` |
| отменён контекст сессии группы | остановка, перебалансировка | выход без `MarkMessage`: событие получит следующий владелец партиции |

Запись исхода (dead, отложить, запарковать) — сама операция MySQL. Если она не удалась, это временная ошибка: `MarkMessage` не вызывается, событие обрабатывается заново после паузы. Ни одна ветка не отмечает offset, не записав исход в `mq_outbox`. Временные ошибки не ограничены числом попыток сознательно: перезапуск MySQL на минуту не должен уводить в dead и парковать получателей. Событие при этом не теряется (оно в Kafka и в `mq_outbox`), а застрявшая партиция видна по алерту. Повтор внутри обработчика (`retryBudget` 30 с в `mq.go`) и подтверждение неприменённого события удаляются.

**Dead и parked вместо DLQ-топика.** Мёртвое событие остаётся строкой `mq_outbox` со всем, что нужно для повтора: топик, получатель, инициатор, метод, полезная нагрузка, трассировка, число попыток, текст ошибки (коды и id, без содержимого — `tools/logaudit`). Получатель с dead-строкой «запаркован»: каждое его следующее событие получает `state = 3` и не применяется, события других получателей идут дальше. Так соблюдается правило «не применять событие получателя раньше упавшего более раннего», а один сломанный ящик не останавливает остальных.

**Автоповтор.** Dead — не окончательное состояние. Relay-лидер раз в минуту и при каждом получении лидерства (то есть при каждом старте и выкатке msg) возвращает полосы с dead-строками: по `due_at ≤ now`, а при получении лидерства — все. Для каждого получателя `Run(R)` переводит его dead и parked строки в pending (`replays + 1`), relay публикует их по возрастанию `id`, консьюмер применяет по порядку. Если событие снова не применилось, оно снова dead с `due_at = now + 15 мин × 2^replays` (не больше 4 ч), получатель снова запаркован. Так исправление, выкаченное в деплое, само снимает парковку, а ошибка, ошибочно попавшая в детерминированные, повторяется через 15 мин, 30 мин, 1 ч… без оператора и без остановки партиции. Алерт `DeliveryDeadEvents` горит, пока dead-строки есть.

**Оператору** (`tools/pluma-admin`; команды пишут в лог, кто и что сделал, без содержимого; изменения inbox-строк — через `userbox.Run(R)`, пул с теми же настройками сессии, что у msg):
- `outbox list [--state pending|published|dead|parked] [--user R]` — метаданные строк;
- `outbox replay --user R` — dead и parked строки R в pending, `replays = 0`;
- `outbox discard --id X` — удалить строку в любом состоянии сознательно (в лог: id, топик, получатель, метод); для inbox-строки затем `replay --user R` для оставшихся.

### 6. Идемпотентность и уникальность

**Почему строка outbox, а не таблица обработанных событий или естественные ключи.**
- Естественных ключей недостаточно. Отправку защищает `(user_id, dialog_message_id)`, удаление и прочтение идемпотентны сами, но правка и закреп — нет: повтор `editMessageToInboxV2` добавляет вторую строку журнала `updateEditMessage` с новым `pts`, а повтор пачки «закрепить, открепить» после падения до коммита offset снова журналирует обе операции.
- Отдельная таблица обработанных событий `(user_id, event_id)` работает, но требует очистки и срока хранения больше, чем хранение топика и время до разбора мёртвых событий. Строка outbox уже существует и удаляется ровно в момент применения: проверка общая для всех событий, атомарна с применением и ничего не хранит после.

**`UNIQUE (user_id, dialog_message_id)` в `messages`** остаётся страховкой (ADR 0011, п. 8): ошибка в коде, которая всё же доставит отправку дважды, получит 1062 и станет dead, а не второй копией. Заодно это индекс для поиска копии по `dialog_message_id` (правка, удаление, прочтение, закреп), которого сейчас нет (известная проблема в STATUS). Код пишет только `dialog_message_id > 0` (проверка в `insertMessage`).

**`random_id` отправителя — постоянная дедупликация (№10):**
- генерируемая колонка `out_random_id = IF(sender_user_id = user_id AND random_id <> 0, random_id, NULL)` и `UNIQUE (user_id, out_random_id)`. Обычный `UNIQUE (user_id, random_id)` невозможен: входящие копии несут `random_id` отправителя, у служебных сообщений 0. NULL в уникальном индексе не конфликтует;
- колонка `messages.pts` — `pts` строки журнала, которая добавила копию в ящик; пишется в той же транзакции, у копий до 003 — 0;
- в транзакции отправителя до выделения id: `SELECT … FROM messages WHERE user_id = :u AND out_random_id IN (...)` через `b.Tx()`. Повторы одного `random_id` с двух устройств или после потерянного ответа сериализуются блокировкой `user_state`, второй видит закоммиченную первую;
- **все** `random_id` запроса уже есть, все найденные сообщения в диалоге запроса (`dialog_id1`, `dialog_id2`) и у всех `pts > 0` → **исходный ответ**: для каждого сообщения строка журнала `(user_id, pts)` (уникальный ключ) даёт исходный `updateNewMessage` с его `pts` и `pts_count`, и ответ строит та же функция `sendReply`, что и в первый раз: `updateMessageID` и `updateNewMessage` с исходными `pts`/`pts_count` (пользователи и чаты — текущие). Транзакции изменений и новых событий нет. Клиент обрабатывает ответ по обычным правилам `pts`: уже применённое пропускает, а `updateMessageID` связывает отправляемое сообщение с id; отставшее устройство видит дыру и делает `getDifference`. Это тот же ответ, который в пределах 90 с давало окно Redis, только без срока;
- часть `random_id` есть (пересылка, альбом), сообщение в другом диалоге (клиент повторно использовал `random_id`) или исходное сообщение удалено, или копия записана до 003 (`pts = 0`) → `RANDOM_ID_DUPLICATE`, как у Telegram. Ответ ошибкой на **полный** повтор не годится: все четыре клиента помечают сообщение неотправленным (Контекст), и пользователь увидел бы неотправленную копию рядом с доставленной;
- окно Redis удаляется целиком: `SendOnce`, `idempotent.go`, `IdempotencyLockTTL`, `sendOnceSection`, `msg_idempotency_bypass_total`. Отправка больше не зависит от Redis. Форму ответа проверяют интеграционный тест и e2e через `pkg/mtclient` по правилам `UpdatesState` (п. 12).

### 7. sync → session: push по порядку и без залипания

**Консьюмер `Sync-T`** — тот же `pkg/mqconsumer` со статическим членством (`sync-<hostname>`), политика best-effort:
- push передаётся пушерам узлов (ниже); offset отмечается, когда push по всем устройствам завершён: доставлен, отброшен окончательно или превращён в пометку resync, которая **разрешена** (`updatesTooLong` доставлен или прошло 30 с). Учёт — непрерывный префикс завершённых offset-ов на партицию; не больше 1024 незавершённых сообщений на партицию, дальше консьюмер ждёт. После `kill -9 sync` незавершённые пуши, в том числе превращённые в неразрешённый resync, придут ещё раз: клиент отбросит уже применённые по `pts`;
- ошибка JSON или неизвестный `method` — пропуск с метрикой;
- **возраст** — по timestamp записи Kafka (= `created_at`, все записи `Sync-T` пишет relay). Push старше `PushMaxAge` = 2 мин не доставляется (`outcome="stale"`): если в нём есть обновления с `pts`, целевые устройства помечаются resync и получат по одному `updatesTooLong`; push без `pts` (звонок, набор текста) просто отбрасывается. После долгого простоя или чтения с начала хранения устройство получает один `updatesTooLong`, а не тысячи старых пушей, вытесняющих свежие;
- онлайн-сессии пользователя (`status.getUserOnlineSessions`): дедлайн 2 с, повтор до 10 с, затем push отбрасывается с метрикой. Поиск сессий и постановка в очереди устройств идут последовательно, в порядке партиции: на этом держится порядок по устройству;
- узел `session`, которого нет в карте пушеров (etcd ещё не обновился после рестарта), — push отбрасывается, устройство помечается resync; пометку заберёт пушер узла, когда тот появится.

**Пушер узла `session`** (`dao/session_client.go`, переписывается):
- один `zrpc`-клиент: `grpc.WithConnectParams` с `Backoff.MaxDelay` 3 с и `MinConnectTimeout` 2 с, `ResetConnectBackoff` при появлении узла в etcd (после долгой недоступности `session` соединение восстанавливается за секунды, а не за 120 с по умолчанию); keepalive 20 с; дедлайн вызова 2 с; breaker клиента выключен (`Middlewares.Breaker: false`): повторами и resync управляет сам пушер;
- **очередь на устройство** (`perm_auth_key_id`): горутина устройства запускается первым push-ем и завершается после 60 с простоя, пуши устройства идут строго по одному и по порядку. Очередь — 256 пушей на устройство и 16384 на узел; постановка никогда не ждёт: места нет — push отбрасывается, устройство помечается resync. Медленное или зависшее устройство держит только свою очередь. Одновременных вызовов на узел — не больше 64;
- исход вызова:

| Ответ | Что значит | Действие |
|---|---|---|
| успех | push в очереди сессии | — |
| `NotFound` | ключа нет в authsession | push отбрасывается без пометки |
| `FailedPrecondition` | у устройства полный канал или authsession не ответил по этому ключу | ещё одна попытка через 100 мс, затем отбросить и пометить resync |
| `DeadlineExceeded` при готовом соединении | зависло одно устройство | отбросить, пометить resync |
| `Unavailable` или соединение не `READY` | недоступен узел | пушер узла на паузе: очереди устройств ждут готовности не дольше 30 с с начала паузы, затем их пуши отбрасываются, устройства помечаются resync |
| любой другой код | — | отбросить, пометить resync |

- **resync:** пометки хранятся в sync по устройству (переживают пересоздание пушера, но не рестарт процесса — его покрывает правило offset-а выше). Перед следующим push-ем помеченному устройству, а без пушей — по обходу раз в секунду (у устройства с неудачами пауза 1 → 30 с), горутина устройства шлёт `updatesTooLong`; клиент немедленно делает `getDifference`. Пометка снимается после успешной отправки или через 30 с (устройство недостижимо и при переподключении получит `new_session_created`);
- флага `unavailable` нет: после рестарта `session` на том же адресе следующий вызов идёт в новое соединение;
- etcd: пустой список узлов тоже применяется (все пушеры закрываются); узел исчез — его пушер закрывается, очереди и пометки отбрасываются: устройства переподключатся к другому узлу и получат `new_session_created`;
- `StreamingSession` и `UseStreamSession` удаляются (fire-and-forget без подтверждений). Потоковый сервис в session остаётся: им пользуется gnetway.

**session:** `session.pushUpdatesData` и `pushSessionUpdatesData` возвращают ошибку вместо `BoolTrue`: authsession ответил, что ключа нет, — `NotFound`; authsession не ответил — `FailedPrecondition` (`auth_unavailable`); `sessionDataChan` полон — `FailedPrecondition` (`channel_full`). Эти коды breaker go-zero отказами не считает, поэтому ни breaker сервера session, ни отказы одного устройства не закрывают узел для остальных. `Unavailable` остаётся только за транспортом: узел недоступен.

**Что если.**

| Событие | Что происходит | Как устройство догоняет |
|---|---|---|
| `session` перезапускается (до 30 с) | пушер узла на паузе; после подъёма (переподключение ≤ 3 с) пуши идут в новое соединение | session потеряла сессии → `new_session_created` → `getDifference`; доставленные позже пуши клиент отбросит по `pts` |
| `session` недоступна дольше 30 с | пуши отброшены, устройства помечены resync | `new_session_created` после переподключения или `updatesTooLong` после подъёма узла |
| у устройства полон канал или оно зависло | его пуши отбрасываются, оно помечено resync; остальные устройства узла не затронуты | `updatesTooLong` |
| устройство офлайн, ключ на узле есть | push в очереди сессии (ограничена, вытесняет старые) | при переподключении получит очередь; вытеснено — дыра → `getDifference` |
| `sync` упал | незавершённые пуши и неразрешённые resync придут снова после рестарта (offset не отмечен) | повторный push или `updatesTooLong` |
| Kafka недоступна | строки `Sync-T` копятся в `mq_outbox` | после восстановления свежие пуши доставляются, старше 2 мин — один `updatesTooLong` |
| потеряны offset-ы `Sync-T` | чтение с начала хранения: старые пуши устарели | один `updatesTooLong` на онлайн-устройство |

**Гарантия журнала.** Push устройству R порождается транзакцией R (ответ RPC, `updatesNotMe`, применение inbox-события) и записан в outbox в той же транзакции, что и строка журнала с его `pts` (ADR 0011, И1). `getDifference` отдаёт все строки до закоммиченного `state.pts` (И3). Поэтому любой потерянный или переставленный push с `pts` восстанавливается `getDifference`, если событие **применено** в ящике R. Исключения: (а) запаркованное событие — его нет в журнале R до автоповтора или `replay` (алерт); (б) обновления без `pts` (bff, `seq`) не журналируются до задачи 010: они долговечны в `mq_outbox`, но теряются, если устарели или не дошли до устройства.

**Реализация (упрощение очередей).** Очереди на устройство не понадобились: консьюмер ждёт, пока push одной записи `Sync-T` завершится на всех её устройствах (`dao.WithBatch` → `Batch.Wait`), и только потом отмечает offset. Записи одного пользователя приходят из одной партиции по порядку, поэтому порядок по устройству держится без очередей, а после падения `sync` незавершённый push приходит снова. Устройства одной записи обслуживаются параллельно (не больше 64 вызовов на узел), одно зависшее устройство задерживает партицию не дольше дедлайна вызова (2 с), недоступный узел — не дольше 30 с паузы. Остальные правила — как выше: коды ответа `session`, пометки resync с `updatesTooLong` перед следующим push-ем и обходом раз в секунду, `PushMaxAge`, пустой список узлов из etcd. Гистограмма задержки — `sync_push_duration_ms` (метрики go-zero принимают целые значения). Код — `app/messenger/sync/internal/dao/pusher.go`, тесты — `pusher_test.go`.

### 8. Процессы и остановка: один процесс — один сервис compose

Супервизор внутри контейнера не пишется: разнесение процессов по сервисам compose переносится сюда из задачи 004.

- `docker-compose.yaml`: вместо одного сервиса `teamgram` — 11 сервисов на одном образе (общий якорь `x-teamgram`): `command` в exec-форме (`["/app/bin/msg", "-f=/app/etc2/msg.yaml"]`), `restart: unless-stopped` (Docker перезапускает с паузой от 100 мс с удвоением до 1 мин), свой `stop_grace_period`, переменные окружения и секреты только нужные сервису (ключ RSA — только gnetway), порты публикует только gnetway. `ENTRYPOINT` в shell-форме, `entrypoint.sh`, `runall-docker.sh` и `HEALTHCHECK` образа (проверял все процессы одного контейнера) удаляются; у gnetway — проверка порта 10443. Проверки по сервисам — задача 004.
- `depends_on` повторяет нынешний порядок старта: idgen, status, authsession, dfs → media → biz → msg → sync → bff → session → gnetway; `docker compose stop` останавливает в обратном порядке. От Kafka и `kafka-init` сервисы teamgram не зависят: они стартуют без брокера (пп. 3–5). Зависимость — только от MySQL, Redis и etcd.
- Сервисы находят друг друга через etcd, как и сейчас: go-zero регистрирует вместо `0.0.0.0` адрес контейнера в сети `teamgram_net`. Сервисы, которые обращались к `127.0.0.1` внутри общего контейнера, переводятся на имена сервисов compose (сейчас таких нет: `127.0.0.1` у dfs — его собственный HTTP для своего ffmpeg).
- **SIGKILL безопасен по построению:** транзакция ящика либо закоммичена со своими строками outbox, либо откатится; строки relay и консьюмера переживают любой обрыв. Пределы остановки — про аккуратность (меньше повторов и ошибок у клиентов), не про корректность. Единственная жёсткая граница — SIGKILL от Docker после `stop_grace_period`: `proc.SetTimeToForceQuit` не работает с `commands.Runner` (Контекст), его вызовы удаляются.

| Сервис | `Destroy` | Предел `Destroy` | `stop_grace_period` |
|---|---|---|---|
| gnetway | закрыть приём соединений | 5 с | 15 с |
| session | дождаться выполняющихся запросов | 10 с | 20 с |
| bff | дождаться RPC (дольше — прерываются, клиент повторит) | 20 с | 30 с |
| sync | остановить консьюмер (закрытие группы ≤ 5 с) и параллельно дать очередям пушеров до 5 с | 6 с | 15 с |
| msg | перестать принимать RPC; параллельно дождаться выполняющихся RPC (≤ дедлайн сервера 40 с) и остановить консьюмер (текущее событие ≤ `MaxBoxOpTime` 26 с, закрытие группы ≤ 5 с); затем relay (`StopRoundWait` 2 с, отпустить блокировку) | 42 с | 50 с |
| biz | дождаться RPC (`dialog.MaxBoxOpTime` 26 с) | 30 с | 40 с |
| media, dfs | дождаться RPC (загрузки дольше прерываются, клиент дозагрузит) | 20 с | 30 с |
| idgen, status, authsession | дождаться RPC | 5 с | 15 с |

Предел `Destroy` — константа каждого сервиса; у msg и sync он вычисляется из констант (`MaxBoxOpTime`, `StopRoundWait`, дедлайн сервера, закрытие группы, ожидание очередей). Юнит-тест проверяет для каждого сервиса `предел + 1 с (пауза Runner) + 5 с ≤ stop_grace_period` по `docker-compose.yaml`. Перезагрузку хоста описывает `docs/ops`: systemd ждёт остановки Docker не дольше `TimeoutStopSec` (по умолчанию 90 с), при меньшем запасе сервисы получат SIGKILL — данные целы.

e2e: `test/e2e/docker-compose.e2e.yaml` ставит всем сервисам `restart: "no"`, а `run.sh` после каждого теста проверяет, что ни один сервис не завершился (`compose ps --status exited`): падение валит тест, а не прячется за перезапуском. Chaos-тесты работают с политикой перезапуска по умолчанию.

### 9. Дедлайны RPC

`Timeout: 0` запрещён. `userbox.CheckRPCTimeout` больше не принимает 0 (заменяет таблицу времени ADR 0011, п. 2). **Правило:** дедлайн клиента не меньше максимального времени операции тех методов сервера, которые этот клиент вызывает. Тест конфигурации в `pkg/conf` читает все `teamgramd/etc*/*.yaml` (кроме `httpserver.yaml`: не собирается, задача 008) и проверяет: нет `Timeout: 0`; правило для каждой пары клиент → сервер по списку вызываемых методов; методы с `userbox.Run` определяются тем же статическим анализом, что и в п. 14 ADR 0011; цепочка ниже.

| Где | Сейчас | Станет | Почему |
|---|---|---|---|
| msg, сервер | 0 | 40 с | `PreBoxTime` 10 с (RPC до транзакции в контексте с этим пределом) + `MaxBoxOpTime` 26 с = 36 с; проверка при старте |
| bff → msg (`MsgClient`) | 0 | 45 с | не меньше сервера msg |
| biz, сервер; bff → biz | 30 с | 30 с | `dialog.MaxBoxOpTime` 26 с (без изменений) |
| msg → biz | 2 с по умолчанию | 5 с явно | msg вызывает только чтения: `user.getMutableUsers`, `user.getMutableUsersV2`, `user.blockedByUser`, `user.resolveUsername`, `username.resolveUsername`, `chat.getMutableChat`; ни один не выполняет `Run` |
| msg → idgen; sync → status; session → status | 2 с по умолчанию | 2 с явно | значение не должно зависеть от умолчаний go-zero |
| sync → chat | 2 с по умолчанию | 5 с явно | только `chat.getChatParticipantIdList` (чтение) |
| sync → session (push) | 2 с по умолчанию | 2 с явно | одна попытка; повторы и resync — пушер (п. 7) |
| media, dfs (серверы и `MiniHttp`), bff → media/dfs, media → dfs | 0 | 120 с | загрузка и обработка больших файлов (ffmpeg); проверяется e2e-загрузкой самого большого файла |
| bff, сервер | 0 | 150 с | не меньше любого вызова, который он делает |
| session → bff (`BFFProxyClients`) | 0 | 150 с | внешний предел запроса клиента |

Дедлайн, истёкший во время транзакции, откатывает её; истёкший после `COMMIT` (он не отменяется, ADR 0011) превращает успешный ответ в ошибку — повтор клиента с тем же `random_id` получит исходный ответ (п. 6). Kafka больше нет ни на одном пути RPC: push-и bff пишутся в `mq_outbox` (п. 4), relay и консьюмеры работают в своих циклах со своими пределами (`RoundTimeout`, паузы консьюмера).

### 11. Миграция, обновление, восстановление

**`teamgramd/deploy/sql/migrate-20261023-delivery.sql`** (по байтовому порядку после файлов 002; дата в имени — день реализации):

```sql
CREATE TABLE IF NOT EXISTS `mq_outbox` (...);   -- как в п. 1

-- Копии без связи с отправителем: dialog_message_id = 0 (ошибка idgen до 002, аудит №2).
-- −id уникален и не пересекается со snowflake (они положительны).
UPDATE `messages` SET `dialog_message_id` = -`id` WHERE `dialog_message_id` = 0;

-- Повторные копии одного сообщения у одного пользователя (повторная доставка, №6):
-- первая (меньший user_message_box_id) остаётся связанной, остальные отвязываются.
UPDATE `messages` m JOIN (
    SELECT user_id, dialog_message_id, MIN(user_message_box_id) AS keep_id
    FROM `messages` WHERE dialog_message_id > 0
    GROUP BY user_id, dialog_message_id HAVING COUNT(*) > 1) d
  ON m.user_id = d.user_id AND m.dialog_message_id = d.dialog_message_id AND m.user_message_box_id <> d.keep_id
SET m.dialog_message_id = -m.id;

-- Повторные исходящие с одним random_id (повтор клиента после окна Redis, №10): первая остаётся.
UPDATE `messages` m JOIN (
    SELECT user_id, random_id, MIN(user_message_box_id) AS keep_id
    FROM `messages` WHERE sender_user_id = user_id AND random_id <> 0
    GROUP BY user_id, random_id HAVING COUNT(*) > 1) d
  ON m.user_id = d.user_id AND m.random_id = d.random_id AND m.sender_user_id = m.user_id AND m.user_message_box_id <> d.keep_id
SET m.random_id = 0;

-- Колонки и индексы: каждый ALTER выполняется, только если его ещё нет
-- (проверка information_schema, PREPARE/EXECUTE).
ALTER TABLE `messages` ADD COLUMN `pts` int(11) NOT NULL DEFAULT '0', ALGORITHM = INSTANT;
ALTER TABLE `messages` ADD COLUMN `out_random_id` bigint(20)
  GENERATED ALWAYS AS (IF(`sender_user_id` = `user_id` AND `random_id` <> 0, `random_id`, NULL)) VIRTUAL;
ALTER TABLE `messages` ADD UNIQUE KEY `user_dialog_message` (`user_id`, `dialog_message_id`), ALGORITHM = INPLACE, LOCK = NONE;
ALTER TABLE `messages` ADD UNIQUE KEY `user_out_random` (`user_id`, `out_random_id`), ALGORITHM = INPLACE, LOCK = NONE;
```

- Повторы не удаляются, а отвязываются: клиенты, которые их уже показали, видят те же сообщения; правки и удаления отправителя дальше применяются к первой копии. Строки журнала не трогаются.
- Пустая база: таблица, колонки и индексы, `UPDATE` ничего не меняют. Повторный прогон: `UPDATE` ничего не находят, `ALTER` пропускаются.
- Время построения индексов на заполненной базе измеряет интеграционный тест миграции (строк в секунду), число записывается в `docs/ops`.

**Обновление** — одним окном вместе с 002 (002 без 003 не выкатывается), процедура `docs/ops/user-state.md` дополняется: закрыть вход (gnetway) → дождаться нулевого лага `Inbox-MainCommunity-S` и `Sync-MainCommunity-S` старой версией → остановить сервисы, резервная копия → миграции 002 и 003 → удалить группы (`kafka-consumer-groups.sh --delete --group` для обеих: иначе они хранят offset-ы старых партиций) → удалить `Inbox-T` и `Sync-T` (они пусты по лагу; число партиций меняется) → дождаться, пока топики исчезнут из `kafka-topics.sh --list` (удаление в KRaft асинхронное) → `topics.sh` → запустить сервисы.

**Откат на версию до 002** (ADR 0011, п. 11) дополняется шагом: перед остановкой дождаться, что в `mq_outbox` нет строк pending и published (relay и консьюмер доработали), и разобрать dead/parked. Старая версия таблицу не читает.

**Восстановление MySQL из резервной копии.** Таблица восстанавливается вместе с данными: pending и published строки копии будут опубликованы и применены, как и должны (у получателей в копии они не применены); published-строки relay сам переводит в pending при получении лидерства (п. 3). Копии в Kafka из потерянного после резервной копии периода несут `id`, которые восстановленный AUTO_INCREMENT выдал бы снова другим событиям. Поэтому до запуска сервисов: `pluma-admin state-raise` (ADR 0011) дополнительно поднимает AUTO_INCREMENT `mq_outbox` на 10⁹, а offset-ы обеих групп переводятся на конец (`kafka-consumer-groups.sh --reset-offsets --to-latest --execute`). Сверка топика, получателя и `created_at` в предпроверке (п. 5) — последняя страховка с алертом: устаревшая копия не применяется, тело события всё равно берётся из строки.

  - консьюмер прерван после commit транзакции получателя и до `MarkMessage` (хук) — после рестарта копия даёт `duplicate` без `Run`;
  - перебалансировка группы посреди потока (второй экземпляр входит и выходит) — ровно одна копия каждого события; перезапуск экземпляра со статическим членством — партиции снова у него не позже чем через 5 с;
  - копия со совпавшим `id` и старым `created_at` — `mismatch`, не применена;
  - рассылка 200 получателям с событием около 4 МиБ — транзакция проходит, раунд relay не больше 16 МиБ;
  - отправка с повтором `random_id`: два «устройства» параллельно — одно сообщение; повтор через час без Redis — ответ равен исходному (`pts`, `pts_count`, сообщение); тот же `random_id` в другом диалоге — `RANDOM_ID_DUPLICATE`; частичный повтор — `RANDOM_ID_DUPLICATE`;
- миграция `migrate-20261023-delivery.sql`: база «до» с копиями `dialog_message_id = 0`, повторными копиями и повторными `random_id` — отвязаны, индексы уникальны, колонка `pts` есть, повторный прогон ничего не меняет, пустая база проходит; скорость построения индексов печатается;
- sync на Kafka с фейковым сервером session: сервер перезапущен на том же порту — пуши продолжаются по порядку; sync остановлен без `Destroy` и запущен — неподтверждённые пуши пришли снова.

**e2e** (`make e2e`, стек compose, `pkg/mtclient`). `pkg/mtclient` получает переподключение (новая сессия, `new_session_created`), флаг `clear_draft`, повтор запроса с тем же `random_id` и `UpdatesState` — правила клиента Telegram: применить при `local + count = pts`, пропустить при меньшем, при дыре и `updatesTooLong` — `getDifference`; тесты проверяют итог по `UpdatesState`, как его увидел бы официальный клиент.
- **Порядок:** 5 отправителей × 200 сообщений одновременно одному Bob, Bob в сети. Пуши Bob-а идут строго по возрастанию: `pts` каждого = предыдущий + `pts_count`, ни одной дыры и ни одного `getDifference` за прогон; `getDifference` от начального состояния возвращает 1000 сообщений с непрерывными `pts`; сообщения каждого отправителя лежат в порядке отправки (номер в тексте растёт вместе с id). Печатается доля откладываний (`deferred` / `applied`).
- **Повтор отправки:** Alice отправляет сообщение и рвёт соединение, не прочитав ответ; переподключается и повторяет запрос с тем же `random_id` — ответ содержит `updateMessageID` и `updateNewMessage` с `pts` и `pts_count` строки журнала, по `UpdatesState` у Alice ровно одно сообщение, у Bob — одно.
- **Chaos** (`make e2e-chaos`, тег `chaos`, политика перезапуска по умолчанию; в CI — по расписанию раз в неделю и вручную, не на каждый push). После каждого сценария: у получателя ровно отправленные сообщения, по одному, в порядке каждого отправителя (`UpdatesState` после push-ей и `getDifference`); `pluma-admin verify-pts` без нарушений у всех; в `mq_outbox` нет строк через 5 с после затишья, dead/parked = 0; дубликатов `(user_id, dialog_message_id)` нет; от перезапуска msg или sync до первого применённого события — не больше 15 с.
  1. **kill обработчика посреди пачки:** Alice отправляет Bob-у 300 сообщений; когда лаг `Inbox-MainCommunity-S` > 50, `docker compose kill -s KILL msg`; Docker поднимает msg.
  2. **Kafka на паузе, kill msg и bff:** `docker compose pause kafka`; Alice отправляет 50 сообщений, часть с `clear_draft` — все ответы успешны, p99 ответа < 1 с; `docker compose kill -s KILL msg bff`, сервисы поднимаются без брокера; ещё 10 отправок успешны; `unpause kafka`.
  3. **рестарт Kafka:** отправки 2 в секунду 60 с; на 10-й секунде `docker compose restart kafka`; вариант — `stop` на 30 с и `start`. Все отправки успешны.
  4. **старт без Kafka:** `docker compose stop kafka`, затем перезапуск всех сервисов teamgram — стек поднимается, отправки успешны; `start kafka` — всё доставлено.
  5. **рестарт session:** Bob в сети; `docker compose kill -s KILL session` во время отправок; sync не перезапускается. После переподключения Bob получает пуши (регрессия залипания) и догоняет пропущенное.
  6. **рестарт sync:** `docker compose kill -s KILL sync` во время отправок.
  7. **рестарт MySQL:** `docker compose restart mysql` во время потока отправок; отправки, упавшие на время рестарта, клиент повторяет с тем же `random_id` — ни одной dead или parked строки, каждое сообщение одно.
  8. **SIGTERM всего стека** во время отправок (`docker compose stop`, затем `start`): каждый сервис останавливается в своём `stop_grace_period`, в логах msg — завершённый `Destroy` с длительностью не больше предела; вариант — то же при Kafka на паузе.
- **Задержка:** `TestSendLatency` (п. 12 ADR 0011) на хосте Linux, база — последний коммит без 003, прогоны чередуются. p50/p95 `messages.sendMessage`; p50/p95 задержки доставки (отправка → push у получателя) для личного чата и basic group из 20; `outbox_publish_delay_seconds`, `outbox_round_seconds` по фазам, `userbox_tx_seconds` (commit MySQL) и `mq_consumer_event_age_seconds` — чтобы было видно, сколько дают commit MySQL, раунд relay и запись в Kafka; доля откладываний. Критерий: `sendMessage` не хуже базы более чем на 20% (ожидается лучше: Kafka ушла из ответа); p95 доставки не хуже базы более чем на max(20%, 10 мс). Цифры — в бриф задачи.

## Последствия

- Событие не может потеряться между commit и Kafka: оно записано той же транзакцией. Применение у получателя ровно одно и атомарно с удалением строки; тело берётся из строки. Порядок по получателю держит не Kafka, а консьюмер по таблице, поэтому повторы relay, таймер, смена лидера, потеря тома или offset-ов Kafka, перебалансировка группы его не ломают. Мёртвое событие не теряется и не пропускается: получатель стоит до автоповтора или оператора, и это видно по алерту.
- Ответ отправки больше не ждёт Kafka; Redis ушёл с пути отправки целиком; Kafka ушла с пути RPC bff. Ни один сервис не зависит от Kafka при старте. Дубликаты `random_id` исключены базой, повтор получает исходный ответ.
- Временный сбой MySQL или Kafka задерживает доставку, но не паркует получателей. Пуши одного устройства идут по порядку, медленное устройство не задерживает другие, рестарт `session` больше не останавливает доставку до рестарта `sync`, потерянный push превращается в `updatesTooLong`, а не в тишину.
- Каждый процесс — свой сервис compose: SIGTERM доходит, упавший сервис перезапускает Docker, chaos-тесты убивают сервисы по одному.
- **Цена:**
  - на каждое inbox-событие: вставка в транзакции инициатора, `UPDATE` финишера, предпроверка, две точечные выборки и `DELETE` в транзакции получателя; на каждый push — вставка и `DELETE`; push-и bff — ещё вставка на пути RPC и до 50 мс опроса relay. Задержка доставки растёт на переход через relay дважды (замер, п. 12);
  - MySQL становится очередью, и отставание доставки — это строки `mq_outbox`: при долгой недоступности Kafka таблица растёт (алерт через 30 с);
  - запаркованный получатель не получает новые сообщения до автоповтора или действия оператора — сознательный выбор порядка против доступности для одного пользователя;
  - выкатка 002+003 пользователям ждёт доставки алертов из задачи 004;
  - миграция строит два уникальных индекса на `messages` и отвязывает исторические дубликаты.
- **Пересмотреть, если:**
  - p95 `outbox_publish_delay_seconds` устойчиво выше 50 мс (relay не успевает);
  - откладывания выводят p95 доставки за критерий п. 12 или их доля вдвое выше измеренной в 003: тогда короткая выдержка перед публикацией строк выше «дыры» в `id` (см. альтернативы);
  - Kafka остаётся главным источником эксплуатационных проблем: консьюмер может читать `mq_outbox` напрямую (вопрос ADR 0005, этап 2);
  - появляется второй хост (RF > 1, `min.insync.replicas` 2);
  - нужно больше одного экземпляра msg с разделением нагрузки relay.

## Рассмотренные альтернативы

- **Kafka — источник истины после ответа брокера** (строка outbox удаляется по подтверждению, у получателя таблица обработанных событий, DLQ-топик). Отклонено: с одной репликой гарантия держится только на fsync одного тома; таблице обработанных событий нужен срок хранения больше хранения топика и времени разбора DLQ; разморозка получателя после DLQ требует служебного сообщения в том же топике, чтобы не обогнать новые события. Строка outbox даёт то же одной таблицей и без зависимости от тома Kafka.
- **DLQ-топик в Kafka.** Отклонено: срок хранения, нет выборки по получателю, повтор по порядку нужно координировать с новыми событиями. Мёртвая строка `mq_outbox` хранит всё нужное, а повтор — это смена состояния, порядок даёт `id`.
- **Только естественные ключи** (`UNIQUE (user_id, dialog_message_id)`). Отклонено: правка и закреп при повторе журналируются второй раз (п. 6). Ключ остаётся страховкой и индексом.
- **Транзакции Kafka (exactly-once продюсер, `read_committed`).** Отклонено: консьюмер пишет в MySQL, а не в Kafka, поэтому дедупликация у получателя нужна всё равно; transactional id и fencing добавляют сложность без выигрыша.
- **Тело inbox-события из копии в Kafka.** Отклонено: при переиспользовании `id` (пересоздание таблицы, неполное восстановление) устаревшая копия применила бы свои данные и удалила строку нового события. Тело берётся из строки, копия — только сигнал, поэтому её тело пустое.
- **Поле `tracked`, которое задаёт вызывающий код, с `CHECK` на соответствие топику.** Отклонено: ошибка одного производителя превращала бы inbox-событие в тихую потерю, а `CHECK` с именами топиков связал бы схему с конфигурацией. Класс — свойство топика в реестре `pkg/outbox`, поля нет.
- **Relay с курсором `id > последний`.** Отклонено: AUTO_INCREMENT выделяется при вставке, а не при commit; строка с меньшим `id`, закоммиченная позже курсора, была бы пропущена навсегда.
- **Несколько relay с `SKIP LOCKED`.** Отклонено: строки одного получателя публиковались бы параллельно.
- **Отправлять по одному сообщению на партицию за раз**, чтобы исключить перестановку при частичном отказе. Отклонено: корректность уже держит консьюмер, а перестановка возможна только при ошибке брокера; пакетная отправка дешевле на группах.
- **Отдельная полоса relay на каждый топик**, чтобы `Sync-T` не ждал `Inbox-T`. Отклонено: без принудительного fsync и с финишером вне раунда push-и не ждут записи на диск; один запрос к брокеру за раунд несёт оба топика.
- **Выдержка 20–50 мс перед публикацией строк выше «дыры» в `id`**, чтобы реже откладывать. Отклонено до замера: откладывание стоит примерно один раунд relay и касается только полосы одного получателя, а выдержка задерживала бы всех получателей при каждой дыре, включая вечные дыры от откатов. Условие пересмотра — в «Последствиях».
- **`flush.messages=1` у `Inbox-T`.** Отклонено: долговечность держит строка `mq_outbox`, а fsync на каждую запись удлиняет каждый раунд.
- **Таймер повторной доставки только по возрасту строки.** Отклонено: при остановленной партиции он перепубликовал бы весь хвост, дописывая копии в ту же партицию, и поднимал бы алерт без потери. Таймер сверяет место копии с offset-ом группы и границами лога.
- **Relay не стартует без топиков; `Emit` отклоняет топики, которых нет в Kafka.** Отклонено: отправка зависела бы от брокера. `Emit` проверяет реестр конфигурации, существование в Kafka — это готовность топика у relay; строки неготового топика ждут, остальные публикуются.
- **Асинхронный продюсер bff с ограниченным буфером или вызов sync по RPC.** Отклонено: оба теряют push-и при сбое Kafka или рестарте sync, у RPC-пути порядок относительно пушей из Kafka не определён. Вставка в `mq_outbox` долговечна, упорядочена и не держит RPC.
- **Блокировать партицию на любой ошибке без DLQ.** Отклонено: одно сломанное событие останавливает всех пользователей партиции. Парковка изолирует одного получателя.
- **Белый список временных ошибок** (первая редакция этого ADR). Отклонено: неизвестная ошибка уводила в dead, и перезапуск MySQL парковал бы каждого активного получателя. Временным считается всё, кроме закрытого списка детерминированных ошибок.
- **Ограничить число повторов временных ошибок и уводить в DLQ.** Отклонено: минутная недоступность MySQL запарковала бы всех получателей.
- **Повторять детерминированные ошибки не меньше 10 мин подряд перед dead.** Отклонено: партиция (1/16 пользователей) стояла бы 10 мин на ошибке кода. Тот же разнос попыток во времени даёт автоповтор полосы (15 мин → 4 ч), не останавливая других.
- **Консьюмер читает `mq_outbox` напрямую, без Kafka.** Технически проще для inbox, но противоречит ADR 0005 и потребовал бы своего распределения получателей между экземплярами; `Sync-T` всё равно идёт через Kafka. Вернуться на этапе 2 новым ADR.
- **Отдельная таблица `random_id` отправителя.** Отклонено: дублирует `messages` и требует срока хранения; генерируемая колонка с уникальным индексом обходится без новых записей.
- **Оставить окно Redis рядом с постоянной дедупликацией.** Отклонено: два пути для одной гарантии.
- **Ответ на полный повтор `random_id`: `RANDOM_ID_DUPLICATE` или `updateNewMessage` с текущим `pts` и `pts_count = 0`.** Отклонено: ошибку все четыре клиента показывают как неотправленное сообщение, а синтетическую форму Telegram не присылает, и её обработка клиентами не определена. Исходный ответ из журнала — то, что клиент получил бы без обрыва.
- **Сбрасывать флаг `unavailable` по таймеру или проверке здоровья.** Отклонено: gRPC сам переподключается; флаг заменяется паузой узла с пределом и resync.
- **Воркер `hash % 16` на узел с повторами внутри воркера.** Отклонено: одно медленное устройство останавливало бы 1/16 устройств узла вместе с их `updatesTooLong`. Очередь на устройство изолирует его.
- **`Unavailable` для ошибок authsession в session.** Отклонено: `Unavailable` ставит на паузу весь узел, а ошибка authsession касается одного ключа — `FailedPrecondition`.
- **Не отмечать offset push-а с resync до `updatesTooLong` без предела.** Отклонено: зависшее устройство остановило бы offset партиции. Предел 30 с.
- **`StreamingSession`.** Отклонено: нет подтверждений доставки, поток не переподключается.
- **Супервизор в контейнере** (скрипт на bash или s6-overlay). Отклонено: временное решение или сторонний init в образе ради схемы, которую задача 004 всё равно заменяет сервисами compose. Разнесение по сервисам перенесено в 003.
- **`proc.SetTimeToForceQuit` как граница остановки.** Отклонено: с `commands.Runner` повторный SIGTERM перехватывается. Граница — `stop_grace_period`.
- **msg → biz 30 с.** Отклонено: msg вызывает только чтения; правило п. 9 сверяет дедлайн с методами, которые клиент вызывает.
- **kafka-exporter для лага.** Отклонено в 003: лаг со стороны брокера считает admin-клиент relay, отдельный контейнер не нужен. Задача 004 может заменить при переходе на свой стек наблюдаемости.
- **Глобальное имя `GET_LOCK('mq_outbox_relay')`.** Отклонено: блокировка общая на сервер MySQL, вторая база на нём осталась бы без relay.

## Вне рамок 003

- Пуши без `pts` (bff, `seq`, `pushRpcResult`) не журналируются, `getDifference` их не восстанавливает — задача 010 (журнал `seq`: ADR 0020).
- Проверки здоровья по сервисам, Alertmanager (условие выкатки 002+003), Loki — задача 004.
- Уведомления на выключенные устройства (APNs, FCM) — задача 009.
- Потребитель `BotSync` (шлюз ботов) в репозитории отсутствует.
- Высокая доступность Kafka и MySQL.
