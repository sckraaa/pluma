# 0029. Наборы стикеров из Telegram по запросу через бота; установленные наборы аккаунта в журнале seq

- Статус: proposed (2026-11-02).
- Задача: 030. Исследование: `docs/tasks/030-research/`. Продолжает ADR 0028 (каталог).

## Контекст
- Каталог (ADR 0028) содержит только наборы, на которые ссылаются общие ответы Telegram. Владелец хочет (2026-11-02), чтобы любой набор открывался в Pluma по ссылке `t.me/addstickers/<имя>` или `t.me/addemoji/<имя>`. Сервер должен брать его у Telegram при первом запросе и пополнять свою базу.
- Клиенты сами разбирают такие ссылки и вызывают `messages.getStickerSet(inputStickerSetShortName)`.
- Боты могут вызывать `messages.getStickerSet` и `upload.getFile`. Это указано на страницах core.telegram.org этих методов («Both users and bots can use this method», проверено 2026-11-02). Вход бота — `auth.importBotAuthorization`, без телефона; аккаунты владельца не участвуют.
- Без своего списка наборов у аккаунта кнопка «Добавить» ничего не сохраняет. Ответы клиентов на эти методы и обновления разобраны по исходникам в `docs/tasks/030-research/` (проверка — `check.md`).

## Решение
1. **Клиент бота на сервере — `pkg/tgbot`.**
   - Вход ботом, переход на DC бота (`USER_MIGRATE_X`), адреса DC из `help.getConfig`.
   - Для файлов на других DC — перенос авторизации (`auth.exportAuthorization` / `importAuthorization`), `FILE_MIGRATE_X`.
   - `FLOOD_WAIT` выжидается в пределах срока запроса.
   - Настройки — `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_BOT_TOKEN` из `.env`. Если они пустые, бот выключен и сервер ведёт себя как раньше.
2. **Получение по запросу — `pkg/catalog/demand`, только по короткому имени.**
   - Набора нет в каталоге → бот берёт его и файлы, импорт идёт путём ADR 0028 (`importer.ImportSet`: перенумерация, `catalog_ids`, `dfs/media.importDocument`).
   - Одна загрузка на имя (singleflight). «Нет такого набора» запоминается на час.
   - Лимиты: до 200 документов в наборе, файл до 10 МиБ, набор до 64 МиБ, 8 параллельных загрузок, 90 с на набор.
   - Хранение рядом с каталогом с `source = 'demand'`. Новый импорт каталога удаляет только `source = 'catalog'`.
3. **Установленные наборы аккаунта — таблица `user_sticker_sets`, пакет `pkg/catalog/installed`.**
   - Три вида (стикеры, маски, эмодзи), у каждого свой порядок. Архивные наборы хранятся отдельно, последний архивированный — первым.
   - Списки `getAllStickers` / `getMaskStickers` / `getEmojiStickers`: у каждого набора `installed_date`, флага `archived` нет. Хэш считается по формуле клиентов (Android `calcStickersHash`, tdesktop `CountStickersOrderHash`). `NotModified` отдаётся только для ненулевого совпавшего хэша.
   - Автоархивации нет: `installStickerSet` всегда отвечает `Success`. Операции идемпотентны. Порядок нормализуется до установленных наборов вида.
4. **Другие устройства аккаунта получают изменения с seq (ADR 0020), кроме устройства, сделавшего изменение (ADR 0022).**
   - Установка → `updateNewStickerSet` (набор целиком, с `installed_date`).
   - Удаление и архивация → `updateStickerSets` (перезагрузить вид).
   - Новый порядок → `updateStickerSetsOrder` с полным сохранённым порядком.
   - Все три добавлены в `userbox.SeqUpdate`. `getDifference` отдаёт непрерывный хвост журнала по порядку. Установка поднимает набор наверх, порядок задаётся целиком, остальное — перезагрузка. Поэтому повтор хвоста приводит к тому же итогу, даже если часть его устройство уже применило.

## Последствия
- Любой набор Telegram доступен по ссылке. Первый запрос ждёт загрузку (секунды), повторный идёт из базы.
- В журнале seq лежит `updateNewStickerSet` целиком (до 200 документов). Это укладывается в лимит события 4 МБ.
- Android молча игнорирует `updateNewStickerSet` для набора, который знает только по просмотру. Он увидит установку при следующей загрузке по хэшу. Это ограничение клиента (`030-research/check.md`).
- Ошибка хранилища в `getAll*` отдаётся клиенту, и Android повторит запрос через секунду. Другого ответа без списка нет.
- `STICKERSET_INVALID` остаётся 400, как в `getStickerSet`; в документации Telegram — 406. Не проверено вживую.
- Вне решения: поиск наборов (`searchStickerSets`), `updateMoveStickerSetToTop` при отправке с `update_stickersets_order`. Порядок на сервере может разойтись с клиентом, который сам поднял набор после отправки: это стоит одной лишней перезагрузки.
