# 0031. Приватность: один вычислитель правил, членство и контакты — от сервиса пользователей

- Статус: proposed (2026-11-03).
- Задача: 034. Исследование: `docs/tasks/034-research/` (`server.md`, `clients.md`, `schema.md`, сверка `check.md`).

## Контекст
- В сервере было два вычислителя правил приватности с разной логикой (`privacyIsAllow` и `CheckPrivacyIsAllow`).
  - Первый на любом правиле «участники чата» отвечал «можно». Android всегда шлёт пустое правило-чат рядом с исключениями-пользователями (`PrivacyControlActivity.java:1072-1126`), поэтому «Никто, кроме B» открывал фото, телефон и статус всем.
  - Второй в большинстве вызовов получал проверку членства «всегда нет». «Все, кроме участников группы X» не работало.
- Результат зависел от порядка правил. Клиенты шлют его по-разному: Android, iOS и tdesktop — исключения, потом базовое правило; Web K — наоборот (`check.md` п. 16-27).
- При отсутствии правил ключа ответ был «можно». Кэш пользователя нёс правила только статуса, фото и телефона; остальные ключи читались в обработчиках отдельно или не проверялись вовсе.
- Найдены утечки: `userFull.profile_photo`, `userFull.about`, `photos.getUserPhotos`, `users.getSavedMusic(ByID)` — последний отдавал любой документ по id.

## Решение
1. **Один вычислитель — `mtproto.EvaluatePrivacy`** (proto, `privacy_rule_helper.go`, `// pluma:`). Результат не зависит от порядка правил, побеждает более частное правило:
   1. зритель в `DisallowUsers` — нет, в `AllowUsers` — да;
   2. зритель — участник чата из `DisallowChatParticipants` — нет, из `AllowChatParticipants` — да (пустые списки не считаются);
   3. боты: `DisallowBots` — нет, `AllowBots` — да;
   4. `AllowPremium` и у зрителя Premium — да;
   5. `DisallowContacts` и зритель — контакт — нет;
   6. базовое правило: `AllowAll` — да, `AllowContacts` — да для контакта, иначе нет.
   - При нескольких базовых правилах считается самое открытое — так их показывают Android и iOS. Нет базового правила — «никто».
   - `AllowCloseFriends` относится только к историям и здесь не действует.
   - Приоритет между «разрешённый пользователь» и «запрещённый чат» не описан в документации и не сверен с Telegram. Выбран более частный.
2. **Закрыто при сбое.**
   - Нет правил ключа — никому, кроме владельца.
   - Неразрешённое правило-чат (членство неизвестно): разрешающее не срабатывает, запрещающее срабатывает.
   - Ошибка чтения правил — ошибка запроса, а не «можно».
3. **Данные для вычислителя готовит сервис пользователей.**
   - Кэш пользователя (`user_data.4`) несёт правила всех 14 ключей.
   - Загрузчики `ImmutableUser` для заданных зрителей (`To`):
     - подгружают строки контактов «владелец → зритель»;
     - раскрывают правила-чаты в список зрителей — участников живых базовых групп (`resolvePrivacyChats`, `mtproto.ResolvePrivacyChats`, внутренние предикаты `pluma_privacyValue*ChatMembers`; клиентам и в хранилище они не попадают).
   - Сервисы, которые показывают пользователя, решают через `ImmutableUser.CheckPrivacyFor(key, viewer)` — с Premium и признаком бота зрителя.
   - Сервис сообщений готовит пользователей групповых сообщений для всех участников группы.
4. **Статус** — `ImmutableUser.StatusFor(viewer)`. Точное время видно, если правило владельца разрешает зрителю, и правило зрителя разрешает владельцу или у зрителя Premium. Если мешает только своё правило зрителя — округлённый статус с `by_me` (core.telegram.org/constructor/privacyKeyStatusTimestamp).
5. **Хранение правил (`account.setPrivacy`).**
   - Пустые исключения отбрасываются. Базовое правило ровно одно: самое открытое из присланных, `DisallowAll`, если не прислано ни одного.
   - `AllowCloseFriends` — `PRIVACY_VALUE_INVALID`. Больше 1000 пользователей и чатов — `PRIVACY_TOO_LONG`.
   - Ограничить голосовые без Premium — `PREMIUM_ACCOUNT_REQUIRED`: tdesktop показывает на это предложение Premium (`api_user_privacy.cpp:282-286`).
   - `account.getPrivacy` при ошибке отвечает ошибкой, а не умолчанием.
6. **Где применяется:**
   - `user.phone`, `user.photo`, `user.status` всех выдач;
   - `userFull`: `about`, `profile_photo`, день рождения, `saved_music`, `voice_messages_forbidden`, `phone_calls_private`, `read_dates_private`;
   - `photos.getUserPhotos` (пустой альбом), `users.getSavedMusic(ByID)` (только свой список и только если видно);
   - поиск по номеру: `contacts.resolvePhone` и `contacts.search` — по правилу «кто найдёт по номеру» владельца номера;
   - приглашения: `createChat` — `missing_invitees` (с `premium_would_allow_invite`), `addChatUser` — 403 `USER_PRIVACY_RESTRICTED`;
   - пересылка: ссылка на автора по правилу `Forwards` с Premium пересылающего;
   - голосовые и кружки: `VOICE_MESSAGES_FORBIDDEN` (400 при отправке, 403 при пересылке, по core.telegram.org);
   - `getOutboxReadDate` с `hide_read_marks`: `USER_PRIVACY_RESTRICTED` и `YOUR_PRIVACY_RESTRICTED` (вызывающий скрывает своё и без Premium);
   - дни рождения контактов (членство в чатах), рассылка статуса (ADR 0030).
7. **Глобальные настройки.** `account.setGlobalPrivacySettings` отвечает сохранённым, а не эхом запроса: настройки отсутствующих в Pluma функций (платные сообщения, подарки) не хранятся и не показываются сохранёнными.

## Последствия
- Правила одинаковы на всех путях. Тесты вычислителя проверяют каждую перестановку правил.
- Каждый `ImmutableUser` несёт правила 14 ключей: несколько сотен байт на пользователя во внутренних ответах. Для 100 пользователей это незаметно.
- Запрос членства в группах выполняется, только если у показываемого пользователя есть правила-чаты.

## Открытые вопросы (сверка с Telegram, `reference-telegram-probe`)
- Приоритет «разрешённый пользователь против запрещённого чата» и наоборот.
- `createChat`, когда отказали все приглашённые: сейчас `USERS_TOO_FEW`.
- Скрываются ли фото, статус и телефон при блокировке.
- `read_dates_private`: для конкретного зрителя (так сделано, по тексту Android `HideReadTimeInfo`) или для всех.
- Пересылка: правило оценивается для пересылающего в момент пересылки, а не для каждого читателя.
- Фото «для всех» (`fallback`) и личное фото контакта не реализованы: отдельная задача.
