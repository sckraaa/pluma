# 0017. Push-уведомления: отдельный сервис на потоке Sync-T, только зашифрованные push

- Статус: accepted
- Дата: 2026-10-25
- Задача 009. Опирается на ADR 0012 (Sync-T — push-класс, доставка не транзакционна) и ADR 0003 (ключи вне БД в открытом виде не лежат).

## Контекст
- **Код.** `account.registerDevice`, `unregisterDevice`, `updateDeviceLocked` — заглушки апстрима (`app/bff/notification`). Отправителя push нет. Таблица `devices` в схеме есть, кодом не используется.
- **Что `sync` уже умеет.** Он раскладывает апдейты пользователя по его онлайн-сессиям (`app/messenger/sync`). Какие апдейты заслуживают push, решает `processUpdates`: новое сообщение, правка, удаление, прочтение, входящий звонок. Флаг доходит только до MTProto-сессии push Android (token_type 7), которую Android сам не регистрирует.
- **Что ждут клиенты** (DrKLO/Telegram 12.9.1, Telegram-iOS, Web K; проверено по коду):
  - **Регистрация.** Android и iOS регистрируют токен с 256-байтовым `secret` и шифруют push всегда; Android незашифрованный push не принимает.
  - **Шифрование.** MTProto 2.0 «сервер → клиент» с `auth_key = secret`, `key_id = SHA1(secret)[12:20]`. Результат — поле `p` (base64url).
  - **Содержимое.** Android рисует текст сам из `loc_key`/`loc_args`/`custom`. iOS показывает уже готовый текст из `aps.alert`, который сервер локализует сам, а id передаются строками.
  - **VoIP.** VoIP-push без входящего звонка iOS наказывает.
  - **Выход.** При выходе клиенты не снимают регистрацию надёжно.

## Решение
1. **Отдельный сервис `push`** (`app/messenger/push`) читает `Sync-T` своей группой консьюмеров, независимо от `sync`.
   - Медленные APNs/FCM не задерживают доставку онлайн-устройствам.
   - Ключи APNs и FCM есть только в контейнере `push`.
   - Порядок по получателю даёт партиция Kafka.
2. **Доставка best effort**, как у Telegram.
   - Неотправленный push не повторяется после дедлайна: устройство догоняет через `getDifference`, когда откроется.
   - Отказ провайдера не держит партицию: у события общий дедлайн, повторы только внутри него.
3. **Только зашифрованные push.**
   - APNs и FCM видят лишь `p` и общий текст-заглушку.
   - Для token_type 1, 2, 9 `secret` обязателен.
   - `secret` хранится запечатанным AES-256-GCM на отдельном ключе `PUSH_SECRET_ENCRYPTION_KEY` из `.env`, AAD — устройство. Ключ есть у bff (регистрация) и у `push` (отправка). `AUTH_KEY_ENCRYPTION_KEY` остаётся только у authsession: bff не должен уметь открыть ключи сессий.
4. **Кому push.** Всем зарегистрированным устройствам получателя, кроме:
   - авторизации, которая сама сделала действие;
   - авторизаций с живой сессией в `status`: они получат апдейт по соединению.
   Служебные push (прочтение, удаление) — другим устройствам того же пользователя, без видимого уведомления.
5. **Устройство привязано к авторизации.**
   - Выход, сброс и `destroy_auth_key` удаляют её устройства.
   - Удалённо завершённой авторизации сначала уходит `SESSION_REVOKE`.
   - Перед отправкой сервис проверяет, что ключ ещё принадлежит пользователю: это ловит пропущенные пути удаления.
6. **Текст для iOS рисует сервер** на языке авторизации (`lang_code` из `initConnection`, шаблоны ru и en). Android и Web получают `loc_key`/`loc_args`, как у Telegram.
7. **Без доставки, пока нет функции.** VoIP-токены (9) и Web push (10) хранятся, но не используются. VoIP-push появится вместе со звонками (ADR 0004), Web push — с раздачей Web K по TLS.

## Последствия
- В compose появляется сервис `push`, в `.env` — пути к ключам APNs и FCM. Без ключей сервис работает, но провайдер выключен (лог и метрика).
- Онлайн-сессия по `status` гасит push. Если соединение оборвалось, а сервер ещё считает сессию живой (до 60 с), push не уйдёт. Android покажет сообщение после переподключения, iOS — нет. Если на устройствах это заметно, пересмотреть правило (например, учитывать время последнего запроса).
- Push не переживают сбой `push` между чтением и отправкой — это осознанная плата за простоту (п. 2).

## Рассмотренные альтернативы
- **Отправка из `sync`.** Отвергнута: медленный провайдер задержал бы онлайн-доставку, а ключи APNs/FCM оказались бы в общем процессе.
- **Outbox-строка на каждый push с повторами** (как inbox). Отвергнута: опоздавший push хуже потерянного, а точность обеспечивает `getDifference`.
- **Незашифрованные push.** Отвергнуты: текст переписки проходил бы через Apple и Google, а Android их не принимает.
- **UnifiedPush/ntfy для Android без Google.** Отложено: официальный клиент его не поддерживает, нужен патч.
