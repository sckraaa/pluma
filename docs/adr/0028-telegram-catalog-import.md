# 0028. Каталог из Telegram: выгрузка через открытую сессию Web K, перенумерация, хранение как ответы методов

- Статус: proposed (2026-11-02). Канал выгрузки и id, прописанные в клиентах, — решения на подтверждение владельцем.
- Задача: 024. Исследование: `docs/tasks/024-research/`.

## Контекст
- У Telegram есть общие для всех данные, которых у Pluma нет: реакции, эффекты, стикеры и наборы эмодзи, подсказки эмодзи, цвета имени и профиля, темы, обои, списки эмодзи по умолчанию, часовые пояса. Таблица методов и эталонные количества — в брифе 024.
- Сейчас эти методы отвечают заглушкой `ERR_ENTERPRISE_IS_BLOCKED` или пустым ответом прокси. Клиенты повторяют часть запросов часто: Android при ошибке и `hash = 0` — каждую секунду (`docs/tasks/024-research/critique.md`, п. A.4).
- Решения владельца (2026-10-30): выгрузить всё с серверов Telegram; id документов и наборов перенумеровать, id Telegram не хранить.
- Ни сторонний вход на запасной аккаунт (задача 019: сброс ключа), ни свой клиент MTProto с входом не нужны. Во встроенном браузере открыта сессия Web K запасного аккаунта, и её `invokeApi` вызывает любые методы (`collect.md`, п. 1).
- **Проверено 2026-11-02:** встроенный браузер (Chromium 152) молча блокирует запросы с web.telegram.org на `http://127.0.0.1`, окна разрешения нет. Локальный приёмник на Mac не годится.

## Решение
1. **Выгрузка — скриптом в открытой сессии Web K.**
   - Только методы чтения и `upload.getFile`, с `noErrorBox` (иначе 401 разлогинит, `collect.md`).
   - Без преобразований tweb: сырой `upload.getFile` частями по 1 МиБ.
   - Метаданные идут по одному запросу с паузой, файлы — не больше 4 запросов на DC.
   - Остановка на `FLOOD_WAIT` дольше 120 с, на 401/406 и на ошибках ключа или сессии.
   - Запуск не чаще раза в сутки и только по команде.
2. **Приёмник — временный, на сервере Pluma, по HTTPS** (решение на подтверждение).
   - Маршрут `https://pluma.chat/collect/…` в Caddy ведёт на сервис `pluma-admin catalog receive`.
   - Сервис принимает только с `Origin: https://web.telegram.org` и одноразовым токеном, пишет выгрузку в `/opt/pluma/catalog/<run>/`.
   - Выгрузка оказывается там, где её импортируют; по Mac гигабайты не гоняются.
   - После выгрузки сервис останавливается, маршрут закрыт.
   - Запасной вариант — Chrome владельца через расширение: Chrome 142+ спрашивает разрешение на доступ к локальной сети, тогда подходит приёмник на Mac.
3. **Формат выгрузки.**
   - Ответы методов как есть, в JSON tweb: предикат в `_`, `long` — число или строка, байты — `{"$b64": …}`.
   - Файлы лежат по ключу (id документа Telegram, тип миниатюры), плюс манифест.
   - Выгрузка удаляется после импорта: в ней `access_hash` и `file_reference` аккаунта.
4. **Импорт — `pluma-admin catalog import <каталог>`.**
   - Каждый объект проверяется по схеме слоя 228; неизвестный предикат останавливает импорт.
   - Наборам и документам выдаются id Pluma. Все ссылки внутри данных переписываются по одной таблице соответствий (полный перечень мест — `critique.md`, C.2).
   - Ссылка на документ, которого нет в выгрузке, — ошибка импорта, а не висячий id.
   - Повторный импорт идемпотентен: файл узнаётся по sha256 и получает прежний id Pluma.
5. **Документы — новым путём dfs/media.**
   - `dfs.importDocument` и `media.importDocument` сохраняют главный файл, а миниатюры берут как есть: `i` и `j` встроенные, `m` webp, видео-миниатюры `f`/`u`/`v`.
   - Атрибуты (`documentAttributeSticker`/`CustomEmoji` со ссылкой на набор, `ImageSize`, `Video`, `Animated`, `Filename`) сохраняются без изменений.
   - `access_hash` = тип хранения << 32 | случайные 32 бита, как в `dfs.uploadDocumentFileV2`, иначе `upload.getFile` отдаст не тот тип файла.
   - Существующие пути загрузки миниатюры теряют (`server.md`, п. 2).
6. **Хранение каталога.**
   - Ответы методов хранятся готовыми: protobuf `mtproto` уже с id Pluma, по ключу «метод + параметр» (язык подсказок, формат тем, имя набора). Отдельная таблица наборов стикеров — по id и `short_name`.
   - Новая версия каталога пишется рядом и включается одним переключением, поэтому полуимпорт никогда не отдаётся.
7. **Хэши.**
   - Считаются по нашим id алгоритмом core.telegram.org/api/offsets (int или long — как у метода).
   - На `hash = 0` и на несовпадение — полный ответ, `NotModified` — только при совпадении.
   - `getAllStickers` и `getFeatured*` не отвечают ошибкой: Android повторяет её в цикле.
8. **Имена и слаги не перенумеровываются.** `short_name` наборов (`EmojiAnimations` и т. п.) и `slug` обоев — имена, а не id; клиенты ищут по ним.
9. **id Telegram, прописанные в клиентах** (tweb, Android — `critique.md`, B) — решение на подтверждение. Варианты: оставить у этих нескольких документов их id Telegram; поправить клиентов; принять потерю этих мест.
10. **Обработчики.**
    - 12 служб (RPCReactions, RPCStickers, RPCCustomEmojis, RPCEmoji, RPCEmojiCategories, RPCEmojiStatus, RPCAccentColors, RPCThemes, RPCWallpapers, RPCTimezones, RPCMessageEffects, RPCSavedMessageTags) регистрируются в bff и маршрутизируются в трёх `session.yaml`.
    - Подмены из `fake_rpc_result.go` удаляются.
    - Методы этих служб, которые не обслуживаются, отвечают `ErrEnterpriseIsBlocked`.
    - Обложки наборов (`inputStickerSetThumb`) получают настоящий `ThumbFilesPlugin`.

## Последствия
- Стикеры, реакции и эмодзи появляются во всех клиентах сразу, без правок клиентов.
- Хранение реакций на сообщениях и установленных наборов пользователей — этап 2. До него `getAllStickers` отвечает пустым списком с `hash = 0`.
- Обновление с Telegram — тем же путём по команде; изменённые наборы сопоставляются по `short_name`; документы, исчезнувшие у Telegram, остаются, потому что на них ссылаются сообщения.
