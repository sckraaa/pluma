# 0013. Наблюдаемость, алерты на телефон, бэкапы

- Статус: accepted
- Дата: 2026-10-23

## Контекст
Выкатка 002+003 пользователям ждёт доставки алертов (ADR 0012, п. 10). Владелец хочет пуши на телефон, не зависящие ни от Pluma, ни от Telegram. Сервер не может сообщить о собственной смерти. Логи шли через Filebeat → Kafka → go-stash → Elasticsearch (≈3 ГБ памяти, без гарантий для сообщений). Образы мониторинга устарели (Prometheus 2.28, Grafana 8 — 2021 год). Бэкапов нет; копии на том же сервере не спасают при его потере.

## Решение
**Алерты.**
- Prometheus → Alertmanager → `alertpush` (`app/ops/alertpush`, только стандартная библиотека Go) → ntfy → приложение ntfy на телефоне. Тема ntfy — длинная случайная строка (`NTFY_TOPIC`), сервер по умолчанию ntfy.sh, можно свой (`NTFY_URL`, `NTFY_TOKEN`). Приоритеты: critical → срочный (5), warning → высокий (4), «починилось» → тихий (2).
- **Датчик жизни.** Постоянно горящий алерт `Watchdog` раз в минуту пингует проверку на healthchecks.io (`HEALTHCHECKS_PING_URL`). Если пинги прекратились (умер хост, Prometheus или Alertmanager), healthchecks.io сам шлёт пуш в ту же тему ntfy. Ни один путь не проходит через Pluma или Telegram.
- Правила: доставка (`delivery.yml`, ADR 0012) и хост/сервисы/бэкапы (`general.yml`): сервис не отвечает, цикл перезапусков, доля серверных ошибок RPC, диск, память, нет свежего бэкапа, не прошла проверка восстановления. Подавление: упавшая Kafka или сервис гасят производные алерты.

**Метрики и дашборды.** Prometheus 3, node-exporter, Grafana 13 с заранее подключёнными источниками и дашбордом «Pluma overview» (сервисы, RPC, доставка, пуши, хост, бэкапы, ошибки в логах). Все образы закреплены по тегу и digest. Данные — в именованных томах.

**Логи.** Elasticsearch, Kibana, Filebeat, go-stash и топик `teamgram-log` удалены. Grafana Alloy читает stdout контейнеров сети `teamgram_net` через Docker API и пишет в Loki (диск, 14 дней). Сервисы пишут JSON без ключей, кодов и текста сообщений (`tools/logaudit`). Jaeger хранит трассы в памяти (последние 50000).

**Процессы.** Каждый сервис — свой сервис compose (ADR 0012, п. 8) с проверкой здоровья (подключение к своему порту) и стартом по цепочке только после того, как предыдущий здоров.

**Бэкапы.** restic, зашифрованные на сервере, в S3-совместимое хранилище вне сервера (Cloudflare R2 или Backblaze B2): ежедневно дамп MySQL (согласованный, `--single-transaction`) и объектное хранилище файлов; раз в неделю — автоматическое восстановление дампа в отдельный MySQL и проверка (`docs/ops/backup.md`). Метрики успеха — через textfile-коллектор node-exporter, алерты `BackupMissing` и `RestoreCheckFailed`.

## Последствия
- Без `NTFY_TOPIC` и `HEALTHCHECKS_PING_URL` стек мониторинга не запускается: выкатка без алертов невозможна по построению.
- Внешние зависимости — ntfy.sh и healthchecks.io (бесплатные тарифы) и S3-хранилище; содержимое алертов — только названия и краткие описания, без данных пользователей; бэкапы зашифрованы ключом, который есть только у владельца.
- Ключ шифрования бэкапов (`RESTIC_PASSWORD`) нужно хранить вне сервера: без него восстановление невозможно.

## Рассмотренные альтернативы
- Telegram-бот — владелец отказался: уведомления не должны зависеть от Telegram.
- Pushover (critical alerts на iOS) — платный; выбран ntfy.
- Свои APNs/FCM в приложение Pluma — нужна своя рассылка вне сервера и готовые клиенты; не сейчас.
- Alertmanager → ntfy напрямую по шаблонам ntfy — зависимость от формата стороннего сервера; мост на 150 строк проще проверять тестами.
- Promtail — устарел, заменён Alloy.
