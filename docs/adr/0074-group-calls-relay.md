# 0074. Групповые звонки из России: труба медиа на узле amf, адреса SFU по стране клиента

- Статус: proposed (2026-11-20). Реализовано в задаче 116; решения 1–6 брифа ждут подтверждения владельца. Направление — решение владельца 2026-11-20: россияне ходят в групповые звонки через amf, как в обычные.
- Задача: 116 (`docs/tasks/116-group-calls-through-ru-node.md`).
- Связано: ADR 0059 §3 (публичные адреса SFU, «труба» перед узлом уже допускалась), ADR 0060 (сквозное шифрование звонков), ADR 0072 §8 (роли узла amf), ADR 0073 (страна клиента за краями).

## Контекст
- SFU стоит на краю Hetzner (195.201.252.126, UDP 20600 и ICE-TCP 20601). Из России этот адрес заблокирован: в журналах SFU ICE-TCP-соединения клиента из России открываются и сразу закрываются, UDP не доходит.
- Обычные звонки из России работают через TURN `@ru` на amf (задача 109). Групповые так не могут: клиенты не используют TURN и STUN в групповых звонках.
  - tgcalls передаёт пустые списки серверов (`tgcalls/group/GroupNetworkManager.cpp:398`), клиент — ICE-controlled (`:420`), кандидаты ответа входа добавляет как есть (`:516-528`, разбор — `GroupInstanceCustomImpl.cpp:2971-2993`; зеркало tgcalls, `d293787`).
  - Web K: `iceServers: []` (`tweb/src/lib/calls/groupCallConnectionInstance.ts:160`), не больше 64 кандидатов (`helpers/sdpSafety.ts:87`).
- Значит, без правки клиентов медиа можно провести через узел, только дав клиенту в ответе входа адрес узла.
- HTTP-CDN (Gcore, край `ru`) несёт MTProto — `phone.joinGroupCall` и обновления звонка уже ходят через него; UDP и ICE-TCP он не несёт.

## Решение
1. **Труба на amf.** Блок `stream` в nginx Pluma на узле (`pluma-ru-nginx`, не nginx владельца): `<адрес узла>:20600 udp reuseport` и `:20601` TCP, апстрим — прямо на публичный адрес SFU (`PLUMA_RU_SFU_ADDR`). Пакеты идут как есть, узел ничего не расшифровывает.
   - `reuseport` обязателен: без него датаграммы одного клиента расходятся по рабочим процессам и уходят к SFU с разных портов (документация `ngx_stream_core_module`, `listen`). Проверено тестом `TestNodeRelay`: без `reuseport` один клиент приходит к SFU с 8–12 портов.
   - UDP `proxy_timeout 30s`, `proxy_responses` не задан; TCP — 5 с на соединение, 60 с простоя; `limit_conn` 32 на адрес клиента; журнала доступа нет.
   - Не DNAT ядра: на amf `ip_forward=0`, и узел по ADR 0072 §8 адресов не пересылает.
2. **SFU знает свои трубы.** `Media.Relays` (`SFU_RELAYS=ru=194.87.226.185:20600/20601`) — именованные наборы адресов перед узлом; `direct` — собственные `PublicIPs`. `JoinRequest.routes` (поле 7) называет наборы по порядку; пусто — `direct`. Ответ входа строится из адресов названных наборов, у последующего набора приоритет ниже. Неизвестный узлу набор вход не роняет: он пропускается, считается в `sfu_route_unknown_total` и пишется в журнал; если не осталось ни одного — `direct`.
3. **bff выбирает набор по стране.** `GROUPCALLS_ROUTES` с грамматикой стран `CDN_ROUTES`; на проде `RU,BY:ru;*:direct`. Страна — по `MD.ClientAddr` через `ipcountry.Locator`, при каждом входе и показе экрана. Россия и Беларусь получают только кандидаты узла, остальные — только прямые: SFU сам выдвигает пару нативным клиентам и не отличает по приоритету прямую пару от пары через трубу.
4. **Наблюдение.** Метка `route` у `sfu_connections`, `sfu_connect_failures_total`, `sfu_ice_pairs_total`; алерты `GroupCallsRelayNoCheck`, `GroupCallsRouteUnknown` (`groupcalls.yml`) и `RuSfuRelayDown` (`ru-node.yml`, по `pluma_ru_sfu_upstream_up` и `pluma_ru_unit_active` из `wgstat.sh`).
5. **Порядок выкладки:** узел (труба слушает) → край (SFU знает `ru`) → дом (bff просит `ru`). Откат — обратный, первым убирается запись `RU,BY`.

## Последствия
- Пользователь из России входит в групповой звонок без VPN, если путь amf → Hetzner держит поток. Длинный поток не замерен (часть 1 брифа — шаг оператора).
- Узел видит то же, что TURN `@ru`: адреса и порты, время и объём. Содержимое — DTLS-SRTP с кадрами tde2e внутри.
- Перезагрузка nginx узла (`deploy.sh apply` при смене любого его файла) меняет сессии трубы: SFU видит клиента с нового порта и переходит на новую пару повторным выдвижением. Проверено тестом `TestRelaySessionChange` (пересыльщик в процессе), на живом nginx не проверено.
- SFU по-прежнему один, на Hetzner: россиянин с медиа идёт Москва → Германия (около 49 мс от amf).

## Отклонённые альтернативы
- DNAT ядра на amf — меняет маршрутизацию чужой машины, против ADR 0072 §8.
- Второй SFU на amf — комната живёт на одном узле, каскада нет (ADR 0059 §3).
- Апстрим через туннель домой — лишние 70+ мс, канал дома, MTU 1280. Остаётся запасом, если прямой путь не держит поток: меняется только `PLUMA_RU_SFU_ADDR`.
- TURN для групповых звонков — нужны патчи четырёх клиентов.
- Всем оба набора кандидатов — SFU не может предпочесть прямую пару.
- bff переписывает JSON ответа SFU — адреса узла разъехались бы по двум конфигурациям.
