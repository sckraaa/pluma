# 0005. Масштаб и инфраструктура

- Статус: accepted
- Дата: 2026-10-21 (по итогам `docs/audit/03-architecture-and-ops.md`)

## Контекст
До 100 пользователей, закрытая аудитория, требование бесперебойности. Аудит показал: ненадёжность происходит не от количества компонентов, а от того, что их гарантии не используются (Kafka коммитит offset при ошибке, счётчики только в Redis, нет супервизора процессов, нет бэкапов).

## Решение
| Компонент | Решение | Условие |
|---|---|---|
| MySQL | оставить — источник истины | версионируемые миграции, бэкапы с проверкой восстановления, лимит соединений согласован с пулами |
| Redis | оставить | только кэш и сессии; счётчики (`pts`, `seq`, id) хранятся в MySQL, Redis — ускорение с восстановлением; AOF, `maxmemory` |
| Kafka | оставить и починить | не коммитить offset при ошибке, ретраи, DLQ, порядок по пользователю, идемпотентные обработчики; рестарт-политика |
| etcd | оставить | дешёв; удаление требует правок в 6 местах |
| MinIO, FFmpeg | оставить | — |
| Prometheus, Grafana | оставить | алерты на доставку и задержки |
| Jaeger | оставить без Elasticsearch | — |
| Elasticsearch, Kibana, Filebeat, go-stash | убрать | заменить на Loki (≈3 ГБ RAM, гарантий для сообщений не дают) |
| Развёртывание | переделать | один процесс — один сервис compose, restart, healthcheck, exec-entrypoint, наружу только gateway |

Модель данных проектируется шард-готовой (ключи по пользователю/peer, `pts` на канал), но шардирование не внедряется.

## Последствия
Надёжность строится на семантике доставки, долговечных счётчиках, супервизии, бэкапах и алертах. Пересмотреть, если число пользователей вырастет на порядок.
