# 0068. Платформа ботов: вход на сайты, мини-приложения, меню вложений, игры, виджеты

- Статус: предложено (2026-11-15)
- Задача: 106 (ветка `task/106-bot-platform`). Продолжение задачи 070 и ADR 0043.
- Связано: ADR 0043 (боты — аккаунты MTProto, токен только хэшем, управление через `pluma-admin`), ADR 0036 (ссылки pluma.chat, сервис `links`), ADR 0041 (всё открыто всем), ADR 0045 (новые методы слоя — `RPCNotServed`), ADR 0009 (свои правки схемы — отдельные коммиты `third_party(proto):`), ADR 0057/0061 (данные пользователей не уходят с домашнего сервера).
- Заменяет: в ADR 0043 «HTTP Bot API и мини-приложения — следующие задачи» для мини-приложений, входа и игр; в задаче 070 «`keyboardButtonUrlAuth` отклоняется `BUTTON_TYPE_INVALID`» и «игры не обслуживаются».

## Решение

### 1. Где живёт
- Всё клиентское и ботовое — в модуле bff `bots`: он уже знает ботов, ожидание ответа бота в Redis и журнал seq бота. Регистрируются `RPCSeamless`, `RPCMiniBotApps`, `RPCMainMiniBotApps`, `RPCPreparedInlineMessages` и новая `RPCBotWidgets`; маршруты — в трёх `session.yaml`. `RPCBotMenu` и `RPCGames` (с `messages.getEmojiGameInfo`) регистрирует в `bots` и маршрутизирует задача 098; здесь их отказы заменяются реализацией. Методы этих служб, которые не обслуживаются (ниже, «Что не делается»), отвечают `ErrEnterpriseIsBlocked`, не Unimplemented.
- Методы виджетов переносятся из `RPCNotServed` в новую службу `RPCBotWidgets` отдельным коммитом `third_party(proto):` (ADR 0009, пометка `// pluma:`), там же — недостающие коды ошибок (`URL_EXPIRED`, `BOT_WEBVIEW_DISABLED`, `THEME_PARAMS_INVALID`, `WIDGET_QUERY_TYPE_UNSUPPORTED` и др., брифа «Ошибки»).
- Выдуманный ответ `TLAccountGetWebAuthorizations` из `fake_rpc_result.go` удаляется.
- Вход на сайты (OIDC и старый формат) — HTTP-обработчики в сервисе `links` на отдельном хосте `oauth.pluma.chat` (Caddy). Отдельный сервис не заводится: `links` уже стоит за Caddy, ходит в `biz` и `dfs` и строит страницы на языке посетителя.

### 2. Настройка ботов — только `pluma-admin`
Разговорного BotFather нет (ADR 0043). Новые подкоманды `pluma-admin bot`: домен входа (`-domain`), главное приложение (`-main-app <url>`), прямые приложения (`bot app add|edit|rm|list`), меню вложений (`bot attach`), игры (`bot game`), клиенты OIDC (`bot login`). Фото, анимации и значки загружаются в `dfs`/`media` тем же путём, что `servicephoto.go`. Владелец бота настроек из клиента не меняет: в API Telegram таких методов нет.

### 3. Ключи бота: выводятся из токена при выдаче и при входе, хранятся зашифрованными
- Для мини-приложений нужен `HMAC_SHA256(key="WebAppData", msg=token)`, для старого формата входа — `SHA256(token)`. Сервер видит полный токен ровно в двух местах: при выдаче (`pluma-admin bot create|token`) и в `auth.importBotAuthorization`. Там оба значения вычисляются и записываются в `bot_secret_keys`; при входе — только если записи нет или она от другого токена (`token_hash` совпадает с `bots.token`).
- Значения запечатываются AES-256-GCM на ключе `BOT_SECRET_ENCRYPTION_KEY` (как `PUSH_SECRET_ENCRYPTION_KEY`, `pkg/pushdevices/seal.go`), дополнительные данные — id бота и назначение ключа. Утечка базы не даёт подделать вход на чужие сайты.
- Новый токен (`bot token`) заменяет ключи в той же транзакции, что и хэш. Бот, который ни разу не вошёл после миграции, получает `BOT_WEBVIEW_DISABLED` на открытие приложений и `urlAuthResultDefault` на кнопку входа, пока не войдёт или не получит новый токен. **Не проверено**, что бот входит токеном при каждом запуске: библиотеки с сохранённой сессией (Telethon, Pyrogram, TDLib), по-видимому, повторно `auth.importBotAuthorization` не зовут, пока ключ авторизации жив (их исходники не читались). Поэтому после выката оператор выдаёт уже работающим ботам новый токен (`pluma-admin bot token`, `docs/ops/bots.md`) — это гарантированно записывает ключи; на повторный вход при перезапуске дизайн не полагается.
- Ed25519 для `signature` — свой ключ Pluma (`WEBAPP_SIGNING_KEY`, 32 байта seed в hex). Ключи Telegram не подходят: у нас нет их закрытой части. Открытый ключ публикуется в `docs/ops/bots.md` и на `https://oauth.pluma.chat/.well-known/webapp-signing-key`; библиотеки проверки третьих сторон настраиваются на него.

### 4. Мини-приложения
- `requestWebView`, `requestSimpleWebView`, `requestMainWebView`, `requestAppWebView` строят `webViewResultUrl`: адрес приложения (кнопка, кнопка меню, `main_app_url`, адрес прямого приложения, адрес меню вложений) + фрагмент `#tgWebAppData=…&tgWebAppVersion=…&tgWebAppPlatform=…&tgWebAppThemeParams=…`, при необходимости `tgWebAppStartParam`, `tgWebAppFullscreen`, `tgWebAppBotInline`, `tgWebAppShowSettings`. Адрес — только `https://`. Версия — по платформе из конфигурации; начальные значения снимаются с настоящего Telegram зондом (`reference-telegram-probe`) до выкатки.
- `query_id` выдаётся там, где есть чат, в который бот может ответить (`requestWebView`, `requestMainWebView` из чата с ботом, `requestAppWebView`); состояние запроса (пользователь, бот, чат, `reply_to`, `silent`, `send_as`) — в Redis на 180 с с продлением на каждом `prolongWebView` (клиенты продлевают раз в 60 с). Потеря Redis закрывает открытые вебвью (`QUERY_ID_INVALID`), данных не теряет.
- `sendWebViewResultMessage` (бот) отправляет результат как инлайн-результат от имени пользователя в чат запроса, через тот же путь, что `sendInlineBotResult`; запрос сгорает; на устройства пользователя уходит `updateWebViewResultSent`. Ответ — `webViewMessageSent` с `msg_id` (`inputBotInlineMessageID64`), если у сообщения есть инлайн-клавиатура.
- `sendWebViewData` создаёт одно сообщение с двумя видами: у пользователя `messageActionWebViewDataSent(text)`, у бота `messageActionWebViewDataSentMe(text, data)`. Для этого `msg.OutboxMessage` получает поле `incoming_action` — действие, которое пишется во входящую копию получателя; это же нужно `messageActionRequestedPeer`/`…SentMe`.
- Разрешение писать: `bot_write_allowed(user_id, bot_id, source)`; источник пишется в `messageActionBotAllowed` (`domain` / `app` / `attach_menu` / `from_request`) один раз в чат с ботом. `bots.canSendMessage` — есть разрешение или пользователь писал боту; `bots.allowSendMessage` — разрешение и служебное сообщение. Запрет боту писать без разрешения остаётся за пределами задачи (так было и в 070).

### 5. Меню вложений и прямые приложения
- Меню вложений включает администратор (как «major advertisers» у Telegram). Список пользователя — установленные им боты (`bot_attach_menu_installs`), `hash` — от id ботов и версий их настроек. `side_menu_disclaimer_needed` всегда ложь: флажок ведёт на соглашение Telegram, которого у Pluma нет.
- `toggleBotInAttachMenu` пишет установку и (с `write_allowed`) разрешение, рассылает `updateAttachMenuBots` всем сессиям пользователя через журнал seq; изменение настроек бота администратором рассылает его всем, кто бота установил.
- `botApp.hash` — от версии записи приложения; `inactive` — пользователь ещё не запускал приложение (`bot_app_launches`).

### 6. Вход по кнопке, по ссылке и на сайт
- Кнопка: `inputKeyboardButtonUrlAuth` принимается, если хост `url` в точности равен домену бота (`bots.login_domain`, без поддоменов, без учёта регистра), иначе `BOT_DOMAIN_INVALID`. Клиент получает `keyboardButtonUrlAuth(text, fwd_text, url, button_id)`; бот, через которого идёт вход, и `request_write_access` хранятся в той же кнопке в сохранённом JSON сообщения (поля, которых нет у конструктора `keyboardButtonUrlAuth`, в TL не кодируются; тест это держит).
- `requestUrlAuth`: если у пользователя уже есть веб-сессия этого бота и домена и не нужен новый доступ — сразу `urlAuthResultAccepted` (так допускает документация); иначе `urlAuthResultRequest`. `acceptUrlAuth` возвращает адрес кнопки с добавленными полями старого формата (`id`, `first_name`, `last_name`, `username`, `photo_url`, `auth_date`, `hash` на ключе `SHA256(token)`) и создаёт или обновляет веб-сессию. `photo_url` — `https://pluma.chat/_l/avatar/<username>`, только при имени пользователя (ADR 0036 п. 4: публичное фото).
- Ссылки из `url_auth_domains` — тот же путь, домены — те, к которым привязан какой-нибудь бот (конфиг приложения строится из `bots.login_domain`).
- Сайт: `oauth.pluma.chat` — провайдер OpenID Connect по образцу Telegram (те же пути, параметры, области и имена утверждений, чтобы сайт переключался сменой издателя), ID-токен RS256 на ключе `OAUTH_SIGNING_KEY_FILE`, JWKS и discovery; плюс старый формат (редирект с полями виджета) для сайтов на прежних библиотеках. Подтверждение — в приложении: страница показывает QR-код и кнопку со ссылкой `https://pluma.chat/oauth?startapp=<token>`, приложение шлёт её в `requestUrlAuth`, сервер отвечает `urlAuthResultRequest` с браузером, платформой, адресом, регионом и четырьмя `match_codes` (одно из них показано на странице), `acceptUrlAuth` с верным кодом подтверждает запрос, страница по опросу получает код авторизации. Ввод телефона на странице и пуш `OAUTH_REQUEST` не делаются: iOS такого пуша не обрабатывает, QR и кнопка работают у всех.
- Веб-сессии: `web_authorizations` (одна на пользователя, бота и домен; браузер, платформа, адрес, регион, даты). `resetWebAuthorization(s)` удаляет запись; следующий вход снова спросит. Выданные сайтам ID-токены не отзываются (refresh-токенов нет).
- Регион адреса — из GeoIP `authsession` (новый RPC), другая копия базы GeoIP не заводится.

### 7. Игры
- Игру заводит администратор (`bot_games`: короткое имя, название, описание, фото, анимация). Бот отправляет её `sendMedia(inputMediaGame(inputGameShortName))`, пользователь пересылает `inputGameID`; инлайн — `inputBotInlineResultGame`.
- Нажатие `keyboardButtonGame` — callback с `game_short_name` в `updateBotCallbackQuery`; ответ бота с `url` — адрес игры.
- Счёт — в `game_scores` по игре, чату и пользователю (чат: канал, базовая группа или пара личного диалога; для инлайн-сообщения — чат, где оно лежит). `setGameScore` без `force` принимает только больший счёт (`BOT_SCORE_NOT_MODIFIED`), с `edit_message` пишет в чат `messageActionGameScore` от имени игрока ответом на игру. `getGameHighScores` — по правилу Bot API (игрок ±2 и тройка лучших).
- `messages.editInlineBotMessage` делается здесь же: без него не работают инлайн-игры и инлайн-виджеты. Правка идёт через `msg.editMessageV2` с новым `edit_type` «бот через инлайн» от имени владельца сообщения, после проверки `via_bot_id`.

### 8. Виджеты
- По коду клиентов, без документации: `inputMediaWidget` (HTML ≤ 64 КиБ) сжимается zlib в `payload`; `shared_widget` заводит общий виджет с `widget_id` и общими данными (`editWidgetData`, `cache_time` → `period` в пределах 5–3600, по умолчанию 30); `getWidgetPublicData` отвечает `notModified` при совпадении `hash`; `editMessageWidgetData` правит данные в сообщении и шлёт `updateMessageWidgetData` с pts; `getBotWidgetQueryAnswer` ждёт бота тем же механизмом, что callback (`updateBotWidgetQuery` в журнал бота с TTL запросов), бот отвечает `setBotWidgetQueryAnswer`. Запросы кошелька — `WIDGET_QUERY_TYPE_UNSUPPORTED` (TON вне проекта).

### 9. Что получает бот (MTProto)
Новые бот-методы: `sendWebViewResultMessage`, `savePreparedInlineMessage`, `bots.requestWebViewButton`, `setGameScore`, `setInlineGameScore`, `getGameHighScores`, `getInlineGameHighScores`, `editInlineBotMessage`, `setBotWidgetQueryAnswer`, `editWidgetData`, `editMessageWidgetData`, `editInlineBotMessageWidgetData`, `sendMedia` с `inputMediaGame`/`inputMediaWidget`. Новые обновления боту: `game_short_name` в callback, `messageActionWebViewDataSentMe`, `messageActionRequestedPeerSentMe`, `updateBotWidgetQuery`, `updateInlineBotWidgetQuery`.

## Последствия
- Боты Pluma получают почти всё, что дают Telegram-боты вне платежей; библиотеки MTProto (Telethon, Pyrogram, TDLib) работают без правок. HTTP Bot API по-прежнему нет.
- Сторонние проверки `signature` и ID-токенов нужно настроить на ключи Pluma; проверка `hash` по токену работает без изменений.
- Три новых секрета (`BOT_SECRET_ENCRYPTION_KEY`, `WEBAPP_SIGNING_KEY`, `OAUTH_SIGNING_KEY_FILE`) и новый хост `oauth.pluma.chat`. Без `BOT_SECRET_ENCRYPTION_KEY` мини-приложения и вход выключены (bff стартует, методы отвечают `BOT_WEBVIEW_DISABLED`/`urlAuthResultDefault`).
- Замена ключа `WEBAPP_SIGNING_KEY` делает недействительными подписи уже открытых приложений; замена `OAUTH_SIGNING_KEY_FILE` — ID-токены, ещё не проверенные сайтами. Порядок замены — в `docs/ops/bots.md`.
- Клиенты не патчатся: всё, что нужно, уже есть в официальных клиентах (меню вложений, вебвью, OAuth-ссылки, игры, виджеты). Текстов на сервере, видимых пользователю, нет, кроме страниц `oauth.pluma.chat` — они идут ключами страниц сервиса `links` на языках сайта, как все его страницы (ADR 0036).

## Что не делается
- Платежи и звёзды в мини-приложениях (`invoice`, `payments.*`), подарки, TON, кошелёк в виджетах, платные медиа (решение владельца).
- `messages.requestChatJoinWebView`, `bots.setJoinChatResults`, `bots.get/editAccessSettings`, боты-стражи вступления (`updateBotChatInviteRequester.query_id`, `chatInviteJoinResultWebView`): это часть потока заявок на вступление, а не мини-приложений; отдельная задача по слову владельца.
- `bots.invokeWebViewCustomMethod`, `bots.checkDownloadFileParams`, статус-эмодзи из приложения (`bots.updateUserEmojiStatus`, `toggleUserEmojiStatusPermission`), медиа-превью ботов (`bots.*PreviewMedia*`), `bots.getPopularAppBots`, гостевые чаты (`setBotGuestChatResult`): у бота нет документированного пути ответа или это отдельные продукты Telegram.
- Ввод телефона на странице входа и пуш `OAUTH_REQUEST`; refresh-токены OIDC; авто-вход `autologin_domains` (официальные сайты Telegram).
- Запрет боту писать пользователю без разрешения (открытый пункт задачи 070).
- Разговорный BotFather.

## Рассмотренные альтернативы
- **Хранить полный токен (зашифрованным).** Отвергнуто: ADR 0043 сознательно держит только хэш; выведенные ключи дают ровно нужное и не дают войти ботом.
- **Принимать ключи Telegram для `signature`.** Невозможно: закрытого ключа нет.
- **Отдельный сервис провайдера входа.** Лишняя служба и память; `links` уже стоит на хосте сайта.
- **Пуш `OAUTH_REQUEST` вместо QR.** Работает только на Android.
- **Состояние вебвью в MySQL.** Запросы живут минуты; Redis с TTL проще, а потеря только закрывает открытое окно.
