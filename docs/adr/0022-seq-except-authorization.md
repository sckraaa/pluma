# 0022. Обновление с seq всем сессиям аккаунта, кроме одной

- Статус: accepted
- Дата: 2026-10-29
- Задача 019. Дополняет ADR 0020 (журнал `seq` аккаунта). Не заменяет его.

## Контекст
- **Новый вход у Telegram** (проверено, `docs/tasks/019-service-messages.md`): все остальные сессии аккаунта получают `updateNewAuthorization` с `unconfirmed` — официальные клиенты показывают баннер «Это вы?». Сама новая сессия его не получает. Подтверждение снимает баннер на всех устройствах тем же обновлением без `unconfirmed` (tdesktop `Authorizations::apply`, Android `UnconfirmedAuthController.processUpdate`, iOS `AccountStateManagementUtils.swift`).
- **Баннер важен и офлайн-устройству.** Если устройство было не в сети, при подключении оно должно увидеть баннер: это защита от угона. Пуш с `seq = 0` до него не доходит, а `getDifference` его не находит.
- **Журнал `seq` (ADR 0020) — один на аккаунт.** Каждая строка достаётся всем авторизациям. Способа пропустить одну авторизацию нет.

## Решение
1. **`updateNewAuthorization` — обновление с `seq`** (`userbox.SeqUpdate`). В свёртке разницы ключ — `hash` авторизации (`seq_fold.go`): клиент заменяет состояние входа, и из двух строк одного входа достаточно последней.
2. **Колонка `user_seq_updates.except_auth_key_id`** (`migrate-20261029-seq-except.sql`), постоянный ключ авторизации, которой строка не достаётся. `0` — всем, как у всех прежних строк.
   - `getDifference` этой авторизации строку пропускает (`dao.SeqUpdates`). `seq` состояния её всё равно учитывает.
   - Запись — `Box.AddSeqUpdateExcept`, `sync_client.EmitSeqUpdateExcept`. Пуш идёт через `sync.updatesNotMe` с этим ключом, а не через `sync.pushUpdates`.
3. **Один писатель — RPC `user.newAuthorization`** (biz user, CRC `1324746836`). Он принимает только `updateNewAuthorization`. Его зовёт `app/bff/authorization/newlogin`:
   - после входа — с ключом новой сессии;
   - при подтверждении (`account.changeAuthorizationSettings`) и при завершении входа (`account.resetAuthorization`) — с `0`.
4. **Сообщение «Новый вход» в журнал не пишется.** Это `updateServiceNotification`, и ADR 0020 держит служебные уведомления вне журнала: Android при каждом таком обновлении создаёт новое локальное сообщение (`MessagesController`, ветка `TL_updateServiceNotification`), так что повтор из `getDifference` дал бы дубль. Сообщение уходит онлайн-сессиям (`sync.updatesNotMe`). Офлайн-устройство получает только баннер. Как ведёт себя Telegram с офлайн-устройствами, не проверено.

## Последствия
- **Пропуск номера `seq`.** У исключённой сессии в потоке пушей может пропасть номер. Тогда клиент сделает `getDifference` и возьмёт `seq` из состояния. Для входа этого не бывает: строку пишут до ответа `auth.authorization`, а клиент после входа зовёт `updates.getState`, и `seq` уже учитывает строку.
- **Хранение.** Строки живут и чистятся как остальные строки журнала (ADR 0020).
- **Другие обновления** с этой колонкой пока не пишутся. Если понадобится «всем, кроме одной сессии», механизм тот же.

## Рассмотренные альтернативы
- **Журнал на каждый ключ.** Отпадает: N копий каждой строки, и `seq` разный у сессий одного аккаунта, а клиенты ждут один `seq` на аккаунт.
- **Баннер только онлайн-сессиям** (`seq = 0`). Отпадает: устройство, которое было не в сети, не узнало бы о входе.
- **Писать в журнал и «Новый вход».** Отпадает: дубли сообщений на Android при каждом повторе разницы.
