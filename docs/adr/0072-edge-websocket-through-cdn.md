# 0072. Доступ через CDN: MTProto в WebSocket через второй ресурс Gcore, прямой путь первым

- Статус: accepted (2026-11-17), с §8 «Российский узел amf». Владелец решил: узел в России — amf, имена `ru.pluma.chat` и `r1.pluma.chat`; остальные решения брифа 109 («Решения к подтверждению») реализованы по рекомендациям и ждут подтверждения. Реализовано задачей 109 в партии `batch/20261117`; проверки владельца на живом Gcore и amf не проводились.
- Задача: 109 (`docs/tasks/109-access-through-cdn.md`).
- Связано: ADR 0057 (дом — ядро, внешние узлы — труба для шифра), ADR 0061 (443 идёт домой DNAT через VPS, TLS заканчивается в домашнем Caddy), ADR 0071 (HTTPS-CDN файлов на Gcore, ресурс `<префикс>.gcorecdn.com`, источник — дом), ADR 0041.
- Не меняет 0057, 0061. Дополняет 0057 §2: вторая труба для шифра — CDN-провайдер для соединений MTProto, третья — российский узел amf (§8). Завершения MTProto вне дома по-прежнему нет.
- Дополняет ADR 0071 §1 (§8 ниже): записи `CDN_ROUTES` со странами принимаются, появляется вторая выдача 202 на amf; определение страны — `authsession.getIpCountry`.

## Контекст

### Чего хочет владелец (2026-11-16/17)
Клиенты Pluma заходят откуда угодно, в том числе там, где адрес VPS или сам протокол заблокированы, без VPN. Большой CDN — только труба: снаружи это обычный HTTPS к общему домену CDN, внутри — MTProto, зашифрованный ключом авторизации между клиентом и домом. Россия с мобильными «белыми списками» — позже, но шов закладывается сейчас.

### Какой транспорт CDN может нести
CDN пропускает HTTP(S) и WebSocket, но не TCP с произвольными байтами. Что есть у клиентов (исходники `~/pluma-work/reference-src-new`, прочитаны 2026-11-17):

- **Web K** ходит только по WebSocket: `new WebSocket(url, 'binary')` (`tweb/src/lib/mtproto/transports/websocket.ts:51-52`), URL строится в `constructTelegramWebSocketUrl` (`src/lib/mtproto/dcConfigurator.ts:53-63`); патч Pluma W-001 заменяет его одним `wss://<host>/apiws` (`clients/patches/web.md`, W-001). Внутри — обфусцированный MTProto (`TcpObfuscated`, `dcConfigurator.ts:85-104`).
- **tdesktop 7.4.1**:
  - TCP (`mtproto/connection_tcp.cpp`) поверх абстрактного сокета `MTP::details::AbstractSocket` (`mtproto/details/mtproto_abstract_socket.h:15-58`); сокет выбирается в `connection_tcp.cpp:529-537` (`WebProxySocket` для WEB-прокси, иначе `AbstractSocket::Create`).
  - HTTP-транспорт есть, но только открытым текстом к IP на порт 80: `http://%1:%2/api` с `kForceHttpPort = 80` (`connection_http.cpp:17`, `:281-285`); он держит обновления длинным опросом `http_wait(100, 30, 25000)` (`session_private.cpp:656`). **Сервер Pluma `http_wait` не обслуживает**: `onHttpWait` ничего не делает (`app/interface/session/internal/sess/session_service_messages.go:250-267`) — по HTTP-транспорту обновления не приходили бы.
  - В клиенте уже есть свой клиент WebSocket по TLS: `Core::WebSocketClient` на `QSslSocket` (`core/websocket_client.h:18-67`; `connectToHostEncrypted` — `websocket_client.cpp:65`; ping/pong — `:21-22`), им пользуются `webauthn/cable_ceremony.cpp` и `wallet/wallet_stream.cpp`.
  - При каждом подключении tdesktop запускает тестовые соединения ко всем адресам сразу, у каждого приоритет (TCP выше HTTP, `session_private.cpp:203-205`), и ждёт лучшего ещё 2 с (`:34`, `:2382-2394`).
- **Android 13.2.1 (tgnet)**: только TCP в C++ (`jni/tgnet/ConnectionSocket.cpp:68`), своего TLS-клиента для MTProto нет. Адреса DC перебираются последовательно, смена адреса после неудачи, текущий адрес запоминается (`jni/tgnet/Datacenter.cpp:374`, `:468`, `:486`; подробности — бриф 092, «Перебор адресов»). В Java уже есть библиотека WebSocket `com.neovisionaries:nv-websocket-client:2.14` (`TMessagesProj/build.gradle:57`, используется в `ui/Wallet/GramWalletStreaming.java`).
- **iOS 13.2 (MtProtoKit)**: TCP на `GCDAsyncSocket` (умеет `startTLS`, `GCDAsyncSocket.m:5860`); соединение создаётся в `MTTcpTransport.m:199` и при поиске адреса в `MTDiscoverConnectionSignals.m:99`; поиск пробует адреса параллельно и через 30 с перепроверяет лучший (`MTDiscoverConnectionSignals.m:260-342`). У адреса есть `host` и флаги (`MtProtoKit/PublicHeaders/MtProtoKit/MTDatacenterAddress.h:5-16`). Минимальная iOS — 15.0 (`Telegram/BUILD:169`), `URLSessionWebSocketTask` уже используется (`submodules/WalletContext/Sources/WalletStreaming.swift`).
- **WEB-прокси Telegram 13.2** (tdesktop `mtproto/web_proxy/`, Android `utils/proxy/WebProxyTransport.java`, iOS `submodules/WebProxyTransport`, `TelegramCore/Sources/Settings/ProxySettings.swift:28-70`):
  - клиент поднимает локальный MTProxy на `127.0.0.1` (Android: `WebProxyTransport.java:323`; `ConnectionsManager.java:675-680`, `:1000-1009`) и несёт его байты кадрами `Open/Data/Close/Window/Ping/Hello/Welcome/AuthChallenge…` (tdesktop `web_proxy_frame.h`, Android `WebProxyTransport.java:55-71`) через страницу оператора в WebView;
  - адрес страницы — `https://host/path/?bridge=<HMAC-SHA256(secret, host[, path])>` (`WebProxyTransport.java:306-322`); tdesktop может открыть её и во внешнем браузере (`web_proxy_transport.cpp:1601-1680`);
  - на стороне оператора нужен ретранслятор этих кадров и затем MTProxy (kod.ru, 24.08.2026, https://kod.ru/telegram-web-proxy-tproxy-server-podrobnosti, прочитано 2026-11-17 через выдачу поиска, сама страница не открывалась — НЕ ПРОВЕРЕНО в деталях);
  - это настройка прокси пользователя: заменяет прямое подключение целиком, сам клиент с прямого пути на прокси не переходит (бриф 092, «Прокси»).

### Gcore (страницы прочитаны 2026-11-17)
- **WebSocket** — опция ресурса «WebSockets» (Content), API `options.websockets {enabled, value}`. Для ресурса с делегированием DNS включена по умолчанию, для CNAME-ресурса выключена. Каждое соединение — отдельное соединение к источнику. **Соединение закрывается, если от источника нет данных дольше read timeout ресурса, по умолчанию 30 с**; Gcore советует слать ping чаще. WAAP может отвечать 403 на `Upgrade` (https://docs.gcore.com/cdn/cdn-resource-options/websockets-allow-permanent-connections-with-the-origin.md).
- **Таймауты:** `proxy_read_timeout` и `proxy_send_timeout` 30 с, `keepalive_timeout` 15 с; поднять выше 30 с — только Enterprise через поддержку, остальным — только уменьшить (https://docs.gcore.com/cdn/getting-started/cdn-timeouts.md).
- **Методы:** по умолчанию ресурс принимает все стандартные методы; опция может ограничить, остальным — 405 (https://docs.gcore.com/cdn/cdn-resource-options/security/specify-http-methods-allowed-for-content-requests-from-the-cdn.md).
- **Ресурс:** разные настройки — разные ресурсы; до 30 ресурсов на аккаунт (https://docs.gcore.com/cdn/getting-started/create-a-cdn-resource/overview.md).
- Остальное о Gcore (бесплатный 1 ТБ, в лимит входит трафик «источник → CDN», Secure Token, логи 3 дня, договор и непрочитанная AUP) — в ADR 0071, «Контекст».
- **НЕ ПРОВЕРЕНО:** доступна ли опция WebSockets на бесплатном/PAYG-плане (страница о плане молчит); какой заголовок с адресом клиента Gcore передаёт источнику (страниц об этом в индексе https://docs.gcore.com/cdn/llms.txt не нашлось); есть ли предел жизни одного соединения WebSocket; считается ли трафик от клиента к источнику (вход) в лимит 1 ТБ.

### Дом сегодня
- Шлюз уже принимает MTProto по WebSocket: `Proto: websocket` (`app/interface/gnetway/internal/config/config.go:31`), порты 11443 и 11444 с PROXY v1 (`teamgramd/etc2/gnetway.yaml:36-52`). Внутри WebSocket тот же разбор транспортов, что для TCP (`server/gnet/server_websocket.go`), кадр может продолжаться в следующем сообщении; сообщение до 16 МиБ (`ws/codec.go:26`); подпротокол `binary` (`ws/codec.go:71-76`); ping клиента шлюз отвечает (`ws/codec.go:161-166`), сам ping не шлёт.
- Домашний Caddy отдаёт Web K и ведёт `/apiws` на 11444 с PROXY v1, чтобы шлюз видел адрес клиента (`teamgramd/deploy/web/Caddyfile`, сайт `{$PLUMA_WEB_DOMAIN}`). Для PROXY v1 шлюз считает соединение в пределах по адресу только после заголовка (`server/gnet/server_gnet.go:69-71`, `:228-271`).
- Источник HTTPS-CDN файлов — отдельный сайт Caddy `cdn-origin.caddy`, подключается только при заданном имени.

## Решение

### 1. Транспорт через CDN — MTProto в WebSocket, у всех четырёх клиентов
- Один контракт: `wss://<хост края>/apiws`, подпротокол `binary`, в бинарных сообщениях — тот же поток байт, что клиент шлёт по TCP на DC 1 (64-байтовый obfuscated2-заголовок и кадры его обычного транспорта, без секрета `dd`/`ee`). Границы сообщений произвольны. Подробно — бриф, «Контракт клиентов».
- Почему WebSocket, а не HTTP-транспорт tdesktop: HTTP-транспорта нет у Android и iOS, у tdesktop он только `http://` на IP:80, а сервер не обслуживает `http_wait` (Контекст). WebSocket уже понимает шлюз и Web K, а у tdesktop, Android и iOS есть готовые клиенты WebSocket по TLS в самом приложении.
- Почему не WEB-прокси Telegram 13.2 как основной путь:
  - он заменяет прямой путь целиком и не переключается сам — это настройка прокси пользователя, а нужен автоматический запасной путь;
  - нужен WebView постоянно, на Linux tdesktop может отправить пользователя во внешний браузер;
  - дому нужны ретранслятор кадров и приём MTProxy с секретом, которого в шлюзе нет (бриф 092, «Сервер сегодня»);
  - его сила — TLS настоящего браузерного движка против распознавания по отпечатку TLS. Это шов для России (§7), не первая ступень.
- TLS края делает системный или уже встроенный стек: iOS — `URLSessionWebSocketTask` (отпечаток CFNetwork, как у всех приложений iOS), Android — Java TLS (Conscrypt) через nv-websocket-client, Desktop — `QSslSocket` (OpenSSL Qt), Web K — браузер.

### 2. Прямой путь первым, край — автоматический запасной
- Нативные клиенты сначала пробуют прямой адрес (как сегодня), край — когда прямой не соединяется или «замерзает» (соединение есть, ответов нет). После перехода на край клиент держится его 30 минут (`sticky`), затем снова пробует прямой путь при следующем переподключении.
- Механизм каждого клиента — его собственный перебор адресов, край добавляется последним адресом DC 1 (бриф, «Контракт клиентов»): tdesktop — тестовое соединение с приоритетом ниже прямого TCP; iOS — адрес с флагом WebSocket в поиске `MTDiscoverConnectionSignals`; Android — локальный мост на `127.0.0.1` последним адресом tgnet.
- Web K не перебирает: страница, открытая с хоста края, ходит в WebSocket своего же хоста. Web K доступен по двум адресам — прямой `web.pluma.chat` и сайт целиком через CDN на хосте края.
- Почему не «весь трафик всегда через CDN»: лишний участок до точки Gcore и обратно домой на каждом пакете, зависимость всех от одного провайдера, Gcore видел бы адреса и время всех пользователей, а не только тех, у кого прямой путь закрыт. Вариант «всегда край» остаётся одной строкой порядка в `pluma_edge` (§4), если владелец решит иначе.

### 3. Сервер: вход «край» в шлюзе и источник края в Caddy
- **Второй ресурс Gcore** на домене Gcore (`<префикс2>.gcorecdn.com`): у ресурса файлов включён Secure Token (ADR 0071), он ответил бы 403 на `Upgrade` без `md5`, а кэш и запросы у края другие. Источник — новое имя дома (`PLUMA_EDGE_ORIGIN_DOMAIN`, A-запись на адрес Pluma, CAA как у остальных имён). Gcore добавляет к каждому запросу `X-Pluma-Edge-Auth` (256 бит, отдельный от `X-Pluma-Origin-Auth` файлов).
- **Caddy, сайт `edge-origin.caddy`** (подключается только при заданном имени, как `cdn-origin.caddy`):
  - без верного `X-Pluma-Edge-Auth` — 403 до разбора пути;
  - `/apiws` → шлюз, новый вход `11445`; Caddy передаёт адрес клиента от Gcore отдельным заголовком `X-Pluma-Client-Addr` (значение исходного `X-Forwarded-For`; свой `X-Forwarded-For` Caddy без `trusted_proxies` перезаписывает), заголовок клиента с тем же именем затирается;
  - остальное — статика Web K из `/srv`, как на `{$PLUMA_WEB_DOMAIN}` (§2);
  - без журнала доступа.
- **Шлюз, вход `Edge`** (`Proto: websocket`, `Edge: true`, порт не публикуется):
  - адрес клиента берётся из `X-Pluma-Client-Addr` при `Upgrade` — последний правильный IP списка (его дописал тот, кто видел соединение клиента; левые элементы клиент может подделать). Нет заголовка или нет адреса — закрыть. Пределы по адресу считаются после заголовка, как для PROXY v1;
  - шлюз шлёт WebSocket ping каждые 20 с (меньше 30 с Gcore), не продлевая этим простой соединения;
  - метрики по входу: соединения, байты до закрытия, причины закрытия — они же пассивные замеры для России (бриф 092, «План замеров», п. 3).
- Почему адрес через заголовок, а не PROXY v1 из Caddy: адрес PROXY v1 Caddy берёт из адреса соединения или из доверенных прокси, а `trusted_proxies` — настройка всего сервера Caddy и затронула бы сайт входа на сайты (он полагается на её отсутствие). Доверие заголовку держится на секрете Gcore, проверенном Caddy, и на том, что 11445 доступен только из сети Docker.

### 4. Где клиент берёт адрес края
- Встроен в сборку списком (`PLUMA_EDGE_WS_URLS`, от 1 до 4 адресов в порядке перебора, переменная репозитория клиента, как адрес сервера). Без адреса края в сборке края нет: заблокированный клиент не получит его с сервера. Поэтому в сборку сразу входят оба края — Gcore и amf (§8).
- Сервер может заменить список ключом `pluma_edge` в `help.getAppConfig`: `{"v":1,"ws":["wss://…/apiws",…],"order":["direct","edge"],"sticky_s":1800}`. Клиент кэширует последнее значение, принимает только `wss://` и не больше 4 адресов; при ошибке разбора — встроенное. Это шов для второго провайдера и для России (§7): новый адрес края или порядок по стране — без выпуска клиентов.
- `dc_options` не используется: в `dcOption` адрес — IP, имени хоста там нет.

### 5. Конфиденциальность
- Шифрование MTProto сквозное между клиентом и домом: ключ авторизации создаётся по DH с RSA-ключом сервера, вшитым в клиент, поэтому ни Gcore, ни VPS не могут встать посередине, даже владея TLS края. TLS края — только маскировка.
- Gcore видит: адрес клиента, время и длительность соединений, объёмы и ритм сообщений WebSocket, хост края и путь `/apiws`, `User-Agent` (у нативных — постоянный `Pluma`, как в ADR 0071). Не видит: содержимое, номер телефона, id пользователя, с кем он говорит. В Log viewer — 3 дня (ADR 0071), сырые логи не включаются.
- Сколько пользователей видит Gcore, решает §2: только тех, у кого не работает прямой путь, и тех, кто открыл Web K по адресу края.

### 6. Отказы
- Gcore недоступен или выключен — клиенты остаются на прямом пути (он первым), Web K по адресу края не открывается, прямой адрес работает.
- Дом недоступен — недоступно всё, как сегодня.
- Источник края отвечает 403 (смена секрета) — край не работает до деплоя, прямой путь работает.
- Звонки (UDP) через CDN не идут: при заблокированном VPS звонки не соединятся — отдельная задача (TURN по TLS).

### 7. Россия — шов
- Записи `pluma_edge` с порядком по стране — когда будет определение страны (`authsession.getIpCountry`, задача «Россия и СНГ»), той же грамматикой, что `CDN_ROUTES` (ADR 0071 §1).
- Российский провайдер с WebSocket и адресами из «белых списков» — новый адрес края, без клиентских сборок.
- Если замеры покажут распознавание по отпечатку TLS, а браузерный TLS проходит, — WEB-прокси Telegram с нашим ретранслятором как третий путь (бриф 092, В4).
- План замеров — бриф 109, «Эксплуатация», «Замеры для России».
- Порядок по стране и российский узел — §8.

### 8. Российский узел amf (дополнение 2026-11-17)
**Контекст** (владелец и замеры 2026-11-17, подробно — бриф 109, «Российский узел amf»): у пользователя в России на домашнем провайдере файловый ресурс Gcore обрывается (`ERR_CONNECTION_RESET`), хотя российские дата-центры Globalping проходят 14/15; адрес Hetzner из России закрыт даже из российского дата-центра; сайты на российском VPS владельца открываются. Владелец отдал Pluma VPS amf (Timeweb, Москва, 2 ГБ памяти, 443 делится по SNI с сайтом владельца через nginx `stream`, 80 занят nginx сайта). Туннель дом → amf: WireGuard работает, путь дом → amf пропускает только MTU 1280.

**Решение.**
1. **amf — труба для шифра, как Hetzner (ADR 0057, 0061), с тремя ролями для пользователей из России:** выдача файлов 202, край WebSocket, TURN. Ядра, ключей, базы и секретов дома на amf нет; секреты amf — только его собственные (ключ подписи выдачи 202, значение доступа к источнику для 202, секрет TURN amf), каждый отдельный от значений Gcore и Hetzner.
2. **Туннель — второй канал WireGuard** `plumaru` (`10.78.0.0/24`, MTU 1280), звонит дом. В отличие от Hetzner, amf не пересылает адреса (DNAT) — все соединения домой открывает сам amf, адрес клиента идёт в PROXY v1. Поэтому дому не нужны ни таблица маршрутов, ни новые `ip rule`: ответы на `10.78.0.1` идут по подключённому маршруту туннеля, а всё остальное — как сегодня, через Hetzner.
3. **Край `ru.pluma.chat` — TLS дома, amf — чистая TCP-труба.** nginx `stream` владельца по SNI отправляет соединение в туннель с PROXY v1 к отдельному серверу Caddy дома (`:8443`, `proxy_protocol` только от `10.78.0.1`), оттуда — на тот же вход `Edge` шлюза с `X-Pluma-Client-Addr` из PROXY. Сертификат выпускает дом под своим ACME-аккаунтом; записи CAA `pluma.chat` не меняются. Узел видит только TLS.
4. **Выдача файлов `r1.pluma.chat` — TLS на amf, кэш nginx.** Без расшифровки HTTP нет кэша, а без кэша узел не снимает отдачу с канала дома (дом → amf 50 Мбит/с). Узел видит то же, что Gcore (ADR 0071 §11): шифр под 256-битными именами, диапазоны, адреса и время; ключи, IV и хэши — только из дома по MTProto. Подпись URL — формула Secure Token Gcore, которую nginx проверяет модулем `secure_link` (`secure_link_md5 "$secure_link_expires$uri <ключ>"`, base64url без `=`; https://nginx.org/en/docs/http/ngx_http_secure_link_module.html, прочитано 2026-11-17), поэтому сервер подписывает выдачу 202 существующим `GcoreSigner`. Куски `slice` по 1 МиБ в кэше на 15 ГБ, 36 ч простоя. Сертификат `r1` выпускает `certbot` на amf; CAA разрешает ему только это имя.
5. **Маршрут по стране.** Страна — `authsession.getIpCountry` по адресу клиента (база GeoIP только в authsession). Файлы: `CDN_ROUTES=RU,BY:202,201;*:201`. Край: `pluma_edge` по записям `EDGE_ROUTES` — России края `ru, gcore` и `order: ["edge","direct"]`, остальным — прямой путь первым. Клиенты страну не знают.
6. **TURN на amf** — coturn с теми же настройками, что на Hetzner, своим секретом (`@ru` в `CALLS_ICE_SERVERS`). Обе стороны звонка получают оба TURN; выбор пары — ICE клиентов. Порядок по стране не делается.
7. **Без Docker на amf**: службы из пакетов Ubuntu, свой экземпляр nginx; nginx владельца получает только файлы Pluma и одну строку `include`.

**Почему не иначе.**
- TLS края на amf: выигрыша нет, а узел видел бы обфусцированный MTProto (содержимое закрыто ключом авторизации, но принцип 0057 — узлы видят только шифр транспорта).
- TLS файлов дома: кэша нет, каждый байт через туннель 50 Мбит/с.
- Российский CDN (Yandex и др., ADR 0071 «Что не делается»): деньги, KYC, условия против прокси у Yandex; amf уже есть и открывается у пользователей. Шов остаётся: ещё одна выдача и ещё один край.
- Пересылка DNAT, как у Hetzner: 443 amf делится по SNI с сайтом владельца, DNAT по SNI невозможен; PROXY v1 даёт адрес клиента проще и без правил маршрутизации дома.

**Последствия.** Новые: второй канал туннеля, сайт Caddy `ru-edge.caddy`, `authsession.getIpCountry` и `pkg/ipcountry`, страны в `CDN_ROUTES` и `EDGE_ROUTES`, вторая выдача, метки секретов TURN, файлы узла `teamgramd/deploy/ru/`, `docs/ops/ru-node.md`. Отказ amf: пользователи из России откатываются на Gcore (файлы — по сигналу отката, край — следующий в списке), остальные не замечают. Отказ дома — как сегодня. Юрисдикция узла — Россия: хостер может получить то, что видит узел (адреса, время, объёмы, шифр файлов), но не содержимое.

**Не проверено** (бриф 109, «Не проверено»): модули nginx в пакете Ubuntu, `include` в `map` модуля `stream`, наследование CAA, путь Hetzner → amf, тариф Timeweb, «белые списки», судьба UDP звонков в российских сетях, использование всех TURN клиентами.

## Последствия
- Клиентские патчи: W-086 (Web K, малый), D-106 (Desktop), A-128 (Android), I-133 (iOS); размеры — бриф 109. Номера D-105 и A-125…A-127 заняты задачей 112.
- Сервер: вход `Edge` в шлюзе, сайт Caddy, ключ `pluma_edge`, транспорт WebSocket в `pkg/mtclient` для e2e.
- Владелец: второй ресурс Gcore, DNS-имя источника, секрет в `.env`, проверки в брифе.
- Трафик в лимите Gcore: всё, что идёт через край, считается дважды (к источнику и к клиенту, если вход считается — НЕ ПРОВЕРЕНО). Сегодня весь исходящий трафик дома ≈ 50 ГБ/мес (ADR 0071), так что и при «всё через край» — порядка 100 ГБ плюс файлы, в пределах 1 ТБ.

## Что не делается
- HTTP-транспорт (`http_wait`) на сервере — не нужен, ни один путь края на нём не держится.
- Свой узел MTProto или TLS-завершение соединений MTProto вне дома (TLS выдачи файлов на amf — как у Gcore, только шифр, §8).
- Звонки через CDN; TURN по TCP/TLS.
- Переключатель края в интерфейсе клиентов: путь выбирается сам (правки клиентов — только где нужно, `clients/patches/README.md`, «Правила»).
