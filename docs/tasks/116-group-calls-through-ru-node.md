# 116. Групповые звонки из России без VPN: медиа через узел amf

- Статус: проект (2026-11-20). Реализация — после подтверждения решений владельцем.
- Поставлена владельцем 2026-11-20: групповые звонки из России без VPN не работают; «через amf и через CDN, как и обычные звонки».
- Зависит от: 093/094 (SFU, сквозные групповые звонки; ADR 0059, 0060), 109 (узел amf, его nginx, `deploy.sh`, TURN `@ru`; ADR 0072 §8), 113 (страна клиента по адресу за краями, `countryClients` в e2e).
- ADR: решение записывается в ADR 0074 первой частью работы (см. «Части»). Оно дополняет ADR 0059 §3 «Публичные адреса» (там уже разрешён адрес-«труба» перед SFU) и ADR 0072 §8 (роли узла amf).
- Ветка: `task/116-group-calls-ru`.

## Цель
Пользователь из России входит в групповой звонок группы или канала без VPN, слышит и видит остальных так же, как пользователь из Германии. Сигнализация, как и у обычных звонков, идёт тем путём, которым клиент вообще ходит к серверу (прямо, край `ru` или край Gcore — задачи 109, 113); медиа — через узел amf, как медиа обычных звонков через TURN `@ru`. SFU остаётся один, на краю Hetzner; узел видит только шифр. Остальные пользователи не замечают ничего.

Как понято «через CDN» в словах владельца: CDN (Gcore, край `ru`) несёт MTProto, то есть `phone.joinGroupCall` и все обновления звонка, — это уже работает. Само медиа (UDP, ICE-TCP, DTLS-SRTP) HTTP-CDN не несёт: у Gcore края — HTTP и WebSocket (бриф 109, «Что это решает и что нет»: «звонки — UDP, CDN их не несёт»). Обычные звонки устроены так же: сигнализация через края, медиа через TURN amf. Если владелец имел в виду иное — решение 1.

## Как сейчас
### Сервер
- SFU (`app/service/sfu`) — контейнер `sfu` на краю Hetzner (`docker-compose.edge.yaml`, выкладка `~/pluma-work/bin/pluma-edge-deploy.sh`). Медиа — UDP 20600 и ICE-TCP 20601 на адресе Pluma 195.201.252.126; управление 20500 и метрики 20501 — на адресе туннеля, bff и Prometheus дома ходят туда по WireGuard.
- Кандидаты в ответе входа строит сам SFU: `config.Addresses` (`app/service/sfu/internal/config/config.go:91`) из `Media.PublicIPs`, `PublicUDPPort`, `PublicTCPPort` → `room.Config.Addresses` (`cmd/sfu/main.go:79`) → `tgcallsjson.BuildResponse` (`app/service/sfu/internal/room/room.go:186`, `pkg/tgcallsjson/response.go`). Все кандидаты — `host`, UDP с приоритетом выше ICE-TCP (`candidatePriority`). bff передаёт JSON ответа клиенту как есть (`JoinResponse.params` в `sfu.proto`).
- Один набор адресов на узел: клиент из России получает тот же адрес Hetzner, что и все.
- ICE SFU (`transport/endpoint.go:197-217`, `mux.go`): pion ice, один мультиплексированный UDP-сокет и один ICE-TCP-слушатель на всех; локальные кандидаты только `host`; адрес клиента SFU узнаёт из его проверок (peer-reflexive); роль выбирается по первой проверке (`sniff.go`): для нативных клиентов SFU — controlling и сам выдвигает пару, с повторным выдвижением раз в 3 с. Первая проверка подлинная только с нашим `USERNAME` и `MESSAGE-INTEGRITY` по нашему паролю; дальше UDP-мукс pion связывает адрес отправителя с ufrag.
- Страна клиента: `pkg/ipcountry.Locator.Country(ctx, MD.ClientAddr)` через `authsession.getIpCountry` с кэшем; так выбираются выдача файлов (`CDN_ROUTES`, `pkg/cdn/delivery.go:113` — грамматика записей), края (`EDGE_ROUTES`, `app/bff/configuration/internal/appconfig/edge.go`) и зеркала сайта. У `groupcalls` своего `Locator` нет.
- Обычные звонки: `CALLS_ICE_SERVERS` с TURN `@ru` на amf отдаётся всем клиентам без выбора по стране; ICE клиентов сам находит рабочий путь (`app/bff/voipcalls/internal/config/config.go:27-39`).

### Клиенты (прочитано 2026-11-20)
- tgcalls групповых звонков TURN и STUN не использует вообще: `portAllocator->SetConfiguration({}, {}, 2, webrtc::NO_PRUNE, …)` (`tgcalls/group/GroupNetworkManager.cpp:398`), клиент — ICE-controlled (`:420`). Кандидаты из ответа входа добавляются как есть (`GroupNetworkManager::setRemoteParams`, `:516-528`), из JSON — `ip`, `port`, `protocol`, `priority`, `type` (`host` → `local`), `foundation`, `network` (`tgcalls/group/GroupInstanceCustomImpl.cpp:2971-2993`). Зеркало tgcalls `~/pluma-work/reference-src-new/tgcalls-mirror`, коммит `d293787`.
- Web K: `iceServers: []` у соединения группового звонка (`tweb/src/lib/calls/groupCallConnectionInstance.ts:160`), не больше 64 кандидатов (`helpers/sdpSafety.ts:87`). `~/pluma-work/reference-src-new/tweb`.
- Значит, единственный способ провести медиа группового звонка через узел без правки клиентов — дать клиенту кандидаты с адресом узла.

### Сеть (замеры 2026-11-20, только чтение)
- С amf до 195.201.252.126: ping 4/4, около 49 мс; TCP 20601, 443, 10443 — соединение открывается; STUN по UDP на TURN края (3478) — ответ с адресом amf (`turnutils_stunclient`); TLS с SNI `sckra.dev` — ответ за 0,18 с, с SNI `pluma.chat` — тишина 20 с (блокировка по имени, не по адресу). Значит, с amf до Hetzner прямой путь есть и для UDP, и для TCP. Не проверено: держится ли поток больше ~16 КБ и несколько Мбит/с минутами (часть 1).
- На amf: nginx 1.28.3 Ubuntu, модуль `stream` — динамический (`/usr/lib/nginx/modules/ngx_stream_module.so`), порты 20600/udp и 20601/tcp свободны, `net.ipv4.ip_forward = 0`, 2 vCPU, около 1,5 ГБ свободной памяти.
- Логи SFU: ICE-TCP-соединения клиента из России открываются и сразу закрываются (из постановки задачи), UDP не доходит.

прочие клиенты  ──UDP 20600 / TCP 20601──────────────────────────────────────────► SFU 195.201.252.126

### 1. Узел — «труба» UDP и TCP на nginx stream Pluma
- В своём экземпляре nginx Pluma (`pluma-ru-nginx`, `teamgramd/deploy/ru/nginx.conf`) — блок `stream` с двумя серверами на адресе узла (`PLUMA_RU_PUBLIC_IPV4`), не на 443 и не в nginx владельца:
  - `listen <адрес узла>:20600 udp reuseport;` → `proxy_pass <адрес SFU>:20600;`
  - `listen <адрес узла>:20601;` → `proxy_pass <адрес SFU>:20601;`
- `load_module /usr/lib/nginx/modules/ngx_stream_module.so;` в начале `nginx.conf` (сейчас там «динамических модулей не нужно» — комментарий меняется). Модули владельца (`/etc/nginx/modules-enabled`) по-прежнему не подключаются.
- `reuseport` обязателен: при нескольких рабочих процессах без него датаграммы одного клиента попадают в разные процессы и уходят к SFU с разных портов (документация `ngx_stream_core_module`, `listen`: «In order to handle packets from the same address and port in the same session, the reuseport parameter should also be specified», прочитано 2026-11-20). Для SFU это был бы новый адрес без проверки ICE — пакеты отбросились бы.
- Таймауты: UDP `proxy_timeout 30s` (проверки согласия клиента и SFU идут каждые 2–2,5 с, `ICE.KeepaliveInterval` 2s; `FailedTimeout` SFU 25s — сессия nginx не должна жить дольше пары), `proxy_responses` не задаётся (по умолчанию ответов сколько угодно, документация `ngx_stream_proxy_module`), `proxy_requests 0` (по умолчанию). TCP: `proxy_connect_timeout 5s`, `proxy_timeout 60s`. Журнал доступа выключен, ошибки — в журнал службы.
- `limit_conn` по адресу клиента (`limit_conn_zone $binary_remote_addr`), например 32 сессии: у одного пользователя два соединения (основное и экран), с запасом на смену сети и NAT семьи. Защита ресурсов узла; SFU и так отбрасывает всё без подлинной проверки ICE и сам ничего не отвечает незнакомым — узел нельзя превратить в усилитель.
- Апстрим — **прямо на публичный адрес SFU** (`PLUMA_RU_SFU_ADDR=195.201.252.126`), не через туннель:
  - ни одного лишнего прыжка: amf → Hetzner около 49 мс, а через дом — amf → дом (около 74 мс) плюс дом → Hetzner, и медиа съедало бы канал дома (дом → amf 50 Мбит/с);
  - без вложения: пакет пересылается как есть, ограничения MTU 1280 туннеля `plumaru` не касаются (пакеты libwebrtc около 1200 байт впритык прошли бы, но без запаса);
  - SFU не надо публиковать ещё и на адресе туннеля.
  Если часть 1 покажет, что длинный поток amf → Hetzner «замерзает», запасной апстрим — туннель (вариант В в «Альтернативах»); переменная та же, меняется адрес.
- Почему nginx, а не DNAT ядра: nginx уже стоит и выкладывается `deploy.sh`, узел по ADR 0072 §8 «не пересылает адресов» (`ip_forward` выключен, `Table = off`), правила ядра на чужой машине владельца и `ip_forward` — риск для его служб. Цена — пакеты идут через пространство пользователя; на десятки участников из России этого с запасом (оценка ниже, замер — часть 6).

### 2. SFU знает свои «трубы» и отдаёт кандидаты по маршруту
- Конфигурация узла SFU: `Media.Relays` — именованные наборы публичных адресов перед этим узлом. В Docker — переменная `SFU_RELAYS`, грамматика по образцу `CALLS_ICE_SERVERS`: записи через `,`, `<имя>=<IPv4 или [IPv6]>:<UDP-порт>/<TCP-порт>`, например `ru=194.87.226.185:20600/20601`; пусто — труб нет. Имя `direct` зарезервировано за собственными `PublicIPs` узла. Ошибка грамматики, повтор имени, имя `direct` — отказ запуска с именем переменной.
- Почему в конфигурации SFU, а не bff: труба стоит перед конкретным узлом (апстрим nginx — адрес этого узла), а адреса, которые видят клиенты, уже живут в конфигурации узла (`Media.PublicIPs`, ADR 0059 §3). При переносе узла меняется одна конфигурация.
- `sfu.proto`: в `JoinRequest` — `repeated string routes = 7;` — наборы адресов по порядку предпочтения; пусто — `direct` (старые bff работают как прежде). `room.Join` строит ответ из адресов названных наборов по порядку.
- Приоритеты кандидатов: внутри набора — как сейчас (UDP выше TCP, IPv4 выше IPv6); между наборами — `localPref` убывает по порядку наборов, так что первый набор клиент проверяет первым (RFC 8445 §5.1.2.1). Повтор одного адреса в двух наборах не выдаётся дважды.
- Набор, которого узел не знает (bff настроен раньше, чем узел), не роняет вход: SFU отдаёт оставшиеся известные наборы, а если не осталось ни одного — `direct`, считает `sfu_route_unknown_total{route}` и пишет предупреждение без данных клиента. На это — тревога (раздел «Наблюдение»). Отказ во входе здесь хуже: клиент из России с VPN войдёт по `direct`.
- ICE через трубу SFU не замечает: первая проверка приходит с адреса amf и порта сессии nginx, она подлинная (ufrag и пароль из ответа), pion заводит peer-reflexive кандидата `amf:порт` и связывает адрес с этим соединением. У каждого клиента своя сессия nginx — свой порт, так что клиенты за одним адресом amf не путаются. ICE-TCP — так же, по одному TCP-соединению nginx на соединение клиента (кадры RFC 4571 идут насквозь). Смена сети клиента — новая сессия nginx и новый адрес для SFU, это обычное повторное выдвижение пары (как смена NAT). Проверяется тестами части 3, не по памяти.

### 3. bff выбирает маршрут по стране
- Переменная `GROUPCALLS_ROUTES` (bff, `GroupCalls.Routes`), грамматика стран — как у `CDN_ROUTES` и `EDGE_ROUTES`: записи через `;`, `<страны через запятую или *>:<наборы через запятую>`, ровно одна запись `*`, страна — не больше чем в одной записи. Пусто — `*:direct`, то есть как сейчас. На проде: `GROUPCALLS_ROUTES=RU,BY:ru;*:direct`.
- `phone.joinGroupCall` и `phone.joinGroupCallPresentation`: страна по `MD.ClientAddr` (`ipcountry.Locator` в `svc` модуля `groupcalls`, тот же клиент `authsession`), наборы записи — в `JoinRequest.routes`. Неизвестная страна и ошибка поиска — запись `*` (метрика `pluma_ipcountry_errors_total` уже есть).
- Почему клиенту из России — только `ru`, без `direct`: SFU выдвигает пару сам (нативные клиенты — ICE-controlled), а с его стороны пары «прямо» и «через amf» неотличимы по приоритету: локальный кандидат один и тот же, приоритет удалённого задаёт клиент по своему типу кандидата, а не по тому, на какой наш адрес он шлёт. Если прямой путь «пропускает первые килобайты и замерзает», SFU мог бы выбрать его и потом терять звонок на 5–25 с. Узел доступен и из-за границы, так что пользователь из России с VPN или ошибка GeoIP ничего не ломают — путь только длиннее. Решение 3.
- Почему остальным — без `ru`: та же неразличимость — иначе часть пользователей из Германии ходила бы к Hetzner через Москву.
- Страна выбирается при каждом входе: переехавший пользователь при следующем входе получает свой набор. Идущее соединение не перестраивается: новые кандидаты клиент получает только новым входом.

### 4. Приватность
- Узел видит то же, что TURN `@ru` обычных звонков: адреса и порты клиентов из России, время и объём пакетов; содержимое — DTLS-SRTP, ключи которого у клиента и SFU, а внутри — кадры tde2e сквозного шифрования (ADR 0060): даже SFU их не читает. Новых данных узел не получает.
- Узел не завершает DTLS и не видит ICE-учётных данных (они в ответе входа, который идёт по MTProto). Журнала доступа нет, журнал ошибок nginx пишет адрес клиента только при ошибке сессии — как TURN узла.
- SFU видит вместо адресов пользователей из России адрес amf — это даже меньше, чем сейчас.

### 5. Лимиты и нагрузка
- Оценка (не замер): звук около 50 пакетов/с и 30–50 Кбит/с в каждую сторону на участника; видео от SFU к получателю — один слой каждого видимого отправителя, до нескольких Мбит/с. 20 участников из России с видео — порядка 40–60 Мбит/с и 5–10 тыс. пакетов/с через nginx в одну сторону. 2 vCPU nginx на это хватает с запасом (по памяти о производительности UDP-прокси nginx — НЕ ПРОВЕРЕНО, замер — часть 6).
- Пропускная способность и тариф трафика Timeweb для amf — НЕ ИЗВЕСТНЫ (вопрос владельцу 4).
- `worker_connections 4096` текущего `nginx.conf`: сессия UDP и соединение TCP занимают по два (клиент и апстрим) — с запасом для 100 пользователей.
- SFU сам понижает слои видео по оценке канала получателя (`Limits.UplinkMbps`, оценка по потерям), лишний прыжок это учитывает без настройки.

### 6. Наблюдение
- SFU: метка `route` у `sfu_connections` и `sfu_connect_failures_total` (наборы, а не адреса: `direct`, `ru`; маршрут соединения — первый набор запроса), новый `sfu_route_unknown_total{route}`.
- Тревоги (`teamgramd/deploy/prometheus/server/rules/groupcalls.yml`):
  - `GroupCallsRelayNoCheck` — за 15 минут были входы по маршруту, а соединений `connected` по нему не было, и `no_check` растёт: до SFU через трубу ничего не доходит (nginx узла, апстрим, экран хостера);
  - `GroupCallsRouteUnknown` — `sfu_route_unknown_total` растёт: узел не знает набора, который просит bff.
- Узел (`teamgramd/deploy/ru/wgstat.sh`, textfile): раз в минуту — `pluma_ru_sfu_upstream_up` (TCP-соединение с апстримом 20601) и `pluma_ru_unit_active{unit="pluma-ru-nginx"}`; тревога `RuSfuRelayDown` в `ru-node.yml`. UDP так не проверить: SFU не отвечает на STUN без учётных данных звонка. Путь UDP целиком подтверждает только `GroupCallsRelayNoCheck` (по факту соединений).
- Ничего из ответа входа (ufrag, пароль, отпечатки) в журналы не пишется — `tools/logaudit` уже это ловит; новые записи журнала — только имена наборов и коды ошибок.

### 7. Выкладка
- Узел: `deploy.sh` — новая переменная `PLUMA_RU_SFU_ADDR` (IPv4, проверка формата), шаблон `stream.conf.tmpl` → `/etc/pluma-ru/stream.conf`, `include` из `nginx.conf` на верхнем уровне; `nginx -t` нового набора, как сейчас. Без переменной блок `stream` не собирается — узел без групповых звонков остаётся прежним. Порты 20600/udp и 20601/tcp открыты: ufw на amf выключен; экран Timeweb — проверить (у TURN узла он пропускает).
- Край: `docker-compose.edge.yaml` — `SFU_RELAYS: ${SFU_RELAYS:-}` в окружении `sfu`; `teamgramd/deploy/sfu/sfu.yaml` и `app/service/sfu/etc/sfu.yaml` — `Relays: "${SFU_RELAYS}"`; в `.env` края `SFU_RELAYS=ru=194.87.226.185:20600/20601`.
- Дом: `GROUPCALLS_ROUTES` в `.env`, `teamgramd/etc2/bff.yaml`, `teamgramd/etc/bff.yaml`, compose bff, `.env.example`.
- Порядок: узел (труба слушает) → край (SFU знает `ru`) → дом (bff просит `ru`). Откат — в обратном порядке, сначала убрать запись `RU,BY` из `GROUPCALLS_ROUTES`.
- Документы: `docs/ops/group-calls.md` (порты, «Перенос», «Неполадки», новые переменные), `docs/ops/ru-node.md` (роль 5 узла, порты, переменная, проверка), `docs/ops/home-server.md` / `edge.md` при необходимости.

## Части работы и порядок
1. **Замер пути amf → Hetzner и ADR 0074.** Длинный поток UDP и TCP с amf до адреса SFU: `iperf3 -s` временно на краю на свободном порту адреса 195.201.252.126 (экран хостера — открыть и закрыть), с amf `iperf3 -u -b 10M -t 120` и TCP `-t 120` в обе стороны. Решает: апстрим прямо (по умолчанию) или через туннель. Записать ADR 0074 (труба медиа групповых звонков на узле, маршруты по стране) с этим замером.
2. **SFU: наборы адресов и маршрут входа.** `config` (`Relays`, разбор `SFU_RELAYS`), `tgcallsjson.BuildResponse` по наборам с приоритетами, `sfu.proto` (`routes`, `make gen` в `app/service/sfu/sfu/gen.sh`), `room.Join`, метрики с меткой `route`. ## Решения к подтверждению
1. «Через CDN» понято как сигнализация через края (уже работает), медиа — через amf; HTTP-CDN медиа звонков не несёт. Так?
2. Труба — nginx stream Pluma на amf, апстрим — прямо на адрес SFU на Hetzner (запасной — через туннель, если замер части 1 покажет «замерзание»).
3. Клиентам из России и Беларуси — только кандидаты amf (без прямых), остальным — только прямые. Беларусь — как в `EDGE_ROUTES` и `CDN_ROUTES` (`RU,BY`).
4. Порты на amf — те же 20600/udp и 20601/tcp, что у SFU. ICE-TCP на 443 amf невозможен: 443 занят разбором SNI владельца, а ICE-TCP не TLS (сделать можно только вторым адресом amf — не в задаче).
5. Неизвестный узлу набор — вход по оставшимся или `direct` с тревогой, а не отказ.
6. SFU остаётся на Hetzner. Перенос SFU на amf (россияне ближе, иностранцы — через Москву, 2 ГБ памяти) — не в задаче.

## Альтернативы
- **А. DNAT ядра на amf (nftables, `ip_forward`).** Быстрее (без пространства пользователя), но меняет маршрутизацию машины, где работают Zabbix, fail2ban и nginx владельца, и противоречит ADR 0072 §8 («узел не пересылает адресов»). Запас, если nginx упрётся в CPU (замер части 6).
- **Б. Второй узел SFU на amf.** Комната живёт на одном узле, каскада нет (ADR 0059 §3): звонок россиян и иностранцев всё равно оказался бы на одном узле. Отклонено.
- **В. Апстрим через туннель** amf → дом → край. Лишние 70+ мс и канал дома, MTU 1280, SFU надо публиковать на адресе туннеля. Только если прямой путь не держит поток.
- **Г. TURN для групповых звонков.** tgcalls и Web K в групповых звонках TURN не используют (`GroupNetworkManager.cpp:398`, `groupCallConnectionInstance.ts:160`); нужны патчи четырёх клиентов — против правила минимальных правок клиентов. Отклонено.
- **Д. Всем — и прямые кандидаты, и кандидаты amf** (как TURN `@ru` обычных звонков всем). SFU не может предпочесть прямой путь (раздел 3 дизайна): часть иностранцев пошла бы через Москву, россияне — через «замерзающий» прямой путь. Отклонено.
- **Е. bff переписывает кандидаты в JSON ответа SFU.** Адреса узла разъехались бы между конфигурациями bff и SFU, bff правил бы чужой ответ. Отклонено.
