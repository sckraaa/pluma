# 108. Сессия отмечает запросы ботов (`RpcMetadata.IsBot`)

- Статус: готово, ждёт выкладки (2026-11-17)
- Решение: без ADR (исправление ошибки; поле уже есть в схеме метаданных).
- Зависит от: 070 (платформа ботов), партия 098–106 (новые проверки `IsBot`).
- Ветка: `task/108-session-is-bot` от `batch/20261115`, влита в партию (`0cd593fb5`).

## Цель
Поле `RpcMetadata.IsBot` (`third_party/teamgram-proto/mtproto/rpc/metadata/rpc_metadata.pb.go:144`) сессия не заполняет: метаданные запроса собираются в `app/interface/session/internal/sess/main_auth_wrapper.go:742-757` без него. Поэтому все проверки `c.MD.IsBot` / `c.MD.GetIsBot()` в bff (около 86 файлов) мертвы: бот не получает `BOT_METHOD_INVALID` там, где Telegram его отказывает, а ветки только для ботов никогда не выполняются. Найдено полным прогоном партии 2026-11-16 (виджеты; путь виджета уже исправлен отдельным поиском, коммит cde8986c7).

## Область
В задаче:
- Сессия заполняет `IsBot` для авторизованного ключа бота: признак берётся один раз при привязке пользователя к ключу (смена `AuthUserId` в `main_auth_wrapper.go:194-219`) из biz user (`users.is_bot` / `bots`), хранится в обёртке, обновляется при входе и выходе. Без лишнего запроса на каждый RPC. Ошибка чтения признака не должна молча делать бота человеком: запрос отвечает временной ошибкой, как другие сбои biz.
- Путь виджета (`cde8986c7`) и `botMarkup`, которые сами ищут признак, переходят на `MD.IsBot`, если это не меняет поведения.
- Аудит всех мест bff, где проверяется `IsBot`: каждая ветка теперь живая. Для каждой — сверить ответ с документацией метода на core.telegram.org (ошибка `BOT_METHOD_INVALID` для методов «только пользователи») и с тем, что бот реально должен уметь (Bot API шлюз, если есть, и задачи 070, 106). Исправить ветки, которые никогда не выполнялись и оказались неверными.
- Деловые подключения (105, `invokeWithBusinessConnection`): `business_connection.go` подменяет `UserId` на владельца и оставляет `IsBot` бота — проверить, что каждый метод, разрешённый боту через подключение, ведёт себя по ADR 0067 (в том числе отказ виджетов в сообщениях пользователя: `INPUT_MEDIA_WIDGET_NOT_ALLOWED`).

Не в задаче: новые методы Bot API; изменения клиентов.

## Тесты
- Модульный тест сессии: метаданные бота несут `IsBot`, человека — нет; смена пользователя ключа меняет признак.
- e2e (`test/e2e`, бот входит через `auth.importBotAuthorization`): несколько методов «только пользователи» отвечают боту `BOT_METHOD_INVALID` (взять из аудита, по одному на область: переводы, игры, быстрые ответы, полные профили); ветки только для ботов работают; существующие e2e ботов проходят.
- Тест, падающий без исправления, — обязателен.

## Проверки владельца
- Бот из `pluma-admin bot create` продолжает отвечать в чате, на кнопки и в инлайн-режиме.

## Решения к подтверждению
- Нет.

## Результат
Сессия заполняет `RpcMetadata.IsBot`: признак читается из `biz` (`user.getImmutableUser`) один раз для пользователя, к которому привязан ключ (первый запрос после входа или после перезапуска сессии), хранится в обёртке ключа вместе с id пользователя и сменяется вместе с пользователем ключа; ошибка чтения не запоминается, запрос получает `INTERNAL_SERVER_ERROR` (клиент повторяет) и не выполняется ни как запрос бота, ни как запрос человека. Ответ `USER_ID_INVALID` — тоже ошибка чтения: `biz` отвечает им на любой сбой загрузки пользователя (`Dao.GetImmutableUser` → `GetCacheUserData`), а пользователи не удаляются, так что пользователь привязанного ключа всегда существует. Все ветки `IsBot` в bff ожили; аудит по страницам методов core.telegram.org исправил неверные, путь виджета и `botMarkup` берут признак из метаданных.

Подробности:
- Сессия: `main_auth_wrapper.go` (`rpcMetadata`, `userIsBot`), клиент `biz` в `dao`/`config`, `BizServiceClient` (5 с, только чтение, ADR 0012 п. 9) в `session.yaml` трёх конфигураций; заметка в `docs/ops/bots.md`.
- Аудит (около 80 файлов): ветки «только пользователи» сверены со страницами методов (переводы, стикеры, гифки, поиск, упоминания, геопозиции, истории, расшифровка, быстрые ответы и Business, мини-приложения, меню вложений, подготовленные сообщения, запрошенные чаты, `invalidateSignInCodes`, `receivedMessages`, метрики) — верны. Исправлено: `messages.getInlineBotResults` и `messages.sendInlineBotResult` («Only users») отвечают боту `BOT_METHOD_INVALID` (раньше бот отсекался только для ярлыка быстрого ответа); `messages.getPeerSettings`, `stories.getChatsToSend`, оба `stories.getPeerMaxIDs` («Only users») отвечают боту `BOT_METHOD_INVALID` вместо урезанного ответа; отправка бота в ярлык быстрого ответа — `QUICK_REPLIES_BOT_NOT_ALLOWED` (страницы `messages.sendMessage`/`sendMedia`; новая ошибка в `rpc_error_codes.go`, `// pluma:`). Правка в ярлыке (`editMessage`) оставлена `BOT_METHOD_INVALID`: страница метода ошибки не называет. `messages.sendMedia` с игрой: бот больше не может отправить игру чужого бота (`GAME_BOT_INVALID`, ветка ожила).
- Деловые подключения: для каждого разрешённого метода (`sendMessage`, `sendMedia`, `sendMultiMedia`, `editMessage`, `deleteMessages`, `readHistory`, `setTyping`, `updatePinnedMessage`, `account.updateProfile`) `IsBot` бота при `UserId` владельца даёт верное поведение: клавиатура бота в сообщении владельца сохраняется (`markupBot`), виджет и игра отказываются, ярлыки и отложенные — `BOT_ACCESS_FORBIDDEN` раньше проверки бота, коды входа в тексте сбрасываются, стикер бота не попадает в недавние стикеры владельца.
- Тесты: модульные в сессии (бот/человек, смена пользователя ключа, после перезапуска, сбой чтения и его повтор, ответ 500 из `rpcRunLoop`; без поля `IsBot` три теста падают — проверено), в bff (признак из метаданных без запросов к сервисам, ошибки ботов в инлайне, историях, `getPeerSettings`, быстрых ответах; тест виджета человека без изменения падает разыменованием nil); e2e `test/e2e/bot_is_bot_test.go` (бот через `auth.importBotAuthorization`: семь методов «только пользователи» по областям, инлайн, быстрый ответ, клавиатуры). На отдельном стенде прошли 34 e2e ботов, инлайна, виджетов, игр, мини-приложений и Business, включая новый.

Решения к подтверждению: ошибка `QUICK_REPLIES_BOT_NOT_ALLOWED` для отправки в ярлык; отказ ботам в `getPeerSettings`, `stories.getChatsToSend`, `stories.getPeerMaxIDs`, `getInlineBotResults`, `sendInlineBotResult`.

Отклонения и открытые вопросы: создание и изменение наборов стикеров ботами по документации разрешено («Both users and bots»), но ADR 0053 п. 12 оставляет ботам `BOT_METHOD_INVALID` до отдельной задачи (наборы `…_by_<бот>`), не менялось. `messages.getGameHighScores` по документации «Only bots», а задача 106 сознательно разрешила его пользователям (Web K) — оставлено. Методы «только пользователи» без проверки `IsBot` вообще (например, `messages.getBotCallbackAnswer`) в объём аудита веток не входили и не проверялись; отказ `USER_IS_BOT` при сообщении бота боту не реализован (ветки нет). Как поведут себя библиотеки ботов (Telethon, Pyrogram, TDLib), если при старте вызывают метод, теперь отвечающий `BOT_METHOD_INVALID`, — не проверено.

Проверка в партии `batch/20261115` (CachyOS, `72fa7dbac`): build и vet обоих модулей, модульные тесты (231 пакет), `-race` (153), `make lint` (0 замечаний), `go test ./tools/...` (6, с журнальным аудитом), интеграционные (70 пакетов), e2e на свежем стенде — 344 PASS, 0 FAIL, 2 SKIP (среди них `TestBotIsBot`). Для выкладки: новый образ `session` (клиент `biz` в `session.yaml`), отдельных переменных и миграций нет. В живых клиентах и с настоящими библиотеками ботов не проверено (`TESTING-BACKLOG.md`, раздел задачи 108).
