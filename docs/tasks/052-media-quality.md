# 052. Качество медиа: сжимаем меньше, чем Telegram

- Статус: in progress (сервер выкачен, патчи Android и iOS влиты 2026-11-03; осталась проверка на устройстве после подписанных сборок)
- Зависит от: —
- Исследование: `docs/tasks/052-research/clients.md` (как сжимают видео четыре клиента, таблицы и точки правки).

## Цель
Медиа в Pluma не хуже, а лучше, чем в Telegram: где сервер или клиент пережимает, пережимать меньше; при отправке видео — выбор качества, как в Telegram, но с более высоким битрейтом на каждом разрешении.

## Решение владельца (2026-11-03)
«В качестве медиа, звонках и т. д. мы хотим не повторять Telegram, а превзойти его. Если мы где-то что-то сжимаем, сжимать меньше. При отправке видео Telegram предлагает выбор качества; у нас он тоже должен быть, но наш битрейт на разрешение должен быть приятнее, чем у Telegram.»

- 2026-11-03, качество по умолчанию: «на мобильном 720, на WiFi 1080». Сервер отдаёт `video_upload_maxbitrate` 50/85/100. iOS выбирает пресет `v*5/100`: 4 (720p) на мобильном интернете, 5 (1080p) на Wi-Fi. Android выбирает ступень `round(v / (100/ступеней)) - 1`: при 85 это 720p у исходника 1080p и лучшая ступень у исходника меньше 720p, при 100 — 1080p. Тест `TestVideoUploadPresets`, коммит `b31ad700`.

## Находки: сервер (`app/service/dfs`, `app/service/media`, `pkg/goffmpeg`)
- **Обычное видео (`video/mp4`) сервер не перекодирует**: `dfs.uploadMp4DocumentMedia` хранит файл клиента как есть и только берёт первый кадр для превью. Качество видео в сообщениях решают клиенты.
- **Видео-аватар** (`uploadProfilePhotoFileV2` → `ConvertToMp4ByPipe(…, 800, 800)`): перекодировался x264 с настройками по умолчанию (crf 23, preset medium) поверх уже сжатого клиентом ролика (Android 1,56–2,6 Мбит/с, iOS до 2,4 Мбит/с), со звуком, если он был.
- **GIF > 10 КБ** (`uploadGifDocumentMedia`; так присылает GIF-файлы tdesktop, `localimageloader.cpp:926-927`): перекодировался в mp4 **с уменьшением до 320 px** по длинной стороне, x264 по умолчанию.
- **Первый кадр** (`GetFirstFrame*`, mjpeg): качество ffmpeg по умолчанию (PSNR ≈ 43 дБ на тестовом GIF). Из этого кадра потом делаются фото-размеры видео-аватара (a/b/c) и превью GIF и видео — двойное сжатие.
- **Stripped-превью (`i`) было испорчено**: сервер квантовал скан таблицами качества 30, а клиенты собирают JPEG с фиксированным заголовком Telegram, в котором таблицы качества 20 (Android `Bitmaps.header` + `ImageLoader.getStrippedPhotoBitmap:1795`; наш `imaging.JpegHeader` — те же байты). Клиент умножал коэффициенты не на те делители: размытая заглушка выходила с завышенным контрастом, средняя ошибка ~20 уровней из 255 против ≤ 6 при совпадающих таблицах (тест `TestStrippedMatchesClientHeader`).
- **Фото**: размеры s/m/x/y/w (90/320/800/1280/2560) и a/b/c/d кодируются Go-кодером JPEG с качеством 95 (по умолчанию `disintegration/imaging`, `io.go:166`) — это уже выше, чем у Telegram Desktop (87). Не менялось. Расхождения с core.telegram.org/api/files: `s` у нас 90 px, в документации 100; видео-аватар у нас типа `v`, в документации анимированная аватарка — `u`, `v` — «video preview». В этой задаче не трогались (константы во вшитом proto), вынесены в вопросы.
- **`account.getAutoDownloadSettings` отдавал `video_upload_maxbitrate = 0`** во всех трёх пресетах. iOS превращает 0 в пресет Medium — **480p, 1,6 Мбит/с** по умолчанию для всех пользователей Pluma на iOS (`LegacyAttachmentMenu.swift:14-53`), т. е. хуже Telegram. На Android 0 в выбранном пресете даёт самую сильную ступень сжатия (`SendMessagesHelper.java:11727-11731`).
- Не используются и не менялись: `FFmpegUtil.ConvertToMp4` (фиксированные 218k) и `ConvertPngToMp4ByPipe`.

## Находки: Telegram и клиенты (подробно — `052-research/clients.md`)
- Android и iOS пережимают видео перед отправкой (Android: 720p — 2,6 Мбит/с, 1080p — 6,8; iOS: 480p — 1,6, 720p — 3,0, 1080p — 6,6). Выбор качества — ползунок; оригинал — только «как файл».
- tdesktop и Web K отправляют оригинал видео (Web K перекодирует только `.mov` HEVC, GIF и видео из редактора — с высоким битрейтом).
- Сервер Telegram для больших каналов сам делает несколько качеств в `alt_documents` (core.telegram.org/api/files); Desktop и Web K их проигрывают (Web K — через HLS-плейлисты `mtproto:<id>`). Что Telegram делает с обычными загрузками в личных чатах — не проверено.

## Что сделано на сервере
| Что | Было | Стало |
|---|---|---|
| Видео-аватар 800×800 | x264 по умолчанию: crf 23, preset medium, звук сохранялся | crf 18, preset slow, профиль High, yuv420p, VBV-потолок 4 Мбит/с (буфер 8 Мбит), без звука |
| GIF → mp4 | 320 px по длинной стороне, x264 по умолчанию | собственный размер GIF, длинная сторона ≤ 720, стороны чётные; те же x264-настройки; размер в `documentAttributeVideo` — по результату |
| Первый кадр (mjpeg) | качество по умолчанию (≈ 43 дБ) | `-qscale 2` (≈ 48 дБ) |
| Stripped-превью `i` | качество 30 при заголовке с таблицами 20 | качество 20 = таблицы заголовка; параметр качества убран из `imaging.EncodeStripped`, константа `StrippedQuality` |
| `video_upload_maxbitrate` | 0 / 0 / 0 | 50 / 100 / 100 (встроенные значения Android `DownloadController.java:261-263`) → iOS по умолчанию 1080p (не выше размера исходника в пикере), Android — без лишнего сжатия |

Обоснование чисел: crf 18 — визуально без потерь для x264 (вместо 23); потолок 4 Мбит/с ≈ 1,5× от лучшего клиентского битрейта аватара, обычные исходники остаются заметно ниже. Замер на тестовом 800×800 (2 с, сложная синтетика): crf 23 — SSIM 0,9947, crf 18 — 0,9980 при росте файла в 1,5 раза. Время: 30 с 720p30 в preset slow — 9 с на 4 потоках Apple M; на CX33 оценочно 20–30 с, поэтому длинная сторона GIF ограничена 720 (тайм-аут RPC 120 с).

Файлы: `app/service/dfs/internal/ffmpegutil/ffmpeg_util.go`, `app/service/dfs/internal/core/dfs.uploadGifDocumentMedia_handler.go`, `app/service/dfs/internal/imaging/stripped.go` и пять вызовов `EncodeStripped` (`dfs.upload{Mp4DocumentMedia,DocumentFileV2,WallPaperFile,ThemeFile,GifDocumentMedia}_handler.go`, `imaging/convert/stripped`), `app/bff/autodownload/internal/core/account.getAutoDownloadSettings_handler.go`.

Тесты: `ffmpeg_util_test.go` (GIF сохраняет размер 704×590; ограничение 720 в обеих ориентациях; аватар 800×800 H.264 High без звука из ролика со звуком; набор аргументов x264 без `-b:v`; PSNR первого кадра ≥ 46 дБ — падает без `-qscale 2`: 43,7 дБ), `imaging/stripped_test.go` (сборка JPEG как у Android, ошибка ≤ 6 уровней — падает при качестве 30: 20,1), `account.getAutoDownloadSettings_handler_test.go` (50/85/100 и TL-кодирование слоя 228).

Проверка (2026-11-03): `go build ./...`, `go vet` (dfs, media, autodownload), `go test` и `-race` затронутых пакетов, `go test ./tools/...` (включая logaudit), `make lint` (0 замечаний) — зелёные; e2e на CachyOS (`pluma-e2e-052`, стенд снят): `TestProfileVideo` и `TestSavedGifs` проходят. ## Решения на подтверждение
- `video_upload_maxbitrate` = 50/85/100, как встроенные значения Android: iOS по умолчанию отправляет 1080p (Wi-Fi и мобильная сеть одинаково). Если на мобильной сети нужен 720p — medium = 80.
- GIF: длинная сторона до 720 px (было 320) ради тайм-аута RPC на CX33; можно 1280, если замер на сервере покажет запас.
- Видео-аватар и GIF всегда без звука, как у Telegram.
- Android: делать ли 1080p ступенью по умолчанию (`maxCompression`), или только запоминать выбор пользователя.
- Таблица Pluma ≈ 1,8–2× Telegram (720p — 5 Мбит/с, 1080p — 12): размер минуты 1080p ≈ 90 МБ.

## Результат
Серверная часть: сервер больше не ухудшает то, что прислал клиент, — видео-аватар и GIF перекодируются в «визуально без потерь» (crf 18, slow, High), GIF больше не уменьшаются до 320 px, первый кадр берётся в лучшем JPEG-качестве, исправлены stripped-превью (таблицы квантования не совпадали с заголовком клиентов), клиенты получают `video_upload_maxbitrate` 50/85/100 вместо 0 (iOS отправлял все видео в 480p). Клиентские патчи — следующий шаг по плану выше.
