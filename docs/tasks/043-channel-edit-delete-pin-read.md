# 043. Каналы: правка, удаление, закрепление, прочтение

- Статус: in progress (сервер готов полностью, ждёт проверки в клиентах)
- Зависит от: 040
- ADR: 0034 «Ящик канала». Исследование: `docs/tasks/035-research/` (`server.md` §1.1, §2.3, §2.5, задача T8; `clients.md` §1 «Read history», «Send and receive»; `plan.md` §2 U1, U5, §3, задача «042» плана).

## Цель
Правки и удаления в канале видят все участники; закрепление работает; галочки прочтения и счётчики непрочитанного согласованы между устройствами.

## Что известно
- **Заблокировано сейчас** (`server.md` §1.1): `msg.editMessageV2` для `PEER_CHANNEL` — `ErrEnterpriseIsBlocked` (`app/messenger/msg/msg/internal/core/msg.editMessageV2_handler.go:41-43`); `msg.deleteMessages` — `ErrPeerIdInvalid` (`msg.deleteMessages_handler.go:32`). Остальные `channels.*` здесь — `missing` в `api-coverage.md`.
- **Обновления с `pts` канала:** `updateEditChannelMessage`, `updateDeleteChannelMessages`; `updatePinnedChannelMessages`; `updateReadChannelInbox` (api.tl:347, свой `pts`), `updateReadChannelOutbox` (`server.md` §2.1, §2.5).
- **`messages.affectedMessages`** из `channels.deleteMessages` и похожих Android пропускает через `processNewChannelDifferenceParams` (`MessagesController.java:8171-8213`, 035): `pts` там должен принадлежать последовательности канала.
- **Прочтение:** `channels.readHistory` и `channels.readMessageContents` (Android — оба; iOS `AccountViewTracker` — `readMessageContents`). Для 100 пользователей состояние прочтения остаётся в `dialogs` (`server.md` §2.3); исследование рекомендует писать только строку читателя.
- **Своим устройствам** (U1, ADR 0034, п. 3): `updateReadChannelInbox` идёт с `seq` своего аккаунта, свёртка — последнее по каналу; его `pts` — текущий `channels.pts`: Web K проводит его через проверку `pts` канала с `pts_count = 0` (`apiUpdatesManager.ts:639-641`, `:696-724`), tdesktop и iOS верят `still_unread_count` только при равном `pts` (`history/history.cpp:2183`, `AccountStateManagementUtils.swift:4725-4764`). Так же своим устройствам — `updateChannelReadMessagesContents`, `updateChannelAvailableMessages`. Как у Telegram — не проверено.
- **`read_outbox_max_id` в супергруппе** (U5, ADR 0034, пп. 1, 3): для зрителя — наибольший `read_inbox_max_id` других участников, вычисляется при чтении; `updateReadChannelOutbox` — пушем без `seq` авторам сообщений в прочитанном диапазоне, только в супергруппах. Определение Telegram не проверено.
- Упоминания: `readMentions`, `getUnreadMentions` — `partial`; таблица упоминаний каналов — по образцу `migrate-20261030-unread-mentions.sql` (`server.md` §2.3). `dialog.getChannelMessageReadParticipants` уже отвечает из `dialogs.read_inbox_max_id`.
- Проверки прав (правка чужого, удаление чужого, закрепление) — по роли, если 042 ещё нет; иначе через `channelperm.Can` (кто из 042 и 043 позже, тот подключает).

## Область
- `PEER_CHANNEL` в `msg.editMessageV2` (`:41`), `messages.editMessage`, `messages.getMessageEditData`.
- `channels.deleteMessages` (`affectedMessages` с `pts` канала), `channels.deleteHistory` (оба варианта; «для себя» — через `available_min_id`), `channels.deleteParticipantHistory`.
- `messages.updatePinnedMessage` и `unpinAllMessages` для каналов (`updatePinnedChannelMessages`).
- `channels.readHistory` (`updateReadChannelInbox` своим устройствам, `updateReadChannelOutbox` остальным), `channels.readMessageContents`, ветки каналов в `readMentions` и `getUnreadMentions`.
- Свёртка правок и удалений в `getChannelDifference` (040) учитывает новые типы записей журнала.
- Не трогаем: реакции (044), просмотры (046).

## Критерии приёмки
- Модульные тесты: сборка ответов и обновлений, `affectedMessages` с `pts` канала.
- Интеграционные тесты на MySQL через `pkg/testinfra`: свёртка журнала «правка, затем удаление»; параллельные удаления не дают дыр в `pts`.
- e2e через `pkg/mtclient`: правку и удаление видит другой участник; прочтение на устройстве A доходит до устройства B; отправитель получает `updateReadChannelOutbox`; тест падает на текущем коде.
- `go run ./tools/apicoverage` перезапущен; обычные проверки: `go build ./...`, `go vet -unreachable=false`, `go test` и `-race` затронутых пакетов, `make lint`, `go test ./tools/...`.
- В клиентах, со скриншотами: правки, удаления и закрепления видят другие участники в iOS, Android, Desktop (CachyOS) и Web K; галочки и счётчики непрочитанного совпадают на двух устройствах одного пользователя.

## Результат
### Прочтение (2026-11-04, ветка `task/038-channel-create`)
Сделано раньше остального 043: без него счётчик непрочитанного у участников канала не сбрасывается, а это блокирует выкат каналов.
- `channels.readHistory` → biz `channel.readHistory`: транзакция ящика читателя, канал не блокируется и его `pts` не растёт. `read_inbox_max_id` двигается только вперёд (`max_id` 0 или выше последнего — до последнего), упоминания до него прочитаны. Своим устройствам — `updateReadChannelInbox` с `seq` (свёртка — последнее по каналу), с `pts` канала и `still_unread_count`. В супергруппе авторам прочитанного — `updateReadChannelOutbox` пушем без `seq` (не больше 1000 авторов). Метку «непрочитано» прочтение не трогает (у каналов её снимает `messages.markDialogUnread`). Не участник публичного канала получает `true` без записи; чужой закрытый — `CHANNEL_PRIVATE`.
- Строка диалога сбрасывается в кэше biz dialog после коммита, как у всех писателей диалогов каналов.
- **Проверка:** интеграционный `TestRead` (только вперёд, упоминания, `seq`-строка с `pts` и счётчиком, пуш автору, не участник; падает без проверки «только вперёд»), модульный `TestSeqFold` (свёртка `updateChannel` и `updateReadChannelInbox` по каналу), e2e `TestChannelRead` (счётчик до и после, второе устройство, автор).

### Правка, удаление, пересылка (2026-11-04)
- **Правка.** `messages.editMessage` в канале → msg `editChannelMessage`: в транзакции редактора под блокировкой канала меняется единственная копия, строка журнала `updateEditChannelMessage` несёт всё сообщение после правки (как ADR 0019), пуш участникам. Кто может: автор своё сообщение в супергруппе; в канале — создатель и админы с `edit_messages` любой пост, автор — свой, пока может публиковать (core.telegram.org/constructor/chatAdminRights). Иначе `MESSAGE_AUTHOR_REQUIRED`.
- **Удаление.** `channels.deleteMessages` → biz `channel.deleteMessages`: свои сообщения — всем, чужие — создателю и админам с `delete_messages`, иначе `MESSAGE_DELETE_FORBIDDEN` (core.telegram.org/method/channels.deleteMessages). Одна строка журнала на запрос (`pts_count` — число id), упоминания удалённых снимаются, `top_message` откатывается к последнему оставшемуся, пуш участникам. Несуществующие и уже удалённые id пропускаются; ничего не удалено — `pts` канала и `pts_count` 0. Не больше 100 id.
- **Пересылка из канала.** `messages.forwardMessages` с `from_peer` канала: сообщения берутся из единственной копии как их видит пересылающий (biz отвечает `CHANNEL_PRIVATE` постороннему закрытого канала); пост канала — `fwd_from` от канала с `channel_post`, сообщение супергруппы — от автора; в «Избранном» `saved_from_peer` — канал. Канал с запретом пересылки — `CHAT_FORWARDS_RESTRICTED`. Служебные сообщения не пересылаются.
- **Проверка:** интеграционный `TestDelete`; e2e `TestChannelEdit` (правка автором доходит до другого участника, чужое не правится и не удаляется, создатель удаляет, удаление доходит пушем, история и разница его учитывают) и `TestChannelForward`.
- **Осталось:** закрепление, `readMessageContents`, ветки каналов в `readMentions` и `getUnreadMentions`.

### Закрепление, поиск, содержимое и упоминания (2026-11-07, ветка `task/043-pin`)
- **Поиск в канале** (`messages.search` → biz `channel.search`): текст (символы `%`/`_` — как текст), автор, тип медиа (как хранится, `GetMediaType`; фото и видео вместе — `MEDIA_PHOTOVIDEO`; голосовые и кружки — один тип, как в ящиках пользователей), даты, закреплённые. Служебные сообщения не находятся, кроме смены фото. Ответ — `messages.channelMessages` со счётчиком всех найденных. Без него не работали вкладки медиа в профиле канала и загрузка закреплённых клиентами.
- **Закрепление** (`messages.updatePinnedMessage`, `messages.unpinAllMessages` для канала): в транзакции закрепившего под блокировкой канала, права — `channelperm` (`PinMessages`: в трансляции и с `edit_messages`). Строка журнала `updatePinnedChannelMessages`, при закреплении — служебное `messageActionPinMessage` (в трансляции — пост без автора), пуш участникам. Сообщение получает флаг `pinned`. `channelFull.pinned_msg_id` — последнее закреплённое. Повторное закрепление закреплённого ничего не пишет.
- **`channels.readMessageContents`:** упоминания среди сообщений прочитаны, своим устройствам — `updateChannelReadMessagesContents` с `seq` (добавлен в `userbox.SeqUpdate`: повтор безвреден). Отметка `media_unread` голосовых в канале не меняется — как её ведёт Telegram в супергруппах, не сверено.
- **Упоминания:** `getUnreadMentions` — поиск по непрочитанным упоминаниям; `readMentions` — все сразу, ответ — `pts` канала с `pts_count` 0 (tdesktop применяет его к каналу, `apiwrap.cpp:2264-2273`; Web K — к общему `pts`, `appMessagesManager.ts:8837-8842`, где больший `pts` даст лишний `getDifference`).
- **Проверка:** интеграционные `TestSearch`, `TestReadContents`, `TestMentions`; e2e `TestChannelPin` (участник без права не закрепляет, ответ и пуш, фильтр закреплённых, `pinned_msg_id`, открепление всех).
- **Осталось:** `channels.deleteHistory` (оба варианта), `channels.deleteParticipantHistory`; проверка в клиентах.

### Удаление истории (2026-11-08, ветка `task/043-delete-history`)
Ветка закрывает остаток 043 на сервере; живая проверка в клиентах не делалась.

- **`channels.deleteHistory` (#9baa9647 и старый #af369d42, он только «для себя», `Bool`).** Обе формы → biz `channel.deleteHistory`. `max_id` 0 или больше последнего — до последнего (Android шлёт `Integer.MAX_VALUE`, `MessagesController.java:10252`; Web K рассчитывает на обрезку сервером, `appMessagesManager.ts`, `flushHistory`).
- **Для всех** (`for_everyone`): только создатель, иначе `CHAT_ADMIN_REQUIRED`; канал больше 1000 участников — `CHANNEL_TOO_BIG` (core.telegram.org/method/channels.deleteHistory). Клиенты предлагают только создателю: tdesktop `PeerData::canRevokeFullHistory` (`data_peer.cpp:1813`), Android и iOS по `channelFull.can_delete_channel` (`ChatActivity.java:3821`, `ChatControllerNavigationButtonAction.swift:144-147`). Удаляется порциями по 1000 в отдельных транзакциях (`dao.DeleteHistory`): канал не заблокирован на всю длинную историю, строка журнала содержит не больше 1000 id, повтор после обрыва доделывает. Первое сообщение канала (создание или миграция) остаётся: Web K, `flushHistory`, «a channel keeps its creation service message through a clear» (комментарий клиента; поведение Telegram напрямую не сверено). Запись порции — общий с `channels.deleteMessages` `deleteRows`: упоминания, `top_message`, журнал, пуш `updateDeleteChannelMessages`. Закреплённые и счётчики комментариев считаются по неудалённым строкам и обновляются сами. Ответ: `updateDeleteChannelMessages` для одной порции; для нескольких — `updateChannelTooLong` с достигнутым `pts`, клиент догружает разницу (тот же комментарий Web K). Ничего не удалено — `Updates` без обновлений.
- **Для себя:** `available_min_id` участника = `max_id + 1` (строка хранит первое видимое; поле на проводе — последнее скрытое, core.telegram.org/constructor/updateChannelAvailableMessages, tdesktop `History::clearUpTill` `<` и `==`, iOS `deleteMessagesInRange(minId: 1, maxId: id)`, Android `obj.getId() <= id`). Канал не блокируется. Отметка прочтения и упоминания до этого id сдвигаются (`moveRead`, общий с `Read`, `updateReadChannelInbox` с `seq`), своим устройствам — `updateChannelAvailableMessages` с `seq` (добавлен в `userbox.SeqUpdate`: клиенты берут максимум, повтор безвреден). Ответ — то же обновление. Вне канала: публичный — `CHANNEL_PARICIPANT_MISSING`, закрытый — `CHANNEL_PRIVATE`. `channelFull.available_min_id` теперь отдаётся участнику (и для скрытой предыстории); вышедшему из публичного канала — нет, его история читается целиком (`TestAvailableMinId`). В `getDialogs` диалог со всей скрытой историей имеет `top_message = 0`, как в `channelDifferenceTooLong`.
- **`channels.deleteParticipantHistory`** → biz `channel.deleteParticipantHistory`: только супергруппа (`CHANNEL_INVALID` для канала), права — `channelperm.DeleteOthers` (`CHAT_ADMIN_REQUIRED`), `participant` — пользователь (иначе `PARTICIPANT_ID_INVALID`: авторы супергруппы — пользователи). 100 новейших за запрос; `offset` = сколько осталось, убывает (core.telegram.org/constructor/messages.affectedHistory), клиенты повторяют при `offset > 0` (Android `MessagesController.java:9634`, tdesktop `apiwrap.cpp:1508`, iOS `DeleteMessagesInteractively.swift:273`). `pts` — канала; пусто — `pts` канала и `pts_count` 0. Служебное сообщение о вступлении тоже удаляется: это сообщение участника. Копия поста канала в группе обсуждения не удаляется: её автор — канал (`postCopy`, core.telegram.org/api/discussion), хотя строка хранит админа, опубликовавшего пост.
- **`messages.deleteHistory` с каналом.** Клиенты зовут для канала только диапазон дат (Web K, tdesktop `deleteMessagesByDates` — оба к отказу готовы): `CHAT_REVOKE_DATE_UNSUPPORTED` (core.telegram.org/method/messages.deleteHistory). Без дат для канала клиенты зовут `channels.deleteHistory`; остаётся `PEER_ID_INVALID` (что отвечает Telegram, не проверено).
- **Проверка:** интеграционные `TestDeleteHistoryForEveryone`, `TestDeleteHistoryPortions` (1100 сообщений), `TestHideHistory`, `TestDeleteParticipantHistory`, `TestDeleteParticipantHistoryKeepsPosts` (копия поста остаётся, счётчик комментариев падает; без исправления тест падает); модульные `TestDeleteHistoryUpdates`, `TestHideHistoryUpdates`, `TestHistoryMaxId`, `TestDeleteHistoryChannel`; e2e `TestChannelDeleteHistory`. Без `updateChannelAvailableMessages` в `SeqUpdate` `TestHideHistory` падает.

## Решения на подтверждение
1. Первое сообщение канала остаётся после очистки для всех (со слов комментария Web K).
2. При повторном входе `available_min_id` по-прежнему задаётся заново (как было): очищенная для себя история снова видна вышедшему и вернувшемуся. Как у Telegram — не проверено.
3. `messages.deleteHistory` с каналом без дат отвечает `PEER_ID_INVALID`. Клиенты так не зовут; ответ Telegram не проверен.
4. Служебное сообщение о вступлении удаляется вместе с сообщениями участника.
5. `channels.deleteParticipantHistory` работает и для автора-админа и создателя (включая первое сообщение супергруппы): право только `DeleteOthers`, как у `channels.deleteMessages`. Защита админов у Telegram не проверена.
6. Диалог, вся история которого скрыта для себя, отдаётся с `top_message = 0`. tdesktop (`History::clearUpTill`, `applyEditionToHistoryCleared`) показывает сообщение с `id == available_min_id` как очистку истории, так что Telegram, возможно, оставляет его верхним сообщением диалога; не проверено, положение такого диалога в списке смотреть в клиентах.
