# 030. Наборы стикеров и эмодзи из Telegram по запросу

- Статус: in-progress (2026-11-02)
- Зависит от: 024 (каталог, импорт документов)
- ADR: новый (бот Telegram на сервере, хранение наборов по запросу)

## Цель
Любой набор стикеров или эмодзи из Telegram доступен в Pluma. Пользователь открывает `t.me/addstickers/<имя>` или `t.me/addemoji/<имя>`, и набор появляется сразу. При первом запросе сервер берёт его у Telegram и пополняет свою базу (запрос владельца, 2026-11-02).

## Что известно
- **Клиенты** сами разбирают такие ссылки и спрашивают сервер `messages.getStickerSet(inputStickerSetShortName)`. Сейчас набора, которого нет в каталоге, сервер не знает и отвечает `STICKERSET_INVALID`.
- **Боты** могут вызывать `messages.getStickerSet` и `upload.getFile`. На страницах core.telegram.org/method/messages.getStickerSet и /upload.getFile: «Both users and bots can use this method», проверено 2026-11-02.
  - Бот входит через `auth.importBotAuthorization(api_id, api_hash, bot_auth_token)`, без телефона и кода.
  - Аккаунты владельца не участвуют.
- **На сервере** (2026-11-02) лежат `TELEGRAM_BOT_TOKEN` и `TELEGRAM_API_HASH` в `/opt/pluma/.env`. Их положил владелец; значения не читались. `TELEGRAM_API_ID` был там раньше (задача 021).
- **Подключение к Telegram** уже есть в `pkg/langpack/telegram.go`: `mtclient` с RSA-ключом Telegram, DC 2. Ответы приходят в слое 228, их разбирает наш кодек, перевод из tweb не нужен.
- **Импорт** — путь задачи 024: `dfs/media.importDocument`, перенумерация и `catalog_ids`.
- **Разница с Telegram:** по документации `STICKERSET_INVALID` у Telegram — ошибка 406, у нас — 400 (`mtproto.ErrStickersetInvalid`). Проверить, что ждут клиенты.

## Область
- **Клиент бота на сервере.**
  - Вход ботом и переподключение.
  - Подключения к другим DC для файлов: `auth.exportAuthorization` / `importAuthorization`, адреса из `help.getConfig`.
  - Обработка `FILE_MIGRATE`, `FLOOD_WAIT`, ограничение частоты.
- **Получение по запросу.**
  - В `messages.getStickerSet` (по имени и по id набора, пришедшего из Telegram) набор, которого нет, берётся у Telegram с ожиданием в несколько секунд.
  - Одна загрузка на набор, сколько бы пользователей ни открыли ссылку одновременно.
  - Ограничения на размер набора и общий объём.
- **Хранение.** Наборы по запросу хранятся отдельно от каталога: `Store.Replace` при новом импорте каталога не должен их удалять. Добавить у набора источник (`catalog` или `demand`), id — через `catalog_ids`.
- **Установка наборов пользователями** (иначе «Добавить» ничего не сохраняет): `installStickerSet`, `uninstallStickerSet`, `getAllStickers`, `getEmojiStickers`, `reorderStickerSets` с хэшем по формуле клиентов и `updateNewStickerSet` / `updateStickerSets` на другие устройства. Это часть этапа 2, без неё задача неполна.
- **Свои эмодзи в сообщениях** из наборов, полученных по запросу, — через `getCustomEmojiDocuments` (документы каталога).

## Критерии приёмки
- Ссылки `t.me/addstickers/…` и `t.me/addemoji/…` открывают набор в Android, iOS, Desktop и Web K. После «Добавить» набор остаётся в панели на всех устройствах аккаунта.
- Повторный запрос того же набора не обращается к Telegram.
- Новый импорт каталога не удаляет наборы, полученные по запросу.
- e2e: набор по имени через поддельный Telegram в стенде. Настоящий Telegram в CI не используется.

## Ход работы
- 2026-11-02: владелец создал бота и положил `TELEGRAM_BOT_TOKEN` и `TELEGRAM_API_HASH` в `/opt/pluma/.env` (значения не читались).
- **Готово в ветке `task/030-sticker-sets-on-demand`:**
  - `pkg/tgbot` (`cb08c9af`) — клиент бота. Вход ботом, переход на его DC, адреса DC из `help.getConfig`, перенос авторизации на DC файла, `FILE_MIGRATE`, `FLOOD_WAIT`, параллельное скачивание. Тесты на поддельном Telegram.
  - `pkg/catalog/demand` и `importer.ImportSet` (`1cfc2bad`). Одна загрузка на имя, «нет такого» запоминается на час, лимиты. Хранение рядом с каталогом: `source = 'demand'`, `migrate-20261103-catalog-demand.sql`, импорт каталога такие наборы не удаляет.
  - `getStickerSet` по имени берёт недостающий набор у Telegram (`5983276d`). Переменные бота передаются в `bff` и `migrate`, пустые — бот выключен. Описание — `docs/ops/catalog.md`.
  - Установленные наборы аккаунта (`d9f20be6`, `1c7665f4`). Таблица `user_sticker_sets` (`migrate-20261103-user-sticker-sets.sql`), пакет `pkg/catalog/installed`. Методы `installStickerSet`, `uninstallStickerSet`, `toggleStickerSets`, `reorderStickerSets`, `getAllStickers`, `getMaskStickers`, `getEmojiStickers`, `getArchivedStickers`. Другие устройства аккаунта получают обновления с `seq` (кроме устройства, сделавшего изменение, ADR 0022): `updateNewStickerSet` при установке, `updateStickerSets` при удалении и архивации, `updateStickerSetsOrder` с полным порядком. Исследование клиентов — `docs/tasks/030-research/`.
- **Решения (подтвердить):**
  - Автоархивации нет: `installStickerSet` всегда отвечает `stickerSetInstallResultSuccess`.
  - Все операции идемпотентны. Установка уже установленного набора поднимает его наверх; удаление или архивация отсутствующего — без ошибки и без обновления.
  - Набор каталога, установленный хоть одним аккаунтом, переживает новый импорт каталога (становится `source = 'demand'` без `kind`).
  - `toggleStickerSets` требует ровно один флаг и не больше 200 наборов, иначе `INPUT_REQUEST_INVALID`.
  - Порядок нормализуется: неизвестные и повторные id отбрасываются, пропущенные дописываются в старом порядке.
  - Три обновления наборов пишутся в журнал `seq` (`userbox.SeqUpdate`). Хвост журнала, применённый заново по порядку, приводит к тому же итогу: установка поднимает набор наверх, порядок задаётся целиком, остальное — «перезагрузить».
  - `STICKERSET_INVALID` остаётся 400, как в `getStickerSet`. В документации Telegram — 406; вживую не проверено.
- **Проверка:** юнит-тесты обработчиков; интеграционный тест `pkg/catalog/installed` на MySQL (порядок, архив, нормализация, строки журнала `seq` с `except_auth_key_id`). Без исправлений тест падал: эти обновления не были в списке `seq`, тема не регистрировалась.
- **Ревью ветки** с перепроверкой каждой находки нашло четыре ошибки, все исправлены, на каждую есть тест, падающий без исправления:
  - «призрак» установленного набора после нового импорта каталога;
  - `getArchivedStickers` с `limit = 0` отдавал наборы, а не только счётчик;
  - `getStickerSet` не отдавал `installed_date` и `archived` аккаунта;
  - архивация набора, которого у аккаунта нет, создавала запись в архиве.
- **Выкачено 2026-11-02 19:24 UTC** (`2023575d`), миграции применены. Проверка на проде через web.pluma.chat: `Free420` (40 стикеров) пришёл из Telegram за ~5 с, `roflmoji` (200 эмодзи) — только через 6 минут повторов клиента. Причины и исправления (`82e9c75f`):
  - прокси session→bff резал любой вызов на 5 с (`bff_proxy_client.go`): для `getStickerSet` и `installStickerSet` теперь 60 с;
  - один `-503 Timeout` Telegram на файл срывал весь набор: бот повторяет запрос до 5 раз с паузой 1, 2, … с, как Telegram Android (`ConnectionsManager.cpp`, `error_code == 500 || error_code < 0`; по локальному дереву исходников, с закреплённым релизом не сверено; в core.telegram.org/api/errors про -503 ничего нет);
  - документы импортировались по одному (вызовы dfs и media на каждый): теперь по 8 сразу, это же ускоряет импорт всего каталога.
- **Выкачено `4f925893` (20:29 UTC), затем OOM `dfs`.** Импорт каталога и наборы по запросу пошли параллельно, и `dfs` вырос до 6,8 ГБ. Ядро убило его трижды (20:31–20:32), другие процессы не пострадали. Причина — апстрим: загрузки в S3 идут с размером `-1`, а minio-go v7.0.49 для них считает объект в 5 ТиБ и держит буфер части ~525 МиБ на каждую загрузку (`OptimalPartInfo`, `api-put-object.go:370`). Исправление (`393af58d`): часть 16 МиБ в `s3PutOptions`, предел объекта 160 ГБ. Оно касается и обычных загрузок пользователей. Импорт каталога прервался на первом же документе, повторить после выкатки.
- **Каталог импортирован 2026-11-02 22:18 UTC.** При первом импорте Redis прода заполнился частями загруженных файлов (они живут 3 ч после записи в S3), и импорт остановился на 20 500 документах. Владелец очистил Redis. Исправление `eef2e4eb`: `dfs.importDocument` удаляет части сразу после записи. Повторный импорт сохранил остальное за 4 мин; Redis держался на 28 МиБ, `dfs` не перезапускался. В базе: 960 наборов каталога и 2 полученных по запросу, 270 ответов, 32 601 документ. Выгрузка удалена с сервера.
- **Проверено в Web K на проде (web.pluma.chat, 2026-11-02):**
  - каталог: 74 реакции, 231 рекомендуемый набор стикеров, 99 наборов эмодзи;
  - ссылка `t.me/addemoji/roflmoji` открывает набор, 200 эмодзи загружаются с нашего сервера;
  - установка через `toggleStickerSet`: набор в `getEmojiStickers` с `installed_date`, с этим хэшем ответ `allStickersNotModified`, `getStickerSet` отдаёт `installed_date`.
- **«Добавить» в окне по ссылке в Web K ничего не делал — ошибка клиента, не сервера.** В закреплённом tweb `346844b` окно кэширует набор под коротким именем, а `toggleStickerSet` ищет его по id и падает до запроса (`appStickersManager.ts`). Живой web.telegram.org/k эту функцию уже переписал (читает переданный набор, `getCachedStickerSets`; проверено в его worker-скрипте 2026-11-02). Тот же шаг на запасном аккаунте Telegram прошёл; наборы потом сняты. Исправление в pluma-web `fe68fd5` (`ci/patch.py`, `sticker_set_toggle`): при промахе набор догружается по id. Образ `ghcr.io/sckraaa/pluma-web:fe68fd56…` владелец поставил на прод 2026-11-02 22:59 UTC. Проверено после этого: `t.me/addstickers/UtyaDuck` → окно → «Добавить» ставит набор (с `installed_date`), и «Duck» появляется в панели стикеров чата. Тестовый набор потом снят.
- **Наблюдение, не правило:** у настоящего Telegram набор `HotCherry`, установленный у запасного аккаунта по умолчанию, пришёл без `installed_date` и в `getStickerSet`, и в `getAllStickers`. `UtyaDuck`, установленный вручную, — с ним. Наш сервер даёт `installed_date` всегда; это совпадает со схемой и с тем, чего ждут Web K и tdesktop.
- **Не проверено в клиентах:** Android, iOS, Desktop. В симуляторе iOS приложение вошло в локальный стенд, а не в прод; тестовых аккаунтов на проде не заводим. Нужен стенд (CachyOS) с каталогом.
