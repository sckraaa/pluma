# 012. Web-клиент (Web K) в облаке

- Статус: todo
- Зависит от: 006 (схема патча и облачной сборки Android — образец)
- ADR: 0008 (layer 228), 0010 (облачные сборки)

## Цель
Официальный веб-клиент Telegram Web K ([morethanwords/tweb](https://github.com/morethanwords/tweb)) с патчем под сервер Pluma.
- Собирается в GitHub Actions в репозитории `sckraaa/pluma-web` так же, как Android в `sckraaa/pluma-android`: закреплённый upstream, скрипт патча с проверками, кэш.
- Проверен входом на локальном стенде.

## Почему Web K
- Его master ближе всех к нашему layer: 229 против 231 у Web A. Значит, коммит с layer 228 свежее, и меньше расхождений.
- Он легче.
- У teamgram есть его форк, так что точки патча уже известны (`docs/audit/04-clients-and-builds.md`, п. 1.5).

Web A (telegram-tt) — возможная отдельная задача потом.

## Контекст
- **Образец — `sckraaa/pluma-android`** (локально `~/pluma-android`; читать можно, менять нельзя). Повторить его устройство, а не изобретать своё:
  - `upstream.env` — закреплённый коммит upstream и версии инструментов;
  - `ci/patch.py` — точные замены, падение при несовпадении, отдельная проверка результата после замен; тесты `ci/patch_test.py`;
  - `config/app.env` — идентичность приложения;
  - `config/dev/` — dev-сервер;
  - `ci/*.sh` — шаги, не зависящие от CI;
  - `.github/workflows/*.yml` — actions закреплены по SHA, `permissions: contents: read`, без `pull_request_target`;
  - README на английском.
- **Точки патча tweb** (`docs/audit/04-clients-and-builds.md`, п. 1.5):
  - `src/lib/mtproto/dcConfigurator.ts` (`constructTelegramWebSocketUrl`, `dcOptions`);
  - `src/lib/mtproto/rsaKeysManager.ts` (ключи в hex: модуль и экспонента);
  - `src/config/app.ts` (`VITE_API_ID`, `VITE_API_HASH`);
  - `src/lib/mtproto/schema.ts` (`layer`).
- **Сервер.**
  - Шлюз принимает MTProto поверх WebSocket на 11443, путь `/apiws`.
  - На стенде e2e порт публикуется через `E2E_GATEWAY_WS_PORT` (`test/e2e/run.sh`, `docs/ops/clients.md`).
  - Сервер один, DC один (id 1); `help.getConfig` отдаёт пустой `dc_options`.
- **Идентичность:** `api_id` 10004 (Web), `api_hash` — свой, 32 hex, сгенерировать; название «Pluma».

## Область
1. **Upstream.** Найти в истории tweb последний коммит, где `schema.ts` даёт `"layer":228`, и закрепить его в `upstream.env`. Обосновать выбор в README: дата, что изменилось в схеме сразу после.
2. **Патч (`ci/patch.py`, стандартная библиотека Python, тесты).**
   - Адрес. Сервер задаётся одним URL WebSocket: `wss://<host>/apiws` для настоящего сервера, `ws://localhost:<port>/apiws` для dev. Все DC клиента ведут на DC 1 этого сервера.
   - HTTP-транспорт tweb (`dcOptions`) отключить или направить туда же. Решение обосновать.
   - Ключ. Публичный RSA-ключ сервера из PEM (PKCS#1) превращается в hex-представление tweb. Отпечаток проверяется тестом на известных ключах Telegram, как в `pluma-android`.
   - Ключи Telegram (прод и тест) убираются.
   - Идентичность: `api_id`/`api_hash`, название «Pluma» в заголовке страницы и в манифесте PWA.
   - Layer — проверка `228`.
   - Всё, что сам клиент шлёт во внешние сервисы Telegram, отключено или направлено на сервер, со списком в README. Это поиск запасных адресов DC, загрузки с `*.telegram.org`, внешние CDN и т. п. Найти поиском по `telegram.org`, `t.me` и известным хостам.
3. **Сборка.**
   - `ci/build.sh`: версия Node и менеджер пакетов — как требует upstream на этом коммите, через закреплённые версии.
   - Результат — статический каталог и архив с SHA-256.
   - Dev-сборка без переменных сервера идёт на dev-сервер. Сборка под сервер берёт URL WebSocket и ключ из переменных репозитория. Половина переменных — ошибка.
4. **CI (`.github/workflows/web.yml`).**
   - Цепочка: `check` (тесты патча, shellcheck) → `build` (кэш менеджера пакетов в `actions/cache`) → артефакт сборки.
   - Еженедельная «канарейка».
   - Артефакт веб-сборки не шифруется: эту статику в любом случае раздаёт публично сайт сервера. Решение записать в README.
5. **Проверка на стенде.** Headless Chromium через Playwright, сценарий в репозитории, запускаемый одной командой:
   - стенд из рабочей копии сервера `~/pluma-work/stand` с `E2E_GATEWAY_WS_PORT`;
   - сборка под одноразовый ключ этого стенда; публичную часть дать `go run ./tools/genserverkey -show <ключ стенда>`;
   - вход по номеру из allowlist с кодом из `test/e2e/run.sh admin login-code`, регистрация, отправка сообщения в «Избранное»;
   - проверка, что сообщение сохранилось.
   - Скриншоты шагов — в игнорируемый git каталог.
   - Стенд и браузерные артефакты удаляются по завершении.
6. **Документы:** README репозитория (на английском, как в `pluma-android`). В `docs/ops/clients.md` сервера — раздел про веб-клиент (на русском).

Не в этой задаче:
- раздача клиента с сервера (TLS, обратный прокси `/apiws`, домен) — отдельная серверная задача;
- web push;
- ребрендинг иконок;
- создание GitHub-репозитория и первый прогон CI (делает ревьюер после ревью).

## Критерии приёмки
- `python3 ci/patch_test.py` зелёный.
- Патч применяется к закреплённому коммиту, проверки после патча проходят. Порча любой точки патча роняет его с понятной ошибкой: проверено тестом или прогоном.
- `ci/build.sh` собирает dev-сборку и сборку под заданный сервер локально; shellcheck и actionlint чистые.
- Сценарий Playwright проходит на стенде: вход, регистрация, сообщение. Лог прогона — в отчёте.
- В собранном бандле нет адресов DC Telegram и его RSA-ключей: проверено скриптом в `check`.
