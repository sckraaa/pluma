# 056. Инцидент 05.11: сеть сервера и потолки памяти

- Статус: done

## Запрос владельца (05.11, после Rescue)
Считалось, что dfs съел память и положил общий сервер, а с ним туннель НАВИгатора. Нужно: выяснить, почему dfs растёт до 7 ГБ; поставить потолки памяти всем контейнерам так, чтобы хосту оставалось не меньше 2 ГБ; защитить sshd и nginx от OOM (`OOMScoreAdjust=-900`); включать осторожно и следить; не трогать настройки туннеля, `/root/neo-backups`, ключи.

## Результат
05.11 сервер упал не из-за памяти, а из-за сети. В 06:20 автоматические обновления перезапустили systemd-networkd. Тот не смог прочитать свой файл: его переписали 29.10 правами `0600`, когда при настройке Floating IP запустили `netplan generate` под `umask 077`. networkd отпустил `eth0`, DHCP-аренду никто не продлил, и в 18:48:34 ядро сняло основной адрес с маршрутом. Первая неудача туннеля НАВИгатора — в 18:49:34. Память весь день была занята на 45%, записей OOM за 05.11 нет. Рост dfs до 6,4–6,9 ГБ был 02.11, при импорте каталога: minio-go при неизвестном размере файла держал на каждую загрузку буфер 528 МБ. Это исправлено тем же вечером (`393af58d6`, `ac2e68b2c`) и уже в проде. Теперь runbook больше не советует `netplan generate` на работающем сервере. У каждого контейнера Pluma свой лимит без подкачки; Go-сервисы держат кучу в 80% от лимита; на общем сервере все контейнеры Pluma в `pluma.slice` с потолком 4,5 ГБ; sshd и nginx защищены от OOM.

- **Сеть.** `docs/ops/deployment.md`: проверка netplan только с `--root-dir`, предупреждение, как проверить права. Сервер после перезагрузки в порядке (`10-netplan-eth0.network` — `0640 root:systemd-network`, `networkctl`: `routable (configured)`).
- **Лимиты.** `mem_limit` = `memswap_limit` у всех 33 сервисов всех compose-файлов, значения — по максимумам Prometheus за 30 дней и `docker stats` (таблица в `memory.md`); Kafka с кучей 512 МБ. Тест `TestComposeMemory` не пропустит сервис без лимита (без изменения падает на 14 сервисах).
- **Go.** `third_party/teamgram-marmota/pkg/commands/memlimit.go`: мягкий лимит рантайма = 80% лимита cgroup, если не задан `GOMEMLIMIT`; юнит-тест разбора cgroup v1/v2.
- **Общий потолок.** `teamgramd/deploy/systemd/pluma.slice` (`MemoryMax=4608M`, без подкачки) и `PLUMA_CGROUP_PARENT` в compose; пусто — Docker по умолчанию (разработка, CI, e2e).
- **Проверено в CI.** e2e теперь падает, если ядро убило любой контейнер стека по лимиту (`check_memory` в `test/e2e/run.sh`). Первые прогоны нашли два слишком тесных лимита: MySQL (1 ГБ, убит после восстановления дампа под потоком сообщений) — теперь 2 ГБ; Jaeger (256 МБ при 50 000 трассировок в памяти) — теперь 512 МБ и 10 000 трассировок. Третий прогон зелёный целиком.
- **Выкачено 05.11** (`1418087a`): все 30 контейнеров Pluma в `pluma.slice` со своими лимитами (`docker inspect`), slice — 2,2 ГБ из 4,5; у dfs мягкий лимит 1228 МБ из 1536; Kafka с `-Xmx512m`; сайт отвечает 200; `pluma-langpacks.timer` снова включён, его запуск отработал в лимите bff (58 из 145 языков обновлены).
- **SSH.** По решению владельца вход только по ключу: `/etc/ssh/sshd_config.d/10-keys-only.conf` (`PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `PermitRootLogin prohibit-password`), читается раньше `50-cloud-init.conf`; `sshd -t`, reload без перезапуска. Вход с Mac владельца по ключу работает, по паролю — `Permission denied (publickey)`, туннель жив.
- **Хост.** `/etc/systemd/system/{ssh,nginx}.service.d/oom.conf` с `OOMScoreAdjust=-900`, значение выставлено и работающим процессам без перезапуска; `nofile.conf` туннеля не тронут; туннель проверен (8082 → 200, 8081 → 302).
- **dfs.** Разбор кода (несколько независимых проверок каждой находки) подтвердил исправленную причину 02.11 и нашёл другие пути, где один запрос может занять гигабайты: `upload.getFile` с непроверенным `limit`, декодирование изображений без проверки размеров, чтение всего файла в память в некоторых загрузках, буфер ответа целиком в `TimeoutHandler` mini-http, части загрузок в Redis не удаляются. Лимит dfs (1,5 ГБ) не даёт им задеть хост; исправления — отдельная задача.

## Решения на подтверждение
- `MemoryMax` slice = 4,5 ГБ: 7,6 ГБ − 2 ГБ хосту − 1 ГБ лимита `lawyer-app-1`. Если у `lawyer-app` поменяется лимит, slice нужно пересчитать.
- Лимиты без подкачки (`memswap_limit` = `mem_limit`): контейнер упирается в лимит сразу, а не медленно уходит в swap.
