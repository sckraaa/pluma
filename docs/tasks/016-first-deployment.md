# 016. Первый запуск на сервере

- Статус: in-progress (сервер, телефон и веб-клиент работают; остался замер задержки)
- Зависит от: 004, 009
- ADR: 0010, 0013, 0014

## Цель
- Pluma работает на сервере владельца, и клиенты под него собираются.
- У Pluma свой адрес: входящий и исходящий трафик стека идёт через него, а не через основной адрес сервера.
- Сервер ничего не собирает: образы для каждого коммита строит CI.

## Критерии приёмки
- Порты Pluma слушает только адрес Pluma, служебные — только `127.0.0.1`.
- Исходящий трафик контейнеров уходит с адреса Pluma.
- Все сервисы healthy. Push-ключи проверены `pluma-admin push check`. Алерты доходят до телефона, бэкап снят и проверен восстановлением.
- Клиенты Android и Desktop собраны под сервер. Владелец вошёл с телефона.
- Runbook: `docs/ops/deployment.md`.

## Результат

**Сервер.** Hetzner CX33 (NBG1): 4 vCPU, 8 ГБ, Ubuntu 26.04, Docker 29. Pluma стоит в `/opt/pluma`.
- Адрес Pluma — Floating IP `195.201.252.126`. Он закреплён в netplan (`60-pluma-floating-ip.yaml`) без перезапуска сети.
- Основной адрес сервера остаётся у прокси владельца: nginx на `127.0.0.1:8081/8082`.
- Старый проект `neo` с сервера убран: контейнеры, образы, кэш сборки, сайты nginx. Данные проекта удаляет владелец.

**Адрес Pluma** (`PLUMA_PUBLIC_IPV4`, `docker-compose.public-ip.yaml`):
- шлюз публикует 10443, 5222 и 11443 только на этом адресе;
- мост `teamgram_net` подменяет исходящий адрес (SNAT, опция `com.docker.network.host_ipv4`) вместо маскарадинга.

Проверено на сервере: контейнер выходит в интернет с `195.201.252.126`, порт 10443 на основном адресе закрыт. В общий compose опцию не вписать: без адреса Docker отказывает, с `0.0.0.0` подставляет 0.0.0.0. Поэтому для неё отдельный файл.

**Образы.** Workflow `images` на каждый коммит `master` собирает `pluma-server`, `pluma-alertpush` и `pluma-backup` (linux/amd64) в GHCR с тегом-коммитом. На сборку уходит около 5 минут. `.env` сервера называет образы своего коммита.

**Секреты.** Созданы на сервере, наружу не выводились:
- ключ сервера: отпечаток `12437915428417313651` (`0xac9c5a2ee92a1b73`);
- пароли и ключи шифрования `.env`;
- тема ntfy;
- push-ключи скопированы с Mac владельца.

Копия `.env` и ключа сервера лежит в `~/pluma-secrets/server` на Mac.

**Клиенты.** Переменные сервера заданы в `pluma-android`, `pluma-desktop` и `pluma-ios`. В iOS нет `PLUMA_TEAM_ID`, поэтому там пока собирается только симулятор.
- Android: ключ подписи, age-ключ и environment `release` созданы. Ключи лежат в `~/pluma-secrets/android`.
- Desktop и iOS получили свои age-ключи.
- Веб-клиенту нужен `wss://`-адрес, раздача с TLS — отдельной задачей.

**Алерты и бэкапы.** Тема ntfy на телефоне владельца, проверка healthchecks.io, бэкапы в Cloudflare R2. Значения владелец внёс сам (`/root/pluma-owner-env.sh`), они не проходили через чат. Тестовый алерт PlumaTest Alertmanager отправил без ошибок. Снимки базы, файлов и ключей сервера в R2, проверка восстановления прошла.

Запуск нашёл две ошибки в `backup.sh`:
- шаги цикла вызывались как `f || log`, а bash в таком вызове отключает `set -e` внутри функции, и упавший restic записывал метрику успеха (`7320ce2e`);
- ловушка выхода проверки восстановления читала уже исчезнувшие локальные переменные, и под `set -u` успешная проверка выходила с кодом 1 (`a476f9fb`).

**Вход.** Владелец вошёл и зарегистрировался с Android-телефона, подписанной сборкой под сервер (2026-10-29). Desktop под сервер собран для трёх систем.

**Веб-клиент** (`docker-compose.web.yaml`, раздел «Веб-клиент» runbook) — `https://web.pluma.chat`; `pluma.chat` и `www` перенаправляют туда.
- Caddy (образ `pluma-web` из CI с сайтом внутри) получает сертификаты Let's Encrypt сам. Его исходящий трафик тоже идёт с адреса Pluma.
- `/apiws` уходит на новый WebSocket-слушатель шлюза `11444` с PROXY protocol v1. В `auths` записаны настоящие адреса клиентов, а не адрес прокси.
- Порт `11443` больше не публикуется.
- Попутно исправлено: на слушателе с PROXY protocol соединение без заголовка проходило мимо лимита соединений на адрес. Теперь оно закрывается (`90dcde90`, тест `TestProxyProtocolV1`).
- Проверено в браузере: экран входа по QR-коду требует MTProto через `wss` и появляется.

**Не сделано / дальше.**
- Замер задержки (ADR 0011, п. 12) — на этом сервере.
