# 102. CDN-DC Pluma: большие файлы с края, ключи дома

- Статус: готово, ждёт выкладки (2026-11-16)
- Решение: ADR 0065 (предложено). Развивает ADR 0057 §3, опирается на ADR 0061 (туннель, край) и ADR 0059 (mTLS управления).
- Зависит от: 096 (дом и край на VPS, туннель `10.77.0.1`/`10.77.0.2`), 057 (правила диапазона `upload.getFile`), 093 (образец отдельного сервиса на краю: SFU, `control-certs.sh`, цели Prometheus).
- Ветка: `task/102-cdn`; патч iOS — ветка `task/102-cdn` в pluma-ios.

## Цель
Большие файлы (видео, документы ≥ 1 МБ) в любых чатах Android, Desktop и iOS качают с узла CDN на VPS, а не с домашнего канала (~57 Мбит/с отдачи). Дом отдаёт узлу одну зашифрованную копию файла; узел хранит и раздаёт только шифр, ключ файла клиент получает от дома. Если узел недоступен, переполнен или исчерпал месячный трафик, всё работает как сегодня — из дома. Web K остаётся на `upload.getFile`.

## Область
В задаче:
- `upload.getFile`: редирект `upload.fileCdnRedirect` по политике ADR 0065 §2.
- `upload.getCdnFileHashes`, `upload.reuploadCdnFile`, `help.getCdnConfig` — настоящие (сейчас заглушки апстрима); `upload.getCdnFile` на DC 1 — `FILE_TOKEN_INVALID`.
- `help.getConfig` `dc_options`: DC 1 и CDN-DC 201 из конфигурации, проверка «DC 1 есть».
- Вынос из gnetway транспорта и ядра рукопожатия в `pkg/mtserver/{codec,handshake}`, obfuscated2 с секретом `dd`.
- Сервис `cdn` (`app/service/cdn`): ограниченный сервер MTProto, хранилище шифра с LRU, свой RSA-ключ, канал управления gRPC mTLS, метрики.
- Дом: `pkg/cdn` (таблицы, шифр, хэши, токены, заливщик, проверка узла), миграция, конфигурация, метрики, алерты.
- `pkg/mtclient`: транспорт obfuscated2 с секретом и CDN-ключ — для e2e.
- e2e-стенд с узлом `cdn`, сквозные тесты.
- Патч iOS I-116.
- Документы: `docs/ops/cdn.md`, `home-server.md`, `clients.md`, `monitoring.md`, `security-setup.md`, реестр `clients/patches/ios.md`, строки `TESTING-BACKLOG`.

Не в задаче (ADR 0065, «Что не делается»): CDN для Web K; `upload.getFileHashes` (остаётся `ErrEnterpriseIsBlocked`); второй узел у другого провайдера; предзагрузка файлов до первого запроса.

## Контракт клиентов
Подробно, с источниками — ADR 0065, «Контекст». Закреплённые исходники — `~/pluma-work/reference-src-new`. То, на чём держится дизайн:
- **Флаг.** Android ставит `cdn_supported` всегда (`FileLoadOperation.java:2465-2470`), tdesktop — на каждом облачном файле (`storage/download_manager_mtproto.cpp:580-582`), iOS — только на движке Rust (`FetchV2.swift:505, 974`; по умолчанию на iOS MtProtoKit, `SyncCore_NetworkEngineSettings.swift:6-11`), Web K — никогда (`apiFileManager.ts:483-487`). Без флага редиректа нет.
- **Ключ и IV.** Ровно 32 и 16 байт, иначе Android — ошибка «bad redirect response» (`FileLoadOperation.java:2602-2611`), tdesktop — отмена загрузки (`download_manager_mtproto.cpp:1018`), iOS — `CDN_REDIRECT_KEY_INVALID` (`FetchV2.swift:1002-1004`). Смещение в IV — `offset/16` big-endian в байтах 12–15 (Android `:1900-1906`, tdesktop `:694-698`, iOS `:929-934`).
- **Хэши.** SHA-256 расшифрованных (открытых) кусков по 128 КБ, выровненных по 128 КБ, последний короче: Android ищет хэш по `offset / 128K * 128K` (`:1889-1897`), tdesktop — по точному смещению запроса 128 КБ и сравнивает со всем буфером, неверный — отмена загрузки (`:690-737`, `download_manager_mtproto.h:26`), iOS хэширует `cleanData` (`FetchV2.swift:616-617`, блок `:124`). Хэш по шифру сломал бы все загрузки.
- **Конец файла.** Пустые `bytes` — конец (Android `:1884-1886`, iOS `FetchV2.swift:926-927`); узел на `offset ≥ size` отдаёт пустые байты.
- **Отступление на мастер.** `FILE_TOKEN_INVALID` из `getCdnFile` — назад на `getFile` (Android `:2583-2589`, tdesktop `:958-980`, iOS с патчем `:1102-1110`); из `reuploadCdnFile` — так же для `FILE_TOKEN_INVALID` и `REQUEST_TOKEN_INVALID` (Android `:2645-2649`, tdesktop через `cdnPartFailed`, iOS с патчем — `fallBackToMaster` с `cdnDisabled`, `:1283-1288`). Другие ошибки Android и tdesktop считают отказом загрузки.
- **Reupload.** Android после вектора хэшей сразу повторяет `getCdnFile`, и на новый `cdnFileReuploadNeeded` снова зовёт reupload (`:2623-2644`) — поэтому вектор отдаётся только когда копия уже на узле (ADR 0065 §4).
- **Ключи CDN.** Android и tdesktop запрашивают `help.getCdnConfig`, когда отпечатка из `resPQ` нет в известных (`Handshake.cpp:404-407`; `session_private.cpp:1028-1031, 2582-2587`); ключ — PKCS#1 PEM (`PEM_read_bio_RSAPublicKey`, `Handshake.cpp:1032`). Отпечаток — стандартный (SHA-1 от TL `n`, `e`, `Handshake.cpp:1033-1053`).
- **Ключи клиентов на узле.** Android и iOS — постоянный (`Datacenter.cpp:1076`, `MTProto.m:909-912`), tdesktop — временный непривязанный (`session_private.cpp:2604-2630`). −404 — новый ключ (Android `ConnectionsManager.cpp:850-855`, tdesktop `session_private.cpp:2689-2711`, iOS `MTProto.m:2125-2132`).
- **`initConnection` на CDN.** tdesktop шлёт `device_model`/`system_version` «n/a», но язык, прокси и `params` — те же (`session_private.cpp:671-707`). Узел ничего из этого не пишет в лог и не хранит.
- **`dc_options`.** tdesktop заменяет весь список DC, если `dc_options` непуст (`mtproto/mtproto_config.cpp:285-289` → `mtproto_dc_options.cpp:198-244`; `config_loader.cpp:234` — путь «special config», не этот), Android — все группы адресов у перечисленных DC (`ConnectionsManager.cpp:3486-3514`), iOS — набор адресов у перечисленных DC (`ManagedConfigurationUpdates.swift:22-38`). Значит DC 1 обязан быть в списке со всеми рабочими адресами.
- **Порты Android.** Без `secret` Android пробует порт адреса, затем 443 и 5222 (`Datacenter.h:84`, `Datacenter.cpp:337-345`); на адресе Pluma 443 и 5222 уходят домой (`teamgramd/deploy/edge/forward.sh`). С секретом — только порт адреса. Отсюда секрет `dd…` у DC 201.
- **tdesktop: HTTP и прокси.** Эндпоинт без `tcpo_only` и без секрета пробуется и по HTTP; при прокси остаются только `static` (`mtproto_dc_options.cpp:686-695`). У DC 1 — `static`, как у вшитого (D-002), у DC 201 — `tcpo_only` и секрет. Номер DC < 1000 (`mtp_instance.h:45`).
- **iOS без патча** на MtProtoKit ветки CDN не прошёл бы: ошибка `getCdnFile` и reupload — загрузка `.failed` (`FetchV2.swift:952-956, 1114-1115, 800`). Патч — Часть G.

## Дизайн

### Таблицы (`teamgramd/deploy/sql/migrate-20261120-cdn.sql`, идемпотентно, `CREATE TABLE IF NOT EXISTS`)
```sql
CREATE TABLE IF NOT EXISTS cdn_files (
  id          BIGINT NOT NULL AUTO_INCREMENT,
  file_kind   TINYINT NOT NULL,            -- 1 document, 2 photo, 3 encrypted
  file_id     BIGINT NOT NULL,
  thumb_size  VARCHAR(8) NOT NULL DEFAULT '',
  size        BIGINT NOT NULL DEFAULT 0,   -- 0: not yet known
  eligible    TINYINT NOT NULL DEFAULT 1,  -- 0: below CDN_MIN_FILE_SIZE, never pushed
  file_token  VARBINARY(32) NULL,          -- random, set with the key
  aes_key     BINARY(32) NULL,
  aes_iv      BINARY(16) NULL,             -- last 4 bytes zero
  hashes      MEDIUMBLOB NULL,             -- SHA-256 of 128 KB plaintext chunks, 32 bytes each
  created_at  BIGINT NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_file (file_kind, file_id, thumb_size),
  UNIQUE KEY uk_token (file_token)
) ENGINE=InnoDB;

CREATE TABLE IF NOT EXISTS cdn_replicas (
  file_row_id BIGINT NOT NULL,
  dc_id       INT NOT NULL,
  state       TINYINT NOT NULL,            -- 0 queued, 1 pushing, 2 ready, 3 absent, 4 failed
  priority    TINYINT NOT NULL DEFAULT 0,  -- 1: asked by reuploadCdnFile
  lease_until BIGINT NOT NULL DEFAULT 0,
  attempts    INT NOT NULL DEFAULT 0,
  next_try_at BIGINT NOT NULL DEFAULT 0,
  last_error  VARCHAR(64) NOT NULL DEFAULT '',
  ready_at    BIGINT NOT NULL DEFAULT 0,
  updated_at  BIGINT NOT NULL,
  PRIMARY KEY (file_row_id, dc_id),
  KEY k_queue (dc_id, state, priority, next_try_at)
) ENGINE=InnoDB;

CREATE TABLE IF NOT EXISTS cdn_nodes (
  dc_id              INT NOT NULL,
  public_key         TEXT NULL,            -- PKCS#1 PEM from the node
  fingerprint        BIGINT NOT NULL DEFAULT 0,
  boot_id            VARBINARY(16) NULL,
  healthy_until      BIGINT NOT NULL DEFAULT 0,
  unhealthy_reason   VARCHAR(32) NOT NULL DEFAULT '',
  egress_month       CHAR(7) NOT NULL DEFAULT '',  -- YYYY-MM of egress_bytes
  egress_bytes       BIGINT NOT NULL DEFAULT 0,
  cache_used         BIGINT NOT NULL DEFAULT 0,
  cache_cap          BIGINT NOT NULL DEFAULT 0,
  rt_key             BINARY(32) NULL,      -- request_token key, current
  rt_key_prev        BINARY(32) NULL,
  rt_key_at          BIGINT NOT NULL DEFAULT 0,
  updated_at         BIGINT NOT NULL,
  PRIMARY KEY (dc_id)
) ENGINE=InnoDB;
```
- Ключ файла и токен создаются один раз (условная запись `UPDATE … WHERE file_token IS NULL`); один шифр на все узлы.
- `rt_key` создаётся домом при первом запуске (условная вставка), меняется раз в 30 дней с хранением предыдущего.

### Пакет `pkg/cdn` (дом)
- `keys.go` — файл: ключ, IV (12 случайных байт + 4 нуля), токен (32 случайных байта); `crypto/rand`.
- `ctr.go` — `Encrypter` поверх `cipher.NewCTR` с IV ADR 0065 §3; `DecryptAt(key, iv, offset, b)` — алгоритм клиентов, для тестов и проверок.
- `hashes.go` — подсчёт по 128 КБ потоком; `Answer(blob, size, offset) []*mtproto.FileHash` — от `offset` вниз до 128 КБ, до 64 кусков (`MaxHashesPerAnswer`).
- `reqtoken.go` — `Sign(key, fileToken, now)`, `Verify(keys, fileToken, token, now)` (срок 10 мин, текущий и предыдущий ключ). Тот же код использует узел (Часть C).
- `policy.go` — `Key(location) (kind, id, thumb, ok)` для трёх видов; порог `CDN_MIN_FILE_SIZE` (кратен 1 МиБ).
- `store.go` — интерфейс `Store`, `mysql.go` и `memstore.go` (как `pkg/twofa`): `Ensure(file)`, `SetKey`, `SetHashes`, `ByToken`, `Enqueue(dc, priority)`, `Claim(dc, lease)`, `MarkReady`, `MarkAbsent`, `MarkFailed(backoff)`, `Node`/`PutNode`, `RotateRtKey`.
- `pusher.go` — заливщик (ниже); `prober.go` — проверка узла; `redirect.go` — решение и кэш; `control.go` — клиент gRPC mTLS (`app/service/cdn/cdn/cdn.proto`).
- `metrics.go`.

### Узел `app/service/cdn`
- `cmd/cdn/main.go`, `etc/cdn.yaml`, `internal/{config,listen,session,store,control,metrics}`, `cdn/cdn.proto` + `gen.sh` (как `app/service/sfu/sfu`).
- `cdn.proto`: `Status() → {dc_id, public_key_pem, fingerprint, boot_id, cache_used, cache_cap, egress_month, egress_bytes}`; `SetRequestTokenKeys{current, previous}`; `Put(stream {header{file_token, size} | chunk{bytes}}) → {size, sha256}`; `Delete{file_token}`; `Inventory() → stream {file_token, size}`.
- `listen` — gnet или `net` на `CDN_LISTEN` (`0.0.0.0:8443` в контейнере), транспорты из `pkg/mtserver/codec`, секрет `CDN_SECRET`; рукопожатие из `pkg/mtserver/handshake` с хранилищем ключей в памяти (до `CDN_MAX_AUTH_KEYS`, 20 000; временные — до их `expires_in`; постоянные — LRU по последнему использованию).
- `session` — минимальная сессия ADR 0065 §5. Ответ на неизвестный auth_key — транспортный −404. Пределы: соединений на адрес 32, рукопожатий на адрес — тот же счётчик, что у gnetway (`ip_limits.go`, вынести общее в `pkg/mtserver/limits` или повторить с теми же числами), запросов в полёте на соединение 16, кадр не больше 1 МБ + заголовки (запрос `getCdnFile` маленький).
- `store` — `CDN_DATA_DIR/files/<hex[0:2]>/<hex(token)>`, `tmp/` для недописанных; LRU по времени последней выдачи (сбрасывается на диск раз в минуту в `index.json` для восстановления порядка), потолок `CDN_CACHE_BYTES`, простой `CDN_IDLE_TTL` (30 дней). `Put` больше потолка — отказ `RESOURCE_EXHAUSTED`. Резерв свободного места диска 2 ГБ: меньше — `Status` сообщает, дом считает узел нездоровым.
- RSA: `CDN_DATA_DIR/rsa.key`, 2048 бит, 0600, создаётся при первом запуске (`pkg/serverkey` для загрузки и отпечатка). Ключ сервера дома на узел не кладётся.
- `control` — gRPC на `CDN_CONTROL_LISTEN` (`0.0.0.0:20510` в контейнере, публикуется на `10.77.0.1`), mTLS с отдельными CA (как `teamgramd/deploy/sfu/control-certs.sh`).
- Месячный счётчик отданных байт хранится в `CDN_DATA_DIR/egress.json` (переживает перезапуск).
- Образ `teamgramd/deploy/cdn/Dockerfile` по образцу `teamgramd/deploy/sfu/Dockerfile` (distroless, nonroot, `CGO_ENABLED=0`).

### Дом: ход вызовов
`upload.getFile` (`app/bff/files/internal/core/upload.getFile_handler.go`), после проверок вида файла и до `DfsDownloadFile`:
1. `cdn_supported` и не `precise`, `svcCtx.CDN != nil`, вид файла подходит (`policy.Key`).
2. Состояние файла из кэша (LRU в памяти по байтам, 64 МБ, TTL 60 с) или MySQL. Нет строки — `Ensure` и узнать размер: документ — `MediaGetDocument`, фото — размер `thumb_size` из `MediaGetPhoto`, секретный — `MediaGetEncryptedFile`; меньше порога — `eligible = 0`.
3. Есть здоровый узел (`healthy_until > now`) и `ready`-копия на нём → `upload.fileCdnRedirect{dc_id, file_token, aes_key, aes_iv, Answer(hashes, offset)}`; метрика `redirect`.
4. Подходит, но копии нет → `Enqueue` (идемпотентно) и обычный ответ из dfs.

`upload.getCdnFileHashes(file_token, offset)` → `ByToken`; нет — `FILE_TOKEN_INVALID`; хэшей ещё нет — `FILE_TOKEN_INVALID`; иначе `Answer`.

`upload.reuploadCdnFile(file_token, request_token)` → ADR 0065 §4: проверка токена файла, подписи (`rt_key`, `rt_key_prev`), `MarkAbsent` + `Enqueue(priority 1)`, ожидание `ready` до `CDN_REUPLOAD_WAIT` (опрос MySQL раз в 250 мс, отмена по контексту), ответ хэшами от 0 или `FILE_TOKEN_INVALID`. Предел на пользователя: 30 reupload в минуту, дальше `FLOOD_WAIT_X` (Redis не нужен — счётчик в памяти bff, одна реплика; при нескольких — в MySQL).

`help.getCdnConfig` → ключи здоровых и нездоровых узлов из `cdn_nodes` (ключ нужен и узлу, временно выведенному из редиректов: клиенты уже на нём качают). CDN выключен — пустой список (не ошибка).

`upload.getCdnFile` на DC 1 → `FILE_TOKEN_INVALID`.

### Заливщик и проверка узла (горутины процесса bff, запускаются только с `CDN_NODE_CONTROL`)
- `Claim` по аренде (`lease_until = now + 10 мин`, продлевается во время заливки), сначала `priority 1`, затем по `id`; одна заливка за раз (`CDN_PUSH_CONCURRENCY`, 1).
- Чтение — `DfsDownloadFile` частями по 1 МБ тем же `location`, что у клиента (для документа — сохранённый `inputDocumentFileLocation` без `file_reference` неприменим: заливщик собирает location из `file_id` и `access_hash` из media; для секретных — из `pkg/secretchat`). Сумма длин частей обязана совпасть с `size`; иначе `MarkFailed("short_read")` с откатом 1, 5, 30, 120 мин, после 8 попыток — `failed` без повторов (алерт).
- Хэши открытого текста считаются по ходу; ключ и токен создаются перед первой заливкой; `Put` с ограничением `CDN_PUSH_RATE_MBIT` (`golang.org/x/time/rate` по байтам). Ответ узла: размер и SHA-256 шифра совпали с посчитанными домом — `SetHashes` и `MarkReady` в одной транзакции.
- Проверка узла раз в 10 с: `Status` (таймаут 3 с) и рукопожатие до `resPQ` на `CDN_DC_ADDRESS` с секретом (отпечаток совпадает с `Status`). Пишет `cdn_nodes`; новый `boot_id` → `SetRequestTokenKeys`. Нездоров, если: нет ответа, отпечатки разные, свободного места меньше резерва, `egress_bytes ≥ CDN_MONTHLY_EGRESS_LIMIT_GB`.
- Раз в 10 мин `Inventory`: `ready`-копии, которых нет на узле, — `absent`; файлы на узле без `ready`-копии дома (оборванная заливка, удалённая строка) — `Delete`.

### Обновления другим устройствам и пользователям
Нет: CDN не меняет состояние чатов, обновлений не шлёт ни дом, ни узел.

### `help.getConfig` `dc_options` (`app/bff/configuration`)
- Конфигурация `ClientDcOptions` в `configuration.yaml` (`teamgramd/etc`, `teamgramd/etc2`): `Dc1: ${PLUMA_DC1_ADDRESSES}` (список `ip:port`, вшитый порт первым), `Cdn: {Id: ${CDN_DC_ID:201}, Address: ${CDN_DC_ADDRESS}, Secret: ${CDN_DC_SECRET}}`.
- Пусто всё — `dc_options` пустой, как сегодня. Задан CDN без `Dc1` — отказ старта. Адрес — только IP (клиенты не резолвят имён, `docs/ops/clients.md:12`), IPv6 — с флагом `ipv6`. Секрет — `dd` + 16 байт (32 hex), иначе отказ (tdesktop `ValidateSecret`, `mtproto_dc_options.cpp:134-140`).
- `config.json` `dc_options` остаётся пустым; список вставляет обработчик (`help.getConfig_handler.go`) из конфигурации.

### Поведение после перезапуска
- bff: аренды заливок истекают и подхватываются; кэш строится заново; `rt_key` — из MySQL; редиректы идут, пока `healthy_until` не истёк (≤ 30 с).
- Узел: индекс — сканированием (`tmp/` чистится), RSA-ключ и счётчик трафика — с диска; ключи клиентов потеряны — −404 и новые рукопожатия; ключ `request_token` дом пришлёт по новому `boot_id` (до этого reupload получит `REQUEST_TOKEN_INVALID` и клиенты докачают из дома).

## Тесты
Модульные:
- `pkg/cdn/ctr`: шифр дома, расшифрованный по алгоритму клиентов (`DecryptAt` повторяет Android/tdesktop/iOS: IV с `offset/16` в байтах 12–15) на смещениях 0, 4096, 1 МБ − 4096, 128 КБ·k, последнем неполном блоке, файле 3 МБ + 17 байт; эталонный вектор, посчитанный независимо (OpenSSL `aes-256-ctr` в тестовых данных).
- `pkg/cdn/hashes`: число кусков, последний короче, `Answer` от невыровненного смещения, за концом файла — пусто, не больше 64.
- `pkg/cdn/reqtoken`: своя подпись проходит, чужой ключ/другой токен/старше 10 мин/из будущего > 1 мин — нет; предыдущий ключ проходит.
- `pkg/cdn/policy`: три вида файлов, остальные — нет; `precise` — нет.
- `pkg/cdn/redirect` на memstore: нет строки → очередь и обычный ответ; маленький → без редиректа и без очереди; `ready` + здоров → редирект с ключом 32, IV 16, хэшами от смещения; нездоров → нет; ошибка Store → обычный ответ.
- reupload: неизвестный токен, плохая подпись, готовность до срока (вектор), не успели (`FILE_TOKEN_INVALID`), предел.
- `pusher` с фальшивыми dfs и узлом: короткое чтение → `failed` с откатом, без `ready`; SHA-256 шифра не совпал → не `ready`; ограничение скорости соблюдается (по времени на маленьком лимите).
- `help.getConfig`: DC 1 со `static`, порядок портов; DC 201 с `cdn|tcpo_only|secret`; пустая конфигурация — пустой список; CDN без DC 1, секрет не той длины, имя вместо IP — отказ.
- Узел: `getCdnFile` — правила диапазона, конец файла, неизвестный токен → reupload-токен, который проверяет `pkg/cdn/reqtoken`; другой метод → `CDN_METHOD_INVALID`; −404 на неизвестный ключ; LRU и простой; восстановление индекса со сломанным `tmp/`; `Put` с обрывом не оставляет файла.
- `pkg/mtserver/codec`: obfuscated2 с секретом — круговой тест с клиентской стороной (`pkg/mtclient`), без секрета — как раньше.
- gnetway: весь пакет без изменений тестов.
- `tools/logaudit` ловит вывод `fileToken`, `aesKey`.
- Хотя бы один тест проверить падающим без изменения (например, `TestConfigDcOptions` на текущем `master` получает пустой список; тест хэшей по шифру вместо открытого текста падает).

Интеграционные (`pkg/testinfra`, MySQL):
