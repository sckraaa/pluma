# 003. Надёжная доставка через Kafka и push в сессии

- Статус: done (2026-10-23)
- Зависит от: 002, 005
- ADR: 0005, 0009, 0011; решение — 0012 (принят)

## Цель
Ни одно сообщение и ни один апдейт не теряется и не дублируется при сбоях обработчиков, рестартах Kafka, `session` или `sync`.

## Область
По `docs/audit/01-…` и `03-…`:
- Консьюмер (форк marmota `pkg/mq/consumer_group.go`): не коммитить offset при ошибке; ретраи с backoff; DLQ-топик; метрики и алерт на DLQ.
- Обработчики inbox/sync идемпотентны: UNIQUE по `dialog_message_id` и `random_id` (не только Redis на 90 с).
- Ключ партиции = получатель, порядок обработки на пользователя сохраняется; push в `sync` распределяется по пользователю, а не round-robin по 100 горутинам.
- Флаг `unavailable` в `app/messenger/sync/internal/dao/session_client.go` сбрасывается при восстановлении соединения (переподключение с backoff).
- Отправка: MySQL→Kafka неатомарна — outbox-таблица в той же транзакции, что и сообщение (задача 002), публикатор outbox. Relay публикует события одного инициатора в порядке commit его транзакций (id строки outbox или `pts` в пределах `user_id`): в 002 публикация идёт из потока запроса сразу после commit, и две транзакции одного пользователя, закоммиченные подряд (отправка с двух устройств), могут опубликоваться в обратном порядке — копии у получателя лягут иначе, чем у отправителя (ADR 0011, п. 4 и 13).
- Публикация в 002 ограничена по времени (`userbox.EventTimeout`, `PublishTimeout`), но продюсер sarama контекста не принимает: событие, засчитанное как неопубликованное, может дойти позже. Relay должен считать событие отправленным только по ответу брокера и не публиковать следующее событие получателя раньше.
- Kafka: restart-политика, персистентный том; таймауты на всех RPC-клиентах (сейчас `Timeout: 0`). Дедлайн RPC, за которым транзакция ящика, — 0 или не меньше операции (`userbox.CheckRPCTimeout`, проверяется при старте msg, biz и bff).
- Остановка контейнера: `Destroy` msg ждёт выполняющиеся запросы и отправки (`MaxRequestTime`), но в `docker compose` сигнал до сервисов не доходит (`entrypoint.sh` запускает их в фоне и ждёт `tail -f`), а `stop_grace_period` по умолчанию 10 с — сервисы убиваются без `Destroy`.

## Критерии приёмки
- Chaos-тесты: kill обработчика посреди пачки; рестарт Kafka; рестарт `session` — после восстановления все сообщения доставлены ровно один раз, в порядке.
- Тест порядка: 1000 сообщений одному пользователю из разных отправителей — апдейты приходят по возрастанию `pts`.

## Ход работы

**Шаг A — outbox, relay, консьюмер, идемпотентность (сделан).** По ADR 0012, пп. 1–6, 11:
- Миграция `migrate-20261023-delivery.sql`: `mq_outbox`; отвязка копий без связи и повторных копий, обнуление повторных `random_id`; `messages.pts`, `out_random_id`, `UNIQUE (user_id, dialog_message_id)` и `(user_id, out_random_id)`. Скорость на MacBook — ~150 000 строк/с.
- `pkg/userbox`: `Emit` проверяет событие (реестр топиков, получатель, 4 МиБ, inbox не самому себе) и пишет строки последними операторами перед `COMMIT` (≤ 4 МиБ на оператор); `TakeEvent`/`FinishEvent`/`KeepEvent`/`FailEvent` — применение по строке, порядок полосы, откладывание (10 раз, затем `lane_blocked`), парковка; `ErrEventNotFinished`; `Deterministic` (закрытый список); `Check` — `max_allowed_packet ≥ 16 МиБ`. `Publish` и публикация после commit удалены.
- `pkg/outbox`: `Insert`, `Notify`, `Load`, relay (лидер по `GET_LOCK` с именем базы, раунд ≤ 500 строк и 16 МиБ, финишер с условием на `revision`, классы ошибок брокера, `RoundTimeout`/`StopRoundWait`, сверка топиков, таймер повторной доставки по offset-у группы и границам лога, автоповтор dead-полос, сброс published при лидерстве, метрики), продюсер sarama по таблице п. 4, команды оператора и `RaiseIds`.
- `pkg/mqconsumer`: группа sarama со статическим членством, `OffsetOldest`, отметка offset-а только завершённого сообщения, временные ошибки — повтор без предела 100 мс → 30 с, детерминированные — 3 попытки и `Dead`, паника — детерминированная, метрики.
- msg: `RunBox` без публикации, inbox-консьюмер с предпроверкой (`duplicate`, `mismatch`), хелпер `apply` с `done`, dead через `FailEvent`; relay в процессе msg; окно Redis `SendOnce` удалено — повтор `random_id` отвечает исходным ответом из журнала или `RANDOM_ID_DUPLICATE`; `pushUserMessage` — через `outbox.Insert`. sync — консьюмер на `pkg/mqconsumer`, `PushClient` удалён. bff — push-и в `mq_outbox` (`SyncClient` поверх `outbox.Insert`), Kafka ушла с пути RPC. marmota `pkg/mq` в коде больше не используется.
- Kafka: `teamgramd/deploy/kafka/topics.sh` (16 партиций, параметры п. 4), `kafka-init` в compose, автосоздание выключено, `restart: unless-stopped`; `testinfra.StartKafka` создаёт топики тем же скриптом и держит порт хоста.
- `pluma-admin outbox list|replay|discard`, `state-raise` поднимает AUTO_INCREMENT `mq_outbox`; `tools/boxaudit` — писать `mq_outbox` могут только `pkg/userbox` и `pkg/outbox`.
- Тесты: юнит (событие, `TakeEvent` на фейковом драйвере, relay на фейковых хранилище и брокере, политика консьюмера на фейковой сессии), интеграционные на MySQL и Kafka (relay, путь msg с настоящими relay и консьюмером, миграция) — `docs/ops/testing.md`. Задержка в тестовом стенде: отправка → применение у получателя ~40 мс.

**Шаг B — push, развёртывание, проверка (сделан).**
- sync → session (п. 7): пуш записи `Sync-T` идёт на все устройства параллельно, offset отмечается после завершения всех (`dao.WithBatch`), поэтому порядок по устройству держится без очередей, а после падения sync незавершённый пуш приходит снова. Вызов 2 с, одна повторная попытка на `FailedPrecondition`, ожидание недоступного узла до 30 с, переподключение с backoff ≤ 3 с, флага `unavailable` нет; пропустившее устройство получает `updatesTooLong` (перед следующим пушем или обходом раз в секунду); пуши старше 2 мин — resync. `session` отвечает `NotFound`/`FailedPrecondition`. Потоковый клиент и round-robin удалены.
- Compose (п. 8): 11 сервисов на одном образе (собирает `idgen`), exec-форма, `restart: unless-stopped`, `stop_grace_period` по таблице ADR, у сервиса только свои переменные, порты и ключ RSA — только у gnetway; entrypoint, лаунчер и healthcheck образа удалены. Бинарники `-trimpath -s -w`, в образе только `bin/` и `etc2/`. Тест `TestComposeServices`.
- Дедлайны (п. 9): `Timeout: 0` нет, `CheckRPCTimeout` отвергает 0, цепочка «клиент ≥ сервер» — тест `TestRPCTimeouts`.
- Алерты (п. 10): `teamgramd/deploy/prometheus/server/rules/delivery.yml` (14 правил, `promtool check` — OK), цели Prometheus по сервисам, метрики sync включены; инструкция `docs/ops/delivery.md`.
- e2e (п. 12): сервисы без перезапусков, прогон падает, если какой-то завершился; хаос-тесты — перезапуск `session` (пуши возвращаются без перезапуска sync), остановка Kafka, `kill` msg посреди отправки (повтор с тем же `random_id`), перезапуск sync — у получателя каждое сообщение ровно один раз и по порядку; 1000 сообщений от трёх отправителей — пуши строго по возрастанию `pts`, `getDifference` полный.

Отличие от ADR: очередей на устройство нет (запись реализации в п. 7 ADR 0012).

## Результат
Доставка ровно один раз и по порядку: событие пишется в `mq_outbox` той же транзакцией, что и сообщение; relay — единственный продюсер Kafka и публикует в порядке commit; консьюмеры применяют событие по строке один раз, не отмечают offset при ошибке, повторяют временные ошибки, детерминированные уводят в dead/parked с автоповтором; повтор `random_id` отвечает исходным ответом. Пуши в `session` — по порядку, без залипания после перезапусков, пропуски догоняются `updatesTooLong` → `getDifference`. Каждый процесс — свой сервис compose с перезапуском и аккуратной остановкой, дедлайны везде, алерты доставки с инструкцией. Проверено интеграционными тестами и хаос-тестами на живом стеке. Условия выкатки 002+003 пользователям: доставка алертов (Alertmanager, задача 004) и замер задержки на Linux (ADR 0011, п. 12).
