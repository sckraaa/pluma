# 003. Надёжная доставка через Kafka и push в сессии

- Статус: todo
- Зависит от: 002, 005
- ADR: 0005, 0009

## Цель
Ни одно сообщение и ни один апдейт не теряется и не дублируется при сбоях обработчиков, рестартах Kafka, `session` или `sync`.

## Область
По `docs/audit/01-…` и `03-…`:
- Консьюмер (форк marmota `pkg/mq/consumer_group.go`): не коммитить offset при ошибке; ретраи с backoff; DLQ-топик; метрики и алерт на DLQ.
- Обработчики inbox/sync идемпотентны: UNIQUE по `dialog_message_id` и `random_id` (не только Redis на 90 с).
- Ключ партиции = получатель, порядок обработки на пользователя сохраняется; push в `sync` распределяется по пользователю, а не round-robin по 100 горутинам.
- Флаг `unavailable` в `app/messenger/sync/internal/dao/session_client.go` сбрасывается при восстановлении соединения (переподключение с backoff).
- Отправка: MySQL→Kafka неатомарна — outbox-таблица в той же транзакции, что и сообщение (задача 002), публикатор outbox. Relay публикует события одного инициатора в порядке commit его транзакций (id строки outbox или `pts` в пределах `user_id`): в 002 публикация идёт из потока запроса сразу после commit, и две транзакции одного пользователя, закоммиченные подряд (отправка с двух устройств), могут опубликоваться в обратном порядке — копии у получателя лягут иначе, чем у отправителя (ADR 0011, п. 4 и 13).
- Публикация в 002 ограничена по времени (`userbox.EventTimeout`, `PublishTimeout`), но продюсер sarama контекста не принимает: событие, засчитанное как неопубликованное, может дойти позже. Relay должен считать событие отправленным только по ответу брокера и не публиковать следующее событие получателя раньше.
- Kafka: restart-политика, персистентный том; таймауты на всех RPC-клиентах (сейчас `Timeout: 0`). Дедлайн RPC, за которым транзакция ящика, — 0 или не меньше операции (`userbox.CheckRPCTimeout`, проверяется при старте msg, biz и bff).
- Остановка контейнера: `Destroy` msg ждёт выполняющиеся запросы и отправки (`MaxRequestTime`), но в `docker compose` сигнал до сервисов не доходит (`entrypoint.sh` запускает их в фоне и ждёт `tail -f`), а `stop_grace_period` по умолчанию 10 с — сервисы убиваются без `Destroy`.

## Критерии приёмки
- Chaos-тесты: kill обработчика посреди пачки; рестарт Kafka; рестарт `session` — после восстановления все сообщения доставлены ровно один раз, в порядке.
- Тест порядка: 1000 сообщений одному пользователю из разных отправителей — апдейты приходят по возрастанию `pts`.
