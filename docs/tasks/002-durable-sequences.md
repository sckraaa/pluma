# 002. Долговечные счётчики и транзакционный путь записи

- Статус: todo
- Зависит от: 005 (нужны работающие тесты)
- ADR: 0005

## Цель
Потеря или перезапуск Redis не приводит ни к потере сообщений, ни к откату `pts`. Каждый `pts`, который видит клиент, закоммичен вместе с сообщением.

## Область
По `docs/audit/01-updates-and-storage.md`:
- Таблица `user_state(user_id, pts, qts, seq, date)` в MySQL — источник истины; id сообщений в ящике (`user_message_box_id`) выделяются там же.
- Сообщение, запись журнала `user_pts_updates` и продвижение `pts` — в одной транзакции; push в реальном времени — только после commit.
- `updates.getState` отдаёт закоммиченное состояние, а не Redis-счётчик.
- Redis-счётчики (idgen) — только как ускорение с прогревом из MySQL, либо убраны с этого пути.
- Ошибки idgen больше не превращаются в `pts=0`/`id=0` (`idgen_client2.go:86`).
- Журнал пишется не best-effort: ошибка записи = ошибка операции.
- Исправить `return err` вместо `err2` при отправке в группу.
- Миграция существующих данных: инициализация `user_state` из максимумов в таблицах.

Не трогаем: `seq`/`getDifference` (010), Kafka (003).

## Критерии приёмки
- Тест: FLUSHALL Redis между отправками → id и `pts` продолжают расти, сообщения не теряются.
- Конкурентный тест: N параллельных отправок одному пользователю → `pts` без дыр и дублей, порядок журнала = порядок `pts`.
- Нагрузочный замер: задержка отправки не хуже текущей более чем на 20% на 100 пользователях.
