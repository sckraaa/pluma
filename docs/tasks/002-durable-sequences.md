# 002. Долговечные счётчики и транзакционный путь записи

- Статус: done
- Зависит от: 005 (нужны работающие тесты)
- ADR: 0005, 0011

## Цель
Потеря или перезапуск Redis не приводит ни к потере сообщений, ни к откату `pts`. Каждый `pts`, который видит клиент, закоммичен вместе с сообщением.

## Область
По `docs/audit/01-updates-and-storage.md`:
- Таблица `user_state(user_id, pts, qts, seq, date)` в MySQL — источник истины; id сообщений в ящике (`user_message_box_id`) выделяются там же.
- Сообщение, запись журнала `user_pts_updates` и продвижение `pts` — в одной транзакции; push в реальном времени — только после commit.
- `updates.getState` отдаёт закоммиченное состояние, а не Redis-счётчик.
- Redis-счётчики (idgen) — только как ускорение с прогревом из MySQL, либо убраны с этого пути.
- Ошибки idgen больше не превращаются в `pts=0`/`id=0` (`idgen_client2.go:86`).
- Журнал пишется не best-effort: ошибка записи = ошибка операции.
- Исправить `return err` вместо `err2` при отправке в группу.
- Миграция существующих данных: инициализация `user_state` из максимумов в таблицах.

Не трогаем: `seq`/`getDifference` (010), Kafka (003).

Дизайн и план проверки — ADR 0011. Выкатка пользователям — только вместе с задачей 003 (ADR 0011, п. 9): до неё сбой публикации после commit оставляет получателя без сообщения.

## Критерии приёмки
- Тест: FLUSHALL Redis между отправками → id и `pts` продолжают расти, сообщения не теряются.
- Конкурентный тест: N параллельных отправок одному пользователю → `pts` без дыр и дублей, порядок журнала = порядок `pts`.
- Нагрузочный замер: задержка отправки не хуже текущей более чем на 20% на 100 пользователях.

## Ход работы

**Шаг A — слой состояния (готов).**
- `third_party/teamgram-marmota`: копия marmota v0.2.0 (ADR 0009) с одним патчем — экспортируемый `sqlx.NewTx` (`// pluma:`); `replace` в `go.mod`.
- Миграция `teamgramd/deploy/sql/migrate-20261022.sql`: таблица `user_state`, `UNIQUE (user_id, pts)` в `user_pts_updates` с удалением дублей, начальные строки пользователей = максимум + 1 000 000. Описание и требования к MySQL — `docs/ops/user-state.md`.
- `pkg/userbox`: `Run` (READ COMMITTED, блокировка `user_state`, выделение `pts` и id в ящике в памяти, журнал одним запросом, условный `UPDATE`, `COMMIT` под своим пределом, проверка неопределённого `COMMIT`, повторы 1213/1205, бюджет 6 с), `Box` (`Tx`, `State`, `NextMessageId`, `AddPtsUpdate`, `Emit`, `InvalidateCache`), записывающая обёртка сессии, `Read`, `Check`, `CheckJournal` (бывший `CheckPtsContinuity` из msg), `Publish` для событий после commit, метрики `userbox_*`.
- Клиент idgen: `NextId`/`NextIds` возвращают ошибку (`INTERNAL_SERVER_ERROR`) вместо 0 (№2); вызывающие в dfs, bff и msg передают её дальше. Из клиента удалены неиспользуемые ключи (`channel_*`, `scheduled_*`, `bot_updates_*`, `story_*`, `message_data_*`).
- Тесты: юнит-тесты `pkg/userbox` на фейковом драйвере SQL (арифметика, повторы и чистый `Box`, остановка после первой ошибки, вложенный `Run`, исход `COMMIT`, `Check`, `Publish`, метрики), клиента idgen и прокси `testinfra`; интеграционные — см. `docs/ops/testing.md` (`pkg/userbox`).
- Замер `BenchmarkRun` (MacBook, colima, MySQL в tmpfs; показательные цифры — только на Linux, ADR 0011 п. 12): транзакция ящика со строкой `messages` и строкой журнала — 8,6 мс подряд для одного пользователя и ~1,0 мс на операцию при 100 пользователях параллельно. Основная часть — сетевые круги через проброс портов: без `interpolateParams` каждый запрос с аргументами — это prepare, execute и close. С `interpolateParams=true` в DSN — 5,7 и 0,67 мс; решение о параметре — при нагрузочном замере.
- Отличия от текста ADR в деталях реализации: `Run`/`Read`/`Check` принимают `*sql.DB` (общий пул go-zero по DSN, `userbox.Open`), уровень изоляции транзакции проверяется по `information_schema.INNODB_TRX` (`@@transaction_isolation` показывает уровень сессии, а не текущей транзакции).

**Шаг B — путь записи (готов).**
- msg: каждое изменение ящика — одна `userbox.Run` (`Dao.RunBox`), события — после commit (`Dao.Publish` на `userbox.Publish`). Ящик инициатора целиком пишется в RPC: отправка (личный чат и basic group, 1..k сообщений, `pushUserMessage`), правка, удаление и revoke, `deleteHistory` и `deletePhoneCallHistory` порциями до 1000 с `offset`, `readHistoryV2`, `readMessageContents`, закреп с уведомлением (закреп и служебное сообщение — одна транзакция, P и P+1), `unpinAllMessages` порциями. Всё, что зависит от ящика, читается под блокировкой: от `dstMessage` BFF берётся только id, `read_inbox_max_id` только растёт, `top_message` и счётчики непрочитанного после удаления и прочтения считаются по `messages`. `dialogs` пишутся в той же транзакции; ключи кэша — `dialog.UpsertCacheKeys` (строка — до и после commit, списки — при создании строки).
- inbox: каждое событие адресовано `user_id` (получатель), `from_id` — инициатор, ключ Kafka — `user_id`; одна `Run` на событие (на порцию — для истории, копий и открепления). Событие с `user_id = from_id` отвергается. Повторяемые ошибки (1213, 1205, неприменённый `COMMIT`, разрыв до `COMMIT`, исчерпанный бюджет `Run` — `userbox.ErrBudget`) повторяются до 30 с с backoff 0,1 → 5 с; иначе лог с методом, получателем и `dialog_message_id` и `msg_inbox_handler_errors_total`.
- Удалено: V3 и флаг `-usev3`, события `Out`, `inbox.readInboxHistory`, `inbox.updateHistoryReaded`, `msg.readHistory`, остатки V1 и события без производителей, `AddToPtsQueue*`/`persistPtsUpdate`, `InsertOrReturnIdTx` на пути записи, gRPC-сервер, клиенты и кодек TL inbox (inbox — схема событий Kafka), неиспользуемый отдельный сервер `msg/msg/cmd`, запись журнала в sync, RPC без вызывающих, писавшие столбцы ящика мимо транзакции: `dialog.insertOrUpdateDialog`, `dialog.updateUnreadCount`, `message.updatePinnedMessageId`, `message.unPinAllMessages`.
- idgen: методы счётчиков и типы `InputId`/`IdVal` удалены из `idgen.tl.proto`, `SeqIDGen` — из конфигов; idgen не ходит в Redis, sync и biz не ходят в idgen.
- `updates.getStateV2` — из `user_state`; `getDifferenceV2` — журнал до закоммиченного `pts`, `difference` после скачка, `differenceSlice` по лимиту строк. BFF `readMessageContents` передаёт msg только id и не шлёт свой push.
- biz dialog: `reorderPinnedDialogs`, `reorderPinnedSavedDialogs`, `setHistoryTTL`, `setChatTheme` — через `Run`: чтение, затем построчные `UPDATE` по ключу в порядке ключа, ошибки возвращаются.
- Старт: msg и biz вызывают `userbox.Check`, в DSN `innodb_lock_wait_timeout=2`; msg не запускается при `MessageSharding > 1`. `Destroy` msg: отказ новым RPC, ожидание выполняющихся, закрытие консьюмера (дожидается текущего события), сброс продюсеров.
- Идемпотентность отправки до 003 — `Dao.SendOnce` (кэш → блокировка 60 с → повторная проверка кэша → транзакция → публикация → кэш ответа → снятие блокировки; каждый шаг в Redis — до 5 с). Отказ Redis на чтении кэша или блокировке — отправка без защиты и `msg_idempotency_bypass_total`; на записи ответа после commit — успех и `msg_post_commit_errors_total{kind="idempotency"}`.
- `tools/boxaudit` (в `go test`): в коде транзакций ящика нет отброшенных ошибок, методов DAO без `Tx`, RPC-клиентов, кэша, Redis, Kafka, idgen и вложенных `Run`. `pluma-admin state-raise`, `state-export-legacy`, `verify-pts` (`userbox.Raise`, `ExportLegacy`, `CheckJournal`), порядок обновления и отката — `docs/ops/user-state.md`.
- Тесты: интеграционные `app/messenger/msg/internal/dao` (полный путь записи, конкурентный, `FLUSHALL`, порции `deleteHistory`, basic group, порядок по получателю, закреп, прочтение в группе, кэш, идемпотентность, повтор обработчика после блокировки, `reorderPinnedDialogs` biz dialog параллельно с удалением в нескольких диалогах — 100 итераций без 1213), `app/service/biz/updates/internal/core`, `userbox` (`Raise`, `ExportLegacy`, `ErrBudget`); юнит — `SendOnce`, ключ Kafka всех inbox-событий (перебором схемы), `Retryable`, `boxaudit` на фикстуре, `pluma-admin`; e2e — `TestDifferenceWithoutPushes`, `TestRedisFlushAll`, `TestDeleteHistoryInPortions` и замер `TestSendLatency` (`docs/ops/testing.md`). Все зелёные, интеграционные — с `-race -count=2 -shuffle=on`.
- Отличия от текста ADR: у inbox удалён и кодек TL с сервисом RPC в схеме, а не только сервер (без gRPC они не нужны); `dialogs` пишутся SQL-запросами `msg/internal/dao/box_store.go` (upsert с `GREATEST`), а не `*Tx`-методами `DialogsDAO`; отправка больше не обнуляет `unread_count` (без сдвига `read_inbox_max_id` это ломало равенство счётчику непрочитанных); `max_id` прочтения больше `top_message` ограничивается им; закреп уже закреплённого и `unpinAllMessages` без закреплённых — пустышки (раньше второе отвечало `MSG_ID_INVALID`); `deleteHistory` с `just_clear` revoke не рассылает; `readMediaUnreadToInboxV2` несёт список id одного отправителя.

**Исправления по ревью.**
- Строка `dialogs` удаляется только в транзакции ящика: без `just_clear` — в транзакции последней порции `msg.deleteHistory` (личный чат и группа), у собеседника при revoke в личном чате — в последней порции `deleteUserHistoryToInbox` (в группе строка получателя остаётся: он остаётся участником). BFF строк `dialogs` больше не удаляет: раньше autocommit-`DELETE` после порций, в том числе у собеседника, гонялся с входящим сообщением. `messages.deleteChat` повторяет `msg.deleteHistory` у каждого участника, пока `offset > 0`, и возвращает ошибку (было: одна порция в 1000 сообщений, ошибка отбрасывалась). biz `dialog.deleteDialog` (исключение из группы) — через `Run`, ключи кэша — `dialog.DeleteCacheKeys`.
- Счётчики без перебора диалога: индекс `messages (user_id, dialog_id1, dialog_id2, deleted, user_message_box_id)` (`migrate-20261022-dialog-index.sql`, online DDL); `top_message` — чтение индекса, `unread_count` — по непрочитанному диапазону, упоминания и реакции — дельтами по изменённым строкам. Прочтение и удаление в диалоге из 20 000 сообщений читают не больше 2000 строк (без индекса — 20 010).
- `getDifference` читает журнал с мастера (`Master()` marmota), как и состояние; реплики `ReadDSN` для ящиков не используются.
- Писатели журнала вне `pkg/userbox` удалены (`Insert`/`InsertTx`/`SelectLastPts` в biz updates); правило `writer` в `tools/boxaudit` проверяет весь репозиторий: SQL записи в `user_state`/`user_pts_updates` вне `pkg/userbox` (Go-строки и XML таблиц DAO) — ошибка `go test`.
- `SendOnce` после захвата блокировки повторно проверяет кэш ответа (иначе повтор, разминувшийся с первым запросом, создавал второе сообщение). TTL блокировки 60 с выведен из шагов под ней (`sendOnceSection` = 51 с), каждый шаг в Redis ограничен 5 с.
- Публикация — сразу после commit, до операций с Redis. Ожидание ответа Kafka ограничено контекстом события (продюсер sarama контекста не принимает: отправка идёт в горутине и может дойти позже); после таймаута события того же топика в транзакции не отправляются, все события транзакции — не дольше 20 с (`userbox.PublishTimeout`). `Destroy` msg ждёт `MaxRequestTime` (66 с), закрытие продюсеров — ещё до 10 с незавершённые отправки. Порядок публикации двух транзакций одного пользователя гарантирует только relay 003 — записано в ADR (п. 4, 13) и бриф 003.
- Дедлайны RPC: `Timeout` biz и `BizServiceClient.Timeout` в bff — 30 с (было 2 с по умолчанию при операции до 26 с), `userbox.CheckRPCTimeout` при старте biz, bff и msg (`docs/ops/user-state.md`).
- Второй `COMMIT` на каждую `Run` (`database/sql` завершает `*sql.Tx` через драйвер) оставлен: убрать его — своя сессия поверх `*sql.Conn` вместо go-zero; комментарий и ADR п. 12 это описывают.
- Тесты: конкурентные (`TestConcurrentBox`, `TestPinnedDialogsWithDeletes`) требуют нулевого прироста `userbox_tx_retries_total{1213,1205}`; новые интеграционные — `deleteHistory` с revoke при входящих, удаление истории группы всеми участниками и с revoke, счётчики без перебора, `getDifference` с отстающей репликой; юнит — гонка `SendOnce`, пределы публикации, публикатор Kafka при молчащем брокере, цикл порций `deleteChat`, `CheckRPCTimeout`, правило `writer`. `TestSendLatency` меряет и время до push у получателя.

## Результат
Счётчики ящика (`pts`, id в ящике) живут только в MySQL и меняются в одной транзакции с сообщениями, `dialogs` (включая удаление строки диалога) и журналом; push и inbox-события уходят сразу после commit, с пределами по времени; `getState`/`getDifference` читают только закоммиченное и только с мастера. Потеря Redis не трогает ни `pts`, ни id (интеграционный тест и e2e с `FLUSHALL`); 4 отправителя × 25 сообщений одному пользователю при его собственных отправках и прочтениях дают журнал без дыр в порядке commit, точные счётчики непрочитанного и ни одного повтора после 1213/1205. Путь записи один (V2), V3 и мёртвые пути удалены, idgen выдаёт только snowflake; журнал и состояние пишет только `pkg/userbox` (`tools/boxaudit`). Зелёные `make ci`, `make test-integration`, `make e2e`.

Не проверено: **критерий задержки** (не хуже базы на 20%). Пары прогонов `TestSendLatency` на macOS (colima, MySQL в tmpfs) дают разброс одного и того же кода больше самого порога (p50 подряд 9,0 и 13,4 мс, параллельно 38,9 и 45,8 мс при базе 11,1 и 37,2 мс), так что прежнее «+4,6%, в пределах 20%» ничего не доказывает. Для сведения, один прогон после исправлений (SENDS=30): подряд p50/p95 10,4/11,5 мс, от отправки до push у получателя 14,1/18,3 мс; параллельно 36,9/56,8 мс, 249 сообщ./с. Замер по ADR п. 12 (`test/load`, Linux, чередование прогонов базы и новой версии, задержка доставки, лаг консьюмера inbox, метрики InnoDB), прогон процедур обслуживания на стенде e2e (обновление → откат → повторное обновление с `state-raise`) и тест `Destroy` msg во время обработчика — до выкатки, которая возможна только вместе с 003.
