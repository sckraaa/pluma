# 029. Установка iOS-клиента с сайта

- Статус: in progress (2026-11-01: решение владельца — оба пути)
- Зависит от: подписанная ad hoc-сборка iOS (готова, pluma-ios `8314118`, запуск `41269958693`); страницы на pluma.chat (pluma-site, раздача — Caddy на сервере)
- ADR: —

## Цель
Человек открывает pluma.chat на айфоне в Safari, нажимает «Установить» и получает Pluma с пушами, без кабеля, Mac и переподписи каждую неделю. Решение владельца (2026-11-01): Ad Hoc, а не TestFlight.

## Почему это не повторит судьбу «сервисов установки»
Массовые сервисы подписывали приложения enterprise-сертификатами (In-House). Apple выдаёт их только для внутренних приложений компании и отзывала за раздачу посторонним; после отзыва переставали запускаться все копии. Ad Hoc — штатный способ Apple для зарегистрированных устройств своего аккаунта: каждое устройство вписано в профиль по UDID, их не больше 100 в год на семейство (iPhone). Профили живут год (сейчас до 2027-08-18).

## Что выяснено по документации Apple (2026-11-01)
- **Установка по ссылке.** Страница с `<a href="itms-services://?action=download-manifest&url=…">` на манифест (XML plist); манифест и IPA — только по HTTPS с сертификатом, которому доверяет устройство; MIME: `application/octet-stream` для `.ipa`, `text/xml` для `.plist`; ссылаться на манифест, не на IPA ([Distribute proprietary in-house apps](https://support.apple.com/en-gb/guide/deployment/depce7cefc4d/web)). Поля манифеста Xcode: URL IPA (HTTPS), картинка 57×57 на время загрузки, большая картинка ([Export an iOS app](https://help.apple.com/xcode/mac/current/en.lproj/dev23ea8b877.html)). Страница Apple описывает этот путь для in-house; что он работает и для Ad Hoc — вывод (у Xcode тот же флажок «Include manifest for over-the-air installation»), проверить на первом же шаге.
  - Сообщения на форуме Apple (не документация): устройство не проходит страницу входа при загрузке IPA — доступ закрывать одноразовым токеном в URL, а не авторизацией.
- **«Режим разработчика».** Нужен для приложений, подписанных сертификатом разработки (development), и для IPA, установленных Apple Configurator; не нужен для TestFlight, App Store и in-house ([WWDC22 «Get to know Developer Mode»](https://developer.apple.com/videos/play/wwdc2022/110344/), [Enabling Developer Mode](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device.md)). Переключатель появляется в настройках только после сопряжения с Mac или установки development-подписанного приложения. Страница [Distributing your app to registered devices](https://developer.apple.com/documentation/xcode/distributing-your-app-to-registered-devices.md) требует его для IPA, экспортированного как «Debugging» (development). Наш IPA подписан Apple Distribution (ad hoc), про него Apple прямо не пишет; на форуме есть сообщение, что ad hoc запросил режим. **Проверить первым делом:** поставить IPA `8314118` на айфон владельца и посмотреть, просит ли iOS «Режим разработчика». Если просит — установка без Mac невозможна, и задача меняется (TestFlight).
- **UDID с сайта.** Профиль конфигурации с полезной нагрузкой `Profile Service`: `PayloadContent.URL` — наш HTTPS-адрес, `DeviceAttributes` — `UDID` (и `VERSION`, `PRODUCT`), `Challenge` — одноразовый токен. После установки айфон шлёт POST: plist атрибутов, подписанный PKCS#7 сертификатом устройства (цепочка «Apple iPhone Device CA»); сервер должен проверить подпись и challenge ([Creating a Profile Server](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/iPhoneOTAConfiguration/profile-service/profile-service.html), архив Apple). Чем закончить обмен, чтобы Safari открыл нашу страницу (в примере Apple — редирект 301), и показывает ли iOS неподписанный профиль как «Не проверен» — проверить на устройстве.
- **Регистрация и профили через API** (спецификация OpenAPI App Store Connect 4.5.1): `POST /v1/devices` (`name`, `udid`, `platform: IOS`), `POST /v1/profiles` (`profileType: IOS_APP_ADHOC`, связи `bundleId`, `certificates`, `devices`; ответ с `profileContent`). Нужен командный ключ API с ролью Admin: индивидуальные ключи к provisioning не допускаются, регистрация устройств и профили — роли Account Holder или Admin ([Creating API keys](https://developer.apple.com/documentation/appstoreconnectapi/creating-api-keys-for-app-store-connect-api.md), [Register a single device](https://developer.apple.com/help/account/devices/register-a-single-device/)).
- **Лимит.** Устройства — на семейство в год; удалённое устройство освобождает место только с новым годом членства ([Distributing your app to registered devices](https://developer.apple.com/documentation/xcode/distributing-your-app-to-registered-devices.md), [Devices overview](https://developer.apple.com/help/account/devices/devices-overview)).

## Проверка на устройстве (2026-11-01, айфон владельца, iOS 26.6.1)
- IPA `8314118` (ad hoc, Apple Distribution) установлен через Finder; пуши приходят.
- С выключенным «Режимом разработчика» приложение не запускается, iOS просит включить режим. **Ad hoc-сборке «Режим разработчика» нужен.** Переключатель этого режима появляется в настройках только после сопряжения с Mac или установки development-подписанного приложения через Configurator (WWDC22); появляется ли он после установки по ссылке на айфоне, который никогда не видел Mac, не проверено (нужен такой айфон).
- Значит, обычному человеку установка ad hoc с сайта даёт как минимум включение «Режима разработчика» с предупреждением о безопасности и перезагрузкой, а возможно, и не работает без Mac вовсе. TestFlight, App Store и in-house этого режима не требуют (WWDC22).

## Решение владельца (2026-11-01)
- На сайте для iOS два способа, человек выбирает сам: **TestFlight** и **Ad Hoc**. После выбора — свои инструкции.
- Сейчас на сайте виден только TestFlight. Ad Hoc делается, проверяется и лежит готовым, но **скрыт**, пока клиент не финальный.
- Ad Hoc: загрузка профиля для UDID → **автоматическое быстрое добавление UDID без одобрения** → установка по ссылке. В инструкции — как включить «Режим разработчика».
- TestFlight собирается в CI pluma-ios второй кнопкой рядом с ad hoc (ветка `task/029-testflight`).

## Проект Ad Hoc (на подтверждение, где помечено)
- Цепочка: страница pluma.chat → профиль `Profile Service` с одноразовым challenge → айфон шлёт подписанный UDID → сервис проверяет подпись устройства и challenge → регистрирует устройство (`POST /v1/devices`), перевыпускает семь ad hoc-профилей (`POST /v1/profiles`) → переподписывает готовый IPA новыми профилями → страница показывает кнопку установки (`itms-services`, манифест на dl.pluma.chat).
- **Где переподписывать — решено владельцем (2026-11-01): на сервере (вариант а).** Ключи — только в окружении отдельного контейнера сервиса установки (не в общем `.env` и не у других сервисов), в логи не попадают ни ключи, ни UDID; профили и устройства — ключом API `4FQM72H54Q` (Admin). Исходные варианты: Сборка в CI уже подписана; для нового устройства нужен только новый профиль внутри IPA и переподпись. Автоматика без одобрения возможна, только если ключи под рукой у сервиса: (а) на сервере — сертификат Apple Distribution с ключом и ключ App Store Connect API (Admin) в `.env`, как ключ APNs; переподпись на Linux инструментом `rcodesign` (проверить, что он подписывает iOS-приложения с расширениями); секунды; (б) в GitHub Actions — отдельное окружение без одобрения, запуск по событию от сервера; минуты на запуск раннера, ключи остаются в GitHub. Риск (а): кто захватит сервер, получит ключ подписи и Admin-ключ команды Apple.
- Злоупотребление: без одобрения любой, кто найдёт скрытую страницу, тратит слот из 100 в год. Ограничения: скрытый адрес, challenge только со страницы, лимит регистраций на IP и в сутки, журнал в `pluma-admin`.
- «Режим разработчика»: переключатель появляется после сопряжения с Mac или установки development-сборки (WWDC22). Появится ли он у айфона, который не видел Mac, после установки по ссылке — проверить на таком айфоне до того, как открывать Ad Hoc.

## Прототип переподписи (2026-11-01, подтверждён)
- `rcodesign` 0.29.0 (релиз indygreg/apple-platform-rs, sha256 сверен), запуск на Mac: в IPA `8314118` в каждый из семи бандлов положен свой ad hoc-профиль (`embedded.mobileprovision`), права каждого бандла сняты с подписи CI (`codesign -d --entitlements`) и переданы по путям: `-e Telegram.plist -e "PlugIns/ShareExtension.appex:Share.plist" …`; `--p12-file` + `--p12-password-file`. Фреймворки и `libswift_Concurrency.dylib` подписаны рекурсивно.
- `codesign --verify --deep --strict` проходит; IPA поставлен на айфон владельца (`devicectl`), приложение запускается и работает (владелец). На сервере тот же `rcodesign` под Linux; права для подписи сервис берёт из подписанного CI IPA, профили — свежие из API.

## Проект сервиса установки (2026-11-01)
- **Сервис** `app/interface/iosinstall`: отдельный бинарник и контейнер `iosinstall`; ключи (`.p12` и пароль, ключ API `4FQM72H54Q`, issuer) — только в его `env_file` на хосте (`/opt/pluma/iosinstall.env`), не в общем `.env`; `rcodesign` (Linux x86_64, версия и sha256 закреплены) — в образе.
- **Адреса** (Caddy, сайт pluma.chat): `GET /ios/adhoc/profile` — `.mobileconfig` с `Profile Service` и одноразовым challenge (Redis, TTL); `POST /ios/adhoc/enroll` — ответ айфона: проверка подписи PKCS#7 по корню Apple (цепочка «Apple iPhone Device CA», даты сертификата устройства не учитываются, как велит Apple) и challenge, затем 301 на страницу ожидания; `GET /ios/adhoc/status?t=` — «готовим» / «готово» со ссылкой `itms-services`; манифест и IPA — по ссылкам с токеном.
- **Новое устройство:** `POST /v1/devices` (если UDID ещё нет) → перевыпуск семи ad hoc-профилей со всеми устройствами (старые удаляются, новые создаются) → переподпись исходного IPA `rcodesign` с правами каждого бандла из файла, который CI кладёт рядом с IPA → атомарная замена текущего IPA и манифеста. Переподписи идут по одной; заявки, пришедшие во время переподписи, ждут следующей. Все устройства получают один и тот же IPA.
- **Исходный IPA:** CI pluma-ios после подписанной сборки ad hoc выкладывает IPA и `entitlements.json` на сервер (отдельный ключ развёртывания с правом записи только в каталог сервиса) — или сервис сам забирает артефакт; выбрать при реализации.
- **Хранение:** таблица устройств (UDID, модель, версия iOS, ID устройства Apple, время, адрес), журнал в `pluma-admin ios-devices list`; лимиты на адрес и в сутки; UDID в логи не пишутся.
- **Сайт** (pluma-site): на /iphone виден TestFlight (кнопка публичной ссылки — когда Apple одобрит бету); скрытая страница Ad Hoc: выбор способа, шаги, профиль, ожидание, установка, как включить «Режим разработчика».
- **Порядок:** после задачи 021 (языковые пакеты) — диск на машине разработки (10 ГБ) не даёт собирать обе параллельно. Перед выкладкой на сервер — закоммитить правку Caddyfile и `docker-compose.web.yaml` лендинга, которая сейчас лежит на сервере незакоммиченной.

## Область, по этапам
1. **Проверка без кода.** IPA `8314118` на айфон владельца через Finder: нужен ли «Режим разработчика», приходят ли пуши. От результата зависит всё дальнейшее.
2. **Установка по ссылке для уже вписанных устройств.** Манифест и IPA на сервере (Caddy, HTTPS), страница pluma.chat/iphone с кнопкой; доступ по одноразовому токену. CI pluma-ios кладёт подписанный IPA и манифест туда, откуда их раздаёт Caddy (как веб-клиент: образ или каталог на хосте — решить).
3. **Сбор UDID с сайта.** Профиль `Profile Service` с challenge, обработчик POST на сервере (проверка подписи устройства и challenge), заявки в базе, одобрение владельцем через `pluma-admin`. UDID — персональные данные: храним только заявки и одобренные устройства, в логи не пишем.
4. **Автоматика.** По одобрению — регистрация устройства и перевыпуск семи профилей через API, переподпись готового IPA новыми профилями (без пересборки), ссылка на установку человеку. Нужен ключ API с ролью Admin (решение владельца).

## Открытые вопросы владельцу
- Ключ App Store Connect API с ролью Admin (для этапа 4).
- Кто одобряет устройства и как человек узнаёт, что можно ставить (письмо, сообщение в Pluma, страница статуса).
- Обновления: человек снова нажимает «Установить»; нужен ли баннер «вышла новая версия» в приложении.

## Критерии приёмки
- Этап 1: записано, нужен ли «Режим разработчика» для ad hoc и работают ли пуши — сделано: нужен, пуши работают.
- Этап 2: на вписанном айфоне установка из Safari по ссылке pluma.chat без кабеля; IPA недоступен без токена.
- Этапы 3–4: новый айфон от открытия pluma.chat до установленного приложения — без Mac и без ручных шагов владельца, кроме одобрения.
