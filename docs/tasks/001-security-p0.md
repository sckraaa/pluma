# 001. Безопасность P0: закрыть критические дыры

- Статус: done в коде (2026-10-21); проверка на живом стеке с официальными клиентами — при первом развёртывании (см. STATUS)
- Зависит от: —
- ADR: 0003, 0009

## Цель
Сервер можно безопасно выставить в интернет для закрытой группы: нет входа без настоящего кода, нет захвата сессий, нет утечки ключей.

## Область
По `docs/audit/02-transport-and-security.md` (P0) и `docs/audit/03-architecture-and-ops.md`:
1. **RSA-ключ.** Удалить `teamgramd/bin/server_pkcs1.key` из репозитория (и добавить в `.gitignore`), генерировать ключ при установке, хранить вне git (файл с правами 0600 / секрет), загрузка по пути из конфига. Скрипт генерации, печатающий отпечаток и публичный ключ для патча клиентов. Историю git не переписываем — ключ просто считается скомпрометированным и не используется.
2. **Коды входа.** Убрать фиксированный `12345`. Регистрация только по allowlist номеров (управляется админ-CLI). Доставка кода: в приложение на уже авторизованном устройстве (`auth.sentCodeTypeApp`); для первого устройства — одноразовый код из админ-CLI. Лимиты попыток и FLOOD_WAIT на `auth.sendCode`/`auth.signIn`/`auth.checkPassword`.
3. **`auth.bindTempAuthKey`.** Полная проверка по спецификации (encrypted_message, nonce, temp_session_id, expires_at, совпадение perm/temp ключей с внешним сообщением) в gateway и authsession; никакого доверия `perm_auth_key_id` до проверки.
4. **Логи.** Убрать из логов `a`, `new_nonce`, `g_b`, части ключей, `aesKey`/`aesIV`, тела сообщений. Уровень debug не должен включать это ни при каких условиях.
5. **Сеть.** В compose наружу публикуется только gateway (и HTTP для веба, если нужен); пароли инфраструктуры из `.env`, не дефолтные.
6. **DoS до аутентификации:** recover в обработке handshake, лимиты размера векторов/строк при декодировании, лимит распаковки gzip, лимит буфера WebSocket.

Не трогаем: 2FA, PFS-сроки, rate limiting по остальным методам — это задача 008.

## Критерии приёмки
- Тесты: вход с неверным кодом отклоняется; превышение попыток → FLOOD_WAIT; подделанный `bindTempAuthKey` отклоняется; handshake с мусором не роняет процесс; gzip-бомба отклоняется.
- `git ls-files | grep -i key` не находит приватных ключей.
- `docker compose config` публикует наружу только gateway-порты.
- grep по коду не находит логирования ключевого материала.

## Результат
**WP1 (пункты 1 и 5) — готов.**

- `tools/genserverkey` + `pkg/serverkey`: генерация RSA-2048, отпечаток по схеме Telegram (проверен на старом ключе и официальном ключе Telegram), публичный ключ для клиентов, hex для Web K.
- gnetway и httpserver не стартуют при отсутствующем ключе, правах для «прочих», несовпадении отпечатка.
- `pkg/conf`: подстановка `${VAR}` из окружения во все конфиги сервисов; пароли только из `.env` (`${VAR:?}`), `.env.example`; убран вывод всего конфига в лог при старте.
- Наружу в Docker только 10443, 5222, 11443; инфраструктура — на 127.0.0.1.
- Инструкция: `docs/ops/security-setup.md`.
- Открытое: etcd/Kafka без аутентификации и нет TLS между сервисами (остаток находки #6); выделенный пользователь MinIO для dfs; контейнеры от root; ADR 0003 просит зашифрованный ключ/KMS — сейчас файл 0600 / compose secret; проверить на первом реальном `docker compose up`; правки `third_party` — отдельными коммитами `third_party(proto): ...`.

**WP3 (пункт 3, находки #3, #4) — готов.**
- authsession проверяет `auth.bindTempAuthKey` полностью (`core/bind_temp_auth_key.go`): `encrypted_message` расшифровывается perm-ключом из `perm_auth_key_id` по MTProto v1 (msg_key, длина, паддинг 0–15 байт); внутри `msg_id` равен msg_id запроса, `seqno` 0, `msg_len` 40; `bind_auth_key_inner` повторяет `nonce`, `perm_auth_key_id`, `expires_at` запроса, а `temp_auth_key_id` и `temp_session_id` совпадают с ключом и сессией, которыми запрос пришёл (session передаёт их в RPC-метаданных). Ошибки: `ENCRYPTED_MESSAGE_INVALID`, `EXPIRES_AT_INVALID`, `TEMP_AUTH_KEY_EMPTY`, `TEMP_AUTH_KEY_ALREADY_BOUND`.
- Привязка пишется одной транзакцией (`SELECT … FOR UPDATE`) и только после проверки. Temp-ключ привязывается к одному perm-ключу на всю жизнь; повтор с тем же perm-ключом допустим. Непривязанные temp-ключи не кэшируются в Redis.
- Срок жизни: `auth_key_infos.expires_at` (миграция `migrate-20261021-pfs.sql`) = время handshake + `expires_in`; при привязке он понижается до `expires_at` клиента. Истёкший temp-ключ authsession считает неизвестным, gateway отвечает транспортной ошибкой -404, и клиент создаёт новый ключ. Срок своих ключей gateway знает сам, остальные temp-ключи перепроверяет в authsession раз в 60 с.
- Gateway больше не читает открытый текст сообщений: убраны «hack» с `PutAuthKey(clone)` и ответ на ping. Маршрут берётся только из данных authsession (`session.RouteKey`). Непривязанный temp-ключ обслуживает отдельный ограниченный `MainAuthWrapper`: без пользователя и perm-ключа, разрешены только `auth.bindTempAuthKey`, `help.getConfig`, `help.getNearestDc`, остальное получает `401 AUTH_KEY_PERM_EMPTY`. Перед каждым сообщением такого ключа gateway перечитывает его в authsession; в wrapper perm-ключа трафик идёт только после подтверждённой привязки. Общий wrapper для `perm_auth_key_id = 0` удалён. Тот же маршрут — в HTTP-транспорте gnetway и при закрытии соединения. Неудачный bind больше не уничтожает wrapper.
- Тесты: authsession (верная привязка; каждое несовпадающее поле; чужой perm-ключ; повтор для другого perm-ключа; при любой ошибке ничего не записано; fuzz расшифровки), session (маршрут, ограничения непривязанного ключа, метаданные bind), gnetway (маршрут не зависит от содержимого сообщения, кэш не «отравляется», сроки ключей).

**WP5 (пункт 6, находки #10–#13, #15, #20, #22, #29) — готов.**
- Handshake в gnetway переписан как конечный автомат по nonce (`handshake_state.go`): каждое сообщение проверяется против состояния (`req_pq` → `req_DH_params` → `set_client_DH_params`), повтор, неверный порядок и параллельные шаги отклоняются и закрывают соединение. RSA и DH считаются в пуле на копии состояния (гонка #29 устранена), результат применяется под мьютексом. TCP/WebSocket и HTTP используют один код (дубликат в `server_http.go` удалён). Из нешифрованных сообщений декодируются только `req_pq(_multi)`, `req_DH_params`, `set_client_DH_params`, `msgs_ack`; проверяется `message_data_length`; внутри — только `p_q_inner_data*` и `client_DH_inner_data`. Попутно: `encrypted_data` строго 256 байт, потерянные ведущие нули RSA восстанавливаются (#28).
- Panic в обработке соединения (OnTraffic, колбэки event loop, задачи пула, OnClose) закрывает только это соединение; в лог — id соединения, тип panic и место, метрика `gnetway_conn_panic_recovered_total`.
- Зашифрованный кадр короче 8+16+48 байт отклоняется до разбора; хвост padded intermediate отбрасывается. `AesIgeDecrypt`: msg_key проверяется по всему тексту (константное время), длина % 4, паддинг 12..1024, без переполнения; одна ошибка `ErrDecryptMessage` без ключевого материала (V1 — паддинг 0..15).
- TL-декодер (`third_party/teamgram-proto`, правки помечены `// pluma:`): длина вектора ограничена остатком входа (≥4 байта на элемент) и бюджетом 16 МиБ на сообщение (размер Go-структур элементов, `Update` > 2 КБ); вложенность рекурсивных типов и Object() ≤ 100; отрицательные длины; контейнеры; тело `message2` без копирования. gzip_packed распаковывается через `LimitReader`, суммарно ≤ 16 МиБ на сообщение (бомба отклоняется). Fuzz-тесты `FuzzDecodeObject`, `FuzzDecodeEachConstructor` (каждый конструктор) — без panic, аллокации ограничены.
- WebSocket: кадр и сообщение ≤ 16 МиБ + 1 КиБ, control-кадры ≤ 125 байт, upgrade-запрос ≤ 64 КиБ, сырой буфер ограничен; из одного WS-сообщения обрабатываются все кадры MTProto, незаконченный кадр сохраняется до следующего (раньше хвост терялся или копился). Abridged-кадр ≤ 8 байт закрывает соединение (раньше «зависал» и буфер рос).
- Таймауты: до первого сообщения, расшифрованного известным ключом, соединение живёт не дольше 60 с с открытия, трафик (включая пинги WS и медленный upgrade) срок не продлевает; после — как раньше (300 с TCP/WS, 60 с HTTP).
- Неизвестный auth_key_id: один запрос в authsession на соединение за раз, сообщения ждут в очереди (≤ 32 и ≤ 16 МиБ); другой ключ во время запроса закрывает соединение.
- HTTP: состояние handshake — в отдельном ограниченном хранилище (4096, TTL 60 с), не в кэше ключей; LRU ключей считает байты (`AuthKeyCacheM` — реальные МБ). Запрос не разбирается повторно, пока не отвечен (раньше каждый байт повторял, например, RSA-расшифровку); отрицательный Content-Length, буфер ≤ 2 × (8 КиБ + 1 МиБ).
- Тесты: полный handshake независимым клиентом (perm/temp, TCP и HTTP по разным соединениям), неверный порядок, короткие кадры всех длин, мусор в DH-шагах, panic, таймауты, очередь запросов ключа, HTTP-флуд, WS (лимиты, кадры через границу сообщений), декодер (огромные векторы, глубина, gzip-бомба 256 МиБ), `AesIgeDecrypt` (паддинг, длины); fuzz handshake.

**WP4 (пункт 4, находки #8, #9, #25) — готов.**
- Handshake: в gnetway и httpserver не логируются `a`, `new_nonce`, `g_b`, `client_DH_inner_data`, temp_key RSA_PAD и расшифрованные данные; `HandshakeStateCtx` печатается без секретов при любом verb (`Format`), `DebugString` удалён. В httpserver убраны дампы `key1/key2`, `paddedDataWithHash`, `encrypted_data`, состояния и запросов.
- Расшифровка: ошибки `EncryptedMessage2` (third_party) больше не содержат `aesKey`, `aesIV`, `auth_key[88:120]` и шифртекст (одна `ErrDecryptMessage`, msg_key сравнивается за постоянное время); ошибка разбора `message2` — только длина, без hex открытого текста. Gateway при сбое расшифровки пишет `auth_key_id`, длину и id соединения. Убраны hex-дампы первых байт соединения (ключи обфускации), PROXY-заголовка с трафиком, WS upgrade-запроса.
- Содержимое: обёртки gRPC всех сервисов логируют только метаданные, без тел запросов и ответов (в т.ч. `authsession.setAuthKey`/`queryAuthKey` с ключом, `code.*`); session — id и типы вместо запросов, токенов `invokeWith*` (APNs/Play Integrity/reCAPTCHA), контейнеров и updates; msg/inbox/sync — без текстов сообщений, Kafka-payload и push-данных; DAO — без data-объектов в ошибках; bff/biz — без телефонов, контактов, токена QR-входа, invite-hash, `phone_code_hash`. Отдельные серверы модулей больше не пишут конфиг целиком (`logx.Infov(c)`), etcd-конфиг — только hosts/key.
- go-zero сам писал тело каждого RPC-запроса на уровне info, SQL с подставленными значениями и аргументы медленных команд Redis. `pkg/logpolicy` отключает это при загрузке конфига (`pkg/conf.Load`) для всех сервисов; метрики длительности SQL go-zero при этом не собирает.
- `Log.Level: info` во всех поставляемых конфигах; debug включается в конфиге и тоже не содержит перечисленного.
- Тесты: ошибки расшифровки `AesIgeDecrypt`/`EncryptedMessage2` без ключевого материала (второй падал на старом коде); handshake на уровне debug не пишет `new_nonce`, `g_b`, ключ; сбой расшифровки не пишет пакет; `HandshakeStateCtx` при всех verb; SQL go-zero до/после `logpolicy.Apply`; все методы gRPC попадают в список. `tools/logaudit` — AST-проверка всего кода (секреты по именам, TL-объекты и строки БД целиком, hex/base64-дампы, форматы `request: %s`), работает в `go test ./...` за ~1 с; исключения — `// logaudit:ok <причина>`.
- Открытое: httpserver дублирует старый handshake без автомата WP5 и без проверки хэша RSA_PAD, падает на неизвестном nonce; отдельные серверы модулей (`app/bff/*`, `app/service/biz/*`, `app/messenger/msg/{inbox,msg}`) грузят конфиг через go-zero напрямую — без `${VAR}` и log policy (в поставку не входят); debug-программы `gnet/codec/checker` (с ключами upstream) и `gnet/pp/c2` стоит удалить; go-zero REST при 5xx пишет запрос целиком (httpserver, dfs).

**Ревью (три линзы, 20 находок) — все исправлены.** Меняют описанное выше:
- WP2: код 6 цифр (клиенты берут длину из `sentCodeType.length`). Лимиты «по IP» считают только промахи (номер не из allowlist, неверный код, неизвестный запрос) плюс 200 запросов кода в час: группа за одним NAT входит свободно; IPv6 считается по /64. Запросы кода на номер — 5 в час с одного адреса и 20 всего; неверные коды на номер — 5/ч, 10/сут, 30/30 дней, считаются только сравнения с живым кодом, верный код возвращает попытку; больше 50 неверных кодов в сутки по всем номерам — ошибка в лог. Проверки истёкшего кода не тратят попытки. `pluma-admin login-code <номер> [id]` показывает все ожидающие запросы и не выдаёт код наугад; код не переживает свой запрос, исчерпанный запрос кода не получает; `login-unblock <номер|IP>` снимает блокировку. Ошибка доставки кода в приложение пишется в лог. Тесты обработчиков `account.changePhone` и `auth.signUp`.
- WP3: непривязанный temp-ключ читается из authsession не больше 64 раз (общий счётчик для всех соединений), дальше -404; handshake и authsession отвергают temp-ключ без положительного `expires_in`; миграция PFS гасит temp-ключи и привязки, созданные до неё; ключи из Redis-хэша старых версий не читаются.
- WP5: вложенность `invoke*`/`initConnection` в session ≤ 10, запрос не копируется на каждом уровне, декодер продолжает глубину и бюджет сообщения (`DecodeBuf.NewNestedDecodeBuf`). Quick ACK считается по открытому тексту (как у клиентов). HTTP: -404 только для неизвестного ключа, при сбое authsession — 502; DH-шаг, чьё состояние вытеснено, получает ответ.
- Развёртывание: HTTP dfs на 127.0.0.1; порты в Docker только IPv4 (IPv6 через docker-proxy сливал всех клиентов в один адрес); в `security-setup.md` — пользователь MySQL и `requirepass` для запуска без Docker, PROXY protocol за TLS-терминатором, сброс сессий для ранее открытой установки.
