# 057. dfs: файлы не держатся в памяти, части загрузок не в Redis

- Статус: done (выкатка — после CI)
- Зависит от: 056 (лимиты памяти; лимит dfs 1,5 ГБ), разбор кода dfs 05.11 (несколько независимых проверок каждой находки).

## Что не так (подтверждено чтением кода)
1. **Части загрузок в Redis.** `upload.saveFilePart`/`saveBigFilePart` пишут каждую часть в Redis (`HSET file_<owner>_<id>`, 3 ч), после переноса в S3 их не удаляют (`dao/ssdb.go`, `DropFile` — только в `importDocument`). Telegram разрешает 4000 частей по 512 КБ (2 ГБ; core.telegram.org/api/files, `upload_max_fileparts_default` у нас 4000), а у Redis `maxmemory 1gb noeviction`: файл больше ~1 ГБ не загружается, и на 3 часа отказывают все записи Redis, включая сессии и коды входа.
2. **`upload.getFile` без проверки `limit`/`offset`.** `dfs` выделяет `make([]byte, limit)` по числу клиента (до 2 ГБ на запрос; `dao/cache_file.go:116`, `minio_util/minio.go:153`).
3. **Декодирование картинок без проверки размеров** (`imaging.Decode`): маленький файл с заявленными 20000×20000 даёт 1,6 ГБ.
4. **Файлы целиком в памяти:** документ-картинка (`ReadAll` + второй буфер размером с файл + фоновая горутина держит его до конца переноса), видео профиля (`ReadAll` только ради md5), GIF, обои, тема.
5. **mini-http буферизует ответ целиком:** при `Timeout` go-zero ставит `TimeoutHandler`, который копит весь ответ ffmpeg в памяти (`teamgramd/etc2/dfs.yaml`, комментарий «No timeout» противоречит значению).
6. **Перенос в S3:** размер неизвестен (`-1`) — minio-go держит буфер части; фоновые горутины без ограничения числа и без срока.

## Решения
- Части — файлами на диске dfs (`/data/parts/<владелец>/<файл>/<номер>`, том `dfs_parts`), запись атомарная (временный файл и переименование), сведения о файле (размеры частей) остаются в Redis. Читатель частей — `io.ReaderAt` с известным размером; при открытии проверяется, что все части на месте (`FILE_PART_X_MISSING`, как у Telegram). Старые загрузки чистит фоновая уборка через 3 ч, как раньше истекал ключ Redis. Перед записью — проверка свободного места (новые части не принимаются, если свободно меньше 1 ГБ).
- После успешного переноса в S3 удаляется запись кэша: скачивание идёт из S3; до этого — из частей, как раньше. Сами части живут свои 3 часа, как жили в Redis: клиент может прислать ту же загрузку ещё раз. Перенос записан рядом с частями и после перезапуска продолжается; такие части уборка не трогает до 24 ч.
- Перенос в S3 с известным размером; не больше 4 переносов разом, срок 15 минут, три попытки.
- `upload.getFile` — правила core.telegram.org/api/files: без `precise` `offset` и `limit` кратны 4 КБ и 1 МБ делится на `limit`; с `precise` кратны 1 КБ и `limit` ≤ 1 МБ; запрос не пересекает границу мегабайта; иначе `LIMIT_INVALID`/`OFFSET_INVALID`. dfs дополнительно не выделяет больше остатка файла.
- Части при загрузке — правила той же страницы: не пустая (`FILE_PART_EMPTY`), не больше 512 КБ (`FILE_PART_TOO_BIG`), номер в `0..3999` (`FILE_PART_INVALID`), у большого файла `1..4000` частей (`FILE_PARTS_INVALID`).
- Картинки: сначала `DecodeConfig`, больше 64 Мп не декодируются (документ остаётся без миниатюры, фото — `PHOTO_INVALID_DIMENSIONS`).
- Пути, которым нужен весь файл в памяти (фото, обои, тема, GIF, видео профиля), не берут файлы больше 64 МБ. Обычные клиенты так не присылают: фото сжимают сами, GIF превращают в mp4, видео профиля — секунды. md5 видео профиля считается потоком.
- mini-http: `TimeoutHandler` выключен в коде, срок — `WriteTimeout` сервера, ответ идёт потоком.

## Результат
Части загрузок теперь хранятся файлами на диске dfs (том `dfs_parts`), а не в памяти Redis. dfs больше не держит загрузки целиком в памяти: файлы до 2 ГБ (4000 частей) идут через читатель частей потоком и в S3 переносятся с известным размером. Клиентские запросы, которые заставляли dfs выделять гигабайты (`upload.getFile` с любым `limit`, картинки с огромными заявленными размерами, `parts` из `InputFile`), проверяются по правилам Telegram.

- **Части.** `dao/parts.go`, `dao/parts_reader.go`: запись атомарная; при отправке проверяются все части (`FILE_PART_X_MISSING`, `FILE_PART_SIZE_CHANGED`, `FILE_PARTS_INVALID`), и проверенная раскладка записывается в сведения о файле: скачивания и mini-http больше не проверяют части заново. Первая часть может быть меньше остальных, как у Android при загрузке ещё пишущегося файла (`FileUploadOperation`, `uploadFirstPartLater`). Новая часть сбрасывает отметку о проверке. Уборка удаляет загрузки через 3 ч простоя. Если на диске меньше 1 ГБ свободного места, новые части не принимаются.
- **Перенос в S3** (`dao/persist.go`): не больше 4 разом, срок 15 мин, 3 попытки. Каждый перенос записан рядом со своими частями и после перезапуска продолжается (`ResumeStores`); уборка не трогает такие части 24 ч. После успеха удаляется запись кэша, и скачивание идёт из S3. Остановка dfs сначала закрывает приём новых переносов (они продолжатся после старта), потом ждёт текущие до 25 с.
- **Правила Telegram** (core.telegram.org/api/files): `upload.getFile` — `checkFileRange` в bff, плюс в dfs не больше 1 МБ на ответ и не больше остатка файла; части — не пустые, до 512 КБ, номер `0..3999`, всего `1..4000`. `file_total_parts = -1` — размер ещё неизвестен (так шлёт Android). Ошибка части при отправке документа доходит до клиента как у Telegram, а не как `MEDIA_INVALID`.
- **Память:** картинки больше 64 Мп не декодируются (документ остаётся без миниатюры, фото — `PHOTO_INVALID_DIMENSIONS`); миниатюра документа-картинки декодируется прямо из частей; целиком в память dfs читает только файлы до 64 МБ; md5 видео профиля считается потоком; mini-http отдаёт ответ потоком (`TimeoutHandler` выключен, срок — `WriteTimeout`).
- **Проверка:** `go build`, `go vet`, `go test -race` (dfs, bff files, `pkg/conf`, `pkg/catalog`, `pkg/webpage`), `make lint`, `go test ./tools/...` — зелёные. Юнит-тесты читателя, проверки частей (включая раскладку Android), переноса и его продолжения после перезапуска, уборки, места на диске, потолка памяти, правил `getFile`, ограничения декодирования. e2e `TestUploadParts`: загрузка из трёх частей, скачивание через границы частей и мегабайтов, отказы по правилам Telegram, загрузка как у Android (`-1`, первая часть последней), `FILE_PART_1_MISSING`. Ревью несколькими независимыми проверками нашло 16 подтверждённых недочётов, все исправлены (среди них две регрессии отправки видео с Android и неограниченное `parts`).
- **При выкатке:** загрузки, начатые до неё, прервутся (их части были в Redis), клиент загрузит заново; старые ключи `file_*` в Redis истекут сами за 3 ч.
- **Не сделано:** у запусков ffmpeg нет собственного срока и ограничения числа одновременных запусков; вывод ffmpeg по-прежнему собирается в памяти (вход ограничен 64 МБ).
