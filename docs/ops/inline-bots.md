# Встроенные инлайн-боты `@gif` и `@pic`

За ботов `@gif` и `@pic` отвечает сам bff `bots`, без процесса бота и без токена (задача 099, ADR 0062). Клиенты находят их по именам из `help.getConfig` (`gif_search_username`, `img_search_username` в `teamgramd/bin/config.json`).
- `@gif` открывает вкладку GIF в панели эмодзи всех четырёх клиентов и отвечает на набранный `@gif`.
- `@pic` отвечает на набранный `@pic` и на поиск картинок в галерее Android.

Ответы — фото и документы из dfs, поэтому телефоны не обращаются к сторонним хостам. Там же — прокси `upload.getWebFile`: миниатюры сторонних инлайн-ботов сервер скачивает сам.

Бота мест `@places` нет (решение владельца 2026-11-16). `venue_search_username` в `config.json` остаётся `foursquare`, ключа `stories_venue_search_username` в `app_config.json` нет. Выбор места в клиентах работает как раньше: Android использует геокодер ОС, у iOS места в пикере выключены.

## Выкатка

1. **До выката — проверить имена.** У людей и каналов не должно быть имён `gif` и `pic`:
   ```bash
   docker exec mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot teamgram -e "SELECT username, peer_type, peer_id, deleted FROM username WHERE username IN (\"gif\",\"pic\")"'
   ```
   - Пустой ответ — всё в порядке.
   - Строка с `peer_type = 2` и `peer_id` 1000101 (`gif`) или 1000102 (`pic`) — бот уже заведён.
   - Любая другая строка — имя занято. Через клиент такое имя не занять (минимум 5 символов), оно могло остаться только от старых данных. Что делать — раздел «Если имя бота занято»; лучше освободить имя до выката.
2. **`.env`** (раздел «Переменные»): `WEBFILE_HMAC_KEY`, `SEARXNG_SECRET`, `SEARXNG_URL=http://searxng:8080`. `INLINE_IMPORT_DAILY_BYTES` можно оставить пустым.
3. **Миграции применяет сервис `migrate`** при старте стека. Оба файла применяются один раз и записываются в `schema_migrations`:
   - `migrate-20261119-inline-bots.sql` — таблицы `inline_media` и `inline_gif_sends`;
   - `z_pluma-inline-bots.sql` — учётные записи ботов: `users` 1000101 `GIF` и 1000102 `Pic`, их строки `username` и `bots` с плейсхолдером `🔍`.

   **`z_pluma-inline-bots.sql` больше не запускается сам.** Если при выкате имя было занято, файл молча пропустил этого бота, но всё равно записан как применённый. После того как имя освобождено, файл запускают вручную (раздел «Если имя бота занято»).
4. **SearXNG.** Добавить `-f docker-compose.search.yaml` в команду сервисов после остальных оверлеев, во все команды compose на сервере, и поднять его: `docker compose -f docker-compose.yaml … -f docker-compose.search.yaml up -d searxng`. Без `SEARXNG_SECRET` compose не стартует.
5. **Перезапустить bff** с новым образом. При старте он сверяет учётные записи ботов с реестром (`pkg/inlinebots`) и начинает принимать запросы только после этой проверки.
6. **Проверить:**
   - в логе bff нет строк `inlinebots: @… is not served`;
   - в Prometheus `inline_bot_misconfigured` равен 0 у `gif` и у `pic`;
   - в клиенте `@pic кот` даёт сетку фото, во вкладке GIF нет ошибки (если GIF ещё никто не сохранял, она пуста — см. «Как отвечает `@gif`»).

## Переменные

Все в `.env`. Compose передаёт их контейнерам `bff` и `migrate`: `pluma-admin` читает тот же `bff.yaml`. Как задавать секреты — `docs/ops/security-setup.md`, раздел 2.

| Переменная | По умолчанию | Что |
|---|---|---|
| `WEBFILE_HMAC_KEY` | пусто | Ключ подписи адресов веб-файлов, не короче 32 байт: `openssl rand -hex 32`. Пусто — прокси выключен: миниатюры сторонних инлайн-ботов уходят как `webDocumentNoProxy`, и клиенты качают их с хоста бота сами, как до задачи 099. |
| `SEARXNG_URL` | пусто | Адрес SearXNG для `@pic`: `http://searxng:8080`. Пусто — `@pic` отвечает пустыми списками. |
| `SEARXNG_SECRET` | — | `server.secret_key` самого SearXNG, `openssl rand -hex 32`. Нужен только `docker-compose.search.yaml`. |
| `SEARXNG_MEMORY`, `SEARXNG_CPUS` | `512m`, `1` | Пределы контейнера `searxng`. При изменении пересчитать `docs/ops/memory.md`. |
| `INLINE_IMPORT_DAILY_BYTES` | 1073741824 (1 ГиБ) | Сколько байт медиа `@gif` и `@pic` могут импортировать в dfs за сутки UTC. |

Разделы `WebFile` и `InlineBots` в `teamgramd/etc2/bff.yaml` (и `teamgramd/etc/bff.yaml`) берут эти переменные. `WebFile.CacheDir` и `WebFile.CacheBytes` не заданы: по умолчанию `/tmp/webfile` в контейнере bff и 2 ГиБ. Раздела `WebFetch` в боевом конфиге нет: `AllowHosts` нужен только стенду e2e (`fakeinline`), в бою загрузка идёт только на публичные адреса.

## Если имя бота занято

Признаки:
- в логе bff — `inlinebots: @gif is not served: username gif belongs to peer … of type …`;
- `inline_bot_misconfigured{bot="gif"} = 1`, срабатывает алерт `InlineBotMisconfigured`;
- в клиентах `@gif` отвечает `BOT_INLINE_DISABLED`, и вкладка GIF пуста.

Второй бот работает. Порядок действий (для `pic` — то же самое с `pic` и 1000102):

1. Посмотреть, чьё имя (запрос из раздела «Выкатка», шаг 1). `peer_type = 2` — пользователь, `peer_type = 4` — канал или супергруппа.
2. Освободить имя.
   - Если имя у живого пользователя или канала, попросить его владельца сменить имя в клиенте (пользователь — «Настройки → Имя пользователя», канал — «Ссылка» в настройках канала). Так строка `username` удаляется штатно, а кэши и собеседники получают обновления. Править `users.username` и `channels` руками нельзя: кэши bff и клиентов останутся со старым именем.
   - Если строка ничья — аккаунт или канал удалён (`users.deleted = 1`, `channels.deleted = 1`, или строки с таким id нет), — удалить её:
     ```bash
     docker exec mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot teamgram -e "DELETE FROM username WHERE username = \"gif\" AND NOT (peer_type = 2 AND peer_id = 1000101)"'
     ```
3. Запустить файл учётных записей вручную. Повторный запуск безопасен: уже заведённое он не трогает.
   ```bash
   cd /opt/pluma && docker exec -i mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot teamgram' < teamgramd/deploy/sql/z_pluma-inline-bots.sql
   ```
   `pluma-admin migrate up` этот файл не запустит: он уже записан как применённый.
4. Перезапускать bff не нужно. Пока бот не обслуживается, bff проверяет реестр каждую минуту (потом раз в 10 минут). В течение минуты в логе появится `inlinebots: @gif is served again`, а `inline_bot_misconfigured` станет 0.

Та же проверка ловит и другие расхождения: аккаунт не бот или удалён, строка `username` помечена удалённой, нет строки `bots`, пустой плейсхолдер, включён `bot_inline_geo`. Причина — в той же строке лога. `pluma-admin bot` встроенных ботов не меняет (ответ `built-in bot, managed by the server`).
- Нет аккаунта, строки `username` или строки `bots` — запустить файл, как в шаге 3.
- Остальное файл не исправит: он только добавляет недостающие строки и не меняет существующие (`INSERT IGNORE`). Такое бывает только после ручной правки этих строк. Вернуть им значения из файла (`users.is_bot = 1`, `users.deleted = 0`, `username.deleted = 0`, у `bots` плейсхолдер `🔍` и `bot_inline_geo = 0`), например:
  ```bash
  docker exec mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot teamgram -e "UPDATE bots SET bot_inline_geo = 0, bot_inline_placeholder = CONVERT(0xF09F948D USING utf8mb4) WHERE bot_id IN (1000101, 1000102)"'
  ```
  Затем сбросить кэш пользователей biz, иначе клиенты получат старые значения: `docker exec redis redis-cli del 'user_data.6#1000101' 'user_data.6#1000102'`.

## Как отвечают боты

- Запрос, на который нет ответа в общем кэше, проходит так:
  - предел — 60 запросов в минуту на пользователя; сверх него клиент получает `FLOOD_WAIT`;
  - бот спрашивает поставщика;
  - найденные медиа импортируются в dfs;
  - ответ кладётся в Redis.
- Кэш общий для всех пользователей: ключ — бот, текст и смещение.
- Срок ответа — 7 с. Что не успело импортироваться, в страницу не попадает, а `next_offset` продолжает с этого места.
- Поставщик упал или за 7 с ничего не готово — пустой список с `cache_time = 0`, без ошибки метода. Клиенты показывают «ничего не найдено», а на ошибку tgnet отвечал бы повторами.
- Текст запроса в лог не пишется. Адреса картинок тоже: в них текст запроса.

### `@gif`

- Поиска GIF по тексту нет. Подходящий поставщик — KLIPY, и только с их письменным согласием на серверную интеграцию (ADR 0062, п. 4.1).
- На пустой запрос (вкладка GIF) отвечает популярным внутри Pluma, до 200 GIF, страницы по 20, `cache_time` 600. Популярное — сумма двух источников:
  - отправки через `@gif` за 30 дней (`inline_gif_sends`);
  - GIF, которые сохранили не меньше трёх разных людей (`user_saved_gifs`).
- Список популярного держится в Redis 10 минут (`inline_local_popular`). Новый популярный GIF появляется в выдаче не сразу, в течение этих 10 минут.
- На запрос с текстом — пустой список.
- Ничего не импортирует: отдаёт документы, которые уже есть в dfs.
- GIF, выбранный во вкладке, Android, iOS и Desktop отправляют с `hide_via`: подписи «через @gif» нет, как в Telegram. Сервер соблюдает `hide_via` только для ботов реестра.

### `@pic`

- Ищет картинки своим SearXNG: `categories=images`, `safesearch=1`, язык сессии. Страницы по 12, `cache_time` 3600.
- Страница ответа SearXNG (до 120 картинок) держится в Redis час (`inline_searxng_<хэш>`), поэтому листание не повторяет поиск. Глубже 5-й страницы SearXNG бот не идёт.
- Картинки скачивает bff, только с публичных адресов (`pkg/webfetch`): не больше 8 МБ, 5 с на файл, 6 загрузок на запрос и 16 на процесс. Картинка пережимается в JPEG не больше 1280 px.
- Если картинка не скачалась, берётся миниатюра движка.
- Импортированное записывается в `inline_media`, при повторной находке файл не качается снова. Пустой запрос — пустой список.
- Текст запроса уходит поисковикам через SearXNG с адреса VPS (исходящий маршрут дома, ADR 0061). Ни пользователь, ни его IP поисковикам не видны.

### Когда появится поиск GIF по тексту

Только после письменного согласия KLIPY и с их ключом, отдельной частью задачи. Тогда в `teamgramd/bin/app_config.json` ставится список эмодзи-категорий вкладки GIF по умолчанию Android (`MessagesController.java:1948-1957`):
```json
"gif_search_emojies": ["👍", "👎", "😍", "😂", "😮", "🙄", "😥", "😡", "🥳", "😎"]
```
После этого — перезапуск bff (`docs/ops/app-config.md`). Пока поиска по тексту нет, список пуст: иначе каждая категория показывала бы пустую выдачу.

## Бюджет импорта

- Счётчик байтов на сутки UTC лежит в Redis (`inline_import_bytes_<ггггммдд>`) и общий для всех реплик bff. Когда он исчерпан, новые картинки не качаются, а `@pic` отдаёт только импортированное раньше.
- Новые сутки начинаются в 00:00 UTC.
- Если Redis потерял счётчик, сутки начинаются заново. Бюджет ограничивает рост dfs, а не счёт за трафик.
- Поднять предел: новое `INLINE_IMPORT_DAILY_BYTES` в `.env` и перезапуск bff; уже потраченное за сегодня учитывается.
- Импортированные файлы не удаляются: в dfs нет удаления, сборка мусора — отдельная задача.
- Сколько занято:
  ```bash
  docker exec mysql sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot teamgram -e "SELECT kind, COUNT(*), ROUND(SUM(bytes)/1048576) AS mib FROM inline_media GROUP BY kind"'
  ```
  `kind` 1 — фото, 2 — GIF. Ещё — метрика `inline_import_bytes_total`.

## SearXNG

- Контейнер `searxng` из `docker-compose.search.yaml`, образ закреплён тегом и digest.
- В сети сервисов, без опубликованного порта, `read_only`, без root.
- Своего состояния нет: настройки — в репозитории, кэши — в памяти.
- **Настройки** — `teamgramd/deploy/searxng/settings.yml`:
  - только JSON;
  - `safe_search: 1`;
  - без лимитера и прокси картинок;
  - 3 с на движок;
  - движки — умолчания SearXNG.

  Движки меняются только в этом файле (`engines: - name: … disabled: true`), затем `docker compose … -f docker-compose.search.yaml up -d searxng`.
- **Блокировки поисковиков.** Движок, который отвечает CAPTCHA или 403, SearXNG сам на время отключает, и отвечают остальные. Если не отвечает ни один, `@pic` даёт пустые списки и срабатывает `InlineProviderFailing{bot="pic"}`. Что смотреть:
  - `docker compose logs --tail=200 searxng` — какие движки отказывают;
  - строки `messages.getInlineBotResults - @pic provider` в логе bff, в них имена отказавших движков.

  Тогда выключить заблокированные движки или включить другие движки картинок.
- **Обновление образа:** поменять в `docker-compose.search.yaml` и тег, и digest; в файле на сервере ничего не править.
- **Память:** предел 512 МБ — оценка. На CachyOS под пробными запросами было около 170 МБ. Через сутки работы дома сверить с `docker stats searxng`.
- **Выключить `@pic`:** очистить `SEARXNG_URL` и перезапустить bff, затем `docker compose … stop searxng`. Бот останется и будет отвечать пустыми списками.

## Прокси веб-файлов (`upload.getWebFile`)

- Миниатюры и контент сторонних инлайн-ботов по адресу клиенты получают как `webDocument`, подписанный `WEBFILE_HMAC_KEY`. Сам файл через `upload.getWebFile` скачивает bff. Хост бота видит адрес VPS, а не адрес пользователя.
- Сервер скачивает только адреса, которые подписал сам. Чужой `access_hash` — `LOCATION_INVALID`.
- Ограничения загрузки:
  - только http(s) и публичные адреса;
  - до 5 переадресаций, 10 с, не больше 20 МБ;
  - типы `image/*`, `video/mp4`, `audio/mpeg`, `audio/ogg`.

  Остальное — `WEBFILE_NOT_AVAILABLE`.
- **Кэш:**
  - файлы целиком на диске контейнера bff (`/tmp/webfile`), до 2 ГиБ и до 24 ч каждый;
  - вытесняются давно не нужные;
  - одна загрузка на адрес одновременно.

  После перезапуска или пересоздания контейнера кэш пуст, файлы просто качаются заново. Эти 2 ГиБ лежат на диске Docker, учитывать их в месте под образы и контейнеры.
- **Смена ключа:** новое значение в `.env`, перезапуск bff. Перестают грузиться только миниатюры результатов, уже показанных клиентам, а новые запросы к ботам получают новую подпись. Ключ не секрет пользователей, но с ним можно заставить сервер скачать любой публичный адрес. Хранить его как остальные ключи `.env`.
- **`webfile_dc_id = 1`** в `config.json`: клиенты Pluma знают только DC 1. Свежая установка, которая запросила веб-файл до первого `help.getConfig`, ждёт его до перезапуска клиента (у клиентов по умолчанию DC 4). Это касается только первых секунд после установки.
- Карты геоточек (`inputWebFileGeoPointLocation`) идут через тот же `upload.getWebFile`, но из своего источника (задача 100, `MAPS_URL`). Если `MAPS_URL` пуст, такой запрос получает `LOCATION_INVALID`, а прокси адресов работает независимо от этого.

## Метрики и алерты

Метрики экспортирует bff. Алерты — группа `inline_bots` в `teamgramd/deploy/prometheus/server/rules/codes.yml`, сводка — в `docs/ops/monitoring.md`.

| Метрика | Что |
|---|---|
| `inline_builtin_requests_total{bot, result}` | Запросы к ботам мимо кэша. `result`: `ok`; `empty` — ничего не найдено, `@pic` без `SEARXNG_URL` или ни одна найденная картинка не импортировалась (бюджет исчерпан, хосты картинок не отдали); `error` — поставщик упал или за 7 с ничего не готово; `limited` — предел 60 в минуту. |
| `inline_builtin_latency_seconds{bot}` | Время ответа мимо кэша. |
| `inline_import_total{kind, result}` | Импорты медиа. `kind`: `photo`, `gif`. `result`: `ok`, `error`, `timeout`, `budget` (бюджет исчерпан), `busy` (нет свободной загрузки процесса). |
| `inline_import_bytes_total{kind}` | Байты, импортированные в dfs. |
| `inline_media_orphans_total` | Файл импортирован, а строка `inline_media` не записалась. Следующий запрос импортирует его снова, рост значит сбои MySQL. |
| `inline_bot_misconfigured{bot}` | 1 — учётная запись бота расходится с реестром, бот отвечает `BOT_INLINE_DISABLED`. |
| `webfile_requests_total{kind, result}` | Части веб-файлов. `result`: `ok`, `invalid`, `unavailable`, `error`. |
| `webfile_cache_bytes` | Занято кэшем веб-файлов на диске. |

| Алерт | Что делать |
|---|---|
| `InlineProviderFailing` | Больше половины запросов к боту за 15 минут — ошибки (и не меньше трёх). Для `pic` — раздел «SearXNG», блокировки поисковиков. Для `gif` — MySQL и сервис media, строки `messages.getInlineBotResults - @gif` в логе bff. Если ошибки — «нет времени» при работающем поставщике: медленные хосты картинок (`inline_import_total{result="timeout"}`). |
| `InlineBotMisconfigured` | Раздел «Если имя бота занято». |
| `InlineImportBudgetSpent` | Бюджет кончился до 18:00 UTC. Посмотреть `inline_import_bytes_total` по видам и `inline_media` (раздел «Бюджет импорта»): это обычный рост от новых запросов или кто-то перебирает слова. Поднимать `INLINE_IMPORT_DAILY_BYTES`, только если диска хватает. |

## После перезапуска

- Ответы, кэши, список популярного и счётчик бюджета лежат в Redis и переживают перезапуск bff.
- Импорт, прерванный посередине, оставляет файл без строки `inline_media`. Следующий запрос импортирует его снова.
- SearXNG без состояния. Пока он недоступен, `@pic` отвечает пустыми списками, а потом работает снова без вмешательства.
- Кэш веб-файлов может пропасть вместе с контейнером, это нормально.
