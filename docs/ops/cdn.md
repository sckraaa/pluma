# CDN больших файлов (HTTPS, Gcore и российский узел)

Решение — ADR 0071, задача 107; выдача 202 и маршрут по стране — ADR 0072 §8, задача 109. Большие файлы (от 1 МиБ, документы и фото; файлы секретных чатов — никогда) патченные Android, Desktop, iOS и Web качают по HTTPS с Gcore CDN. Gcore тянет шифр из дома, ключи и хэши остаются дома. Старые сборки, официальные клиенты и сессии без признака `pluma_cdn` качают всё из дома, как раньше.

## Как устроено
- Клиент просит часть файла (`upload.getFile` с `cdn_supported`). Если у его ключа есть признак `pluma_cdn` и файл подготовлен, bff отвечает `upload.fileCdnRedirect`:
  - `dc_id` = 201 — номер выдачи, клиент к нему не подключается;
  - ключ и IV файла;
  - хэши частей по 128 КБ;
  - `file_token` = `PLH1` ‖ id ‖ срок ‖ подписанный URL `https://<префикс>.gcorecdn.com/o/<64 hex>?md5=…&expires=…`.
- Клиент качает диапазоны по этому URL, расшифровывает, сверяет хэши. При любой ошибке файл докачивается из дома.
- Gcore на промахе кэша тянет куски по 10 МБ у **источника** — слушателя в bff (порт 20480, только сеть Docker). Caddy публикует его на имени `PLUMA_CDN_ORIGIN_DOMAIN`. Источник шифрует на лету и отвечает только на запросы с верным заголовком `X-Pluma-Origin-Auth`; без него — 403.
- Подготовка файла — только хэши (одна подготовка за раз, чтение до 800 Мбит/с). Шифр не хранится нигде, кроме кэша точек Gcore.
- Раз в минуту bff проверяет выдачу:
  - 4 КБ канарейки `/c/v1` через Gcore — ждёт 206;
  - тот же URL с испорченной подписью — ждёт 403/410.
  - Не прошла — через ≤ 3 минуты редиректов нет (`cdn_deliveries.unhealthy_reason`).
- Выдача выходит из маршрута до конца месяца (UTC), когда её трафик за месяц (байты источника + оценка отдачи Gcore) достиг `CDN_GCORE_MONTHLY_GB`.

## Выдача 202 и маршрут по стране (задача 109)
- **Выдача 202** — nginx Pluma на российском узле amf (`https://r1.pluma.chat`, `docs/ops/ru-node.md`). Подпись — та же формула Secure Token, что у Gcore (`gcore-md5`), со своим ключом `CDN_RU_TOKEN_KEY`; nginx узла проверяет её модулем `secure_link`. Кэш — на узле, куски по 1 МиБ.
- **Маршрут по стране** — `CDN_ROUTES`, записи `<страны через запятую или *>:<выдачи по порядку>` через `;`, ровно одна запись `*`, страна — не больше чем в одной записи. Рекомендуемое значение: `RU,BY:202,201;*:201`.
  - Страну адреса клиента (`MD.ClientAddr`) называет `authsession.getIpCountry` по базе GeoIP дома, ответы кэшируются в bff (`pkg/ipcountry`, 10 000 адресов на час). Спрашивается только у клиента с `pluma_cdn`, которому может уйти редирект, и только если в маршруте есть записи со странами.
  - Неизвестная страна (нет базы, частный адрес, authsession не ответил — `pluma_ipcountry_errors_total`) — запись `*`.
  - Внутри записи — как раньше: первая здоровая выдача в бюджете, которую ключ не избегает; выбор держится за ключом 10 минут. Удержание помнит запись: клиент, сменивший страну (включил или выключил VPN), сразу получает выдачу своей новой записи.
  - Клиент из России при нездоровой 202 уходит на 201 (следующую в записи), при отказе обеих — качает из дома.
- **Источник различает выдачи по `X-Pluma-Origin-Auth`.** У каждой выдачи своё значение: у 201 — `CDN_ORIGIN_AUTH`, у 202 — `CDN_RU_ORIGIN_AUTH`. Источник сравнивает заголовок со всеми значениями за постоянное время и считает байты той выдаче, чьё значение пришло (бюджет `cdn_delivery_usage`, метрики по `dc`). Две выдачи `gcore-md5` с одним значением (например, пустой `CDN_RU_ORIGIN_AUTH` — тогда 202 взяла бы общий `CDN_ORIGIN_AUTH`) — bff не стартует: их байты не различить.
- **Проверка 202** — та же канарейка раз в минуту, но соединение идёт на `CDN_RU_HEALTH_ADDR` (`10.78.0.1:443`, nginx `stream` узла через туннель); SNI, `Host` и имя в сертификате — `r1.pluma.chat`, сертификат проверяется. Исходящий трафик дома идёт через Hetzner, а путь Hetzner → amf может быть закрыт так же, как обратный (не проверено). Так проверяются nginx узла, его кэш, подпись и туннель, но не доступность amf из российских сетей: её показывают откаты клиентов (`pluma_cdn_fallback_total{dc="202"}`, `CdnFallbackHigh`).
- **Бюджет 202** — `CDN_RU_MONTHLY_GB` [2000 в `docker-compose.yaml`]: предел от разгона, не тариф провайдера (тариф трафика Timeweb не проверен, проверка владельца 8 брифа 109). 80 % — `CdnBudget{dc="202"}`.

## Порядок включения
1. Сервер с пустыми `CDN_*`: редиректов нет, источник не слушает, метрик `pluma_cdn_*` нет.
2. DNS, аккаунт и ресурс Gcore, проверка 0, `.env`, деплой. В Grafana `pluma_cdn_delivery_healthy{dc="201"}` = 1.
3. Проверки 1–6.
4. Выпуск клиентов с патчем.

## Аккаунт и ресурс Gcore (делает владелец)
1. **Аккаунт.**
   - Регистрация на gcore.com на почту владельца, включить 2FA.
   - Карта для CDN не нужна; добавлять ли её — решение владельца (см. «Трафик и бюджет»).
   - Gcore может попросить пройти KYC (MSA §2.17).
2. **CDN → CDN resources → Create CDN resource.**
   - Домен — **Gcore domain**, префикс нейтральный, без слов Pluma: `<префикс>.gcorecdn.com`.
   - **Origin → URL / IP** = значение `PLUMA_CDN_ORIGIN_DOMAIN`.
   - **Advanced → Host header override** = то же имя.
   - Ресурс оживает примерно через 15 минут. Сразу после этого — **проверка 0**, до остальных настроек: свой домен ресурса после создания не меняется.
3. **Настройки ресурса (OPTIONS):**
   - **Origin pull protocol: HTTPS** (порт 443).
     - Проверку сертификата источника портал не настраивает: она есть только в API (`proxy_ssl_enabled` + CA + обязательный клиентский сертификат).
     - Это **не условие запуска** (ADR 0071 §3): заголовок закрывает источник от чужой нагрузки, а подмену шифра ловят хэши клиентов.
     - Если владелец решит включить:
       - CA — корень цепочки сертификата источника: `openssl s_client -connect <PLUMA_CDN_ORIGIN_DOMAIN>:443 -showcerts`;
       - клиентский сертификат — одноразовый самоподписанный;
       - API-токен Gcore создать на время настройки и удалить, дому его не давать.
   - **HTTP headers → Request headers:** `X-Pluma-Origin-Auth` = значение `openssl rand -hex 32`, сгенерированное дома. Оно же — `CDN_ORIGIN_AUTH` в `.env`.
   - **Access → Secure token:**
     - включить;
     - ключ — `openssl rand -hex 16` дома (32 символа), он же — `CDN_GCORE_TOKEN_KEY`;
     - «Add a client's IP to the token» — **не** отмечать (мобильные сети меняют адрес).
   - **Cache → Query string:** Ignore query string, режим **Ignore all**. Иначе каждый подписанный URL — отдельный объект кэша.
   - **Cache → CDN caching:** Origin controlled, Default cache expiry — 1 день. Источник сам шлёт `Cache-Control`.
   - **Cache → Always online:** выключить. Включённая опция отдаёт устаревший кэш в ответ на 403/404 источника.
   - **Content → Large files delivery optimization:** включить (куски по 10 МБ). Gzip, Brotli и Fetch compressed — выключены: с этой опцией они несовместимы, а шифр не сжимается.
   - **HTTP headers → Access-Control-Allow-Origin:** адрес веб-клиента Pluma (`https://<PLUMA_WEB_DOMAIN>`), отметить «Always add … regardless of response code».
   - **HTTP headers → Response headers (add):** `Access-Control-Expose-Headers: Content-Range, Content-Length`, тот же флажок. Без него веб-клиент не прочитает `Content-Range` и откатится домой.
   - **Enable Network Error Logging** — выключить. Иначе браузеры шлют Gcore отчёты о сетевых ошибках веб-клиента.
   - Logs uploader, Raw Logs, Origin Shielding — не включать.
   - Сохранить. Если «Large files delivery optimization» включили после первых запросов — **Purge all**.
4. В `.env` дома: `CDN_GCORE_BASE_URL=https://<префикс>.gcorecdn.com`, ключи из шага 3, деплой.

**Если Secure Token недоступен** на бесплатном плане или не проверяется для уже закэшированного объекта (проверка 2), подпись переходит на `path-hmac`: подпись в пути URL, её проверяет источник.
1. В портале выключить Secure Token.
2. В `.env`:
   - `CDN_GCORE_SIGNER=path-hmac`;
   - `CDN_GCORE_TOKEN_KEY` = `openssl rand -base64 32` (32 байта).
3. Деплой, затем повторить проверки 1–4а.

URL тогда `https://<префикс>.gcorecdn.com/t/<срок>/<подпись>/o/<64 hex>`. Все клиенты в одном окне `CDN_URL_TTL` получают один URL. Кэш между окнами не общий: каждые 6 ч каждый кусок тянется из дома заново.

## DNS
Зона `pluma.chat` в Cloudflare: A-запись `PLUMA_CDN_ORIGIN_DOMAIN` (например, `o1.pluma.chat` — имя не секрет, оно попадает в журналы Certificate Transparency) → 195.201.252.126, без проксирования. CAA уже разрешает выпуск домашнему аккаунту Let's Encrypt (`docs/ops/home-server.md`, «Сертификаты и CAA»). VPS ничего нового не нужно: 443 уже уходит домой DNAT.

## Переменные
В `.env` дома только имена, значения не пересылать и не логировать. Пустые значения берут умолчания в скобках; описание — `.env.example`.

| Переменная | Что |
|---|---|
| `CDN_GCORE_BASE_URL` | `https://<префикс>.gcorecdn.com`. Пустая — CDN выключен: нет редиректов, источник не слушает |
| `CDN_GCORE_TOKEN_KEY` | секрет. Ключ Secure Token (6–32 символа, `openssl rand -hex 16`); при `path-hmac` — 32 байта в base64 (`openssl rand -base64 32`) |
| `CDN_GCORE_SIGNER` | `gcore-md5` или `path-hmac` [`gcore-md5`] |
| `CDN_GCORE_MONTHLY_GB` | бюджет месяца выдачи, ГБ (10⁹ байт) [800] |
| `CDN_ORIGIN_AUTH` | секрет. Значение `X-Pluma-Origin-Auth`, 64 hex (`openssl rand -hex 32`); то же — в настройках ресурса |
| `PLUMA_CDN_ORIGIN_DOMAIN` | имя источника для Caddy. Пустое — Caddy его не обслуживает |
| `CDN_ROUTES` | маршрут по стране [`*:201`]; с выдачей 202 — `RU,BY:202,201;*:201` (раздел «Выдача 202 и маршрут по стране») |
| `CDN_RU_BASE_URL` | `https://r1.pluma.chat`. Пустая — выдача 202 выключена |
| `CDN_RU_TOKEN_KEY` | секрет. Ключ подписи выдачи 202, 6–32 символа (`openssl rand -hex 16`); то же значение — в `/etc/pluma-ru/env` узла |
| `CDN_RU_ORIGIN_AUTH` | секрет. `X-Pluma-Origin-Auth` выдачи 202, 64 hex (`openssl rand -hex 32`), **не равен** `CDN_ORIGIN_AUTH`; то же значение — в `/etc/pluma-ru/env` узла |
| `CDN_RU_HEALTH_ADDR` | куда идёт проверка 202: `10.78.0.1:443` [хост `CDN_RU_BASE_URL`] |
| `CDN_RU_MONTHLY_GB` | бюджет месяца выдачи 202, ГБ [2000] |
| `CDN_URL_TTL` | срок подписанного URL, не больше 24 ч [6h] |
| `CDN_KINDS` | `document`, `photo` [`document,photo`]; `encrypted` отвергается при старте |
| `CDN_ORIGIN_LISTEN`, `CDN_PREPARE_RATE_MBIT`, `CDN_MIN_FILE_SIZE`, `CDN_HEALTH_EVERY`, `CDN_AVOID_TTL` | оставить пустыми (умолчания: `0.0.0.0:20480`, 800, 1 МиБ, 1m, 1h) |
| `CDN_DEV_ALLOW_HTTP` | **никогда не задавать дома**. `1` разрешает `http://` только стенду e2e; на проде горит `CdnDevHttp` |

`CDN_NODE_CONTROL` и `PLUMA_DC1_ADDRESSES` задачи 102 не задавать: их больше нет.

При неверном значении bff не стартует и называет переменную, без значения:
- `BaseURL` не `https://`;
- ключ не той длины;
- `CDN_ORIGIN_AUTH` или `CDN_RU_ORIGIN_AUTH` не 64 hex; две выдачи `gcore-md5` с одним значением источника;
- `CDN_RU_HEALTH_ADDR` не `хост:порт`;
- маршрут без записи `*`, со страной в двух записях или с выключенной выдачей;
- `encrypted` в `CDN_KINDS`.

  - Обычный `pluma-deploy.sh` (`up -d`) пересоздаёт оба, когда их окружение изменилось.
- **Исходящий адрес дома** (через него идут проверки здоровья): `docker run --rm --network pluma_teamgram_net alpine wget -qO- https://ifconfig.me` → 195.201.252.126.
- **Выдача 202** (после туннеля и узла, `docs/ops/ru-node.md`, порядок первого включения): в `.env` — `CDN_RU_BASE_URL`, `CDN_RU_TOKEN_KEY`, `CDN_RU_ORIGIN_AUTH`, `CDN_RU_HEALTH_ADDR=10.78.0.1:443`, при желании `CDN_RU_MONTHLY_GB`, и `CDN_ROUTES=RU,BY:202,201;*:201`; деплой. Те же `CDN_RU_TOKEN_KEY` и `CDN_RU_ORIGIN_AUTH` — в `/etc/pluma-ru/env` узла (создать `openssl rand` на одной машине, перенести по SSH без печати). В логе bff — `cdn: delivery 202 (r1.pluma.chat) is healthy`, в Grafana — `pluma_cdn_delivery_healthy{dc="202"}` = 1.
- **После деплоя:**
  - в логе bff — `cdn: delivery 201 (<префикс>.gcorecdn.com) is healthy`;
  - в Grafana — `pluma_cdn_delivery_healthy{dc="201"}` = 1;
  - `pluma_cdn_dev_http{dc="201"}` = 0.

## Проверки владельца
Подписанный URL канарейки на час печатает команда в контейнере bff:

```bash
docker compose exec bff ./pluma-admin -f ../etc2/bff.yaml cdn canary-url 201
docker compose exec bff ./pluma-admin -f ../etc2/bff.yaml cdn canary-url -expired 201   # URL с уже прошедшим сроком
```

Команда печатает URL и строку `curl`, которая берёт тот же диапазон, что проверка bff (ждать `206 4096`). URL работает час: в заметки его не сохранять. Результаты записывать в бриф 107.

0. **HTTPS на домене ресурса** — сразу после создания ресурса, до остального.
   - С компьютера: `curl -sS -o /dev/null -w '%{http_code} %{ssl_verify_result}\n' https://<префикс>.gcorecdn.com/`. Нужно `ssl_verify_result` = 0; код ответа любой.
   - Тот же адрес открыть в браузере телефона: сертификат принят без исключений.
   - Не принят:
     - удалить ресурс;
     - создать новый на своём нейтральном домене (не `pluma.chat`) с «Get free Let's Encrypt certificate» и CNAME на Gcore;
     - `CDN_GCORE_BASE_URL` — этот домен.
1. **206 на произвольный диапазон** (жёсткое требование: документация Gcore код не называет). По URL канарейки — `curl -sS -D - -o /dev/null -r <диапазон> '<URL>'`:

   | Диапазон | Ждать `Content-Range` | Длина |
   |---|---|---|
   | `131072-135167` | `bytes 131072-135167/262144` | 4096 |
   | `200000-` | `bytes 200000-262143/262144` | 62144 |
   | `0-0` | `bytes 0-0/262144` | 1 |

   - Код везде 206, `Content-Length` = длина.
   - Повторить на настоящем файле ≥ 25 МБ: URL из инструментов разработчика веб-клиента (проверка 6), диапазон через границу куска 10 МБ, например `-r 10485000-10486999`. `Content-Range` точно такой же, после `/` — размер файла.
   - Не 206 или другой диапазон — CDN не включать и сообщить: запасной дизайн — Cloudflare (ADR 0071, «Последствия»).
2. **Secure Token работает** (для `gcore-md5`):
   - URL без `?md5=…&expires=…` → 403;
   - URL с испорченным `md5` → 403 или 410. Менять **первый** символ значения `md5`: последний несёт только 2 бита из 6, его замена может не изменить подпись;
   - URL из `canary-url -expired` → 403 или 410;
   - **для объекта, уже закэшированного**:
     - валидный URL дважды — второй ответ HIT в Log viewer (колонка статуса кэша);
     - затем тот же путь с испорченным `md5` → 403/410.
   - Опции нет, или закэшированный объект отдаётся без верного токена (тогда и проверка bff даст `token_off`) → перейти на `path-hmac` (раздел выше) и повторить проверку 1.
3. **Кэш общий для разных URL** (`gcore-md5`):
   - `canary-url` дважды с разницей больше секунды даёт два разных URL одного объекта;
   - запросить оба — второй HIT в Log viewer;
   - `pluma_cdn_origin_bytes_total` от второго не растёт.
4. **Источник закрыт.** Оба запроса → 403, одинаково:
   - `curl -sS -o /dev/null -w '%{http_code}\n' https://<PLUMA_CDN_ORIGIN_DOMAIN>/c/v1`;
   - то же для `…/o/$(openssl rand -hex 32)`.

   4а. **Устаревший кэш не отдаётся:**
   - в настройках ресурса Always online выключен;
   - при `path-hmac` URL из `canary-url -expired` → 403/410, а не 200/206.
5. **Сети.** С телефонов и компьютеров в Европе и через VPN из России — строка `curl` из `canary-url` (на телефоне — открыть URL в браузере: скачается файл 256 КБ). Записать сеть, город, результат. Без VPN из России — для сведения, не условие.
6. **Веб-клиент.** Файл ≥ 1 МБ качается через CDN. В инструментах разработчика:
   - запросы к `*.gcorecdn.com` со статусом 206;
   - без ошибок CORS;
   - без предварительного `OPTIONS`, либо `OPTIONS` успешен.

   CSP веб-клиента Pluma (`connect-src`) должна разрешать `https://<префикс>.gcorecdn.com`.

## Неполадки
Выдача выпала из маршрута (`CdnDeliveryUnhealthy`):
- причина — `select dc_id, unhealthy_reason, from_unixtime(healthy_until/1000) from cdn_deliveries;`;
- в логе bff — `cdn: delivery 201 (<хост>) is out: <причина>`.

| Причина | Что значит | Что делать |
|---|---|---|
| `status` | канарейка не 206, или испорченная подпись не 403/410 | `canary-url` и `curl -D -` вручную. 403 на валидный URL от Gcore — ключ Secure Token в портале и `CDN_GCORE_TOKEN_KEY` разные. 403 от источника (в Log viewer — промах кэша с 403) — `X-Pluma-Origin-Auth` в портале и `CDN_ORIGIN_AUTH` разные. 5xx — источник: `docker compose logs --tail 100 bff \| grep 'cdn origin'`, Caddy (`web`), DNS имени источника |
| `range` | другой `Content-Range` | опция «Large files delivery optimization», Purge all; проверка 1 |
| `bytes` | другие байты или длина | включено сжатие (Gzip, Brotli, Fetch compressed) — выключить, Purge all |
| `timeout`, `network`, `tls` | Gcore не ответил за 10 с, не соединился или его сертификат не принят | исходящая сеть дома (туннель, `wg show pluma`), статус Gcore; `tls` — сертификат ресурса (проверка 0). У 202 — туннель узла (`wg show plumaru`, `ping 10.78.0.1`), nginx `stream` владельца на `10.78.0.1:443` (`owner-nginx.sh check`), сертификат `r1` на узле (`certbot` узла) |
| `token_off` | испорченная подпись отдана: URL перестали истекать | Secure Token выключили в портале — включить; если включён, а закэшированный объект отдаётся без токена — перейти на `path-hmac` |
| `store` | bff не подписал URL | лог bff |

- **После починки:**
  - через ≤ 3 минуты проверка снова проходит, редиректы возвращаются сами;
  - ключи клиентов, откатившихся от выдачи, избегают её ещё до часа (`CDN_AVOID_TTL`).
- **`CdnFallbackHigh`:**
  - канарейка проходит, а клиенты откатываются;
  - проверить настоящий файл (проверка 1, вторая часть) и коды в Log viewer;
  - 404 — файл удалён или перестал попадать под политику; если их много — сообщить;
  - `Content-Range` другой — как `range` выше.
- **`CdnPrepareFailing`:**
  - причины — `sum by (result) (increase(pluma_cdn_prepare_total[1h]))` и `select last_error, count(*) from cdn_replicas where state = 4 group by last_error;`;
  - `read_error`, `short_read` — dfs или Garage (`docker compose logs --tail 100 dfs`);
  - `store_error` — MySQL;
  - такие файлы идут из дома, ничего не теряется.
- **`CdnOriginBusy`:**
  - больше 1 % запросов Gcore к источнику получили 503 (заняты все `Origin.MaxConcurrent` = 16);
  - обычно это канал дома или медленный dfs: `pluma_cdn_origin_inflight`, отдача туннеля в node-exporter;
  - поднимать предел только вместе с каналом.
- **Обрывы ответов источника** — `pluma_cdn_origin_requests_total{code="aborted"}`: чтение dfs сломалось посреди ответа. Gcore такой кусок не кэширует. Причина — в логе bff (`cdn origin: connection cut mid-answer`).

## Трафик и бюджет
- В бесплатный 1 ТБ месяца Gcore входят и отдача клиентам, и тяга с источника.
- Дом считает:
  - `origin` — точно, по источнику;
  - `edge_est` — оценку отдачи: размер файла на первый редирект пары «ключ, файл» за сутки.
  - Метрика — `pluma_cdn_usage_bytes{dc,kind}`, в MySQL — `cdn_delivery_usage`.
- Месяц — UTC. Часовой пояс сброса у Gcore не проверен; запас 200 ГБ это покрывает.
- **80 %** — `CdnBudget`.
- **100 %** — выдача вне маршрута до 1-го числа, всё качается из дома, `pluma_cdn_redirects_total{result="budget"}`.
- Раз в месяц сверить с порталом Gcore (Statistics): трафик ≈ origin + edge_est. Если портал заметно больше — оценка занижена, снизить `CDN_GCORE_MONTHLY_GB`.
- Без карты Gcore сверх 1 ТБ, вероятно, останавливает отдачу (вывод из совета на странице бесплатного плана, не проверено). С картой — €0,01/ГБ сверх 1 ТБ; тогда `CDN_GCORE_MONTHLY_GB` можно поднять.

## Смена ключей
- **Ключ Secure Token:**
  - новый `openssl rand -hex 16` — в портал и в `.env` (`CDN_GCORE_TOKEN_KEY`), сразу деплой;
  - пока они расходятся, Gcore отвечает 403: клиенты обновляют URL, затем докачивают из дома; проверка выводит выдачу (`status`);
  - старые URL перестают работать сразу.
- **`CDN_ORIGIN_AUTH`:**
  - новое значение `openssl rand -hex 32` — в портал (Request headers) и в `.env`, сразу деплой;
  - около минуты источник отвечает 403 на промахи кэша, клиенты на них откатываются домой.
- **Ключи выдачи 202** (`CDN_RU_TOKEN_KEY`, `CDN_RU_ORIGIN_AUTH`): новое значение — в `.env` дома и в `/etc/pluma-ru/env` узла, деплой дома и `deploy.sh` узла (`docs/ops/ru-node.md`). Пока они расходятся, проверка выводит 202 (`status`), клиенты из России идут на 201 или домой.
- После утечки любого из двух — сменить сразу. Утёкший ключ подписи открывает только шифр; ключ к шифру — только дома.

## Выключение и откат
- **Выключить выдачу 202:** убрать `CDN_RU_BASE_URL` и вернуть `CDN_ROUTES=*:201` (или пустой) в `.env`, деплой. Запись маршрута с выключенной выдачей bff не примет: менять обе переменные вместе.
- **Выключить CDN:**
  - убрать `CDN_GCORE_BASE_URL` из `.env`, деплой;
  - редиректов нет сразу, источник перестаёт слушать;
  - клиенты с открытыми загрузками получают ошибку от Gcore и докачивают из дома.
- **Убрать имя источника:**
  - удалить `PLUMA_CDN_ORIGIN_DOMAIN` из `.env` и пересоздать `web`;
  - удалить A-запись.
- **Кэш Gcore** очищается сам: объект, который 36 ч никто не запрашивал, удаляется. Сразу — Purge all в портале или удаление ресурса.
- **Откат сервера на версию без задачи 107:** новые таблицы ей не мешают. Код задачи 102 с пустым `CDN_NODE_CONTROL` таблиц CDN не касается.

## Что видит Gcore
`docs/ops/security-setup.md`, раздел 9 «CDN больших файлов: что видит Gcore» (ADR 0071 §11).

## Не проверено
Списком — бриф 107, «Не проверено». Для эксплуатации важнее всего:
- 206 с точным `Content-Range` (проверка 1);
- сертификат `*.gcorecdn.com` (проверка 0);
- Secure Token на бесплатном плане и для закэшированного объекта (проверка 2);
- значение Always online по умолчанию;
- часовой пояс сброса месяца;
- поведение без карты сверх 1 ТБ;
- текст AUP и KYC.
