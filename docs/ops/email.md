# Почта восстановления облачного пароля

Задача 091, ADR 0058. Сервер шлёт письма с кодами двух видов: подтвердить адрес, заданный как почта восстановления облачного пароля, и восстановить забытый пароль. Других писем нет. Письма уходят через Resend (`pkg/mail`), поставщика можно заменить, не меняя остального кода.

Без ключа (`MAIL_API_KEY` пуст) почта выключена: `account.getPassword` отдаёт `has_recovery = false`, задать почту нельзя (`EMAIL_INVALID`), «Забыли пароль?» ведёт к сбросу через 7 дней, кто не вошёл нигде — к `pluma-admin password reset` (`docs/ops/security-setup.md`, раздел 7).

## Что нужно один раз

1. Аккаунт на resend.com (бесплатный план: 100 писем в сутки, 3000 в месяц). Данные о письмах и сами письма Resend хранит в США 30 дней, в том числе код из тела письма; поэтому код у нас живёт 30 минут и годится один раз. Владелец это принял (ADR 0058, «Решения владельца»).
2. Domains → Add Domain → `pluma.chat`, регион `eu-west-1`.
3. В Cloudflare добавить записи ровно из вкладки Records домена в Resend (значения брать оттуда), режим «DNS only», без прокси:
   - MX `send` → `feedback-smtp.eu-west-1.amazonses.com`, приоритет 10;
   - TXT `send` → `v=spf1 include:amazonses.com ~all`;
   - TXT `resend._domainkey` → ключ DKIM из панели;
   - TXT `_dmarc` → `v=DMARC1; p=none;` (желательно; позже `p=quarantine`, затем `p=reject`, когда письма идут с `dmarc=pass`).
   Корневые записи `pluma.chat` (сайт) не трогать.
4. Дождаться «Verified» у домена.
5. В настройках домена выключить отслеживание открытий и кликов: ссылок и картинок в письмах нет, отслеживание только добавит чужие ссылки.
6. API Keys → Create: имя `pluma-server`, Permission `Sending access`, Domain `pluma.chat`. Ключ показывается один раз — сразу в `.env` на сервере, больше никуда (ни в чат, ни в репозиторий, ни в заметки).

## Настройка сервера

В `.env`:

```
MAIL_API_KEY=re_…
MAIL_FROM=Pluma <noreply@pluma.chat>
```

Затем `docker compose up -d bff` (bff перечитывает `.env` при пересоздании контейнера). Ключ без `MAIL_FROM` или с неверным адресом — bff не стартует и пишет `MAIL_FROM is not a valid address` (сам ключ в лог не попадает).

Раздел `Mail` в `teamgramd/etc2/bff.yaml` (и `teamgramd/etc/bff.yaml` без Docker):

| Поле | Что это |
|---|---|
| `Provider` | `resend` (единственный) |
| `ApiKey` | `${MAIL_API_KEY}` |
| `From` | `${MAIL_FROM}` |
| `ReplyTo` | адрес для ответов; по решению владельца не задаётся |
| `Endpoint` | другой адрес API (тестовый стенд: `test/e2e/fakemail`) |
| `DailyLimit` | писем на весь сервер за сутки UTC, по умолчанию 80 — ниже 100 бесплатного плана |

Миграция `teamgramd/deploy/sql/migrate-20261116-password-email.sql` (колонки `email`, `email_unconfirmed`, `email_set_at` в `user_passwords`) применяется сервисом `migrate` сама, повторный запуск безопасен. Адрес хранится открыто: его надо отправлять; кода в MySQL нет никогда.

## Проверка после включения

1. В любом клиенте: Настройки → Конфиденциальность → Облачный пароль → задать пароль с почтой. Должно прийти письмо «Pluma: …» на языке приложения, код из него подтверждает почту.
2. Заголовки письма у получателя: `dkim=pass`, `spf=pass`, `dmarc=pass` (Gmail: «Показать оригинал»). Письмо не в спаме.
3. В логе bff строка `twofa: user N: the setup email … was sent as <id>`; в Resend → Emails то же письмо.
4. Дальше — строки задачи 091 в `docs/project/TESTING-BACKLOG.md`.

## Как это работает

- Код — 6 цифр, живёт 30 минут, в Redis лежит только HMAC-SHA256 под `LOGIN_CODE_HMAC_KEY` (`twofa_email_code_<назначение>_<user_id>`). Пять неверных вводов сжигают код. Код восстановления привязан к паролю: после смены пароля старый код не подходит.
- Пределы: письмо одному человеку не чаще раза в 60 с, 5 в час, 10 в сутки (отдельно для подтверждения и для восстановления); 10 писем в час на одно устройство; `DailyLimit` на весь сервер. Ввод кодов: 10 в час и 30 в сутки на человека, 10 в час на устройство. Сверх — «подождите» (`FLOOD_WAIT_X`).
- Письмо, которое Resend не принял, повторяется до трёх раз (паузы 0,5 и 1,5 с) только при временной ошибке, с тем же ключом идемпотентности — второго письма не будет. Не принятое письмо возвращает только минутный предел человека; часовой, суточный и суточный предел сервера оно тратит, чтобы повторы при сбое поставщика не исчерпали письма всем. Пользователь видит «подождите минуту», а при задании почты настройки всё равно сохраняются, и «Отправить снова» повторит письмо. Первый облачный пароль с почтой включается только после ввода кода из письма.
- После восстановления другие сессии не завершаются; все устройства получают сообщение от служебного аккаунта 777000 о сбросе пароля с устройством и местом.
- В логах нет ни кодов, ни адресов, ни ключа (`tools/logaudit` не даёт их вывести).

## Метрики и алерты

`password_email_send_total{purpose, result}` (`ok`, `retryable`, `permanent`, `limited`) и `password_email_code_total{purpose, result}` (`ok`, `invalid`, `expired`, `limited`); алерты — группа `password_email` в `teamgramd/deploy/prometheus/server/rules/codes.yml`, описание — `docs/ops/monitoring.md`.

| Алерт | Что делать |
|---|---|
| `PasswordEmailSenderFailing` | Resend недоступен или ограничивает скорость. Строки `was not sent (retryable, <код>)` в логе bff; страница состояния Resend. Обычно проходит само |
| `PasswordEmailSenderRejected` | Код в строке `was not sent (permanent, <код>)`: `invalid_api_key`, `missing_api_key` — ключ отозван или не задан, выпустить новый (ниже); `validation_error` про домен — проверить «Verified» и записи DNS; `monthly_quota_exceeded` — кончилась квота месяца, ждать следующего или сменить план (решение владельца) |
| `PasswordEmailBruteForce` | Строка `possible brute force` в логе bff называет пользователя. Код сгорает после пяти ошибок, а пределы ввода держат перебор; если атака продолжается, предупредить владельца аккаунта |

## Ротация ключа

1. В Resend создать новый ключ (`Sending access`, домен `pluma.chat`).
2. Заменить `MAIL_API_KEY` в `.env`, `docker compose up -d bff`.
3. Проверить: «Отправить снова» в настройках пароля приходит; в логе нет `permanent`.
4. Удалить старый ключ в Resend.

При утечке ключа — сразу удалить его в Resend (письма перестанут уходить до шага 2): с ключом только на отправку с одного домена злоумышленник может лишь слать письма от `pluma.chat`.

## Без Resend

Почта выключается пустым `MAIL_API_KEY` и перезапуском bff; уже заданные адреса остаются в базе, но `has_recovery` ложно, пока почта выключена. Другой поставщик — новая реализация `mail.Sender` в `pkg/mail` и значение `Mail.Provider`.
