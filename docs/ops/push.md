# Push-уведомления

Сервис `push` отправляет уведомления в APNs (iOS) и FCM (Android). Устройство их получает, когда приложение закрыто или в фоне (задача 009, ADR 0017).

- Он читает тот же поток апдейтов, что и `sync` (`Sync-T`), своей группой `Push-MainCommunity-S`.
- Ключи провайдеров смонтированы только в его контейнер.
- Содержимое push зашифровано ключом устройства. Apple и Google видят только заглушку «Новое сообщение».

## Первый запуск

1. **Ключи в `.env`** (`.env.example`):
   - `PUSH_SECRET_ENCRYPTION_KEY` — `openssl rand -hex 32`. Им bff и push хранят ключи устройств, отдельно от `AUTH_KEY_ENCRYPTION_KEY`. Без него bff и push не стартуют.
   - `APNS_KEY_ID`, `APNS_TEAM_ID` — Key ID ключа APNs и Team ID аккаунта Apple.
   - `APNS_KEY_FILE` — путь к `.p8` на хосте.
   - `FCM_CREDENTIALS_FILE` — путь к JSON-ключу сервисного аккаунта FCM на хосте.
   - Файлы ключей — с правами 600, вне git. Пустой файл выключает провайдера.
2. **Откуда ключи.**
   - **APNs.** developer.apple.com/account → Keys → ключ с Apple Push Notifications service, окружение Sandbox & Production. Один ключ годится и для обычных, и для VoIP push. Bundle ID приложения `chat.pluma.app` — с Push Notifications.
   - **FCM.** Отдельный сервисный аккаунт проекта Firebase с ролью Firebase Cloud Messaging API Admin (не ключ Admin SDK: тот открывает весь проект). В проекте должен быть включён Firebase Cloud Messaging API (V1).
3. **Проверка ключей** (ничего не доставляет):
   ```bash
   docker compose exec push ./pluma-admin -f ../etc2/push.yaml push check
   ```
   - Хороший ответ — «the key works (the test token was refused, as expected)» для APNs production, APNs sandbox и FCM.
   - «the key is refused» — ключ отозван, не тот Key ID или Team ID, у сервисного аккаунта нет роли.

## Клиенты

- **Android.** В сборку `pluma-android` подставляется `google-services.json` того же проекта Firebase, что и ключ сервера. Он хранится в секрете GitHub Actions. С файлом другого проекта FCM отвечает `SENDER_ID_MISMATCH`, и устройство забывается.
- **iOS.** Нужны bundle ID с Push Notifications и App Group для Notification Service Extension: оно расшифровывает push. Это делается вместе со сборкой iOS (задача 006).
- **Web K** регистрирует Web push (тип 10). Такие устройства хранятся, но push им не отправляется: Web push появится вместе с раздачей Web K по TLS.
- **VoIP-токены iOS** хранятся. VoIP push будет только для входящих звонков, когда появятся звонки (ADR 0004).

## Кому и что приходит

- **Кому.**
  - Push получают устройства получателя.
  - Не получает авторизация, которая сама сделала действие (например, прочитала историю).
  - Не получают авторизации с живой сессией: им апдейт приходит по соединению. Сессия считается живой ещё до 60 с после обрыва связи.
- **Что.**
  - Новые сообщения всех видов, альбомы и пересылки.
  - События групп: создание, добавление, удаление, выход, название, фото.
  - Закрепления.
  - `READ_HISTORY` — прочитано на другом устройстве.
  - `SESSION_REVOKE` — сеанс завершён с другого устройства; устройства этого сеанса забываются.
- **Настройки получателя.**
  - Чат в mute: видимого push нет. Android раз в 15 с получает служебный `MESSAGE_MUTED`, если не отказался от него (iOS отказывается всегда). Упоминание проходит и в mute.
  - Выключенный предпросмотр — push без текста.
  - Беззвучный чат или беззвучное сообщение — без звука.
  - iOS с код-паролем (`account.updateDeviceLocked`) после периода неактивности получает только «Новое сообщение».
- **Ещё не отправляются:** правки, реакции, удаления (`MESSAGE_DELETED`), каналы, отложенные сообщения.
- **Если push не дошёл,** его не повторяют. Устройство догоняет пропущенное через `updates.getDifference`, когда приложение откроется.
- **Недействительный токен.**
  - FCM: устройство удаляется.
  - APNs: устройство помечается, и на следующую регистрацию того же токена iOS получает `TOKEN_WAS_INVALIDATED` и берёт новый.

## Метрики и алерты

- **`push_sent_total{provider, result}`** — отправки в `apns` и `fcm` по результатам:
  - `sent`;
  - `token_invalid`;
  - `auth_failed` — провайдер не принимает ключ;
  - `rejected` — провайдер отверг запрос, ошибка у нас;
  - `unavailable` — провайдер не ответил после трёх попыток или 30 с пропускается после пяти отказов подряд;
  - `disabled` — нет ключа.
- **`push_dropped_total{reason}`** — кому push не ушёл и почему: `initiator`, `online`, `unbound` (авторизации больше нет), `muted`, `error`.
- **Алерты** (`teamgramd/deploy/prometheus/server/rules/push.yml`):
  - `PushServiceDown` — сервис лежит. Уведомлений нет, сообщения доходят при открытии приложения.
  - `PushProviderAuthFailed` — Apple или Google не принимают ключ. Запустить `push check`, при необходимости выпустить новый ключ.
  - `PushProviderDisabled` — устройства платформы есть, а ключа нет.
  - `PushErrors` — больше 20% отправок не проходит 15 минут: сбой у провайдера или ошибка в запросах (`rejected` в логах push).

## Смена ключей

- **APNs.**
  1. Создать новый ключ в Apple Developer.
  2. Заменить файл и `APNS_KEY_ID`, затем `docker compose up -d push`.
  3. Проверить `push check`, затем отозвать старый ключ. Устройства перерегистрировать не нужно.
- **FCM.**
  1. Создать новый JSON-ключ сервисного аккаунта.
  2. Заменить файл, затем `docker compose up -d push`.
  3. Проверить `push check`, затем удалить старый ключ в Google Cloud Console.
- **`PUSH_SECRET_ENCRYPTION_KEY`.** С новым ключом сохранённые устройства не открываются: push не уходят, пока клиенты не зарегистрируются заново. Android перерегистрируется раз в 3 часа, iOS — при запуске. Менять ключ только при утечке.
  - Строки, которые не открываются, сервис пропускает с ошибкой в логе и не удаляет. Новая регистрация клиента заменяет их, а ошибочно заданный ключ ничего не стирает: верните прежний, и всё заработает.
