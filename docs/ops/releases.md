# Выпуски клиентов на сайте (`/dl/`)

Сервис `releases` (задача 054, ADR 0035) принимает от CI подписанные сборки клиентов, раздаёт их на сайте по адресам `/dl/…` и даёт `help.getAppUpdate` знать о текущем выпуске каждой платформы. Отдельной DNS-записи не нужно: адреса живут на именах сайта (`PLUMA_SITE_DOMAINS`), Caddy передаёт `/dl/*` в контейнер `releases:9097`.

## Как устроено
- **Адреса:**
  - `POST /dl/upload` — CI выкладывает выпуск (`Authorization: Bearer <токен загрузки>`, `multipart/form-data`);
  - `GET /dl/releases.json` — текущие выпуски всех платформ для сайта (версия, сборка, дата, заметки, ссылки, размеры, SHA-256);
  - `GET /dl/<платформа>/latest[/<арх>]` — переход (302, без кэша) на установщик текущего выпуска;
  - `GET /dl/<платформа>/<версия>/<файл>` — сам файл, неизменяемый (`Cache-Control: immutable`);
  - `GET /dl/desktop/current4` — для апдейтера Desktop: по ключу системы (`mac`, `armac`, `win`, `win64`, `winarm`, `linux`) версия и путь пакета текущего выпуска; апдейтер дописывает путь к префиксу `<сайт>/dl/desktop` и качает `GET /dl/desktop/<платформа>/<версия>/<пакет>`;
  - `GET /dl/health` — проверка (`204`).
- **Платформы:** `android`, `ios`, `macos`, `windows`, `linux`.
- **Форма загрузки:**
  - поля `platform`, `version`, `build`, `notes_en`, `notes_ru`, `can_not_skip` (по желанию: `1` — обязательный выпуск, только `android` и `ios`; `0` или нет поля — необязательный; другое значение и `1` у Desktop — `400`, раздел «Обязательный выпуск»);
  - файлы — части `installer[.<арх>]` и `update[.<арх>]`.
- **Требования к версиям и файлам:**
  - Android: версия `12.9.1.NNNNN` (4 части, только цифры — так клиент сравнивает версии; номер сборки — 5 цифр с нулями, чтобы строковое сравнение клиента совпадало с числовым) и ровно один установщик `.apk`;
  - iOS: версия `12.9.2` (версия Telegram, одна у всех сборок с этого апстрима), файлов нет (IPA раздаёт `iosinstall`, запись нужна для `help.getAppUpdate`); приложению версия показывается с номером сборки, `12.9.2 (36)`;
  - Desktop: версия `7.0.9.NNNNN` (версия tdesktop и номер сборки), установщик обязателен; пакеты обновления называются так, как их называет Packer (`tmacupd<сборка>`, `tarmacupd…`, `tx64upd…`, `tarm64upd…`, `tupdate…`, `tlinuxupd…`), с номером сборки выпуска: его и сравнивает апдейтер Pluma (`PlumaBuild`), `AppVersion` приложения остаётся версией tdesktop. Пакет `tmacupd` универсальной сборки macOS служит и Intel, и Apple Silicon, если в выпуске нет отдельного `tarmacupd`.
- **Хранение.**
  - Файлы — в томе `releases_data`, каталог `files/<платформа>/<версия>`. Каталог выпуска не перезаписывается: повтор сборки с той же версией и теми же файлами — `409` (CI принимает его за повтор при перезапуске задачи; флаг обязательности остаётся прежним, кроме случая ниже); тот же номер с другой версией или другими файлами и версия другой сборки у выпуска с файлами — `422` (CI падает). iOS-выпуск файлов не имеет и может повторять версию: его сборки различает номер (ADR 0037). Выпуски публикуются по одному; каталог версии без строки в таблице (загрузку прервали между ними) удаляется следующей загрузкой этой версии, недокачанные части в `work/` — при запуске сервиса.
  - Записи — в таблице `app_releases` (миграция `migrate-20261105-app-releases.sql`). Текущий выпуск платформы — последняя по номеру сборки запись, не отозванная.
  - APK Android дополнительно кладётся в DFS документом: `help.getAppUpdate` отдаёт его клиенту, и тот качает его по MTProto.
- **Что видят приложения** (`help.getAppUpdate`, платформа по `api_id` авторизации):
  - Android — `help.appUpdate` с документом APK, если клиент по своему правилу сравнения считает версию новее;
  - iOS — `help.appUpdate` со ссылкой, только сборкам, поставленным с сайта (`app_version` оканчивается на ` adhoc`) и с меньшим номером сборки; сборки TestFlight обновляет TestFlight. Ссылка — `itms-services://…` с билетом обновления, если задан `PLUMA_IOS_UPDATE_SECRET` и `iosinstall` уже переподписал текущий выпуск: установка идёт прямо из приложения (`ios-install.md`, «Обновление из приложения»). Иначе — `<сайт>/iphone/install`;
  - Desktop — обновляется своим апдейтером, `help.getConfig` даёт ему `autoupdate_url_prefix = <сайт>/dl/desktop`;
  - Web — `help.noAppUpdate`, он обновляется с сервера.
- **Ошибки.** Если таблица или документ недоступны, `help.getAppUpdate` отвечает `help.noAppUpdate` и пишет ошибку в лог, а не 500.

## Панель
Раздел «Выпуски» панели (`docs/ops/admin-panel.md`) показывает сборки всех платформ и делает то же, что `pluma-admin release withdraw|restore`: **откатить** текущую сборку и **вернуть** отозванную. Сервис отдаёт это на маршрутах `/internal/releases` (не под `/dl/`, Caddy их не проксирует), порт `127.0.0.1:9097` опубликован на хосте только для панели.
- Токен: `RELEASES_ADMIN_TOKEN` в `.env` (не менее 32 символов, `openssl rand -hex 32`), его видят сервис `releases` и панель. Пустой — маршруты отвечают 503, раздел показывает, что не настроен.
- Новая сборка появляется только из CI (`POST /dl/upload`), из панели не загружается.

## Первое включение
1. **Токен загрузки** — со своей машины, ничего не печатается:
   ```bash
   teamgramd/deploy/releases/put-token.sh neo_old
   ```
   Скрипт создаёт `/opt/pluma/releases/upload-token` (режим 0400), если его нет, и записывает его секретом `RELEASES_UPLOAD_TOKEN` окружения `release` в pluma-android, pluma-ios и pluma-desktop (нужен `gh` с правом на эти репозитории).
2. **`.env` сервера:** `PLUMA_RELEASES_URL=https://pluma.chat` — адрес сайта без `/` на конце. Без неё `bff` не предлагает обновлений и не даёт префикс Desktop, а `releases` не запускается.
3. **Запуск** — в команду сервисов добавляется `-f docker-compose.releases.yaml`:
   ```bash
   docker compose -f docker-compose.yaml -f docker-compose.public-ip.yaml -f docker-compose.web.yaml -f docker-compose.releases.yaml up -d --no-build releases
   ```
   Затем `bff` пересоздаётся с новой переменной (`up -d --no-build bff`). Если в выкатке изменился Caddyfile (маршрут `/dl/*`), контейнер `web` пересоздаётся (`--force-recreate --no-deps web`), как описано в `ios-install.md`.

## Проверка
- `curl -so /dev/null -w '%{http_code}\n' https://pluma.chat/dl/health` — `204`.
- `curl -s https://pluma.chat/dl/releases.json` — `{"platforms":{…}}`; пока выпусков нет — `{"platforms":{}}`.
- После первой загрузки из CI: `curl -sI https://pluma.chat/dl/android/latest` — `302` на `/dl/android/<версия>/Pluma-<версия>.apk`.

## Отзыв и возврат выпуска
Плохой выпуск отзывается — текущим снова становится предыдущий, сайт и приложения сразу видят его:
```bash
S="docker compose -f docker-compose.yaml -f docker-compose.public-ip.yaml"
$S exec bff ./pluma-admin -f ../etc2/bff.yaml release list android
$S exec bff ./pluma-admin -f ../etc2/bff.yaml release withdraw android <сборка>
$S exec bff ./pluma-admin -f ../etc2/bff.yaml release restore android <сборка>
```
Файлы отозванного выпуска остаются на месте: уже выданные ссылки на конкретную версию продолжают работать. Отзыв не догоняет то, что уже раздано:
- Android, успевший **получить предложение**, продолжает его показывать (клиент хранит его и не реагирует на `help.noAppUpdate`), пока пользователь не закроет его или не поставит другую сборку; успевший **поставить** — обратно не откатывается (у старой версии меньше `versionCode`). Исправление — следующая сборка с большим номером: её предложение заменяет прежнее.
- iPhone: после отзыва приложение экран обновления больше не получает (уже открытый ответ `help.noAppUpdate` не закрывает, `ApplicationContext.swift:589-599` в `release-13.2`; он уходит кнопкой «Пропустить» или перезапуском), и билеты обновления из приложения, выданные на отозванную сборку, перестают приниматься в течение 30 секунд (`iosinstall` сверяет сборку с текущим выпуском; если сервис `releases` в это время не отвечает — до пяти минут). Но страница установки (`iosinstall`) продолжает раздавать последний переданный ей IPA, и приложениям старше предыдущей сборки предлагается эта страница. Вернуть хороший — запуском workflow pluma-ios с `ipa` на последнем хорошем коммите или следующей сборкой.
- Desktop: апдейтер, уже скачавший пакет, поставит его при перезапуске; исправление — следующая сборка.

## Когда приложения узнают о выпуске
Решение владельца 2026-11-13: новый выпуск доходит до приложений примерно за час (задача 095). Как часто спрашивает каждый клиент (исходники клиентов в версиях, на которых собирается Pluma):
- **Android** спрашивает `help.getAppUpdate` при каждом возврате в приложение, если с прошлой проверки прошло не меньше `inapp_update_check_delay` секунд (`LaunchActivity.java:6134`, вызов из `onResume` `:7267`; ключ читается в `MessagesController.java:3216-3233`, без него — сутки, `:1595`; DrKLO/Telegram `7be672ea`). Сервер отдаёт `3600` (`docs/ops/app-config.md`): приложение, которое открывают, узнаёт о выпуске в пределах часа. Пока приложение открыто без перерыва, проверки нет.
- **iOS** спрашивает при запуске приложения и затем раз в 12 часов (`managedAppUpdateInfo`, `AppUpdate.swift:37-48`, запуск в `AccountTaskManager.swift:148`; Telegram-iOS `release-13.2`). Ключа конфига для этого нет; час — только правкой клиента (бриф задачи 095).
- **Desktop** проверяет `GET /dl/desktop/current4` раз в 8–16 часов (`UpdateDelayConstPart`/`UpdateDelayRandPart`, `config.h:27-28`; `update_checker.cpp:1726-1737`; tdesktop v7.4.1), если в настройках включено автообновление. Час — только правкой клиента.
- **Web** раз в 30 минут читает файл `version` своего сайта и, если он отличается от версии загруженной страницы, показывает в меню кнопку обновления (`src/components/sidebarLeft/index.ts:396-411`, tweb `aa74832e`). Сборка Pluma пока оставляет `version` апстрима (`2.3 (686)`, `clients/patches/web.md`), поэтому новая выкладка Web этой кнопкой не замечается; это правка клиента.

## Обязательный выпуск
Выпуск Android или iOS можно сделать обязательным: `help.getAppUpdate` предлагает его с `can_not_skip`, и приложение показывает экран обновления без «Пропустить». Это флаг выпуска (`app_releases.can_not_skip`), он записывается вместе с выпуском, одной строкой таблицы.

**При загрузке (основной способ).** Обязательность задаётся при загрузке, а не после неё: Android, получивший предложение версии, ответы на ту же версию больше не рассматривает (`LaunchActivity.java:6153-6155`, DrKLO/Telegram `7be672ea`), и флаг, поставленный позже, до него не доходит (см. ниже).
- Форма загрузки: поле `can_not_skip=1`; `0` или его отсутствие — необязательный выпуск. Любое другое значение отвечает `400` (а не тихо считается необязательным), `1` для `macos`, `windows`, `linux` — тоже `400`.
- CI pluma-ios: ручной запуск workflow `ios` с отмеченными `ipa` и `mandatory` (вход по умолчанию выключен). Обычная сборка из `main` загружается необязательной. `mandatory` без `ipa` или без подписанных сборок (`PLUMA_TEAM_ID`) останавливает запуск сразу: выпуска не будет.
- CI pluma-android: такой же вход `mandatory` у workflow `android` (ручной запуск `main` без `abis` и `dev_address`) — правка подготовлена, в репозиторий клиента ещё не внесена (бриф задачи 095). До неё Android-выпуск делается обязательным только командой ниже.
- Повтор загрузки той же сборки (перезапуск задачи CI): необязательный повтор обязательного выпуска — `409`, выпуск остаётся обязательным (повтор не отменяет `release mandatory`). Обязательный повтор выпуска, загруженного необязательным, — `422` с подсказкой: CI падает, а не сообщает об успехе, пока выпуск остаётся необязательным; сделать его обязательным может только оператор, помня об ограничении Android ниже.

**Командой оператора** флаг ставится и снимается у уже загруженного выпуска:
```bash
S="docker compose -f docker-compose.yaml -f docker-compose.public-ip.yaml"
$S exec bff ./pluma-admin -f ../etc2/bff.yaml release list                        # колонка MANDATORY
$S exec bff ./pluma-admin -f ../etc2/bff.yaml release mandatory android <сборка>
$S exec bff ./pluma-admin -f ../etc2/bff.yaml release optional android <сборка>
```
Платформы — `android` и `ios`; для `macos`, `windows`, `linux` команда отвечает ошибкой: апдейтер Desktop берёт из `current4` только версию и путь пакета (`ParseCommonMap`, `update_checker.cpp:608-690`), обязательных обновлений у него нет. Web обновляется с сервера, у него их тоже нет. Флаг действует сразу, без перезапуска сервисов; панель его пока не показывает и не меняет.

Что делает каждое приложение:
- **Android.**
  - Новое предложение с `can_not_skip` открывает полноэкранный `BlockingUpdateView` вместо листа обновления (`LaunchActivity.java:6157-6159`, `:1402-1408`). Предложение сохраняется, и при каждом возврате в приложение экран открывается снова (`:7264-7265`).
  - Открываясь так, экран заново спрашивает сервер: если пришёл `help.appUpdate` без `can_not_skip`, экран закрывается и предложение забывается (`BlockingUpdateView.java:305-323`). На `help.noAppUpdate` экран остаётся.
  - Если приложение уже получило предложение **той же версии**, новый ответ оно не смотрит (`LaunchActivity.java:6153-6155`). Поэтому `release mandatory` не действует на тех, кто уже увидел выпуск необязательным: обязательный выпуск загружается сразу обязательным (вход CI `mandatory`). Опоздали — следующая сборка, сразу обязательная.
  - Скрытый выход: десять нажатий на картинку экрана закрывают его и забывают предложение (`BlockingUpdateView.java:75-81`); при следующей проверке (не раньше часа) сервер предложит выпуск снова.
- **iOS** (только сборки с сайта, ` adhoc`; TestFlight обновляет TestFlight).
  - С `can_not_skip` на экране обновления нет кнопки «Пропустить» (`UpdateInfoController.swift:134`; поле `blocking`, `AppUpdate.swift:22-34`).
  - Экран показывается, когда ответ отличается от прежнего (`ApplicationContext.swift:589-599`); `blocking` входит в сравнение, поэтому смена флага показывает экран заново при следующем опросе (запуск приложения или 12 часов).
  - Закрывает ли что-то показанный экран, когда выпуск стал необязательным или отозван, по коду не видно: новый ответ только открывает экран, старый не убирается (не проверено на устройстве). Перезапуск приложения убирает экран, если сервер больше не предлагает обязательный выпуск.
- **Отмена.** Снять обязательность — `release optional`; Android снимает экран при следующем возврате в приложение (см. выше). Отозвать обязательный выпуск: сначала `release optional`, потом `release withdraw`, иначе Android, уже показавший экран, получает `help.noAppUpdate` и экран не снимает.

## Место на диске
Каждый выпуск занимает свой каталог в томе `releases_data` (APK около 80 МБ, Desktop — несколько установщиков и пакетов по 100 МБ). Старые каталоги удаляются вручную, когда их выпуски отозваны или давно заменены; текущий и предыдущий выпуск каждой платформы оставлять для отката:
```bash
$S -f docker-compose.releases.yaml exec releases du -sh /data/files/android/*
$S -f docker-compose.releases.yaml exec releases rm -rf /data/files/android/<старая версия>
```
Запись в `app_releases` остаётся; если удалённый выпуск потом вернуть (`restore`), ссылки на его файлы ответят 404.

## Выключить
Убрать `-f docker-compose.releases.yaml` из команды и `docker compose … rm -sf releases`. Маршрут `/dl/*` тогда отвечает 502, остальной сайт не затронут; `help.getAppUpdate` продолжает отвечать по таблице, а скачивание APK по MTProto работает (документ в DFS).
