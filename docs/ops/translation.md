# Перевод сообщений

Перевод сообщений, расшифровок и опросов своей моделью (задача 101, ADR 0064). Переводит необязательный сервис `translate` — `llama-server` из llama.cpp с моделью HY-MT1.5-1.8B (Tencent) в отдельном контейнере. bff ведёт очередь, кэш и разметку сущностей (`pkg/translate`) и отправляет движку запросы по протоколу OpenAI `POST /v1/chat/completions`. Без движка (`TRANSLATE_URL` пуст) перевод выключен.

Этот файл сейчас описывает образ, оверлей, проверку движка и первый замер (часть 1 задачи); включение, метрики, тревоги и замер на домашнем сервере дописываются частью 10.

## Образ `pluma-translate`
`teamgramd/deploy/translate/Dockerfile`:
- стадия `model` скачивает GGUF и `License.txt` модели с Hugging Face по адресам, закреплённым на ревизии `265b2e61` репозитория `tencent/HY-MT1.5-1.8B-GGUF`, и сверяет SHA-256 обоих; запуск контейнера от сети не зависит;
- из официального образа `ghcr.io/ggml-org/llama.cpp:server-b11913` (выпуск 2026-10-27, закреплён по digest) берётся только `/app` (llama-server и библиотеки ggml для всех вариантов x86: нужный выбирается при запуске по процессору). Сам официальный образ несёт ещё ffmpeg (около 780 МБ), который серверу не нужен, поэтому основа — тот же `ubuntu:26.04`, что у `pluma-stt`, с `libgomp1`, `libssl3t64`, `libstdc++6` и `curl` для проверки здоровья;
- `/model/License.txt` — соглашение модели, `/licenses/NOTICE` — фраза §3(d) лицензии Tencent, `/licenses/llama.cpp.LICENSE` — MIT;
- пользователь без прав (65532), `HEALTHCHECK` по `GET /health` (без токена; 503, пока модель грузится).

Размер на диске — около 2,05 ГБ (модель `Q8_0` 1,91 ГБ + 0,15 ГБ основа и llama.cpp); с `Q6_K` — около 1,6 ГБ.

### Запуск (`teamgramd/deploy/translate/entrypoint.sh`)
Переменные окружения контейнера (оверлей передаёт их из `.env`):

| Переменная | По умолчанию | Что |
|---|---|---|
| `TRANSLATE_THREADS` | 6 | потоки генерации и разбора запроса |
| `TRANSLATE_SLOTS` | 4 | одновременных запросов (`--parallel`); у bff должно быть то же |
| `TRANSLATE_CTX` | 16384 | контекст всего движка, делится поровну между слотами (4096 на слот); у bff должно быть то же |
| `TRANSLATE_API_TOKEN` | пусто | токен, который шлёт bff (`TRANSLATE_TOKEN` в `.env`), не короче 32 знаков; пусто — без токена |

Флаги `llama-server` сверены с `common/arg.cpp` выпуска b11913: `--no-kv-unified` (у каждого слота свой контекст, по нему bff ограничивает ответ), `--load-mode none` (модель читается в память, а не отображается: лимит памяти контейнера держит её целиком, под давлением она не вытесняется и не перечитывается с диска), `--cache-ram 0` (без кэша запросов: каждый текст другой, а кэш держал бы тексты сообщений в памяти), `--no-slots` (`GET /slots` показывал бы, над чем работают слоты), `--no-webui`, `--fit off`, `--metrics`. Токен передаётся `llama-server` через окружение (`LLAMA_API_KEY`), а не в командной строке. Если токен задан, запрос без него к `/v1/*` и `/metrics` получает 401; `/health` открыт всегда. Токен — без запятых: `llama-server` делит `LLAMA_API_KEY` по запятым на несколько ключей, и запуск с такой строкой отклоняется.

В журнале `llama-server` при уровне по умолчанию нет ни текстов, ни переводов — только время обработки по слотам (проверено на замере: поиск слов корпуса в `docker logs` пуст). Повышать уровень журнала (`-lv`) на сервере нельзя: на отладочном уровне пишется тело запроса.

### Оверлей `docker-compose.translate.yaml`
Сервис `translate`: `mem_limit = memswap_limit = ${TRANSLATE_MEMORY:-3584m}`, `cpus: ${TRANSLATE_CPUS:-6}`, `cpu_shares: 256` (при нехватке процессора уступает остальной Pluma), `cgroup_parent`, `read_only`, без опубликованных портов, сеть `teamgram_net`. Модель внутри образа: другая модель или квантование — другой образ (`PLUMA_TRANSLATE_IMAGE`) и его имя в `TRANSLATE_MODEL`.

## Проверка движка
Набор `pkg/translate/enginetest` проверяет любой движок через клиент, профиль и разметку сервера (на машине с Go):

```bash
TRANSLATE_ENGINE_URL=http://127.0.0.1:18080 TRANSLATE_ENGINE_MODEL=hy-mt1.5-1.8b-q8_0 \
TRANSLATE_ENGINE_TOKEN=<токен> TRANSLATE_ENGINE_SLOTS=4 TRANSLATE_ENGINE_CTX=16384 TRANSLATE_ENGINE_STRICT=1 \
go test -count=1 -timeout 60m -v -run 'TestEngine$' ./pkg/translate/enginetest
```

Проверяется: здоровье; перевод без сущностей во всех направлениях замера (ru⇄en, ru⇄kk, uk→ru, en→kk; текст не пустой, не равен исходному, без разметки запроса, с именами и числами, которые перевод обязан сохранить); сообщения с сущностями всех видов (неприкосновенные — код, упоминания, хештеги, свой эмодзи, ссылки, адреса — на месте с теми же атрибутами; доля сообщений, у которых теги прошли без запасного пути, не ниже `TRANSLATE_ENGINE_MIN_KEPT`, по умолчанию 0,5); самое длинное сообщение (4096 знаков) в пределах срока сервера; чужой токен — «движок недоступен», а не «плохой элемент»; вдвое больше запросов, чем слотов, — все обслужены. `TRANSLATE_ENGINE_STRICT=1` — для нашего `translate` (401 на чужой токен, все запросы сверх слотов обслужены очередью). Порт `translate` на сервере не опубликован: для проверки запустить контейнер того же образа отдельно с `-p 127.0.0.1:18080:8080`.

Замер — тот же пакет (`TestBench`), с `TRANSLATE_ENGINE_BENCH=1`: время каждого сообщения корпуса (20, 60, 300 и 4096 знаков) p50/p95, пачка из 20 на слотах движка, доля сохранённых тегов; `TRANSLATE_ENGINE_VARIANTS` сравнивает варианты запроса, `TRANSLATE_ENGINE_OUT` пишет все переводы в файл для чтения. Корпус свой (`corpus.go`), чужих текстов в нём нет. Память — снаружи: `docker stats` и `memory.stat` контейнера (`anon` — сам процесс; `file` — страничный кэш от чтения модели при запуске, вытесняемый).

## Замер
### Первый проход: машина сборки (2026-11-16, часть 1)
Не домашний сервер: AMD Ryzen 5 5600 (Zen 3, AVX2, без AVX-VNNI), DDR4, 32 ГБ; контейнер с теми же пределами, что в оверлее (`--cpus 6 --cpu-shares 256`, память 4 ГБ, `--read-only`), 6 потоков, слоты по 4096 токенов. Набор `pkg/translate/enginetest`, три прогона каждого сообщения, перевод — через профиль `hy-mt1.5` как в bff. Цифры домашнего сервера (i5-13500T, ядра P и E) будут другими — их снимает часть 10 до включения.

Время одного сообщения, p50 / p95, секунды (`Q8_0`, 4 слота, без другой нагрузки):

| Направление | 20 знаков | ~55 знаков | ~320 знаков (около 55 слов) | ~3900 знаков |
|---|---|---|---|---|
| ru→en | 0,44 / 0,54 | 0,81 / 0,95 | 4,2 / 5,0 | 47,6 / 57,0 |
| en→ru | 0,44 / 0,48 | 0,99 / 1,12 | 6,7 / 7,2 | 69,4 / 74,4 |
| uk→ru | 0,52 / 0,63 | 1,23 / 1,39 | 6,1 / 6,8 | — |
| ru→kk | 0,48 / 0,56 | 1,39 / 1,39 | 7,1 / 7,8 | — |
| kk→ru | 0,71 / 0,83 | 1,39 / 1,54 | 5,5 / 6,3 | — |
| en→kk | 1,11 / 1,24 | 1,31 / 1,43 | 10,1 / 10,9 | — |

- Генерация одного запроса — около 25 токенов/с, разбор запроса — около 175 токенов/с (журнал `llama-server`). Самое длинное сообщение укладывается в срок клиента bff (10 с + 25 мс × знак = 106–109 с) с запасом около 35 %.
- Пачка из 20 сообщений чата (ru→en, по кругу 20, 58 и 303 знака) на всех слотах: 1 слот — 40,0 с, 2 — 25,5 с, 4 — 19,9 с.
- Порог включения из брифа (60 слов p95 ≤ 6 с, пачка 20 ≤ 25 с при 4 слотах): здесь пачка проходит, одно сообщение — только ru→en (5,0 с); en→ru 7,2 с и uk→ru 6,8 с — выше порога на этой машине. Решение — по замеру на домашнем сервере.
- `Q6_K` (тот же прогон): одно сообщение в среднем на 15–20 % быстрее (en→ru ~320 знаков 5,3 / 5,5 с, uk→ru 4,9 / 5,4 с, ru→en ~3900 знаков 39 / 56 с), пачка 20 — 18,4 с, память на 0,4 ГБ меньше; один раз kk→ru зациклился до `max_tokens` (ошибка элемента, повтор по разделу 6 ADR). Качество `Q6_K` против `Q8_0` формально (chrF++ на FLORES) не сравнивалось — это часть 10. По умолчанию остаётся `Q8_0` (ADR 0064, раздел 2).

Память контейнера (`memory.stat`, `anon` — процесс; контекст выделяется при запуске целиком, от текстов почти не растёт):

При запуске контейнеру начисляется ещё страничный кэш файла модели (`file`, до 1,2 ГБ, вытесняемый): в пределе 4 ГБ `docker stats` показывал 2,85–2,89 ГиБ. ### Шаблон запроса и температура
Сравнивались на 13 сообщениях с сущностями всех видов (`TaggedSamples`, 24 перевода за прогон, три прогона на вариант):

| Вариант | Теги сохранены (все направления) | Без казахского |
|---|---|---|
| профиль как был: «форматированный» шаблон карточки, ответ только внутри `<target>` | 27 из 72 (38 %) | 13 из 36 (36 %) |
| тот же шаблон, ответ читается и без `<target>` | 48 из 72 (67 %) | 27 из 36 (75 %) |
| тот же шаблон, ответ модели начат с `<target>` (assistant prefill `llama-server`) | 43 из 72 (60 %) | 24 из 36 (67 %) |
| английский текст инструкции (вместо китайского карточки) | 4 из 23 | — |
| температура 0,2 вместо 0,7 | 10 из 24 (как 0,7 в том же прогоне) | — |

Главная причина потерь: модель чаще всего возвращает перевод со всеми тегами на местах, но без обёртки `<target>…</target>`, которую просит шаблон. Остальные случаи — потерянная `>` (`</s1 за`), лишний закрывающий тег, пустой тег в конце, перевод одного куска вместо всего текста; их ловит проверка разметки, и элемент идёт запасным путём кусками.

Выбрано: **«форматированный» шаблон карточки без изменений, ответ читается с `<target>` и без него** (`pkg/translate/profile_hymt.go`, `Answer`; ответ, повторяющий `<source>` запроса, по-прежнему не перевод), **температура 0,7 карточки** (ниже — без выигрыша в тегах). Профиль остаётся версией 1: запросы и ключи кэша не изменились, а перевод ещё нигде не включён. Prefill не взят: хуже по замеру и требует второго сообщения в протоколе. После выбора проверка `TestEngine` дала 14–16 из 24 сохранённых (порог набора — 0,5).

Запасной путь кусками заметно хуже по смыслу: модель переводит обрывки фраз по отдельности («Write it down. support@… Or call them.»), а куски на казахский — часто не на казахский. Поэтому важна именно доля сохранённых тегов.

### Казахский
HY-MT1.5-1.8B не годится для казахского, как его пишут в Казахстане (кириллица):
- на казахский (`kk`) модель пишет казахский **арабским письмом** (как в Синьцзяне; китайское имя языка в карточке — 哈萨克语) или отвечает по-русски, по-украински, иногда кусками на хинди или тамильском, при температуре 0,7 и 0 одинаково;
- с казахского на русский и английский смысл теряется («Үйге келе жатып нан мен сүт ала келші…» → «When I go to bed at night…»).

Украинский, немецкий, английский и русский в тех же прогонах переводятся осмысленно. Судя по соседям в таблице языков карточки (тибетский, уйгурский, монгольский, кантонский), `kk` модели — казахский Китая; в карточке это не сказано (не проверено). Что делать — решает владелец: убрать `kk` из таблицы языков профиля (клиент получит `TO_LANG_INVALID` при переводе на казахский; перевод с казахского сервер запретить не может — язык источника определяет клиент) или оставить как есть.
