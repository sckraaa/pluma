# Перевод сообщений

Перевод сообщений, расшифровок и опросов своей моделью (задача 101, ADR 0064). Переводит необязательный сервис `translate` — `llama-server` из llama.cpp с моделью HY-MT1.5-1.8B (Tencent) в отдельном контейнере. bff ведёт очередь, кэш и разметку сущностей (`pkg/translate`) и отправляет движку запросы по протоколу OpenAI `POST /v1/chat/completions`. Без движка (`TRANSLATE_URL` пуст) перевод выключен.

Документ описывает выкладку и включение, переменные, метрики и тревоги, образ и оверлей, проверку движка, замеры и план замера на домашнем сервере.

## Порядок выкладки
1. **Сервер с выключенным переводом.** Коммит с задачей 101 выкладывается как обычно; без `TRANSLATE_URL` перевод выключен: `messages.translateText` отвечает `ERR_ENTERPRISE_IS_BLOCKED`, как раньше, а ключи `translations_manual_enabled` и `translations_auto_enabled` клиенты получают со значением `disabled` (кнопок перевода нет). Миграция `teamgramd/deploy/sql/migrate-20261119-translation.sql` (таблицы `translation_cache` и `peer_translation_settings`) применяется сервисом migrate, повторный запуск безопасен.
2. **Замер на домашнем сервере** — раздел «Домашний сервер: план замера» ниже. По его итогам — значения `TRANSLATE_*` в `.env` (слоты и контекст читают и bff, и `translate`, см. «Переменные»).
3. **Включение** (раздел «Включение»). Перевод становится доступен всем пользователям сразу: отдельного включения для одного человека нет.
4. **Проверка качества владельцем** — пункты задачи 101 в `docs/project/TESTING-BACKLOG.md`.
5. **Раскрытие по §3(e) лицензии модели** в эту выкладку не входит: по решению владельца (2026-11-15) оно — отдельный шаг выпуска после его проверки качества и до публичного объявления перевода (раздел «Лицензия»).

## Включение
1. Образ: CI собирает `pluma-translate` (`.github/workflows/images.yml`), модель внутри образа. В `.env` сервера:

   ```
   PLUMA_TRANSLATE_IMAGE=ghcr.io/sckraaa/pluma-translate:<коммит>
   TRANSLATE_URL=http://translate:8080
   TRANSLATE_MODEL=hy-mt1.5-1.8b-q8_0
   TRANSLATE_TOKEN=<openssl rand -hex 32>
   TRANSLATE_PROFILE=
   ```

   и значения замера: `TRANSLATE_THREADS`, `TRANSLATE_SLOTS`, `TRANSLATE_CTX`, `TRANSLATE_MEMORY`, `TRANSLATE_CPUS` (без них — значения по умолчанию из таблицы «Переменные»). `TRANSLATE_TOKEN` один на двоих: bff его отправляет, `translate` требует; без запятых. Наружу порт `translate` не публикуется, токен — вторая защита внутри сети compose.
2. Запустить движок, дождаться `healthy`, перезапустить bff:

   ```bash
   docker compose -f docker-compose.yaml -f docker-compose.public-ip.yaml -f docker-compose.translate.yaml up -d translate
   docker compose -f docker-compose.yaml -f docker-compose.public-ip.yaml -f docker-compose.translate.yaml ps translate   # healthy
   docker compose -f docker-compose.yaml -f docker-compose.public-ip.yaml up -d bff
   ```

   Пока модель грузится (секунды), `/health` отвечает 503, а переводы — `FLOOD_WAIT_10`. `~/pluma-work/bin/pluma-deploy.sh` пока не тянет `pluma-translate` и не подключает оверлей (в отличие от `stt`): до его правки после каждой выкладки нового коммита — `docker pull` образа с новым тегом и первая команда выше.
3. Проверить:
   - `docker compose … ps translate` — `healthy`; в логе bff нет `translate: the engine is unavailable`;
   - `help.getAppConfig` отдаёт оба ключа `enabled`: клиенты применяют его при следующем запросе конфигурации (перезапуск клиента);
   - перевести сообщение в клиенте; в Prometheus растёт `translate_items_total{source="engine"}`, `translate_engine_up` = 1, в Grafana — строка «Translation».

**Выключить или откатить:** `TRANSLATE_URL=` и перезапуск bff — оба ключа снова `disabled`, клиенты прячут перевод при следующем `help.getAppConfig`; `translate` можно остановить (`… stop translate`). Кэш переводов остаётся в MySQL и уходит по сроку (`CacheTTL`). Падение движка ключи не переключает: короткий сбой клиенты переживают через `FLOOD_WAIT_X`.

## Переменные
| Переменная | Где | Значение |
|---|---|---|
| `TRANSLATE_URL` | bff | адрес движка: `http://translate:8080` или любой сервис с `POST /v1/chat/completions`; пусто — перевод выключен |
| `TRANSLATE_MODEL` | bff | имя модели, на которое отвечает движок (`MODEL_NAME` образа: `hy-mt1.5-1.8b-q8_0`); обязательно вместе с `TRANSLATE_URL`. Входит в ключ кэша: после смены всё переводится заново |
| `TRANSLATE_TOKEN` | bff, `translate` | Bearer-токен, не короче 32 знаков, без запятых; пусто — без токена |
| `TRANSLATE_PROFILE` | bff | шаблоны запроса и выборка модели (`pkg/translate`); пусто — `hy-mt1.5` |
| `PLUMA_TRANSLATE_IMAGE` | compose | образ `translate` |
| `TRANSLATE_MEMORY` | compose | потолок памяти контейнера без подкачки, по умолчанию `3584m` (`Q8_0`, 4 слота); пересчитать `docs/ops/memory.md` |
| `TRANSLATE_CPUS` | compose | CPU контейнера, по умолчанию 6; вес `cpu_shares: 256` — при нехватке процессора движок уступает остальной Pluma |
| `TRANSLATE_THREADS` | `translate` | потоки генерации и разбора запроса, по умолчанию 6 |
| `TRANSLATE_SLOTS` | bff, `translate` | одновременных запросов, по умолчанию 4 |
| `TRANSLATE_CTX` | bff, `translate` | контекст всего движка в токенах, по умолчанию 16384 (по 4096 на слот) |

**Слоты и контекст — одни на двоих.** bff шлёт движку столько запросов сразу, сколько слотов, и ограничивает ответ контекстом одного слота (`TRANSLATE_CTX / TRANSLATE_SLOTS`). `TRANSLATE_SLOTS` и `TRANSLATE_CTX` из `.env` читают и bff (блок `Translate`, `Slots` и `Context`), и `translate`; пустые — 4 и 16384 у обоих. После смены пересоздать оба сервиса: `bff` и `translate`. Если у движка слотов меньше, чем у bff (пересоздан только один), лишние запросы ждут в очереди движка и тратят свой срок; если контекст слота меньше, чем думает bff, длинные тексты не переводятся (тревога `TranslateItemsFailing`).

Остальные настройки — блок `Translate` файла `bff.yaml` (значения по умолчанию — `pkg/translate/config.go`; задаются там же, коммитом):
- `SyncWait` 25 с — сколько ждёт пачка чата, `SyncWaitSingle` 45 с — один текст (экран перевода iOS не повторяет `FLOOD_WAIT`, поэтому ждёт дольше). Не успели — `FLOOD_WAIT_X`, а работа продолжается в кэш; Android, tdesktop и Web K повторяют сами;
- `Timeout` 10 с + `TimeoutPerChar` 25 мс × знак — срок одного обращения к движку; до двух повторов с паузами 1 и 3 с, затем элемент «не удался» на `FailedTTL` 60 с;
- `CacheTTL` 720 ч — перевод хранится 30 дней после последнего чтения; подметальщик удаляет просроченное;
- `MaxItemLength` 4096, `MaxItems` 100, `MaxRequestLength` 32768 — пределы запроса (сверх — `INPUT_TEXT_TOO_LONG`);
- `ItemsPerMinute` 300, `ItemsPerHour` 3000 — элементов в движок на человека (кэш бесплатен; сверх — `FLOOD_WAIT_X`).

## Метрики
Метрики bff (`pkg/translate/metrics.go`, ADR 0064 §13); без `TRANSLATE_URL` не публикуются. Тексты в метки не попадают — только длины, счёты и время.

| Метрика | Что |
|---|---|
| `translate_requests_total{method, result}` | ответы методов перевода: `ok`, `wait` (не успели за `SyncWait`), `down` (движок недоступен), `failed` (элемент недавно не удался), `limited` (предел частоты), `stopped`, `canceled`, `invalid`, `off`, `internal` |
| `translate_items_total{source}` | элементы по источнику: `cache`, `engine`, `empty` (нечего переводить); доля `cache` — польза кэша |
| `translate_engine_seconds` | время одного элемента в движке, вместе с запасным путём кусками |
| `translate_engine_errors_total{kind}` | неудачные попытки: `busy` (503, 429), `down`, `timeout`, `unavailable`, `rejected`, `bad_answer`, `other` |
| `translate_engine_up` | 1 — движок берёт элементы, 0 — ждём его проверку здоровья (раз в 5 с) |
| `translate_queue_depth` | элементы в очереди, в движке и в ожидании повтора |
| `translate_markup_fallback_total` | ответы, потерявшие теги: перевод кусками, без части оформления |
| `translate_cache_rows` | строк в `translation_cache` (раз в 5 минут) |
| `translate_cache_errors_total{op}` | сбои чтения, записи и подсчёта кэша |
| `translate_limit_errors_total` | проверки пределов, не дошедшие до Redis (элементы пропущены без предела) |

Метрики самого `llama-server` (`--metrics`) Prometheus не читает: при заданном токене `/metrics` требует его же, а метрик bff для тревог и панелей хватает.

## Тревоги
Правила — `teamgramd/deploy/prometheus/server/rules/translate.yml`, панели — строка «Translation» дашборда «Pluma overview».
- **`TranslateEngineDown`** — движок 10 минут недоступен: переводы отвечают `FLOOD_WAIT_10`, новые элементы не ставятся. Срабатывает, только если кто-то пытался переводить. `docker compose … ps translate`, `docker compose … logs --tail 50 translate bff` (в логе bff — `the engine is unavailable` с причиной); сверить `TRANSLATE_URL`, `TRANSLATE_TOKEN` (401 — токены разные или в одном есть запятая), `docker inspect` — `OOMKilled` (поднять `TRANSLATE_MEMORY` или уменьшить слоты). Перезапуск: `docker compose … -f docker-compose.translate.yaml up -d translate`; bff подхватит движок сам по проверке здоровья.
- **`TranslateItemsFailing`** — движок отвечает, но элементы не переводятся. В логе bff — `failed (<kind>) after N attempts` (длина и язык, без текста). `rejected` — движок отверг запрос: чаще всего контекст слота меньше, чем думает bff (после смены `TRANSLATE_SLOTS`/`TRANSLATE_CTX` пересоздан только один из `bff` и `translate`); `timeout` — движок слишком медленный для `Timeout` (см. «Замер»); `bad_answer` — ответ не перевод (пустой, повтор запроса, обрыв по `max_tokens`): при росте после смены модели или квантования — вернуть прежний образ.
- **`TranslateTooSlow`** — больше половины пачек чата не успевают за `SyncWait`: людям приходится ждать. Grafana: время движка и очередь; `docker stats translate`. Меры по порядку: убедиться, что ничего постороннего не нагружает процессор (медиасервер, `stt`); `Q6_K`; больше `TRANSLATE_CPUS`/`TRANSLATE_THREADS` — только по замеру, не в ущерб звонкам.
- **`TranslateCacheFailing`** — кэш в MySQL не читается или не пишется: каждый перевод снова идёт в движок. Лог bff (`is not cached`, `count the cache`), `docker compose logs mysql`.

Запасной путь разметки (панель «Translation failures», `markup fallback`) тревоги не имеет: это качество, а не поломка. Его заметный рост после смены модели или профиля — повод вернуть прежние.

## Образ `pluma-translate`
`teamgramd/deploy/translate/Dockerfile`:
- стадия `model` скачивает GGUF и `License.txt` модели с Hugging Face по адресам, закреплённым на ревизии `265b2e61` репозитория `tencent/HY-MT1.5-1.8B-GGUF`, и сверяет SHA-256 обоих; запуск контейнера от сети не зависит;
- из официального образа `ghcr.io/ggml-org/llama.cpp:server-b11913` (выпуск 2026-10-27, закреплён по digest) берётся только `/app` (llama-server и библиотеки ggml для всех вариантов x86: нужный выбирается при запуске по процессору). Сам официальный образ несёт ещё ffmpeg (около 780 МБ), который серверу не нужен, поэтому основа — тот же `ubuntu:26.04`, что у `pluma-stt`, с `libgomp1`, `libssl3t64`, `libstdc++6` и `curl` для проверки здоровья;
- `/model/License.txt` — соглашение модели, `/licenses/NOTICE` — фраза §3(d) лицензии Tencent, `/licenses/llama.cpp.LICENSE` — MIT;
- пользователь без прав (65532), `HEALTHCHECK` по `GET /health` (без токена; 503, пока модель грузится).

Размер на диске — около 2,05 ГБ (модель `Q8_0` 1,91 ГБ + 0,15 ГБ основа и llama.cpp); с `Q6_K` — около 1,6 ГБ.

### Запуск (`teamgramd/deploy/translate/entrypoint.sh`)
Переменные окружения контейнера (оверлей передаёт их из `.env`):

| Переменная | По умолчанию | Что |
|---|---|---|
| `TRANSLATE_THREADS` | 6 | потоки генерации и разбора запроса |
| `TRANSLATE_SLOTS` | 4 | одновременных запросов (`--parallel`); bff читает ту же переменную |
| `TRANSLATE_CTX` | 16384 | контекст всего движка, делится поровну между слотами (4096 на слот); bff читает ту же переменную |
| `TRANSLATE_API_TOKEN` | пусто | токен, который шлёт bff (`TRANSLATE_TOKEN` в `.env`), не короче 32 знаков; пусто — без токена |

Флаги `llama-server` сверены с `common/arg.cpp` выпуска b11913: `--no-kv-unified` (у каждого слота свой контекст, по нему bff ограничивает ответ), `--load-mode none` (модель читается в память, а не отображается: лимит памяти контейнера держит её целиком, под давлением она не вытесняется и не перечитывается с диска), `--cache-ram 0` (без кэша запросов: каждый текст другой, а кэш держал бы тексты сообщений в памяти), `--no-slots` (`GET /slots` показывал бы, над чем работают слоты), `--no-webui`, `--fit off`, `--metrics`. Токен передаётся `llama-server` через окружение (`LLAMA_API_KEY`), а не в командной строке. Если токен задан, запрос без него к `/v1/*` и `/metrics` получает 401; `/health` открыт всегда. Токен — без запятых: `llama-server` делит `LLAMA_API_KEY` по запятым на несколько ключей, и запуск с такой строкой отклоняется.

В журнале `llama-server` при уровне по умолчанию нет ни текстов, ни переводов — только время обработки по слотам (проверено на замере: поиск слов корпуса в `docker logs` пуст). Повышать уровень журнала (`-lv`) на сервере нельзя: на отладочном уровне пишется тело запроса.

### Оверлей `docker-compose.translate.yaml`
Сервис `translate`: `mem_limit = memswap_limit = ${TRANSLATE_MEMORY:-3584m}`, `cpus: ${TRANSLATE_CPUS:-6}`, `cpu_shares: 256` (при нехватке процессора уступает остальной Pluma), `cgroup_parent`, `read_only`, без опубликованных портов, сеть `teamgram_net`. Модель внутри образа: другая модель или квантование — другой образ (`PLUMA_TRANSLATE_IMAGE`) и его имя в `TRANSLATE_MODEL`.

## Проверка движка
Набор `pkg/translate/enginetest` проверяет любой движок через клиент, профиль и разметку сервера (на машине с Go):

```bash
TRANSLATE_ENGINE_URL=http://127.0.0.1:18080 TRANSLATE_ENGINE_MODEL=hy-mt1.5-1.8b-q8_0 \
TRANSLATE_ENGINE_TOKEN=<токен> TRANSLATE_ENGINE_SLOTS=4 TRANSLATE_ENGINE_CTX=16384 TRANSLATE_ENGINE_STRICT=1 \
go test -count=1 -timeout 60m -v -run 'TestEngine$' ./pkg/translate/enginetest
```

Проверяется: здоровье; перевод без сущностей во всех направлениях замера (ru⇄en, ru⇄kk, uk→ru, en→kk; текст не пустой, не равен исходному, без разметки запроса, с именами и числами, которые перевод обязан сохранить); сообщения с сущностями всех видов (неприкосновенные — код, упоминания, хештеги, свой эмодзи, ссылки, адреса — на месте с теми же атрибутами; доля сообщений, у которых теги прошли без запасного пути, не ниже `TRANSLATE_ENGINE_MIN_KEPT`, по умолчанию 0,5); самое длинное сообщение (4096 знаков) в пределах срока сервера; чужой токен — «движок недоступен», а не «плохой элемент»; вдвое больше запросов, чем слотов, — все обслужены. `TRANSLATE_ENGINE_STRICT=1` — для нашего `translate` (401 на чужой токен, все запросы сверх слотов обслужены очередью). Порт `translate` на сервере не опубликован: для проверки запустить контейнер того же образа отдельно с `-p 127.0.0.1:18080:8080`.

Замер — тот же пакет (`TestBench`), с `TRANSLATE_ENGINE_BENCH=1`: время каждого сообщения корпуса (20, 60, 300 и 4096 знаков) p50/p95, пачка из 20 на слотах движка, доля сохранённых тегов; `TRANSLATE_ENGINE_VARIANTS` сравнивает варианты запроса, `TRANSLATE_ENGINE_OUT` пишет все переводы в файл для чтения. Корпус свой (`corpus.go`), чужих текстов в нём нет. Память — снаружи: `docker stats` и `memory.stat` контейнера (`anon` — сам процесс; `file` — страничный кэш от чтения модели при запуске, вытесняемый).

### Шаблон запроса и температура
Сравнивались на 13 сообщениях с сущностями всех видов (`TaggedSamples`, 24 перевода за прогон, три прогона на вариант):

| Вариант | Теги сохранены (все направления) | Без казахского |
|---|---|---|
| профиль как был: «форматированный» шаблон карточки, ответ только внутри `<target>` | 27 из 72 (38 %) | 13 из 36 (36 %) |
| тот же шаблон, ответ читается и без `<target>` | 48 из 72 (67 %) | 27 из 36 (75 %) |
| тот же шаблон, ответ модели начат с `<target>` (assistant prefill `llama-server`) | 43 из 72 (60 %) | 24 из 36 (67 %) |
| английский текст инструкции (вместо китайского карточки) | 4 из 23 | — |
| температура 0,2 вместо 0,7 | 10 из 24 (как 0,7 в том же прогоне) | — |

Главная причина потерь: модель чаще всего возвращает перевод со всеми тегами на местах, но без обёртки `<target>…</target>`, которую просит шаблон. Остальные случаи — потерянная `>` (`</s1 за`), лишний закрывающий тег, пустой тег в конце, перевод одного куска вместо всего текста; их ловит проверка разметки, и элемент идёт запасным путём кусками.

Выбрано: **«форматированный» шаблон карточки без изменений, ответ читается с `<target>` и без него** (`pkg/translate/profile_hymt.go`, `Answer`; ответ, повторяющий `<source>` запроса, по-прежнему не перевод), **температура 0,7 карточки** (ниже — без выигрыша в тегах). Профиль остаётся версией 1: запросы и ключи кэша не изменились, а перевод ещё нигде не включён. Prefill не взят: хуже по замеру и требует второго сообщения в протоколе. После выбора проверка `TestEngine` дала 14–16 из 24 сохранённых (порог набора — 0,5).

Запасной путь кусками заметно хуже по смыслу: модель переводит обрывки фраз по отдельности («Write it down. support@… Or call them.»), а куски на казахский — часто не на казахский. Поэтому важна именно доля сохранённых тегов.

### Казахский
HY-MT1.5-1.8B не годится для казахского, как его пишут в Казахстане (кириллица):
- на казахский (`kk`) модель пишет казахский **арабским письмом** (как в Синьцзяне; китайское имя языка в карточке — 哈萨克语) или отвечает по-русски, по-украински, иногда кусками на хинди или тамильском, при температуре 0,7 и 0 одинаково;
- с казахского на русский и английский смысл теряется («Үйге келе жатып нан мен сүт ала келші…» → «When I go to bed at night…»).

Украинский, немецкий, английский и русский в тех же прогонах переводятся осмысленно. Судя по соседям в таблице языков карточки (тибетский, уйгурский, монгольский, кантонский), `kk` модели — казахский Китая; в карточке это не сказано (не проверено). Что делать — решает владелец: убрать `kk` из таблицы языков профиля (клиент получит `TO_LANG_INVALID` при переводе на казахский; перевод с казахского сервер запретить не может — язык источника определяет клиент) или оставить как есть.
