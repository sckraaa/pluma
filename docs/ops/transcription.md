# Расшифровка голосовых и кружков

Кнопка «→A» у голосового сообщения и кружка (задача 090, ADR 0056). Звук распознаёт необязательный сервис `stt` — модель GigaAM-v3 `e2e_rnnt` int8 на sherpa-onnx в отдельном контейнере. bff ведёт очередь и кэш в MySQL, декодирует запись в WAV 16 кГц моно своим ffmpeg и отправляет движку по протоколу OpenAI `POST /v1/audio/transcriptions`. Без движка (`STT_URL` пуст) кнопка отвечает ошибкой `TRANSCRIPTION_FAILED`.

Пределов для пользователей нет (решение владельца 2026-11-12): запись любой длины, сколько угодно расшифровок, тексты хранятся бессрочно. Ничего из того, что просит пользователь, не отклоняется из-за объёма. Защищён только движок: одна запись за раз на слот, срок по настоящей длине звука, очередь в MySQL без предела и по порядку запросов, терпеливые повторы.

## Порядок выкладки
Сначала сервер и `stt`, потом клиенты, в которых кнопка снова показана (снятие патчей A-109, I-109, D-084, W-068; в той же сборке клиентов — метка «служебный аккаунт», решение владельца 2026-11-12). Android запоминает любую ошибку расшифровки как окончательный пустой текст и больше не спрашивает (`TranscribeButton.java:679-685, 741-754`): если кнопка появится раньше движка, у этих сообщений навсегда останется «слова не распознаны».

## Включение
1. Миграция `teamgramd/deploy/sql/migrate-20261115-voice-transcription.sql` (таблицы `transcription_jobs` и `transcription_requests`); сервис migrate применяет её сам, повторный запуск безопасен.
2. Образ: CI собирает `pluma-stt` (`.github/workflows/images.yml`), модель внутри образа. В `.env`:

   ```
   PLUMA_STT_IMAGE=ghcr.io/sckraaa/pluma-stt:<коммит>
   STT_URL=http://stt:9379
   STT_MODEL=gigaam-v3-e2e-rnnt
   STT_TOKEN=<openssl rand -hex 32>
   STT_LANGUAGE=
   ```

   `STT_TOKEN` один на двоих: bff его отправляет, `stt` требует. Наружу порт `stt` не публикуется; токен — вторая защита внутри сети compose.
3. Запустить движок и перезапустить bff:

   ```bash
   docker compose -f docker-compose.yaml -f docker-compose.public-ip.yaml -f docker-compose.stt.yaml up -d stt
   docker compose -f docker-compose.yaml -f docker-compose.public-ip.yaml up -d bff
   ```

   `~/pluma-work/bin/pluma-deploy.sh` делает это сам, как только в `.env` есть `PLUMA_STT_IMAGE=ghcr.io/…` и `STT_URL=http://stt:…`.
4. Проверить: `docker compose … ps stt` — `healthy`; в логе `stt` строка `model gigaam-v3-e2e-rnnt (nemo_transducer) loaded`; расшифровать голосовое в клиенте; в Prometheus растёт `transcribe_jobs_total{result="done"}`.

Выключить: `STT_URL=` и перезапустить bff; `stt` можно остановить. Готовые тексты остаются в таблице и снова отдаются после включения той же модели.

## Переменные
| Переменная | Где | Значение |
|---|---|---|
| `STT_URL` | bff | адрес движка; пусто — расшифровка выключена |
| `STT_MODEL` | bff | имя модели, как его знает движок; обязательно вместе с `STT_URL`. Входит в ключ сохранённого текста |
| `STT_TOKEN` | bff, `stt` | Bearer-токен, не короче 32 символов; пусто — без токена |
| `STT_LANGUAGE` | bff, `stt` | язык речи; пусто — язык модели. bff сообщает его движку в каждом запросе, наш `stt` — модели Whisper (какой бы язык ни был у образа). GigaAM слышит только русский: `stt` с другим языком не запускается (в логе `speaks "ru", STT_LANGUAGE is …`), а не расшифровывает всё неверно. Модель, которая определяет язык сама (Parakeet TDT v3), его не получает |
| `STT_TIMEOUT` | bff | сколько движок может думать над записью: `<длительность>+<множитель>x`, то есть столько плюс множитель секунд на секунду звука; длина — та, что получилась при декодировании, а не та, что объявил клиент. Пусто — `30s+0.5x` (GigaAM на 2 CPU). Медленному движку или удалённому с очередью — больше, например `2m+2x`; основа от 1 с до часа, множитель от 0 до 20 |
| `PLUMA_STT_IMAGE` | compose | образ `stt` |
| `STT_MEMORY` | compose | потолок памяти контейнера `stt` без подкачки, по умолчанию `768m`; от длины записи не зависит. Другие модели — в таблице раздела «Замена модели» |
| `STT_CPUS` | compose | CPU контейнера `stt`, по умолчанию 2 |
| `STT_THREADS` | `stt` | потоки вычислений, по умолчанию 2 (по числу CPU контейнера) |

Настройки очереди — в блоке `Transcribe` файла `bff.yaml` (значения по умолчанию, менять там же):
- `Workers` 1 — сколько записей отдаётся движку одновременно, по числу его слотов (наш `stt` распознаёт одну запись за раз; лишние исполнители только ждут своей очереди, попыток не тратят);
- `MaxAttempts` 4 — сколько попыток, на которых движок взял звук и не дал ответа (500, обрыв, тайм-аут), получает запись; паузы 5 с, 30 с, 2 мин;
- `FailedTTL` 10 мин — через сколько после такого провала запись пробуется снова по новому нажатию (в это время нажатие получает «в работе», а не ошибку);
- `SyncWait` 3 с — сколько ответ ждёт текст, потом «в работе» и обновление; `DeliverDelay` 1 с.

## Как это работает
- Одна запись (документ) распознаётся один раз для всех читателей, пересылок и чатов: задание в `transcription_jobs` по паре «документ + модель». У каждой пары «пользователь + сообщение» свой `transcription_id` (строка `transcription_requests`): tdesktop ищет сообщение обновления только по нему. Если медиа сообщения отредактировали, id остаётся прежним, а новая запись получает своё задание: текст одной записи никогда не отдаётся за другую.
- Текст готов за 3 с — он в ответе. Иначе ответ «в работе» с пустым текстом, а через исполнитель и подметальщик приходит ровно одно `updateTranscribedAudio` во все сессии пользователя, не раньше чем через секунду после ответа.
- Очередь — таблица с арендой, без предела длины; записи берутся по порядку постановки. Перезапуск bff посреди задания безопасен: задание подхватывается после истечения аренды, ожидающие получают обновление.
- Срок попытки растёт с записью: скачивание и декодирование — 90 с плюс 4 с на мегабайт документа (размер знает сервер); время движка — `STT_TIMEOUT` от длины декодированного звука. Длительность в атрибуте задаёт клиент, ей не верят ни для срока, ни для аренды.
- На диске только копия документа: он скачивается во временный файл (его размер, час голосового — 7–15 МБ) и удаляется после попытки. Декодированный звук на диск не пишется: ffmpeg сначала прогоняет запись в никуда, чтобы узнать её длину, а потом декодирует заново прямо в запрос к движку (WAV без размеров в заголовке, отсчёты до конца потока, поэтому запись длиннее 37 часов не упирается в 4 ГиБ RIFF). Память bff от длины записи не зависит.
- Перед скачиванием bff проверяет место на диске временного каталога (это диск хоста, на нём же MySQL и Kafka): нужно размер документа плюс 1 ГиБ запаса. Если места меньше, запись ждёт 30 с и проверяет снова, попытка не тратится, в журнале bff — `waits for free disk`, растёт `transcribe_jobs_total{result="no_room"}`, срабатывает алерт `TranscriptionNoDisk`.
- `stt` читает WAV по мере распознавания и режет речь на куски (Silero VAD, до 20 с): в памяти только кусок в модели и буфер детектора, поэтому память `stt` от длины записи тоже не зависит (замер — в разделе «Память и CPU»).
- Движок занят (503, 429) — попытка держит скачанную запись и спрашивает снова каждые 2 с. Движок недоступен (никто не слушает адрес) или отвергает настройку (401, 403, 404: токен, имя модели, язык) — спрашивает снова с паузой от 2 до 30 с, причём сначала звуком без отсчётов (только заголовок WAV): `stt` проверяет имя модели и язык, когда звук уже идёт, и дочитывает его до конца, прежде чем ответить, поэтому вся запись уходит движку только тогда, когда он принял пустой звук. Ни то ни другое не попытка и не имеет предела: запись ждёт движок сколько нужно, ожидающие не получают пустого текста. Об этом сообщает алерт `TranscriptionEngineDown`.
- Текст длиннее 1 МиБ (около 11 часов русской речи) клиентам не отдаётся: Android рвёт соединение на пакете больше 2 МиБ (`tgnet/Connection.cpp:216`), а ответ на `messages.transcribeAudio` не сжимается. Такая запись — окончательный отказ, как нераспознаваемая; в журнале bff — `the text is longer than a client takes`.
- Ошибка движка 400/415/422 и ошибка ffmpeg — окончательный отказ (`TRANSCRIPTION_FAILED`, у ожидающих — пустое обновление). Остальное (500, 502, обрыв посреди ответа, тайм-аут, 413 чужого движка) — попытка; после `MaxAttempts` ожидающие получают пустое обновление, а новое нажатие ставит запись снова, не раньше `FailedTTL`.
- Экземпляр bff берёт только задания своей модели (`STT_MODEL`). Задания другой модели, которые никто не взял минуту, он «перевешивает»: ожидающие их читатели переходят на его модель и получают её текст, а не пустое обновление. Все экземпляры bff должны работать с одной моделью.
- Одноразовые голосовые и кружки не расшифровываются (`MSG_VOICE_MISSING`, решение владельца 2026-11-12); клиенты кнопку у них не показывают.
- Ни сервер, ни `stt` не пишут текст и звук в журналы и на диск (у `stt` файловая система только для чтения). bff держит копию записи во временном файле только на время попытки.

## Замена модели
Другая модель sherpa-onnx в нашем сервисе — другой образ. Образ определяют аргументы сборки `teamgramd/deploy/stt/Dockerfile`: `MODEL_URL`, `MODEL_SHA256`, `MODEL_KIND`, `MODEL_NAME`, `MODEL_LANGUAGE`. `MODEL_KIND`: `nemo_transducer` (GigaAM rnnt, Parakeet TDT), `nemo_ctc` (GigaAM ctc), `whisper`. SHA-256 другого архива посчитать у скачанного файла (`sha256sum`) — сборка его сверяет.

Проверенные значения (архивы релиза `asr-models` sherpa-onnx, `https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/<архив>`):

| Модель | `MODEL_NAME` | `MODEL_KIND` | `MODEL_LANGUAGE` | Архив | `MODEL_SHA256` | `STT_MEMORY` |
|---|---|---|---|---|---|---|
| GigaAM-v3 `e2e_rnnt` int8 (по умолчанию) | `gigaam-v3-e2e-rnnt` | `nemo_transducer` | `ru` | `sherpa-onnx-nemo-transducer-punct-giga-am-v3-russian-2025-12-16.tar.bz2` | `f9620a0099019c6afcee26525ef9ed3297fa50dd5691c1902af0c948fc1a470b` | `768m` |
| GigaAM-v3 `e2e_ctc` int8 | `gigaam-v3-e2e-ctc` | `nemo_ctc` | `ru` | `sherpa-onnx-nemo-ctc-punct-giga-am-v3-russian-2025-12-16.tar.bz2` | `20e41e160efa6f2460a7ef6554cdbbb9e8fffb2b92e6bc708e9406bd8b9256ea` | `768m` |
| Parakeet TDT 0.6b v3 int8 (25 европейских языков, язык определяет сама) | `parakeet-tdt-v3` | `nemo_transducer` | пусто | `sherpa-onnx-nemo-parakeet-tdt-0.6b-v3-int8.tar.bz2` | `1495e91b59d7fc53ddca91f3431758ec99f8fa253fdb0e1e851be0f72b14b0f9` | `2g` (при `768m` убит OOM при загрузке) |

**Сначала попробовать** на машине сборки, не трогая сервер:

```bash
docker buildx build -f teamgramd/deploy/stt/Dockerfile \
  --build-arg MODEL_URL=https://github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/sherpa-onnx-nemo-ctc-punct-giga-am-v3-russian-2025-12-16.tar.bz2 \
  --build-arg MODEL_SHA256=20e41e160efa6f2460a7ef6554cdbbb9e8fffb2b92e6bc708e9406bd8b9256ea \
  --build-arg MODEL_KIND=nemo_ctc \
  --build-arg MODEL_NAME=gigaam-v3-e2e-ctc \
  -t pluma-stt:gigaam-v3-e2e-ctc --load .
docker run --rm -d --name stt-try -p 127.0.0.1:9379:9379 --read-only \
  --memory=768m --memory-swap=768m --cpus=2 pluma-stt:gigaam-v3-e2e-ctc
```

и прогнать набор проверок (раздел «Проверка движка»), глядя на память (`docker stats stt-try`). Если контейнер падает при загрузке (код 137, `OOMKilled`), модели мало памяти — поднять `--memory` и запомнить число: оно пойдёт в `STT_MEMORY`.

**На сервер** образ попадает только из CI: сервер ничего не собирает (`docs/ops/deployment.md`), а CI собирает `pluma-stt` из значений по умолчанию `ARG MODEL_*` в `Dockerfile`. Поэтому смена модели — коммит:
1. В `teamgramd/deploy/stt/Dockerfile` поменять значения по умолчанию `ARG MODEL_URL`, `MODEL_SHA256`, `MODEL_KIND`, `MODEL_NAME`, `MODEL_LANGUAGE` на строку таблицы выше или на свои проверенные (и комментарий о модели). CI соберёт `ghcr.io/sckraaa/pluma-stt:<коммит>` вместе с остальными образами.
2. Перед выкладкой этого коммита в `.env` сервера: `STT_MODEL=<новый MODEL_NAME>`; если модели нужно больше памяти — `STT_MEMORY` из таблицы (и `STT_CPUS`, `STT_THREADS`), с пересчётом `docs/ops/memory.md`; если она медленнее — `STT_TIMEOUT`; если она говорит на другом языке — `STT_LANGUAGE`. `docker-compose.stt.yaml` на сервере не править: это файл репозитория, правка мешает следующей выкладке.
3. Выложить коммит как обычно (`pluma-deploy.sh`): он заменяет в `.env` тег текущего коммита на новый — в том числе у `PLUMA_STT_IMAGE`, если тег у него тот же, что у `pluma-server`, — вытягивает `pluma-stt` нового коммита, поднимает `stt` и перезапускает bff.
4. Проверить: `docker compose … ps stt` — `healthy`, в логе `stt` строка `model <имя> (<kind>) loaded`, голосовое в клиенте.

Вместо сборки можно примонтировать каталог модели с `model.yaml` и задать `STT_MODEL_DIR` (так удобно пробовать модели на машине сборки):

```yaml
name: gigaam-v3-e2e-ctc      # имя, на которое отвечает сервис (STT_MODEL)
kind: nemo_ctc
language: ""                  # язык модели; запрос с другим — 404; Whisper берёт STT_LANGUAGE
files:                        # необязательно: иначе ищутся по именам архивов sherpa-onnx
  model: model.int8.onnx
  tokens: tokens.txt
vad:
  model: silero_vad.onnx      # по умолчанию silero_vad.onnx рядом
  max_segment: 20             # секунд за проход, 5–30
```

Старые тексты остаются в `transcription_jobs` под прежним именем модели и не отдаются; новые запросы распознаются заново. Записи, которые в момент смены ждали в очереди, через минуту переходят на новую модель, и ожидающие получают её текст. Клиенты, уже сохранившие текст (Android — навсегда, iOS — в сообщении), сами его не перезапросят. Откат — выложить предыдущий коммит и вернуть прежний `STT_MODEL`: старые тексты снова отдаются из таблицы.

## Замена движка
Любой сервис с `POST /v1/audio/transcriptions` (speaches, LocalAI, удалённый сервис). Проверено со speaches 0.9.0-rc.3 и faster-whisper-small: протокол совместим без правки сервера, но эта модель теряет последнюю фразу записи, в 10 раз медленнее GigaAM и требует около 1,6 ГБ. Порядок: в `.env` поменять `STT_URL`, `STT_MODEL`, при необходимости `STT_TOKEN`, `STT_LANGUAGE` и `STT_TIMEOUT`, перезапустить bff; оверлей `stt` не поднимать. Что сервер требует от движка:
- запрос — multipart: поля `model`, `response_format=json`, `language` (если задан) и затем `file` (WAV, PCM s16le, 16 кГц, моно, любой длины); заголовок `Authorization: Bearer <STT_TOKEN>`, если токен задан;
- ответ 200 — JSON с полем `text` (пустая строка — речи нет); 400/415/422 — звук не разобрать, отказ окончательный; 503 и 429 — «занят», 401/403/404 — «недоступен» (ждём, не попытка); остальное — попытка, повтор позже;
- тайм-аут запроса — `STT_TIMEOUT`, по умолчанию 30 с плюс половина длительности записи; в него входит и время в очереди удалённого сервиса. Набор проверок требует, чтобы движок укладывался в половину этого срока;
- запись длиннее предела модели движок режет сам. Чужой движок с собственным пределом длины (413) — попытка: длинные записи на нём провалятся после `MaxAttempts`; у нашего `stt` предела нет.

## Проверка движка
Набор `pkg/transcribe/enginetest` проверяет любой движок через клиент и декодер сервера (на машине с Go и ffmpeg):

```bash
STT_ENGINE_URL=http://127.0.0.1:9379 STT_ENGINE_MODEL=gigaam-v3-e2e-rnnt \
STT_ENGINE_TOKEN=<токен> STT_ENGINE_SAMPLE=/путь/к/голосовому.ogg STT_ENGINE_TIMEOUT=<STT_TIMEOUT, если задан> \
STT_ENGINE_EXPECT=слово1,слово2 STT_ENGINE_STRICT=1 STT_ENGINE_LONG=25m \
go test -count=1 -timeout 60m -v ./pkg/transcribe/enginetest
```

`STT_ENGINE_STRICT=1` — только для нашего `stt`: он ещё проверяет отказ на не-WAV, пустой текст на тишине и «недоступен» на чужое имя модели. `STT_ENGINE_LONG` — дополнительно одна запись не короче заданного (образец по кругу с паузами): из неё ничего не должно пропасть, и движок должен уложиться в половину срока. Для `stt` на сервере порт не опубликован: запустить контейнер того же образа отдельно с `-p 127.0.0.1::9379`.

## Память и CPU
Потолок `stt` — 768 МБ без подкачки и 2 CPU (`STT_MEMORY`, `STT_CPUS`; `docker-compose.stt.yaml`, внутри `pluma.slice`, `docs/ops/memory.md`). Распознаётся одна запись за раз; занятый сервис отвечает 503, очередь держит bff. bff запускает ffmpeg и держит копию документа во временном файле на диске контейнера.

## Наблюдение
Метрики bff: `transcribe_requests_total{result}` (`cached`, `done`, `pending`, `failed`, `off`, `refused`, `internal`), `transcribe_jobs_total{result}` (`done`, `retry`, `busy`, `down`, `no_room`, `failed`, `rejected`, `lost`, `retired`), `transcribe_queue_depth`, `transcribe_oldest_job_seconds`, `transcribe_engine_seconds`, `transcribe_audio_seconds_total`, `transcribe_ratings_total{model,good}` — оценки людей по моделям, по ним видно, что модель плоха. Метрики `stt` (`stt_requests_total`, `stt_recognition_seconds`, `stt_audio_seconds_total`, `stt_model_info`) Prometheus находит по DNS (задача `ops.stt`); без сервиса цели нет.

## Алерты
- **`TranscriptionEngineDown`** — движок 5 минут нельзя использовать: никто не слушает `STT_URL`, или он отвергает токен, имя модели или язык. Записи ждут его, ничего не проваливается. `docker compose … ps stt`, `docker compose … logs --tail 50 stt bff`; сверить `STT_URL`, `STT_MODEL` (с `name` в `model.yaml` образа), `STT_TOKEN`, `STT_LANGUAGE` (в логе `stt` — `another language` или отказ запуска `speaks …`).
- **`TranscriptionNoDisk`** — 5 минут на диске временного каталога bff меньше, чем размер очередной записи плюс 1 ГиБ. Записи ждут, ничего не проваливается. `df -h` на хосте; в логе bff — `waits for free disk` с размерами; освободить место (кэш сборки Docker, старые образы, журналы).
- **`TranscriptionQueueStuck`** — запись ждёт текста больше 30 минут. Час речи занимает у движка минуты, поэтому такое ожидание — зависание или очередь, которую движок не успевает разбирать. Движок завис (сторожевой таймер сам завершает процесс, если кусок речи в модели дольше минуты плюс четырёх своих длин, Docker его поднимает) — поднять `stt`; задания дождутся. Очередь растёт (`transcribe_queue_depth`) — движку не хватает CPU: `STT_CPUS`, `STT_THREADS`.
- **`TranscriptionFailing`** — больше половины попыток за 30 минут неудачны (движок взял звук и не дал ответа, или звук отвергнут). Частые причины: движок не укладывается в `STT_TIMEOUT` (в логе bff — `context deadline exceeded`), падает на записях (500, в логе `stt` — `recognition`), записи не декодируются (в логе bff — ошибка ffmpeg).

## Что делать при сбое
- Движок остановлен или отвергает настройку: запросы ждут сколько угодно, кнопка крутится, пустых текстов нет. Поднять `stt` или исправить `.env` — записи распознаются по порядку, ожидающие получают текст обновлением.
- Движок берёт звук и падает (500, обрыв, тайм-аут): повторы 5 с, 30 с, 2 мин; после четвёртой попытки ожидающие получают пустой окончательный текст (Android: «слова не распознаны» навсегда, iOS и Web — ошибка). Новое нажатие после этого получает «в работе», и запись пробуется снова через 10 минут после провала (`FailedTTL`).
- Удалить текст одной записи: строка `transcription_jobs` по `document_id`; следующий запрос распознает её заново.

## Хранение
Тексты лежат в `transcription_jobs` бессрочно и не удаляются вместе с сообщением: документ может жить в других копиях и пересылках (решение владельца 2026-11-12). Они попадают в резервные копии вместе с базой.
