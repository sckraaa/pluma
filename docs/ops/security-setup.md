# Первичная настройка: ключ сервера и секреты

Что сделать один раз при установке сервера, до выдачи клиентов. Основание — задача `docs/tasks/001-security-p0.md`, ADR 0003.

## 1. RSA-ключ сервера

Клиент шифрует этим ключом начало handshake. Публичная часть вшивается в каждый клиент, приватная есть только у сервера. Кто владеет приватной частью, может выдать себя за сервер (MITM при создании auth_key).

Ключ из upstream teamgram (`teamgramd/bin/server_pkcs1.key`, fingerprint `12240908862933197005` = `0xa9e071c1771060cd`) лежал в git, поэтому **считается скомпрометированным навсегда**. Из репозитория он удалён, историю не переписывали. Клиенты с этим ключом не использовать.

Сгенерировать свой ключ (из корня репозитория):

```bash
go run ./tools/genserverkey -out secrets/server_pkcs1.key
```

- Файл создаётся с правами `0600`. Существующий файл утилита не перезаписывает: новый ключ ломает все клиенты со старым.
- `secrets/` в `.gitignore` и `.dockerignore`: ключ не попадёт ни в git, ни в образ. В контейнер он монтируется как compose secret (`/run/secrets/server_pkcs1.key`).
- Сделайте офлайн-копию ключа (например, в менеджере паролей). Потеря ключа = пересборка всех клиентов.

Утилита печатает:

| Что | Куда |
|---|---|
| `KeyFingerprint` (беззнаковое десятичное) | `.env` → `SERVER_RSA_KEY_FINGERPRINT` |
| hex fingerprint (`0x…`) | Android: `serverPublicKeysFingerprints` в `TMessagesProj/jni/tgnet/Handshake.cpp` |
| PEM `BEGIN RSA PUBLIC KEY` | iOS (MtProtoKit), Android (tgnet), Desktop (`kPublicRSAKeys`) — см. `docs/audit/04-clients-and-builds.md` |
| `modulus` / `exponent` в hex | Web K: `publisKeysHex` в `src/lib/mtproto/rsaKeysManager.ts` |

Повторно вывести эти данные (или проверить ключ, вшитый в патч клиента): `go run ./tools/genserverkey -show <файл>`. Принимается приватный ключ или публичный (PKCS#1 или PKIX).

### Проверки при старте gnetway (и httpserver)

Сервис не запустится и напишет причину, если:
- файл ключа отсутствует, не читается или это не обычный файл;
- файл доступен «прочим» пользователям (любые биты `o`; лечится `chmod 600`). Чтение группой (`0640`) допустимо;
- ключ не PKCS#1 PEM (`BEGIN RSA PRIVATE KEY`), зашифрован или не 2048 бит (другие размеры клиенты Telegram не поддерживают);
- fingerprint ключа не совпадает с `KeyFingerprint` в конфиге (например, оставили старое значение после генерации);
- список `RSAKey` пуст или ключ указан дважды.

## 2. Пароли инфраструктуры (`.env`)

```bash
cp .env.example .env && chmod 600 .env
openssl rand -hex 24   # по одному значению на каждый пароль
```

Заполните все пустые значения. Пока хоть одно пустое, `docker compose` откажется запускаться с ошибкой `required variable … is missing a value`. Используйте только hex: значения подставляются в YAML и DSN как есть.

| Переменная | Назначение |
|---|---|
| `MYSQL_ROOT_PASSWORD` | root MySQL, только для администрирования |
| `MYSQL_PASSWORD` | пользователь `teamgram`, под которым ходят сервисы |
| `REDIS_PASSWORD` | `requirepass` Redis |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | ключ S3 dfs в Garage: `GK` + 24 hex и 64 hex (ADR 0014) |
| `GARAGE_RPC_SECRET`, `GARAGE_ADMIN_TOKEN` | секреты узла Garage, по `openssl rand -hex 32` |
| `GRAFANA_ADMIN_PASSWORD` | вход в Grafana |
| `SERVER_RSA_KEY_FILE` | путь к ключу на хосте, по умолчанию `./secrets/server_pkcs1.key` |
| `SERVER_RSA_KEY_FINGERPRINT` | fingerprint из `genserverkey` |
| `LOGIN_CODE_HMAC_KEY` | ключ HMAC для хранения кодов входа (`openssl rand -hex 32`, не короче 32 символов), см. раздел 7 |

Конфиги сервисов (`teamgramd/etc2`, `teamgramd/etc`) берут секреты из окружения через `${ИМЯ}`. Если переменная не задана, сервис не стартует и называет её. В ошибках фигурируют только имена переменных, без значений. Конфиг целиком в лог при старте больше не пишется.

## 3. Запуск в Docker

```bash
docker compose -f docker-compose-env.yaml up -d   # инфраструктура
docker compose -f docker-compose-env.yaml ps      # дождаться healthy у mysql, redis, kafka и etcd (Garage без healthcheck: его ждёт storage-init)
docker compose up -d --build                      # сервисы teamgram
```

Сервисы подключаются к Kafka при старте и без неё не работают, поэтому запускайте их, когда инфраструктура healthy. Контейнер `teamgram` сам становится healthy, когда запущены все 11 сервисов и gateway принимает соединения (`docker compose ps`).

Сеть:
- Наружу опубликованы только порты клиентов: `10443` и `5222` (MTProto TCP), `11443` (WebSocket для веб-клиентов), и только по IPv4 (`0.0.0.0:…`). Сеть `teamgram_net` без IPv6: если опубликовать порт и на IPv6, Docker проводит такие соединения через docker-proxy, и gateway видит всех IPv6-клиентов как один адрес моста (`172.20.0.1`). Тогда один клиент исчерпывает лимиты входа «по IP» для всех IPv6-пользователей, а в уведомлениях о входе и в `pluma-admin` стоит адрес моста. Нужен IPv6 — сначала включите его в `teamgram_net` (или запустите gnetway с `network_mode: host`), чтобы до gateway доходили настоящие адреса. Адреса IPv6 лимиты считают по /64.
- Gateway должен видеть настоящий адрес клиента. Если перед ним стоит TLS-терминатор или балансировщик (например, для WebSocket веб-клиентов), он должен передавать адрес по PROXY protocol, иначе все клиенты за ним — один адрес для лимитов входа.
- Внутренние gRPC-порты (`20xxx`), метрики и dfs HTTP доступны только внутри сети `teamgram_net`.
- Порты для администрирования привязаны к `127.0.0.1`: MySQL 3306, Redis 6379, etcd 2379, Garage S3 3900, Kafka 9092/9094, Grafana 3001, Prometheus 9090, Alertmanager 9093, Jaeger 16686/14268. С другой машины к ним ходят через SSH-туннель: `ssh -L 3001:127.0.0.1:3001 user@server`.
- Публикация портов в Docker обходит ufw/iptables INPUT. Поэтому любой новый порт добавляйте с `127.0.0.1:`, если он не должен быть открыт в интернет.

Проверить итоговую публикацию портов: `docker compose config | grep -A3 ports` (или `docker ps`).

## 4. Обновление существующей установки

- **MySQL:** переменные `MYSQL_*` применяются только при первой инициализации (пустой `./data/mysql`). Для уже созданной базы смените пароли вручную:
  ```sql
  ALTER USER 'teamgram'@'%' IDENTIFIED BY '<MYSQL_PASSWORD>';
  ALTER USER 'root'@'%' IDENTIFIED BY '<MYSQL_ROOT_PASSWORD>';
  ALTER USER 'root'@'localhost' IDENTIFIED BY '<MYSQL_ROOT_PASSWORD>';
  ```
- **Grafana:** пароль из переменной действует только для нового тома: `docker exec grafana grafana-cli admin reset-admin-password <пароль>`.
- **Redis:** новый пароль применяется после перезапуска контейнера. **Garage:** новый ключ S3 dfs `storage-init` не заменит (ключ с другим секретом — ошибка): удалить старый ключ в Garage (`docker compose -f docker-compose-env.yaml exec garage /garage key delete --yes <id>`), затем `docker compose up storage-init`.
- **Ключ:** клиенты со старым (скомпрометированным) ключом перестанут подключаться. Их нужно пересобрать с новым публичным ключом.
- **Временные ключи (PFS):** до запуска новой версии authsession примените `mysql -uroot -p teamgram < teamgramd/deploy/sql/migrate-20261021-pfs.sql` (колонка `auth_key_infos.expires_at`). Без неё authsession не прочитает ни один ключ, и клиенты не подключатся. Новая база получает колонку сама. Миграция также гасит все временные ключи, созданные до неё: их привязки записывал старый `auth.bindTempAuthKey`, который ничего не проверял, так что любая из них могла быть подделана. Клиенты получат -404 и создадут новые временные ключи; постоянные ключи и входы сохраняются. Ключи, которые старые версии teamgram держали только в Redis (`auth_keys_<id>`), больше не читаются.
- **Если старая установка была доступна из интернета** (MySQL и Redis без паролей были опубликованы до задачи 001), в базу и Redis мог писать кто угодно: подделать привязки, ключи, коды. После обновления завершите все сессии: при остановленных сервисах `DELETE FROM auth_users; DELETE FROM auths; DELETE FROM auth_key_infos; DELETE FROM auth_keys;` и удалите их кэш в Redis (`redis-cli -a "$REDIS_PASSWORD" --scan --pattern 'auth_*' | xargs -r redis-cli -a "$REDIS_PASSWORD" del`; не `FLUSHALL`: в Redis лежат pts и счётчики id). Всем пользователям придётся войти заново, зато не останется ключей, которые мог создать посторонний. Проверьте и `phone_allowlist`.

## 5. Запуск без Docker (`teamgramd/etc`)

`teamgramd/bin/runall2.sh` подхватывает переменные из `.env` в корне репозитория. Ключ берётся из `secrets/server_pkcs1.key` (в конфиге путь `../../secrets/server_pkcs1.key` относительно `teamgramd/bin`).

Сервисы подключаются к MySQL пользователем `teamgram`, а не `root`, и передают Redis пароль `REDIS_PASSWORD`. На хосте их нужно завести один раз:

```sql
CREATE USER IF NOT EXISTS 'teamgram'@'localhost' IDENTIFIED BY '<MYSQL_PASSWORD>';
GRANT ALL PRIVILEGES ON teamgram.* TO 'teamgram'@'localhost';
FLUSH PRIVILEGES;
```

В `redis.conf` задайте `requirepass <REDIS_PASSWORD>` и перезапустите Redis (или `CONFIG SET requirepass …` и `CONFIG REWRITE`). Без этого сервисы не стартуют: `Access denied for user 'teamgram'` или ошибка `AUTH` в Redis.

Все внутренние порты в `teamgramd/etc` слушают только `127.0.0.1`, включая HTTP dfs (`11701`, его читает ffmpeg самого dfs; без аутентификации). Открытыми в интернет на хосте могут быть только порты клиентов (`10443`, `5222`, `11443` и HTTP-транспорт, если он нужен); остальное закройте файрволом. Тест `pkg/conf` (`TestDeployListeners`) не даёт добавить в `teamgramd/etc` другой слушатель на `0.0.0.0`.

## 6. Ротация ключа

1. Сгенерируйте новый ключ в отдельный файл: `go run ./tools/genserverkey -out secrets/server_pkcs1.next.key`.
2. Добавьте его в `RSAKey` второй записью (`teamgramd/etc2/gnetway.yaml`) со своей переменной fingerprint. Пропишите в `docker-compose.yaml` второй secret и переменную, а в `.env.example` — переменную. Gateway объявляет в `resPQ` оба fingerprint, и клиенты с любым из ключей работают.
3. Выпустите клиенты с новым публичным ключом.
4. Когда старых клиентов не останется, уберите старый ключ из конфига и удалите файл.

## 7. Вход: allowlist номеров и коды

Регистрация закрытая. Войти или зарегистрироваться можно только с номера из allowlist (таблица `phone_allowlist` в MySQL). На любой другой номер `auth.sendCode`, `auth.signIn`, `auth.signUp`, `auth.resendCode`, `auth.cancelCode` и `account.sendChangePhoneCode`/`account.changePhone` отвечают `PHONE_NUMBER_INVALID`. Есть ли у номера аккаунт, по ответу не понять. Фиксированного кода (`12345`) и SMS-провайдера больше нет.

**Как доставляется код** (6 цифр из `crypto/rand`; у Telegram 5, но официальные клиенты берут длину поля из `auth.sentCodeType*.length`):
- У аккаунта есть другая авторизованная сессия. Код приходит сообщением от служебного аккаунта (777000) в приложение, клиенту отвечаем `auth.sentCodeTypeApp`, как Telegram. Если пользователь нажмёт «отправить по SMS» (`auth.resendCode`), запрос переходит к администратору.
- Других сессий нет (первое устройство, новый аккаунт, смена номера). Клиент видит «код отправлен по SMS» (`auth.sentCodeTypeSms`), но ничего не отправляется: администратор выдаёт код вручную. До этого никакой код не подходит.

Код хранится в Redis только как HMAC-SHA256 на ключе `LOGIN_CODE_HMAC_KEY`. Открытого кода нет ни в Redis, ни в логах. Код живёт 10 минут после выдачи, запрос (`phone_code_hash`) — 1 час.

**Лимиты** (ответ `FLOOD_WAIT_X`, счётчики в Redis). Лимиты «с IP» рассчитаны на то, что вся группа может входить с одного адреса (офис, семья, NAT): они считают только промахи или заведомо выше нужного группе.

| Что | Лимит |
|---|---|
| Запросы кода (`sendCode`, `resendCode`, `sendChangePhoneCode`) на номер с одного адреса | 5 в час |
| … на номер всего | 20 в час |
| … на auth key | 10 в час |
| … с IP (все запросы) | 200 в час |
| Номера не из allowlist (в любом методе с номером) с IP | 30 в час |
| Проверки номера по allowlist в `signIn`, `signUp`, `cancelCode`, `changePhone` | 30 в час на auth key |
| Неверные коды (`signIn`, `changePhone`) на номер | 5 в час, 10 в сутки, 30 за 30 дней |
| Неудачные проверки кода с IP (неверный код, неизвестный или истёкший запрос) | 30 в час |
| Проверок на один `phone_code_hash` | 5, дальше `PHONE_CODE_EXPIRED` |

Верный код в лимиты не засчитывается. На номер считаются только сравнения с живым кодом: проверки запроса без кода (ждёт администратора, истёк, чужой) номер не блокируют. При 6 цифрах и 30 попытках в месяц подбор кода к одному номеру — около 0,04% в год, ко всей группе из 100 номеров — около 3,6% в год при атаке на всех сразу. Настоящая защита — пароль 2FA (задача 008). Если неверных кодов по всем номерам больше 50 за сутки, bff пишет в лог ошибку `possible brute force`.

Обратная сторона лимитов: кто знает номер из allowlist, может исчерпать его общие лимиты (20 запросов кода в час с 4 и больше адресов или неверные коды на собственном запросе к номеру, если у владельца есть активная сессия), и владелец получит `FLOOD_WAIT`. Снимается командой `login-unblock` (ниже).

При недоступном Redis или MySQL вход не работает (fail closed).

**Администрирование** — `tools/pluma-admin`. Утилита берёт MySQL и Redis из конфига bff, секреты — из окружения.

```bash
# на хосте, из корня репозитория (MySQL и Redis слушают 127.0.0.1)
set -a; . ./.env; set +a
go run ./tools/pluma-admin allowlist add +79991234567 Иван Петров
go run ./tools/pluma-admin allowlist list
go run ./tools/pluma-admin allowlist remove +79991234567
go run ./tools/pluma-admin login-code +79991234567
go run ./tools/pluma-admin login-code +79991234567 3fa1c2d9   # если запросов несколько
go run ./tools/pluma-admin login-unblock +79991234567
go run ./tools/pluma-admin login-unblock 203.0.113.7

# или внутри контейнера
docker compose exec teamgram /app/bin/pluma-admin -f /app/etc2/bff.yaml login-code +79991234567
```

`login-code` работает только после того, как пользователь ввёл номер в приложении. Запрос кода может сделать любой, кто знает номер, поэтому команда не выбирает «последний» запрос сама. Если ожидающий запрос один, она создаёт для него новый код (предыдущий перестаёт действовать) и печатает его вместе со временем и IP запроса. Если запросов несколько, она печатает таблицу (ID, время, адрес, использованные проверки) и ничего не выдаёт: спросите владельца, когда и откуда он запрашивал код, и повторите команду с ID нужного запроса. Передайте код только владельцу номера по доверенному каналу. Повторно код не показать: при необходимости выдайте новый.

Код действует 10 минут, но не дольше самого запроса (1 час с момента запроса): напечатанное время — настоящее. Для запроса, которому осталось меньше 3 минут или в котором уже исчерпаны 5 проверок, команда код не выдаёт и просит пользователя запросить новый в приложении.

`login-unblock <номер>` обнуляет лимиты номера: запросы кода и неверные коды (пользователь получает `FLOOD_WAIT` на любую попытку входа). `login-unblock <IP>` — лимиты адреса (для IPv6 — его /64). Сначала выясните, откуда шли запросы: если номер блокирует посторонний, разблокировка поможет только до следующей его серии.

`allowlist remove` не завершает уже открытые сессии: их закрывают в приложении (Настройки → Устройства).

**Обновление существующей установки.** Новая база создаёт таблицу сама (`teamgramd/deploy/sql/migrate-20261021.sql`). В уже работающей примените миграцию вручную: `mysql -uroot -p teamgram < teamgramd/deploy/sql/migrate-20261021.sql`. Она переносит в allowlist номера всех существующих обычных аккаунтов. Тестовые аккаунты (`user_type = 5`) не переносятся: их номера добавьте командой `allowlist add`, если они нужны. Затем задайте `LOGIN_CODE_HMAC_KEY` в `.env`: без него bff не запустится.

## 8. Логи

Во всех конфигах `Log.Level: info`. Для разбора проблем уровень можно поднять до `debug` в конфиге нужного сервиса и перезапустить его. Ни на каком уровне в лог не попадают: секреты handshake (`new_nonce`, `a`, `g_b`, временные AES-ключи, расшифрованные данные), байты auth key и ключи сообщений, коды входа и `phone_code_hash`, токены QR-входа, пароли и конфиги с паролями, тексты и медиа сообщений, контакты и номера телефонов. Вместо объектов пишутся id, размеры и типы. При ошибке расшифровки gateway пишет только `auth_key_id`, длину и номер соединения.

go-zero сам по себе пишет тела RPC-запросов, SQL с подставленными значениями и аргументы медленных команд Redis. Это отключается при старте каждого сервиса (`pkg/logpolicy`, вызывается из загрузки конфига). Медленные RPC по-прежнему видны в логе, но только по имени метода; метрики длительности SQL go-zero при этом не собирает.

Регрессию ловит тест `tools/logaudit` (входит в `go test ./...`): он ищет в коде логирование секретов, TL-объектов целиком и дампов байтов. Если находка не утечка, вызов помечается комментарием `// logaudit:ok <причина>`.

## Что ещё не закрыто

etcd, Kafka и Elasticsearch/Kibana работают без аутентификации. Они не опубликованы наружу, но доступны любому контейнеру в `teamgram_net`. Между сервисами нет TLS. Это задачи следующих этапов (см. `docs/audit/02-transport-and-security.md`, #6).
