# Состояние ящиков пользователей (`user_state`)

Счётчики общего ящика пользователя (`pts`, `user_message_box_id`; позже `qts` и `seq`) хранятся в MySQL, в таблице `user_state`, и меняются только в транзакции, которая пишет сами данные и строки журнала `user_pts_updates`. Код — `pkg/userbox`, решение — ADR 0011, задача — `docs/tasks/002-durable-sequences.md`. Redis эти счётчики больше не хранит, idgen к Redis не подключается (выдаёт только snowflake-id).

Кто пишет: msg (отправка, правка, удаление, прочтение, закреп — в RPC; доставка получателям — в inbox-консьюмере, по транзакции на событие, которая и удаляет строку события `mq_outbox`) и biz dialog (перестановка закреплённых диалогов, TTL и тема чата). `updates.getState`/`getDifference` читают закоммиченное состояние и журнал до него. Правила кода внутри транзакции проверяет `tools/boxaudit` (запускается `go test`).

## Требования к MySQL

Настройки проверяет `userbox.Check`: msg и biz вызывают её при старте и не запускаются, если настройка неверна. Ошибка называет переменную. msg, кроме того, не запускается при `MessageSharding` больше 1: транзакции ящика и миграция знают одну таблицу `messages`.

| Переменная | Значение | Зачем |
|---|---|---|
| `innodb_lock_wait_timeout` (сессия) | не больше 2 с: параметр `innodb_lock_wait_timeout=2` в DSN сервиса | ожидание блокировки строки пользователя обрывается сервером ошибкой 1205, и транзакция повторяется; отменённый запрос не держит транзакцию на сервере дольше 2 с |
| `innodb_flush_log_at_trx_commit` | 1 (по умолчанию) | клиент видит `pts` сразу после commit; commit, потерянный при сбое MySQL, откатил бы `pts` под клиентом |
| `binlog_format` при включённом binlog | `ROW` (по умолчанию) | транзакции ящика идут в READ COMMITTED, ему нужен построчный binlog |
| `sync_binlog` при включённом binlog | 1 (по умолчанию) | то же, что `innodb_flush_log_at_trx_commit` |

В DSN не должно быть `clientFoundRows=true`: по `RowsAffected` upsert-а код отличает создание строки от изменения.

Реплики чтения (`ReadDSN` в секции `Mysql`) для ящиков не используются: `user_state` и журнал `user_pts_updates` читаются с мастера (DSN записи). `getDifference`, прочитавший состояние с мастера, а журнал с отстающей реплики, отдал бы `pts` без строк до него, и клиент потерял бы эти обновления.

## Дедлайны RPC

Запрос, за которым транзакция ящика, должен жить дольше неё, иначе ожидание блокировки занятого пользователя заканчивается голым `DeadlineExceeded`, а `COMMIT`, успевший пройти, отвечает клиенту ошибкой. Значение 0 (без дедлайна) запрещено: такой запрос может висеть вечно (ADR 0012, п. 9). При старте проверяет `userbox.CheckRPCTimeout`; всю цепочку «клиент ждёт не меньше сервера» — тест `TestRPCTimeouts` в `pkg/conf`.

| Где | Значение в `teamgramd/etc*` | Почему |
|---|---|---|
| `Timeout` msg | 40000 | `MaxRequestTime` msg = 26 с плюс запрос до транзакции |
| `MsgClient.Timeout` в bff | 45000 | не меньше сервера msg |
| `Timeout` biz, `BizServiceClient.Timeout` в bff | 30000 | `dialog.MaxBoxOpTime` = 26 с |
| `BizServiceClient.Timeout` в msg, `ChatClient.Timeout` в sync | 5000 | только чтения |
| клиенты idgen, status, authsession, `SessionClient` sync | 2000 | короткие вызовы; повторы и resync — у вызывающего |
| `Timeout` media и dfs, `MiniHttp` dfs, клиенты media и dfs | 120000 | загрузка и обработка больших файлов |
| `Timeout` bff, `BFFProxyClients` в session | 150000 | не меньше любого вызова bff |

Образ MySQL из `docker-compose-env.yaml` (8.0) с параметрами по умолчанию требованиям сервера удовлетворяет; это проверяет интеграционный тест `TestCheckServerSettings` в `pkg/userbox`.

## Миграция `teamgramd/deploy/sql/migrate-20261022-dialog-index.sql`

Заменяет индекс `messages.user_id (user_id, dialog_id1, dialog_id2)` на `(user_id, dialog_id1, dialog_id2, deleted, user_message_box_id)`: верхнее сообщение диалога и непрочитанные читаются из индекса, а не перебором всех сообщений диалога под блокировкой ящика. Online DDL (`ALGORITHM=INPLACE, LOCK=NONE`): чтение и запись `messages` идут, пока строится индекс. Время — порядка построения индекса по всей `messages`. Повторный прогон строит тот же индекс заново.

## Миграция `teamgramd/deploy/sql/migrate-20261022.sql`

Что делает:
1. создаёт `user_state` (на свежей установке таблица остаётся пустой: строка пользователя появляется при первой записи в его ящик);
2. удаляет дубли `(user_id, pts)` в `user_pts_updates`, оставляя самую новую строку, и делает индекс `user_id (user_id, pts)` уникальным;
3. добавляет строку каждому существующему пользователю: `pts` и `last_message_box_id` на 1 000 000 выше максимума в журнале и в `messages`. Клиенты могли видеть значения Redis-счётчиков выше записанного в MySQL; скачок вперёд стоит каждому устройству одного `updates.getDifference`, а шаг назад сломал бы доставку.

Повторный прогон ничего не меняет: существующие строки `user_state` не трогаются. Поднять отставшие строки (после отката на старую версию или восстановления из резервной копии) — отдельная команда обслуживания (ADR 0011, п. 11).

**Время.** Уникальный индекс строится по всей `user_pts_updates`. Перед окном оценить размер:

```sql
SELECT table_rows, data_length FROM information_schema.tables
WHERE table_schema = 'teamgram' AND table_name = 'user_pts_updates';
```

Тест `TestMigrationSpeed` (`pkg/userbox`, тег `integration`) печатает скорость миграции. Замер на MacBook (colima, MySQL в tmpfs): 50 000 строк журнала по ~300 Б JSON — 0,7 с, около 70 000 строк в секунду. На сервере с диском скорость ниже; для оценки окна прогнать тест на целевом хосте.

## Миграция `teamgramd/deploy/sql/migrate-20261023-delivery.sql`

Задача 003, ADR 0012. Что делает:
1. создаёт `mq_outbox` — события транзакций ящика до применения (inbox) или публикации (push);
2. отвязывает копии без связи с отправителем (`dialog_message_id = 0`) и повторные копии одного сообщения у одного пользователя (первая по `user_message_box_id` остаётся связанной): `dialog_message_id = -id`;
3. у повторных исходящих с одним `random_id` (повтор клиента после окна Redis) обнуляет `random_id`, первое сообщение его сохраняет;
4. добавляет колонки `messages.pts` (у старых строк 0) и генерируемую `out_random_id`, уникальные индексы `user_dialog_message (user_id, dialog_message_id)` и `user_out_random (user_id, out_random_id)` — online DDL.

Строки и журнал не удаляются: клиенты, показавшие повторы, видят те же сообщения. Повторный прогон ничего не меняет (каждый `ALTER` выполняется, только если его результата ещё нет). Время — построение двух индексов по всей `messages`; `TestDeliveryMigrationSpeed` (`pkg/outbox`, тег `integration`) печатает скорость. Замер на MacBook (colima, MySQL в tmpfs): 100 000 строк — 0,65 с, около 150 000 строк в секунду; на сервере с диском медленнее.

## Порядок обновления

Выкатывать пользователям 002 и 003 — одним окном (002 без 003 не выкатывается: ADR 0011, п. 9, ADR 0012, п. 11) и только вместе с доставкой алертов (задача 004). Формат inbox-событий изменился (получатель — `user_id`; копия в Kafka — только ссылка на строку `mq_outbox`), старые события новая версия не обработает; число партиций топиков меняется с 3 на 16.

1. Остановить gnetway (закрыть вход клиентов).
2. Дождаться нулевого лага обеих групп старой версией: в контейнере kafka `/opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9094 --describe --group Inbox-MainCommunity-S` (и `Sync-MainCommunity-S`), колонка `LAG` равна 0 по всем партициям.
3. Остановить сервисы, сделать резервную копию MySQL.
4. Применить `migrate-20261022-dialog-index.sql`, `migrate-20261022.sql` и `migrate-20261023-delivery.sql` (в этом порядке, как их сортирует имя).
5. Удалить группы (иначе они хранят offset-ы старых партиций): `kafka-consumer-groups.sh --bootstrap-server localhost:9094 --delete --group Inbox-MainCommunity-S`, то же для `Sync-MainCommunity-S`.
6. Удалить `Inbox-T` и `Sync-T` (по шагу 2 они пусты): `kafka-topics.sh --bootstrap-server localhost:9094 --delete --topic Inbox-T`, то же для `Sync-T`; дождаться, пока они исчезнут из `kafka-topics.sh --list` (удаление в KRaft асинхронное).
7. Создать топики: `docker compose up kafka-init` (или `teamgramd/deploy/kafka/topics.sh <брокер>` без Docker). Брокер больше не создаёт топики сам (`KAFKA_AUTO_CREATE_TOPICS_ENABLE=false`).
8. Выкатить новую версию (DSN msg и biz с `innodb_lock_wait_timeout=2`, idgen без `SeqIDGen`, секции `Topics`, `Relay`, `InboxConsumer` msg и `SyncClient` bff — уже в `teamgramd/etc*`) и запустить.

После обновления каждое устройство один раз получит скачок `pts` и сделает `updates.getDifference`.

## Доставка событий: `mq_outbox`

Событие транзакции ящика — строка `mq_outbox`, записанная той же транзакцией (ADR 0012). Relay в процессе msg публикует строки в Kafka по возрастанию `id` (одновременно публикует один relay базы: блокировка `GET_LOCK`); push-строку он удаляет после ответа брокера, inbox-строку удаляет транзакция получателя, применившая событие. Ни msg, ни bff, ни sync не ждут Kafka при старте: без брокера строки копятся в таблице и уходят после его возвращения.

Строки, которые не уходят сами:
- **dead** — событие не применилось после трёх попыток с детерминированной ошибкой (или строка блокировала полосу получателя); **parked** — более поздние события того же получателя. Relay повторяет такие полосы сам: через 15 мин, 30 мин, 1 ч… до 4 ч и при каждом старте msg. Исправили причину — `pluma-admin outbox replay -user <id>` (по порядку `id`, счётчик повторов с нуля); событие не нужно доставлять — `outbox discard -id <id>`, затем `replay` для оставшихся. Посмотреть — `outbox list -state dead` (без содержимого).
- **pending/published долго** — нет брокера, топик не готов (нет 16 партиций) или консьюмер стоит: метрики relay и консьюмера (`outbox_*`, `mq_consumer_*`, ADR 0012, п. 10).

`id` строк не переиспользуется: `TRUNCATE` и пересоздание `mq_outbox` запрещены.

## Обслуживание: `pluma-admin`

Команды запускаются с конфигом bff (MySQL и Redis, `-f`), как остальные команды `pluma-admin`.

| Команда | Когда |
|---|---|
| `state-raise -by 1000000 [-user <id>]` | после восстановления MySQL из резервной копии и при повторном обновлении после отката, **при остановленных msg и biz**: `pts` и `last_message_box_id` всех (или одного) поднимаются на запас выше максимума в журнале и в `messages`, недостающие строки добавляются; без `-user` ещё и AUTO_INCREMENT `mq_outbox` поднимается на 10⁹ (копии в Kafka не должны совпасть по `id` с новыми событиями) |
| `state-export-legacy -margin 1000000` | откат на версию до 002, **при остановленных сервисах**: счётчики каждой строки `user_state` плюс запас пишутся в Redis в ключи старой версии (`pts_updates_ngen_<u>`, `message_box_ngen_<u>`; `SET`, не `INCR`). Redis — из секции `KV` конфига (в поставляемых конфигах это тот же сервер, что `SeqIDGen` старого idgen) |
| `verify-pts [-after <pts>] <user id>` | в любой момент: дыры и пересечения журнала пользователя до закоммиченного `pts`. Одна дыра размером с запас миграции или `state-raise` — это скачок, а не потеря |

**Откат на версию до 002** (ADR 0011, п. 11): остановить gnetway; дождаться, что в `mq_outbox` нет строк pending и published (`pluma-admin outbox list -state pending`, то же для `published`), а dead и parked разобраны (события нового формата должна обработать новая версия); остановить сервисы, сделать резервную копию; `pluma-admin state-export-legacy -margin 1000000`; вернуть `SeqIDGen` в конфиг idgen, выкатить старую версию и запустить. Таблицы `user_state`, `mq_outbox` и уникальные индексы остаются, старая версия `mq_outbox` не читает.

**Повторное обновление после отката:** миграция (ничего не меняет), затем до запуска — `pluma-admin state-raise -by 1000000`, затем запуск.

**Восстановление MySQL из резервной копии:** клиенты видели `pts` и id новее копии. После восстановления и до запуска сервисов — `pluma-admin state-raise -by 1000000` (поднимает и `id` событий) и перевод offset-ов обеих групп на конец: `kafka-consumer-groups.sh --bootstrap-server localhost:9094 --reset-offsets --to-latest --execute --group Inbox-MainCommunity-S --topic Inbox-T`, то же для `Sync-MainCommunity-S` и `Sync-T`. Строки pending и published из копии relay опубликует заново, получатели применят их один раз.
