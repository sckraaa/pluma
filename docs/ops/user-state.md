# Состояние ящиков пользователей (`user_state`)

Счётчики общего ящика пользователя (`pts`, `user_message_box_id`; позже `qts` и `seq`) хранятся в MySQL, в таблице `user_state`, и меняются только в транзакции, которая пишет сами данные и строки журнала `user_pts_updates`. Код — `pkg/userbox`, решение — ADR 0011, задача — `docs/tasks/002-durable-sequences.md`. Redis эти счётчики больше не хранит, idgen к Redis не подключается (выдаёт только snowflake-id).

Кто пишет: msg (отправка, правка, удаление, прочтение, закреп — в RPC; доставка получателям — в inbox-консьюмере, по транзакции на событие) и biz dialog (перестановка закреплённых диалогов, TTL и тема чата). `updates.getState`/`getDifference` читают закоммиченное состояние и журнал до него. Правила кода внутри транзакции проверяет `tools/boxaudit` (запускается `go test`).

## Требования к MySQL

Настройки проверяет `userbox.Check`: msg и biz вызывают её при старте и не запускаются, если настройка неверна. Ошибка называет переменную. msg, кроме того, не запускается при `MessageSharding` больше 1: транзакции ящика и миграция знают одну таблицу `messages`.

| Переменная | Значение | Зачем |
|---|---|---|
| `innodb_lock_wait_timeout` (сессия) | не больше 2 с: параметр `innodb_lock_wait_timeout=2` в DSN сервиса | ожидание блокировки строки пользователя обрывается сервером ошибкой 1205, и транзакция повторяется; отменённый запрос не держит транзакцию на сервере дольше 2 с |
| `innodb_flush_log_at_trx_commit` | 1 (по умолчанию) | клиент видит `pts` сразу после commit; commit, потерянный при сбое MySQL, откатил бы `pts` под клиентом |
| `binlog_format` при включённом binlog | `ROW` (по умолчанию) | транзакции ящика идут в READ COMMITTED, ему нужен построчный binlog |
| `sync_binlog` при включённом binlog | 1 (по умолчанию) | то же, что `innodb_flush_log_at_trx_commit` |

В DSN не должно быть `clientFoundRows=true`: по `RowsAffected` upsert-а код отличает создание строки от изменения.

Реплики чтения (`ReadDSN` в секции `Mysql`) для ящиков не используются: `user_state` и журнал `user_pts_updates` читаются с мастера (DSN записи). `getDifference`, прочитавший состояние с мастера, а журнал с отстающей реплики, отдал бы `pts` без строк до него, и клиент потерял бы эти обновления.

## Дедлайны RPC

Запрос, за которым транзакция ящика, должен жить дольше неё, иначе ожидание блокировки занятого пользователя заканчивается голым `DeadlineExceeded`, а `COMMIT`, успевший пройти, отвечает клиенту ошибкой. Проверяет `userbox.CheckRPCTimeout` при старте: значение 0 (без дедлайна) или не меньше длительности операции, иначе сервис не запускается.

| Где | Значение в `teamgramd/etc*` | Нужно не меньше |
|---|---|---|
| `Timeout` biz | 30000 | `dialog.MaxBoxOpTime` = 26 с (сброс кэша 5 с, `Run` до 16 с, сброс кэша 5 с) |
| `BizServiceClient.Timeout` в bff | 30000 | то же |
| `Timeout` msg | 0 | `MaxRequestTime` msg = 66 с (шаги идемпотентности в Redis, `Run`, публикация событий до 20 с) |
| `MsgClient.Timeout` в bff | 0 | то же (не проверяется при старте: держать 0) |

Образ MySQL из `docker-compose-env.yaml` (8.0) с параметрами по умолчанию требованиям сервера удовлетворяет; это проверяет интеграционный тест `TestCheckServerSettings` в `pkg/userbox`.

## Миграция `teamgramd/deploy/sql/migrate-20261022-dialog-index.sql`

Заменяет индекс `messages.user_id (user_id, dialog_id1, dialog_id2)` на `(user_id, dialog_id1, dialog_id2, deleted, user_message_box_id)`: верхнее сообщение диалога и непрочитанные читаются из индекса, а не перебором всех сообщений диалога под блокировкой ящика. Online DDL (`ALGORITHM=INPLACE, LOCK=NONE`): чтение и запись `messages` идут, пока строится индекс. Время — порядка построения индекса по всей `messages`. Повторный прогон строит тот же индекс заново.

## Миграция `teamgramd/deploy/sql/migrate-20261022.sql`

Что делает:
1. создаёт `user_state` (на свежей установке таблица остаётся пустой: строка пользователя появляется при первой записи в его ящик);
2. удаляет дубли `(user_id, pts)` в `user_pts_updates`, оставляя самую новую строку, и делает индекс `user_id (user_id, pts)` уникальным;
3. добавляет строку каждому существующему пользователю: `pts` и `last_message_box_id` на 1 000 000 выше максимума в журнале и в `messages`. Клиенты могли видеть значения Redis-счётчиков выше записанного в MySQL; скачок вперёд стоит каждому устройству одного `updates.getDifference`, а шаг назад сломал бы доставку.

Повторный прогон ничего не меняет: существующие строки `user_state` не трогаются. Поднять отставшие строки (после отката на старую версию или восстановления из резервной копии) — отдельная команда обслуживания (ADR 0011, п. 11).

**Время.** Уникальный индекс строится по всей `user_pts_updates`. Перед окном оценить размер:

```sql
SELECT table_rows, data_length FROM information_schema.tables
WHERE table_schema = 'teamgram' AND table_name = 'user_pts_updates';
```

Тест `TestMigrationSpeed` (`pkg/userbox`, тег `integration`) печатает скорость миграции. Замер на MacBook (colima, MySQL в tmpfs): 50 000 строк журнала по ~300 Б JSON — 0,7 с, около 70 000 строк в секунду. На сервере с диском скорость ниже; для оценки окна прогнать тест на целевом хосте.

## Порядок обновления

Выкатывать пользователям — только вместе с задачей 003 (ADR 0011, п. 9): до неё сбой публикации после commit или потеря события в консьюмере оставляет получателя без сообщения. Формат inbox-событий изменился (получатель — `user_id`, нет полей `out` и V3), поэтому старые события новая версия не обработает.

1. Остановить gnetway (закрыть вход клиентов).
2. Дождаться нулевого лага консьюмера inbox: в контейнере kafka `/opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9094 --describe --group Inbox-MainCommunity-S`, колонка `LAG` равна 0 по всем партициям `Inbox-T`.
3. Остановить сервисы, сделать резервную копию MySQL.
4. Применить `migrate-20261022-dialog-index.sql` и `migrate-20261022.sql` (в этом порядке, как их сортирует имя).
5. Выкатить новую версию (DSN msg и biz с `innodb_lock_wait_timeout=2`, idgen без `SeqIDGen` — уже в `teamgramd/etc*`) и запустить.

После обновления каждое устройство один раз получит скачок `pts` и сделает `updates.getDifference`.

## Обслуживание: `pluma-admin`

Команды запускаются с конфигом bff (MySQL и Redis, `-f`), как остальные команды `pluma-admin`.

| Команда | Когда |
|---|---|
| `state-raise -by 1000000 [-user <id>]` | после восстановления MySQL из резервной копии и при повторном обновлении после отката, **при остановленных msg и biz**: `pts` и `last_message_box_id` всех (или одного) поднимаются на запас выше максимума в журнале и в `messages`, недостающие строки добавляются |
| `state-export-legacy -margin 1000000` | откат на версию до 002, **при остановленных сервисах**: счётчики каждой строки `user_state` плюс запас пишутся в Redis в ключи старой версии (`pts_updates_ngen_<u>`, `message_box_ngen_<u>`; `SET`, не `INCR`). Redis — из секции `KV` конфига (в поставляемых конфигах это тот же сервер, что `SeqIDGen` старого idgen) |
| `verify-pts [-after <pts>] <user id>` | в любой момент: дыры и пересечения журнала пользователя до закоммиченного `pts`. Одна дыра размером с запас миграции или `state-raise` — это скачок, а не потеря |

**Откат на версию до 002** (ADR 0011, п. 11): остановить gnetway; дождаться нулевого лага `Inbox-MainCommunity-S` (события нового формата должна обработать новая версия); остановить сервисы, сделать резервную копию; `pluma-admin state-export-legacy -margin 1000000`; вернуть `SeqIDGen` в конфиг idgen, выкатить старую версию и запустить. Таблица `user_state` и уникальный индекс остаются.

**Повторное обновление после отката:** миграция (ничего не меняет), затем до запуска — `pluma-admin state-raise -by 1000000`, затем запуск.

**Восстановление MySQL из резервной копии:** клиенты видели `pts` и id новее копии. После восстановления и до запуска сервисов — `pluma-admin state-raise -by 1000000`.
