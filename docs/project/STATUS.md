## Известные проблемы и риски
- **Остаточные риски безопасности до задачи 008:** нет 2FA (подбор 6-значного кода ко всей группе из 100 номеров — порядка 3,6% в год при постоянной атаке); кто знает номер из allowlist, может держать владельца в `FLOOD_WAIT` (снимается `pluma-admin login-unblock`); нет recover в `runLoop` session; нет лимитов по числу соединений с IP и верхней границы `expires_in`; etcd/Kafka без аутентификации и нет TLS между сервисами (порты закрыты снаружи). Legacy `httpserver` со старым handshake не запускается и не публикуется — удалить или переписать в 008.
- Истёкшие temp-ключи не удаляются из БД, `auth.dropTempAuthKeys` не реализован (задача 008).
- `pts`/id только в Redis — потеря Redis = потеря сообщений (002).
- Kafka коммитит offset при ошибке; после рестарта `session` пуши не идут до рестарта `sync` (003).
- Свежие клиенты на layer 229–232; держим клиентов на 228 (ADR 0008). Обновление layer зависит от upstream `teamgram/proto` — генераторы TL не открыты.
- Каналы: 1 из 74 методов; звонки: 0 из 45; push: заглушка.
- `contacts.importContacts` — заглушка апстрима: пишет в лог «License key … required» и возвращает пустой ответ, поэтому официальный клиент не добавит контакт по номеру (работает только `contacts.resolvePhone`). `tools/apicoverage` считает такие обработчики заглушками (`blocked`/`partial`).
- Консьюмеры Kafka стартуют с `OffsetNewest`: сообщения, отправленные до первого назначения партиций группе, теряются. На свежем запуске это первые секунды (003).
