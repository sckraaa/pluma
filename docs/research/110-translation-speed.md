# Ускорение перевода HY-MT1.5-1.8B на i5-13500T (исследование, 2026-11-17)

Только чтение: код `pkg/translate`, `teamgramd/deploy/translate/entrypoint.sh`, `docs/ops/translation.md` и источники ниже (все прочитаны 2026-11-17). Ничего не запускалось. Оценки времени — арифметика по нашим замерам, а не замер; что не подтверждено источником, помечено **НЕ ПРОВЕРЕНО**.

## 0. Итог в одной таблице

Целевое сообщение ~320 знаков. «Тяжёлое» направление — на русский/казахский (en→ru, uk→ru, ru→kk: ~150 токенов ответа), «лёгкое» — ru→en (~70 токенов ответа). p95 ≈ p50 × 1,17 (по нашим замерам: 6,4/7,6, 9,1/10,3).

Вывод: **порог 320 знаков p95 ≤ 6 с достигается только сочетанием** «привязка к ядрам P + квантование 4-5 бит + параллельные куски по предложениям». Каждая мера по отдельности даёт 1,2–1,6×, а нужно ~2×. «Как в Telegram» (~2 с) на этой модели и этом процессоре недостижимо для тяжёлых направлений: 150 токенов ответа за 1,5 с — это 100 ток/с генерации одного текста, а пропускная способность памяти позволяет максимум ~40 ток/с даже на 1,13-ГБ Q4_K_M (76,8 ГБ/с / 1,13 ГБ ≈ 68 ток/с теоретически, на практике 40–60 % от пика). ~2 с дают только маленькие seq2seq-модели (Marian/Bergamot) или GPU (§7).

Пачка из 20 ≤ 25 с достигается уже A+C (или C при удачном замере).

## 1. Что делается сейчас (код)

- `entrypoint.sh`: `--threads 6 --threads-batch 6 --parallel 4 --ctx-size 16384 --no-kv-unified --cache-ram 0`; flash attention не задан (по умолчанию `auto`), KV-кэш f16, привязки к ядрам нет. Оверлей: `cpus: 6` — это квота CFS, не привязка: потоки llama.cpp ходят по ядрам P и E.
- `http_engine.go`: `POST /v1/chat/completions`, одно сообщение `user`, `cache_prompt` не передаётся → по умолчанию `true` (README сервера), т. е. совпадающий префикс прошлого запроса в слоте уже переиспользуется. `--cache-ram 0` выключает только хранилище запросов в памяти хоста (`--cache-idle-slots` его требует), а не повторное использование KV внутри слота.
- `scheduler.go`: не больше `Slots` элементов в движке, **один запрос на элемент**; запасные куски элемента идут «one after another in its slot». **Длинные тексты на предложения не делятся** — 4000 знаков идут одним запросом (отсюда 70–86 с и тайм-ауты).
- `markup.go`, `pieces`: деление есть только в запасном пути (куски между неприкосновенными сущностями, последовательно, без тегов).
- `profile_hymt.go`: шаблоны карточки; `{target_language}` стоит в начале шаблона (после ~6–10 токенов), `{source_text}` — в конце; `max_tokens = 3/2·знаки + 64`.

## 2. Модель времени по нашим замерам

Дома (2026-11-17): `tg128` ≈ 17 ток/с (одинаково при 4–8 потоках), `pp512` ≈ 95–102 ток/с. Время запроса ≈ P/pp + G/tg (P — токены запроса, G — ответа).

Подгонка к замерам (оценка, **НЕ ПРОВЕРЕНО** токенизатором — проверить через `POST /tokenize` llama-server):
- en→ru 10,2 с: P ≈ 130 (шаблон ~25–30 + ~75 токенов английского текста) → 1,3 с; G ≈ 150 → 8,8 с. Итого 10,1 ✓.
- ru→en 6,4 с: P ≈ 180–230 → 1,8–2,3 с; G ≈ 70 → 4,1 с. Итого 5,9–6,4 ✓.
- Отсюда русский ≈ 2,1 знака/токен, английский ≈ 4,4 знака/токен в токенизаторе Hunyuan (словарь 120 818, config.json модели).

**Главная статья — генерация (85 % времени тяжёлого направления).** 17 ток/с × 1,91 ГБ ≈ 32 ГБ/с — 42 % от пика памяти процессора (76,8 ГБ/с, DDR5-4800 ×2, спецификация Intel). Плато `tg` на 4–8 потоках — признак либо упора в память, либо ожидания медленных потоков (ядра E); различить может только замер с привязкой.

Масштабирование слотов (CachyOS, `docs/ops/translation.md`): пачка 20 на 1/2/4 слотах — 40,0 / 25,5 / 19,9 с, т. е. 4 слота дают 2,0× пропускной способности одного. Значит, на 4 параллельных потоках каждый идёт ≈ 0,5–0,65 скорости одиночного (нижняя граница из пачки, где есть и разбор; верхняя — из оценки «чтение весов 59 мс + счёт 4 токенов ~10 мс/токен при pp 100»).

## 3. Квантование

| Файл (официальный, `tencent/HY-MT1.5-1.8B-GGUF`) | Размер | Байт на токен против Q8_0 |
|---|---|---|
| Q8_0 | 1,91 ГБ | 1,00 |
| Q6_K | 1,47 ГБ | 0,77 |
| Q5_K_M | нет официального; своё из BF16 ≈ 1,28 ГБ (5,7 бит/вес по таблице llama.cpp) | 0,67 |
| Q4_K_M | 1,13 ГБ | 0,59 |
| IQ4_XS / IQ4_NL | нет официального; своё ≈ 1,0–1,05 ГБ | ~0,54 |

Скорость:
- Если `tg` упирается в память, выигрыш ∝ 1/байты: Q4_K_M — до 1,69×. Наш замер на CachyOS для Q6_K дал 1,18–1,25× при 1,30× меньше байт, т. е. ~75–80 % от пропорции. Отсюда ожидание: Q5_K_M ≈ 1,35×, **Q4_K_M ≈ 1,45–1,55×** (`tg` ≈ 25–26 ток/с), IQ4_XS ≈ 1,55–1,6×.
- Таблица llama.cpp (`tools/quantize/README.md`, Llama-3.1-8B, железо не указано): tg128 Q8_0 50,9 → Q6_K 58,7 (1,15×) → Q5_K_M 67,2 (1,32×) → Q4_K_M 71,9 (1,41×) → IQ4_NL 76,6 → IQ4_XS 77,5 (1,52×); pp512 почти не меняется (865 → 822). Совпадает с нашей оценкой.
- Разбор запроса (`pp`) на CPU у K-квантов может быть медленнее Q8_0 (у Q8_0 и Q4_0/IQ4_NL есть пути с переупаковкой весов при загрузке). Форк ik_llama.cpp показывал на AVX2 pp512 Q8_0 148 → 268 и IQ4_XS 74 → 270 ток/с против тогдашней основной ветки (обсуждение #164, 2024-12) — данные старые, основная ветка с тех пор ускорилась; поддержку архитектуры HunYuanDense форком **НЕ ПРОВЕРЕНО**. Мерить `llama bench -p 512 -n 128` на Q8_0/Q6_K/Q4_K_M/IQ4_XS.

Качество (для перевода):
- Технический отчёт HY-MT1.5 (arXiv 2512.24092, табл. 4, FLORES-200): 1.8B оригинал / FP8 / **Int4 (GPTQ)** — XCOMET-XXL EN⇔XX 0,8942 / 0,8905 / **0,8665** (−3,1 %), XX⇔XX 0,7840 / 0,7794 / **0,7336** (−6,4 %), ZH⇔XX 0,8361 / 0,8379 / 0,8060. Сами авторы: Int4 — «significant accuracy degradation», FP8 — почти без потерь.
- Q4_K_M — не GPTQ-Int4 (часть тензоров в Q6_K, блочные масштабы); насколько он лучше, для этой модели не опубликовано (**НЕ ПРОВЕРЕНО**). Ожидать потерю между Q6_K (≈0) и Int4 GPTQ.
- Marchisio и др., «How Does Quantization Affect Multilingual LLMs?» (arXiv 2407.03211, EMNLP Findings 2024): квантование сильнее бьёт по языкам не на латинице (наш русский, украинский, казахский), автоматические метрики занижают вред (японский: −1,7 % по метрикам против −16 % у людей).
- Вывод: Q4_K_M/IQ4 — только после chrF++/COMET на FLORES-200 ru⇄en, uk→ru, en→ru против Q8_0 (шаг 6 плана замера в `docs/ops/translation.md`) и чтения переводов. Компромисс — Q5_K_M (собрать самим из BF16 `llama-quantize`; лицензия Tencent HY-MT допускает производные — **проверить** по `License.txt`).
- 2-битная HY-MT1.5-1.8B (AngelSlim SEQ, 574 МБ, 2026-04-29, `tencent/Hy-MT1.5-1.8B-2bit-GGUF`): требует тип `q2_0c` из PR llama.cpp #19357 — **черновик, не влит**, ядра только Arm SME2/KleidiAI, x86 нет, мейнтейнер предлагал сводить к Q2_K. Для нас неприменимо.

## 4. Параметры llama.cpp на гибридном Intel

Процессор (Intel ARK, 230578): 6 P (HT, до 4,6 ГГц, база 1,6) + 8 E (до 3,2, база 1,2), 20 потоков, 35 Вт базовая / 92 Вт турбо, AVX2 (AVX-VNNI в спецификации Intel не указан; llama.cpp пишет `AVX_VNNI = 1/0` в журнале при старте — посмотреть).

- **Привязка к ядрам P.** llama.cpp делит работу на равные доли по потокам, быстрые ждут медленных: обсуждение #572 (i7-12700H, 6P+8E, q4_0): все ядра 482 мс/токен → только P (`numactl -C 0-5 -t 6`) 202 мс/токен (2,4×), на 65B — 3×. Статья arXiv 2411.19542 (Intel, 12900K/Ultra 125H) называет причиной именно статическое разбиение в llama.cpp. У нас `--cpus 6` без привязки — потоки могут попадать на E. Сделать: в оверлее `cpuset: "<6 первых потоков P на разных ядрах>"` (номера — `lscpu -e=CPU,CORE,MAXMHZ`, у Raptor Lake обычно CPU 0–11 — потоки ядер P, **проверить**) или `--cpu-mask`/`--cpu-range` + `--cpu-strict 1` в llama-server (одно ядро на поток). `-t 6` (по числу физических P). Ожидание: `tg` 17 → 20–24 ток/с (если сейчас мешают E) или без изменений (если упор в память); оценка, **НЕ ПРОВЕРЕНО** — первым делом замер `llama bench` с `--cpuset-cpus`, он уже описан в плане.
- **Цена на общей машине.** Ядра P нужны и Pluma, и медиасервису. `cpu_shares: 256` остаётся, но 6 занятых потоков P во время пачки заметнее для Pluma, чем размазанные по E. Проверить шагом 5 плана (RPC p95 bff во время пачки). Компромисс — 4 ядра P (`-t 4`): при упоре в память `tg` почти тот же (плато 4–8 потоков).
- **Лимит мощности 35 Вт** (`T`-модель): под длительной нагрузкой ядра P сбрасывают частоту; для `pp` (счёт) это важнее, чем для `tg` (память). Посмотреть частоты во время пачки (`turbostat`/`/proc/cpuinfo`) — **НЕ ПРОВЕРЕНО**.
- **`-t` против `-tb`.** `-tb` — потоки разбора запроса (счёт, не память): здесь больше потоков помогает. Но квота контейнера 6 CPU: `-tb 12` при `cpus: 6` только упрётся в квоту. Вариант: `cpuset` = 12 потоков P (6 ядер × HT), `-t 6 -tb 12`, квота 6–8; выигрыш HT для матричного умножения **НЕ ПРОВЕРЕН** — мерить `llama bench -t 6,12 -p 512`.
- **`--poll`** (по умолчанию 50): потоки крутятся в ожидании — лишняя загрузка процессора соседям, скорость почти не меняет; можно `--poll 0` при общей машине, проверить, что `tg` не падает.
- **Flash attention на CPU**: при контексте ~300–600 токенов внимание — единицы процентов счёта; `auto` уже стоит. Скорость ±0.
- **KV-кэш q8_0** (`-ctk q8_0 -ctv q8_0`): на токен KV f16 = 2 × 32 слоя × 4 KV-головы × 128 × 2 байта = 64 КиБ (config.json). На 300 токенах — 19 МБ против 1,9 ГБ весов (< 1 % трафика) → скорость ±0. Память: 4 слота × 4096 × 64 КиБ = 1 ГиБ → 0,5 ГиБ (совпадает с нашим замером: 4×4096 на 770 МиБ больше 1×4096). Полезно, если делим на куски и хотим больше слотов (см. §6). Для квантованного V раньше требовался flash attention — **проверить** на b11913.
- **batch/ubatch** (2048/512 по умолчанию): наши запросы < 2k токенов, при параллельных кусках непрерывная пачка (`--cont-batching`, включена по умолчанию) и так сводит их разбор в один ubatch. Менять незачем.
- **Число слотов против задержки.** Слоты не замедляют одиночный запрос, пока простаивают; при занятых 4 слотах каждый идёт ~0,5–0,65 скорости. 2 слота: одиночный в пачке быстрее, пачка 20 медленнее (CachyOS: 25,5 против 19,9 с). Для порога пачки нужны 4 слота.

## 5. Спекулятивное декодирование

- llama-server поддерживает: `--model-draft` + `--spec-type draft-simple`, `--spec-draft-n-max` (по умолчанию 3), а также без черновика: `ngram-simple`, `ngram-map-k`, `ngram-mod`, `ngram-cache` (README сервера и `docs/speculative.md`, 2026-11-17). EAGLE-3/DFlash/MTP требуют обученных под цель голов — для HY-MT их нет.
- Черновик той же семьи: `tencent/Hunyuan-0.5B-Instruct` — `HunYuanDenseV1ForCausalLM`, `vocab_size` 120 818, как у HY-MT1.5-1.8B (оба config.json). Совпадение спецтокенов и шаблона чата для llama.cpp **НЕ ПРОВЕРЕНО** (при несовпадении спекуляция не включается). Это общая модель, не переводчик: доля принятых токенов на переводе неизвестна.
- Арифметика на CPU: черновик 0,5B (~0,55 ГБ Q8_0) ≈ 0,28 шага цели; проверка 4 токенов ≈ 1,2 шага цели (упор в память + счёт). При n=3: стоимость ≈ 3×0,28 + 1,2 = 2,05 шага. Ожидаемо принятых + 1: при доле принятия 0,5 — 1,88 токена (0,92× — медленнее), 0,7 — 2,53 (1,23×), 0,85 — 3,1 (1,5×). При занятых слотах (пачка) пакет уже упирается в счёт — выигрыш исчезает или становится потерей.
- n-граммные режимы рассчитаны на повтор текста (правка кода, рассуждения); в переводе ответ на другом языке, совпадают только имена, ссылки, теги — выигрыш ~0. `ngram-mod` общий на все слоты, но и это не меняет вывода.
- **Не рекомендуется** до замера доли принятия черновиком; не входит в путь к порогу.

## 6. Кэш префикса и деление на предложения

**Кэш префикса.** Уже включён (`cache_prompt` по умолчанию true, выбор слота по сходству `--slot-prompt-similarity` 0,10). Но шаблоны HY-MT ставят язык в начало («Translate the following segment into {target_language}…», «…翻译为{target_language}，…»): общий префикс с прошлым запросом другого языка — несколько токенов. Для простого шаблона сам шаблон ~25–30 токенов (0,25–0,3 с при pp 100) — немного. Для размеченного (китайская инструкция + `<source>`) шаблон длиннее (~60–90 токенов, **НЕ ПРОВЕРЕНО**) — 0,6–0,9 с. Важно при делении на куски: 4 куска × шаблон = 4 повторных разбора. Нельзя менять шаблон карточки (ADR 0064, замеры тегов) — но при одном языке подряд (типичная пачка одного чата) префикс до `{source_text}` и так совпадает. Опция: `--kv-unified` (общий KV для слотов) позволил бы делить префикс между слотами — как это работает при `--no-kv-unified`/лимите `max_tokens` на слот, **НЕ ПРОВЕРЕНО**; не трогать без замера.

**Деление на предложения и параллель на слотах** (сейчас не делается). Для 320 знаков en→ru, 4 куска:
- разбор: 4 × ~28 (шаблон) + 75 (текст) ≈ 187 токенов одним пакетом → ~1,9 с при pp 100 (с кэшем префикса того же языка ≈ 75–100 токенов → ~0,9 с);
- генерация: 150 / 4 ≈ 38 токенов на кусок, самый длинный ≈ 1,3 × 38 ≈ 49; на 4 параллельных потоках 8,5–14 ток/с на поток (§2), берём 11 → ~4,5 с;
- итого ≈ 6,4 с (против 10,1) — 1,6×; ru→en ≈ 4,7 с (против 6,4) — меньше выигрыш, т. к. там велика доля разбора, а шаблон повторяется.
- с привязкой и Q4_K_M (`tg` одиночный ~30, на потоке при 4-х ~19, pp ~120): en→ru 187/120 + 49/19 ≈ 1,6 + 2,6 = 4,2 с; с кэшем префикса ≈ 3,3 с.
- 4000 знаков (сейчас 70–86 с и тайм-ауты): ~1900 токенов ответа на русский; 4 потока × 19 ток/с ≈ 76 ток/с → ~25 с + разбор ~5 с ≈ 30 с (Q8_0 без привязки: 4 × ~10 = 40 ток/с → ~50 с). Тайм-ауты уходят в любом варианте.

Ограничения и что учесть в коде (`pkg/translate`):
- пропускная способность движка не растёт: деление ускоряет **одиночный** текст при свободных слотах, а в пачке (все слоты заняты) только добавляет повторы шаблона (−5…−10 %). Значит, делить только `PriorityManual` и длинные тексты, и только на свободные слоты (планировщик: единица работы — кусок, а не элемент; ключ кэша — по-прежнему элемент);
- теряется контекст между предложениями (местоимения, род, согласование в русском) — для коротких сообщений лучше 2 куска по ~150 знаков, чем 4 по предложению; HY-MT меряли на FLORES-200 — это корпус отдельных предложений (отчёт), т. е. уровень предложения — его родной режим, но связность абзаца не проверена (**НЕ ПРОВЕРЕНО**);
- резать только вне сущностей (тег `<sN>` не должен пересекать границу куска) и вне неприкосновенных узлов; нумерация тегов — своя в каждом куске; склейка с исходными пробелами/переводами строк. Механизм уже близок к `markup.pieces` (там деление между неприкосновенными узлами, последовательно) — нужен параллельный вариант с границами предложений;
- больше 4 слотов (6–8 с KV q8_0) для кусков даст мало: пакет 8 уже ближе к пределу счёта (pp 100 ток/с = 10 мс/токен → 8 токенов ≈ 80 мс на шаг при 59 мс чтения весов).

## 7. CTranslate2 и seq2seq

- CTranslate2 (MIT) поддерживает Transformer/Marian (OPUS-MT), M2M-100, NLLB, T5/MADLAD-400 и из декодерных — Llama, Mistral, Qwen2, Gemma и др.; **HunYuanDense в списке нет** — для HY-MT неприменим.
- Порядок скорости (README CTranslate2): Transformer-base (Marian/OPUS-MT) int8, 4 потока Xeon 8275CL — 696–1126 токенов/с (пакетная пропускная способность, newstest2014 en→de), память ~0,5 ГБ. Это на порядок быстрее нашей генерации и даёт «как в Telegram» ~1–2 с, но: модели на пару языков (десятки пар для ~30 языков), качество хуже LLM, NLLB/SeamlessM4T — CC-BY-NC (исключены), OPUS-MT — CC-BY 4.0, MADLAD-400 — Apache 2.0, но 3B+ (медленнее HY-MT). Модели Firefox Translations (Bergamot/Marian) — русский и украинский с английским есть, казахского в найденных списках нет, лицензия моделей не подтверждена (**НЕ ПРОВЕРЕНО**). Сущности в тегах эти модели не держат (Marian умеет только при обучении с разметкой).
- Вывод: как замена HY-MT — нет; как быстрый путь для коротких ru⇄en/uk→ru — возможен, но это вторая модель, второй профиль и второй контейнер; предмет отдельного исследования «модель лучше».

## 8. Рекомендованный порядок (что делать и проверить)

1. **Замер привязки** (дёшево, без кода): `llama bench` с `--cpuset-cpus` на 6 физических ядрах P, `-t 4,6`, `-tb 6,12`, Q8_0/Q6_K/Q4_K_M (+ свои Q5_K_M, IQ4_XS). Смотреть `tg128`, `pp512`, частоты под нагрузкой. Если `tg` растёт — `cpuset` в оверлей (коммит), `--cpu-strict 1`.
2. **Качество квантований**: FLORES-200 chrF++/COMET ru⇄en, en→ru, uk→ru для Q8_0/Q6_K/Q5_K_M/Q4_K_M + чтение `TRANSLATE_ENGINE_OUT` + доля сохранённых тегов (`TaggedSamples`). Брать самое лёгкое, у которого падение chrF++ ≤ ~1 пункта и теги не хуже.
3. **Деление длинных и одиночных текстов** на куски по предложениям с параллелью на свободных слотах — задача в `pkg/translate` (планировщик + разметка), с тестами; включать для `PriorityManual` и для текстов > ~150 знаков.
4. KV q8_0 — только если после деления понадобится больше слотов при том же `TRANSLATE_MEMORY`.
5. Спекулятивное декодирование и смена движка — не делать.

Оценка после 1+2(Q4_K_M)+3: 320 знаков на русский p95 ≈ 4–5 с, на английский ≈ 3–4 с; пачка 20 ≈ 20–23 с; 4000 знаков ≈ 30 с. Всё это — арифметика по модели §2, подтверждать замером `TestBench`.
