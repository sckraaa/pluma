# Итог аудита (2026-10-21)

Подробности по областям: [01 апдейты и хранилище](01-updates-and-storage.md), [02 транспорт и безопасность](02-transport-and-security.md), [03 архитектура и эксплуатация](03-architecture-and-ops.md), [04 клиенты и сборки](04-clients-and-builds.md).

## Вердикт
**Ядро teamgram оставляем и глубоко исправляем, не переписываем.** Модель хранения (ящик сообщений и `pts` на пользователя, журнал `user_pts_updates`) повторяет устройство Telegram для личных чатов и обычных групп; каналы добавляются отдельным модулем. Переделать нужно выдачу и сохранение последовательностей, путь записи сообщения, семантику доставки и безопасность. Инфраструктуру (MySQL, Redis, Kafka, etcd, MinIO) оставляем: проблема не в инструментах, а в том, что их гарантии не используются.

**В текущем виде сервер нельзя выставлять в интернет.**

## Оценки по областям (пересекаются, не суммировать)
- Безопасность: P0 5–8 дней, P1 ~2 недели.
- Надёжность фундамента (счётчики, доставка, развёртывание, тесты): 4–6 недель.
- Апдейты без каналов: 5–7 недель; каналы и супергруппы: ещё 6–10 недель.

## Принятые по итогам решения
- ADR 0005 — инфраструктура: оставить и починить, лог-стек ELK заменить на Loki.
- ADR 0004 — звонки: пересмотрено в пользу родного протокола клиентов + свой SFU на основе `tgcalls/tools/go_sfu`.
- ADR 0008 — клиенты закрепляются на версиях layer 228.
- ADR 0009 — форки `teamgram/proto` и `teamgram/marmota` под нашим контролем.
- План этапа 0 — задачи 001–010 в `docs/tasks/`.
